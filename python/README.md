# agent_tools — the agent helper package

Agent-workflow Python is moving into one standard-library package, `agent_tools`, under `python/` (with its `pyproject.toml`).

## Package and launchers

`lib/agent-tools.nix` builds it into one Python environment, import-checks every module so that a broken import fails `just build`, and holds the command table.

Each row becomes a `~/.agents/bin/<command>` launcher, which unsets the `NIX_PYTHON*` variables and runs `python3 -I -m agent_tools.<module>` from that environment, so nothing on `PYTHONPATH` or in the working directory can shadow the store copy; `just agent-installed-skill-tests` proves it.

## Review packaging and feasibility

`review-package` and `review-feasibility` use the package command table; their source entry points are `python -m agent_tools.review_package` and `python -m agent_tools.review_feasibility`.

Actual production and generic projection share packing and the external `artifact-budget` policy queried by PATH; projection binds its policy identity.

`review-feasibility project` reads committed plans and authenticated Git history without mutating them, while `validate-result` checks closed canonical v3 results and producer exits.

Actual production also calls external `sdd-workspace` by PATH.

## `verified-tree`

`verified-tree` records a passing run of the declared verification against the git tree it verified (what a Git-backed build sees: the index's entries with tracked files' working-tree edits applied, built in a temporary index, so an untracked file is outside it until committed) as `verified-tree.json` in the worktree's own git directory; `verified-tree check` answers `verified` only for that same tree under the same verification ids, which is how sdd's final gate lets ship skip a rerun (#263).

## `launch-scope`

`launch-scope` (#276) contains a lifecycle agent's long commands: `launch-scope exec` checks that the launch (or worker) is live, runs the command in a new session whose processes carry `AGENT_LAUNCH_SCOPE=<repo-scope>/<run-id>/<action-id>/<nonce>` (`<repo-scope>` is a hash of the registry's real path, so another repository's launch with the same run and action ids is never touched), and kills whatever the command left behind when it returns, while `launch-scope reap --action-id` (an owner, before its exit write) and `reap --sweep` (the orchestrate-issues stop pass, for every non-current launch of the run) kill the marked processes, and the process groups those processes prove, recorded in a host-local registry under the ledger repository's git common dir at `agent-launch/<run-id>/<action-id>/`; on darwin an Apple platform binary (`/bin`, `/usr/bin`) exposes no environment, so an orphaned group holding only such processes is never proved and survives a sweep.

`launch-scope scratch` (#277) prints the launch's one scratch root, a `launch-scope-*` directory under the system temp directory that the owner and its workers share, recorded as `scratch.json` in the launch's registry directory; once a reap finds the launch's processes gone it force-removes every worktree registered inside that root, present or missing, and deletes the root, never running a repository-wide `git worktree prune` (#277 D10); and every reap reports the registered worktrees outside the main checkout and outside every recorded root as `unattributed_worktrees`, deleting none of them.

## `lane-triage`

`lane-triage evaluate --repo-root <root> --input -` (#279) reads an owner's triage record on stdin, reads `bindings.workflow.light_lane` (an optional `resolve-project` member; absent or `null` means unsupported) through `agent_tools.resolve_project.resolve`, the one public function that composes exactly what `resolve-project resolve` prints, and prints the verdict `{hits, lane, mode}` without writing anything: `lane` is `light` only when no signal is `hit` or `doubt` and no predicted path matches a `risk_paths` glob, an absent or `null` member exits 2 with `light_lane_unsupported`, and `from-issue` Phase 0 records the verdict while every attempt still runs full.

## `sdd-gate`

`sdd-gate review PLAN_FILE --skill-dir DIR --task N [--standards PATH]... [--repo-root R --run-id I --action-id A --worker-id W]` (#353) gates one sdd task's evidence and renders the reviewer's dispatch brief, so a controller dispatches by a file path instead of composing the brief. `--standards` (repeatable) names a project standards index; the three lifecycle identity flags are all given or all absent, and `--worker-id` goes with them. Any other shape prints `sdd-gate: invalid invocation` on stderr, nothing on stdout, and exits 2. The task's base is the commit in the plan ledger's `Task <N>: dispatched (base <sha>)` line, which `sdd-gate next` writes; the head is the current checkout's `HEAD`, read once.

`review` runs seven steps in order and stops at the first that fails, naming it as `step`: `ledger` (the workspace `sdd-workspace` prints holds a `progress.md` whose header names this plan and which records exactly one base for the task), `release-worker` (under a lifecycle identity only, `workflow-state release-worker --event returned`), `review-package` (build the package for `base..head` with `review-package`, or reuse an existing one), `validate-report` (the artifact-budget authority validates the report, which must be `complete` or `decompose_required` and name this package root), `budget-check` (an independent `artifact-budget check` says `within_budget`), `metrics-match` (that check's metrics equal the report's) and `render-brief` (fill `task-reviewer-prompt.md` from `--skill-dir` and write `task-<N>-review-dispatch.md` in the workspace atomically).

A package is never deleted or overwritten. A fresh one saves its validated report beside it as `review-<base7>..<head7>.report.json`, for either state; an existing root is reused only when its manifest's `range` is exactly the base and head and that saved report exists, otherwise `review-package` refuses, so a repeated call is safe.

Stdout is one compact JSON object and a newline. Ready, exit 0: `command`, `outcome` (`ready`), `task`, `brief_path`, `base_sha`, `head_sha`, `manifest_root`, `metrics` and `standards` (the documents the brief quotes). Refused: `command`, `outcome` (`refused`), `step`, `gate`, `detail` (one line of at most 300 characters naming the cause, with the tail of a failed child's stderr where it has one, never artifact content), `report` and `completed_steps` (the steps that ran and passed, in order). `gate` is `decompose_required` (exit 3, with the validated report in `report`) for a package that must be split, `failed` (exit 2) for every other refusal of `review-package` to `metrics-match`, and `null` (exit 2) elsewhere; `report` is `null` unless `gate` is `decompose_required`, and no brief file exists after a refusal unless an earlier call wrote it.

`sdd-gate next PLAN_FILE --skill-dir DIR [--standards PATH]... [--completed N [--parked K]] [--task M [--context-file PATH]] [--delivery-base SHA] [--repo-root R --run-id I --action-id A]` closes task `N`, opens task `M` or both, and renders the implementer's dispatch brief. At least one of `--completed` and `--task` is required and both may be given; `--parked` goes with `--completed` and `--context-file` with `--task`; `N`, `K` and `M` are positive integers, `SHA` is a full 40-hex commit id, and the identity flags are all three or none. There is no `--worker-id` (the command registers the worker itself) and no stdin flag. Any other shape is the same `sdd-gate: invalid invocation`.

`next` runs up to eleven steps in order and stops at the first that fails; a step that does not apply to the call does not run and is not listed in `completed_steps`: `ledger` (the ledger is this plan's, its recorded delivery base and `--delivery-base` agree and at least one exists, the completed task has a `dispatched` line, the task to dispatch has at most one; nothing is written until every read has passed, and then the delivery base is recorded if new), `ledger-complete` (with `--completed`), `mark-progress` (under an identity: `workflow-state mark-progress`, and a non-zero exit or an unreadable reply reports `"refused"` without stopping the call), `review-package`, `validate-report`, `budget-check` and `metrics-match` (the same package gate as `review`, over the cumulative range delivery base to `HEAD`), `task-brief` (the installed `task-brief` command copies the task's plan member into the workspace), `prepare-brief` (record the task's base if new, then render the brief once in memory), `register-worker` (under an identity: `workflow-state register-worker`) and `write-brief` (`task-<M>-implementer-dispatch.md`, atomically). A ledger that cannot be read or appended to is refused at the step that needs it (`ledger`, `ledger-complete`), except that the `Delivery gate:` line is refused at `metrics-match` with gate `failed` and that step is not listed as passed. A worker is registered only after the brief has rendered; a failed brief write releases the worker it registered with `release-worker --event stopped` before the refusal is printed, and when that release fails too the refusal's `detail` names the worker and the command to run first. Every `next --task` call under an identity registers a fresh worker, so before `register-worker` it reads the task's existing brief and refuses, at that step, while `workflow-state check-worker` reports the worker that brief names as live: the owner releases it and calls again (a brief with no worker line, or a worker that is not live, changes nothing).

The ledger gains only four line shapes, one write each and never the same line twice: `Delivery base: <sha40>`; `Task <N>: complete (commits <base7>..<head7>, review clean)` (or `, <K> parked)`); `Delivery gate: <base40>..<head40> root_bytes=<n> total_bytes=<n> file_count=<n> largest_member_bytes=<n>`; and `Task <M>: dispatched (base <sha40>)`. `review` and `next` read `dispatched` and `next` also reads `Delivery base`; `workflow-state resume-pack` reads `complete`. A repeated call writes nothing new.

Ready, exit 0, in this key order: `command` (`next`), `outcome` (`ready`), `completed`, `task`, `brief_path`, `report_path` (`task-<M>-report.md` in the workspace), `base_sha` (the task's base), `worker_id`, `mark_progress` (`skipped` without an identity, else the `workflow-state` outcome or `refused`), `delivery` (`base_sha`, `head_sha`, `manifest_root`, `metrics`) and `standards`; the members that do not apply to the call are `null` (`[]` for `standards` without `--task`). Refusals and exit codes are `review`'s.

## adopt-project

`adopt-project plan` asks four kinds of open question: `project-id`, answered by declaring exactly one remote or authoring a contract with the project id, and `candidate-class` (#340), one per tracked or targeted-ignored agent path that no classification row settles (none covers it, or a targeted-ignored one it covers resolves outside the repository or cannot be read), keyed by its `subject` (the path) and carrying the one `value` the question accepts: `archive-history` for a tracked path, which plans a `git mv` to `.agents/knowledge/archive/adopted/<path>`, `retain-product` for an ignored one, and `null`, no answer, for a secret-shaped tracked path, which stays open until a central classification row covers it or it leaves the repository, or for a tracked symlink resolving outside the repository, which stays open until it leaves the repository; `plan --answer QUESTION SUBJECT VALUE` (repeatable, order-independent) settles a `candidate-class` question, refusing the first violation as `adopt.decisions.invalid_answer` (an id other than `candidate-class`, `path-reference` or `reference-policy`, a subject answered twice, or a value other than the offered one) or `adopt.decisions.unmatched_answer` (a subject that is not an undecided candidate, a path occurrence or a reference policy of this inspection, by the answered id), checking each answer in `(id, subject, value)` order and changing nothing on a refusal; the answers enter `decisions.answered` and therefore `plan_id`, and `apply --plan-id` re-applies them from the stored plan (refusing a malformed `decisions.answered` as `adopt.plan.malformed`), so the plan id, not an `apply` flag, authenticates them. The third and fourth kinds, `path-reference` and `reference-policy`, are described below; `--answer` settles them through the same flag, pass and refusals.

`adopt-project plan` rewrites relative Markdown link targets across its moves (#345): outbound in every Markdown file a `git-mv` moves, inbound in every other tracked Markdown file (a regular `.md`/`.markdown` blob at the base revision, strict UTF-8, not secret-shaped; a `generated_file` projection target is left to its regeneration). `agent_tools.adopt_links` owns the grammar — inline links and images on one line and reference definitions, outside fenced code, code spans and link titles — and resolves a target against the tracked paths of a tree, never the filesystem: a target is relative unless it is empty, starts with `#` or `/`, carries a URL scheme or holds a backslash, and it resolves when its percent-decoded path, joined to the containing directory, names a tracked file or a directory inside the root. The rewritten bytes come from the plan's base revision, each changed file is a `write-file` at the path the file has after the moves and placed before the projection regenerations, and a rewritten target keeps its anchor or query, title, angle brackets and trailing slash, and its leading `./` unless the new path climbs out with `../`; a bare target is percent-encoded and an angle target encodes only `%`, `#`, `?`, `<`, `>` and line breaks, and gains a leading `./` when its path would otherwise open with a URL scheme (`urn:x.md`), so the emitted path names the same file and stays relative; a link that already fails to resolve, a URL and a link the moves leave correct stay byte-identical. The plan document and the adoption evidence record carry `link_rewrites` (`inbound` and `outbound` link counts and sorted files, `unrewritable` `path`/`target` entries and an `already_broken` count), which is the seventh input of `plan_id`. The ready gate `no-unrewritable-link` (`adopt.link.unrewritable`) keeps the plan `draft` when a link targets a file the plan deletes or a directory that no longer exists after the moves and whose files did not all move, by the same relative tails, under one new directory, and `apply`'s commit gate `no-new-broken-link` (`adopt.gate.no-new-broken-link`), before `cold-clone-resolves`, fails when any Markdown file in the index has more non-resolving relative links, each side counted against its own tree, than its pre-move counterpart at `HEAD` (a file with no counterpart is compared with zero); because the verification commands and a `pre-commit` hook run after it, the same count over the commit against its parent is proved again once the commit exists, and a failure there refuses `adopt.commit.new_broken_link` with the worktree and branch retained. Prose mentions of moved paths, inline HTML and root-relative targets are never rewritten, and a path literal in a non-Markdown file is left to the `path-reference` question.

`adopt-project plan` asks about every path literal in a tracked non-Markdown text file that names something its moves relocate (https://github.com/fagenorn/nix-config/issues/350), and edits nothing without an answer. `agent_tools.adopt_references` scans the base revision's regular, non-Markdown, non-secret blobs that git judges text and that decode as strict UTF-8, found by one `git grep` for the first path segment of each move source, leaving out `.agents/artifacts/`, `.agents/knowledge/archive/` (each tested on the base path, so a file under them is editable only by the adoption that moves it) and the files adoption itself may write (the contract, `.gitignore`, the runtime sentinel, a legacy binding config and a `generated_file` projection target). A token is a run of characters bounded by whitespace or one of `"`, `'`, `` ` ``, `,`, `;`, `:`, `=`, `(`, `)`, `<`, `>`, `|`, `&`, `#`, `!`, read as an optional leading `./` or `/`, a path up to its first glob segment and a tail; it is an occurrence when it contains `/` or is the whole content of a quoted string, and a reading of it (the plain one here, the pattern one below) gives a path that names a file or directory of the base tree, where a move source is that path or lies under it, so `.claude/` counts when `.claude/specs` moves. A moved file, or a directory whose members all moved by the same relative tails under one new directory, has a single successor; a path that survives or dissolves maps to the successors of its wholly moved subtrees, carried only for an empty, `/` or `/**` tail. An occurrence that no answer decides (its own, or its policy's, below) opens a `path-reference` question unless its policy's question is open; the question is keyed by its `subject`, `<path>:<line>:<column>`, with an `answers` list and no recommended value: `extend`, offered when the token is a quoted element of a bracketed, braced or parenthesised sequence (it follows `[`, `{`, `,`, a `(` that does not open a call, or the start of its line, and ends the line or precedes `,`, `]`, `)` or `}`) or the only content of its line after indentation and an optional `- `, adds one quoted element or one copied line per successor beside the literal; `rewrite`, offered for a single successor, replaces the token; `retain`, always offered, leaves the file as it is. `plan --answer path-reference SUBJECT VALUE` settles one, after any `candidate-class` answers, whose moves the references are derived from; an unknown subject refuses `adopt.decisions.unmatched_answer` and a repeated subject or a value the occurrence does not offer refuses `adopt.decisions.invalid_answer`. An open reference keeps the plan `draft` through `no-open-decisions`; no gate and no `verify` check is added. Each file with an `extend` or `rewrite` answer is one `write-file` after the Markdown link rewrites and before the projection regenerations, in the same commit as the moves, unless another file is left at its `target` (below). The plan document and the adoption evidence record carry `path_references`, one row per occurrence sorted by path, line and column (`subject`, `path`, `line`, `column`, `literal`, `answers`, `answer`, `additions`, `replacement`, `target`, `policy`, `decided_by`; `answer` is the effective answer), which enters `plan_id` as its eighth input, and the record's `decisions_accepted` lists the answers. Variables are not followed, a regular-expression spelling is read only as the pattern reading below describes, a joined path is not resolved as a whole (a quoted segment that alone names a path of the tree is still an occurrence), URLs and bare unquoted single words are not recognised, and an unquoted element of a YAML flow sequence that shares its line with other flow-sequence text (a bracket, a comma or another element) is never offered `extend` (one that touches its bracket is no occurrence at all); one alone on its line counts as the only content of its line.

A file the plan moves is read like any other, at its base path, and edited at its destination (https://github.com/fagenorn/nix-config/issues/372). An occurrence's `path` and `subject` stay the base path; its row's `target` is the file's destination, or its own path when the plan does not move it. An edited moved file is one `write-file` at its `target`, after its `git-mv` and in the same commit, with `before` the hash of the base bytes. A path that more than one file of the base tree is left at (two moves onto it, or one move onto a tracked file that stays) gets no such write, whatever the answers: the rows keep their answers, and two moves onto one path keep the plan `draft` through `no-existing-destination`. `apply` is unchanged: it recomputes the plan from the stored answers and applies the operations the plan lists.

Every occurrence in a moved file belongs to one policy, whose subject is `<tree>:<class>`. The tree is the path of the classification row that moved the file, or the candidate's own path for an `archive-history` answer; the class is the lower-cased text from the last dot of the file name, or `-` for a name with no such suffix (a dotfile included). A file the plan does not move has no policy. The `reference-policy` question has seven members: `id`, `subject`, `answers` (`rewrite` and `retain`, never `extend`), `value`, `basis`, `impact` and `recommendation`. `value` comes from a closed table: `rewrite` for the classes `.py`, `.sh`, `.bash`, `.zsh`, `.nix`, `.yaml`, `.yml`, `.toml`, `.js`, `.mjs`, `.cjs` and `.ts`; `retain` for `.json`, `.jsonl`, `.ndjson`, `.csv`, `.tsv`, `.txt` and `.log`; null for every other class. The recommendation is printed and never applied: nothing is edited without an answer.

An occurrence is decided by its own `path-reference` answer; else by its policy's answer when the occurrence offers that value; else by none, so a `rewrite` policy leaves an occurrence that offers no `rewrite` open, and `extend` is never a policy answer. A policy opens its question while it is unanswered and at least one of its occurrences has no answer of its own; during that time its occurrences open no question of their own, though they stay listed in `path_references` and can still be answered one by one. Once the policy is answered, each occurrence still without an effective answer opens a `path-reference` question. The open questions are ordered by id as in `QUESTION_IDS`, the `reference-policy` ones by subject. `plan --answer reference-policy SUBJECT VALUE` is checked after the other two ids: a subject that is the policy of no occurrence of this inspection refuses `adopt.decisions.unmatched_answer`, and a value outside `rewrite` and `retain` or a subject answered twice refuses `adopt.decisions.invalid_answer`.

Each `path_references` row carries `target`, `policy` (null for a file the plan does not move) and `decided_by` (`occurrence`, `policy` or null), and the plan document and the adoption evidence record carry `reference_policies`, one row per policy that has an occurrence, sorted by subject, which enters `plan_id` as its ninth input. A row has thirteen members: `subject`, `tree`, `class`, `recommended`, `answer` (the policy's answer or null), `files` (distinct base paths), `occurrences`, `rewritable` (occurrences that offer `rewrite`), `rewritten`, `retained` and `extended` (occurrences decided with that answer, whoever decided it), `open` (occurrences no answer decides) and `overridden` (occurrences their own answer decides). The human view adds one `policy <subject>: ...` line per row after the `references:` line and an `open reference-policy <subject> (answers: ..., recommended: ...): ...` line per open policy. A plan stored before this contract no longer equals its re-derivation, so `apply` refuses it and the operator plans again.

A token that the plain reading does not make an occurrence is read a second time as a regular-expression spelling, only when it starts with `^` or holds `\.` (also `\\.`, as a TOML or JSON string spells it). The reading takes the anchor `^`, one escape for the whole token, an optional `/` prefix, the path decoded segment by segment (the escape replaced by `.`) up to its first empty, glob or backslash-bearing segment, and the rest verbatim as the tail. The forms offered keep the anchor, the escape and the tail, and a carried form exists only for a successor made of letters, digits, `_`, `-`, `.` and `/`. Not read: an end anchor, character classes, groups, alternation and a `./` prefix inside a pattern. The plain reading decides alone whenever it yields an occurrence. The `git grep` prefilter keeps one limit: a file is scanned only when it holds the first path segment of a move source as written, so an escaped first segment with an interior dot (`foo\.bar` for `foo.bar`) is not found.

A tracked `.claude/settings.json` is classified `legacy-native-store` and `retain-product`, so classification opens no `candidate-class` question for it and plans no relocation of it; it appears in the plan's `evidence` and in the record's `sources` with `after` null. The path literals inside it are ordinary occurrences: each may open a `path-reference` question, and an `extend` or `rewrite` answer produces one in-place `write-file` of the settings file.

`adopt-project verify --register` reads one pinned commit of the remote and nothing from the checkout (https://github.com/fagenorn/nix-config/issues/363). It lists `origin` once, fetches its default branch into `refs/remotes/origin/<branch>`, pins and exports that commit and resolves the contract there; a resolving contract that names another branch `origin` lists is the one hop, fetched, pinned, exported and confirmed the same way, and every check then reads the one pinned commit, the fetched objects and those remote-tracking refs being the only repository writes. The default branch's contract stays the authority when it resolves: `--integration-branch NAME` equal to the branch it names (or to the default branch when it names none) changes nothing, and any other operand refuses. The operand takes effect only when that contract does not resolve (it is accepted only with `--register` and at most once, refusing `adopt.verify.integration_branch_without_register` and `adopt.verify.integration_branch_repeated` as `adopt_failure`): the named branch must be listed by `origin`, must not be the default branch, and its own contract must resolve and name it, with no further hop. A run that selects its branch this way carries a `branch_override` object (`branch`, `default_branch` and `reason`, whose one value is `default_contract_unresolved`) in the report and in its registry entry, and in no other run; a later registration of the project that did not need the operand drops it from the entry, another project's registration leaves it, and a repeated operand registration writes the same bytes. The report `schema_version` stays 2 and the registry `schema_version` 1, and no reader decides anything from the member. Every operand that the remote or the branch's contract does not confirm refuses `not_integrated` with `adopt.registration.integration_branch_unresolved`; a pinned commit with no adoption evidence record refuses `not_integrated` with `adopt.registration.not_integrated`, and when the default contract did not resolve and no operand was given its message names `--integration-branch`.

## Transaction core

`agent_tools.transaction_core` is the transaction core's library surface, with no command-table row, and whose first caller is `workflow-state`, which mints one created-only *run transaction* per attempt run in `<ledger root>/.superpowers/attempt-transactions/` through `agent_tools.attempt_identity` (pure rules) and `agent_tools.attempt_store` (store root, mint lock, binding and `migrate`'s rows) and finds it by the read-only `TransactionStore.lookup` (#337): slice 1 (#204) holds caller-rooted transaction state under a closed schema and lifecycle, slice 2 (#205) adds fenced custody — a lease authority over concurrency keys in `agent_tools.transaction_custody`, epoch-fenced writes, and evidence and grant admissibility derived from the fence — and slice 3 (#206) adds the administrative protocol — a durable write intent before every external call, inspection before any retry, and an automatic-retry budget — in `agent_tools.transaction_invocation`; slice 4 (#207) then adds an immutable proof plan compiled at creation (`agent_tools.transaction_plan`), core-collected obligations, and one convergence cohort (at most three attempts) that `settle_proof` alone seals into `succeeded` or parks as `proof_rejected` or `proof_did_not_converge`, never rolling back (`agent_tools.transaction_proof`); slice 5 (#208) adds an immutable recovery plan compiled at creation beside the proof plan (`agent_tools.transaction_recovery_plan`), rollback anchors verified in `ready` before publication, `abandoned` only while no action has had an effect, and `begin_recovery`, `settle_recovery` and `roll_forward` as the only ways into `recovering`, into `rolled_back` and to a linked child transaction (`agent_tools.transaction_recovery`); slice 6 (#209) writes a permanent, content-addressed terminal receipt under the store root's `receipts/` and reads it back before the one `state.json` write that enters any terminal, which ends with a `receipt_sealed` event naming it, then re-reads that receipt on every load (`agent_tools.transaction_receipt`), and makes `dispose_failed` the only way into `failed`: it takes a fresh grant and one closed ground, and it yields an `effects_unobservable` qualifier with per-key hazard markers only when a human grant at the transaction's authority class asserts an observability ground (`agent_tools.transaction_disposition`), with the `transaction-state/v6` validator and snapshot fold in `agent_tools.transaction_history`, over the durable-file primitives in `agent_tools.transaction_storage`.

From schema 9 `workflow-state` also holds attempt custody in the core ([design spec](../.agents/artifacts/specs/2026-10-10-issue-338-fenced-custody-receipts-design.md)). Each implementation attempt has one custody transaction, created under the creation key `attempt-custody/v1:<run>:<issue>:<attempt>` with the closed subject schema `attempt-custody/v1` (run, issue, attempt, worktree, prior, `bound_launch`), the authority class `attempt-custody` and the single concurrency key `attempt-worktree:<path>`, so one live worktree has one holder across runs. A launch is a custody span whose executor is the launch's action id (`<issue>:<attempt>:<launch>`), so the key's epoch is the launch generation; the lease's validity is the attempt's budget window (`deadline_at`), and `renew(custody, ttl_ms=…)` is the one in-place renewal, used when `declare-lane` re-bases that deadline (a transaction parked longer than the core's parked-custody window quiesces under `renew` instead of renewing). `agent_tools.attempt_custody` holds the pure rules, the closed subject and the settle planner, which turns one ledger attempt, its custody transaction and its lease record into ordered core operations; `agent_tools.attempt_store` applies the plan to `TransactionStore` under the store lock. The settle step runs inside `commit_state`: the core is brought to the ledger's state first, the ledger is published, and the seal of each issue's latest attempt is applied last, so a core refusal leaves the ledger untouched and an interrupted seal is completed by a later write, after a reap when its span has lapsed by then. The subject's worktree is fixed at creation, and a live attempt that the ledger records at another worktree is refused as a `custody projection mismatch`. A verdict that records no merge (`stopped` or `failed`, from the owner, a refusal or a supersession) seals the transaction `abandoned` with a receipt that lists its stops and owner results; a synthesized stop (`stalled`, `expiry`) parks it and never seals. A `merged` attempt, or a failed one over a recorded merge, seals `succeeded` once its issue's delivery transaction has (next paragraph); one whose issue has no installed contract has no delivery proof and stays unsealed, and so does one whose delivery never completes. The helper-facing contract (schema 9, fencing, late results) is in `home/common/agent-skills/README.md` § Attempt custody and fencing.

From schema 10 the control plane decides from the store ([design spec](../.agents/artifacts/specs/2026-10-11-issue-339-control-plane-cutover-design.md)). Each installed delivery contract has one *delivery transaction*, created under the key `attempt-delivery/v1:<issue>:<contract digest>:<n>` with the closed subject `attempt-delivery/v1` (run, issue, contract digest, contract), the authority class `attempt-delivery`, the single concurrency key `attempt-delivery:<run>:<issue>`, a proof plan with one required `event` obligation per postcondition the contract marks `required`, and a journal: every delivery object of the ledger as an `event` evidence entry `<kind>:<id>` holding its canonical text, appended under a short span of the executor `delivery:<issue>`. A delivery remainder has *remainder custody*, a custody transaction under `attempt-custody/v1:<run>:<issue>:r<n>` with the closed subject `remainder-custody/v1` and the same worktree key as its source attempt, planned by the attempt rows. A held owner claim is the *claim entry* on the launch's open span, `admission-claim:<action id>:<epoch>`, so the span closing releases it and control counts a launch's slots from its open claimed span, falling back to the ledger's `admission` block for the controller's own slots, for a live launch without such a span and, for the `host_capacity` gate, for a launch the store has no view of. A write that adds a release other than a refusal moves every custody transaction parked for `suspended:host_capacity` back to `created` with the `capacity_released` transition, which is how the next sweep sees the gate open; an `owner_unavailable` release closes the launch's span in its own write. When the delivery is complete the delivery transaction seals `succeeded` (its receipt's evaluations are the required postconditions with their observations), and each unsealed custody transaction of that issue then seals `succeeded` under a span of the executor `<issue>:<attempt or r<n>>:seal`, after one `delivery-receipt` evidence entry citing the delivery receipt's digest. A delivery object, owner result or reconciled merge that reaches a sealed transaction is recorded as a *supplement* with `record_post_terminal` and never changes the receipt. `agent_tools.attempt_identity`, `agent_tools.attempt_custody` and `agent_tools.attempt_delivery` are pure and import no skill script (the delivery model's canonical-text function is passed in); `agent_tools.attempt_store` and `agent_tools.attempt_delivery_store` apply their plans to `TransactionStore`, and no `transaction_*` module changed for it.

The [#117 attempt-lifecycle decision](../.agents/artifacts/specs/2026-09-20-issue-117-attempt-lifecycle-first-consumer-design.md) selects attempts as the transaction core's first consumer and ship-release second.

The decision governs the planned single-store migration, immutable subject/identity, fenced custody and terminal evidence, and maps the already-delivered agent-slot admission (#150) and delivery contracts, remainders and authorization continuity (#151/#171) onto that core.

The decision is an architecture decision, and its runtime is the code described above: #123 delivered the core, and #125 moves the attempt lifecycle onto it in three packages, run identity (#337), attempt custody and receipts (#338) and the control-plane cutover (#339). `workflow-state` still writes each run's ledger, whose attempt fields are the projection of the custody transactions, and `home/common/agent-skills/README.md` holds the helper-facing contract of that lifecycle.

## Release profiles

The authored `release` member of `.agents/project.json` is required and has two forms (#124 D1): `"unsupported"`, or `{"profiles": {<profile-id>: <profile>}}` with exactly that member and a non-empty map. A profile's `publication` is `"none"` or `{"actions": [...]}` with at least one action, and a profile with `"publication": "none"` is a publication-free profile (#368 D1, D2): it declares its target, requirements and bindings like any other and passes the same same-repository rule. The grammar holds it to three further rules: its `activation` must be `"none"` (anything else is one `contract.release.invalid` violation, and the activation is then judged no further), its `proof.obligations` must be `[]` (a non-empty list is one `contract.release.invalid` violation and each obligation is still judged), and it can name no recovery unit, because the existing rule that a recovery key names no action or unit reports each entry as `contract.release.reference_unknown` (#368 D11). Two tiers judge a profile. The grammar (`release_profile.grammar_violations`) runs inside `resolve-project resolve`: every violation is `invalid_contract` with a `contract.release.*` repair, and a profile that names an adapter outside the closed registry (`release_adapter.REGISTRY`) or an operation the adapter does not support is a grammar violation, never a lookup fallback (D7). Admissibility (`release_profile.admissibility_findings`, D3) runs over a grammar-valid profile only: it reports every finding of its four rules (`observation_deadline`, `rolled_back_reachable`, `restore_anchor`, `core_plans`) as `{rule, pointer, reason, detail}`, and the same function feeds `capabilities.release`, which is `unsupported` for `"unsupported"`, `blocked` with `release_profile_inadmissible` for the first inadmissible profile, `blocked` with `release_adapter_unavailable` when a bound adapter's declared executable is not on `PATH`, and `available` otherwise (D23); it is also `unsupported` when no profile declares a publication, before any admissibility or executable check, and otherwise that logic runs over all profiles, publication-free ones included (#368 D4). `compile_profile` returns a deep-frozen `ResolvedReleaseProfile` or raises `ProfileInadmissible`, and its `digest` covers the authored profile and the bound adapters' identities only (D5, D23). A publication-free profile compiles to empty graphs, read through `release_profile.phase_nodes`, the one post-grammar reader of a phase's authored nodes. `bind_candidate(compiled, candidate)` takes only a `ResolvedReleaseProfile` and returns the exact inputs of `TransactionStore.create` (`proof`, `recovery`, `concurrency_keys`, `subject`), so the core recompiles what the profile lowered (D5, D20). It refuses a compiled profile with no publication node with `ValueError` naming the profile, before it reads the candidate, so a publication-free profile never reaches `TransactionStore.create` (#368 D3), and `release_adapter.core_binding` over such a profile has no compiled node, so it refuses every request for it (#368 D8).

The resolved snapshot has a fifth member, `release`, derived rather than authored (#368 D5): `{"targets": [...]}`, where `release.targets` is built by `release_profile.release_targets` from the authored `release` member alone, so a profile that fails admissibility is listed all the same. It is `{"targets": []}` for `"unsupported"`. Otherwise it holds one entry per `bindings.targets` handle of every profile, ordered by profile id and then handle: `profile`, `adapter` (the registered adapter the target's alias binds), `target` (the normalized target, with `handle` and `kind`) and `operations` (the sorted, duplicate-free operations the profile's publication actions and activation units run against that handle). Every target of a publication-free profile is listed with an empty `operations` (#368 D6). The other four members of the snapshot are unchanged by it.

`release profile inspect <profile-id> [--repo-root PATH]` (#124 D15, D18) prints one compact sorted-key JSON `ReleaseProfileInspection` and exits 0 whether the profile is admissible or not, because diagnosis never mutates (#69); a publication-free profile is reported with exit 0, empty `publication` and `activation` graphs and an empty `handoffs` list (#368 D7). It is read-only: no adapter is invoked, nothing is written, no network is used, and the only child process is `git rev-parse HEAD` in the project root under a 10-second bound (a failure reports `source_revision: null`). It resolves the project as `resolve-project resolve` does, so a resolver refusal reaches the caller byte for byte with exit 2; `"unsupported"` is `release_unsupported` (repair `release.profile.declare`) and an unknown id is `profile_unknown` (repair `release.profile.unknown`), both exit 2. The report has exactly seven members: `schema_version`, `subject` (project, root, revision and installed platform), `profile` (id, version, digest, target, per-node deadlines, limits, `admissible`), `graphs` (the ordered publication and activation nodes, the handoff, the derived and authored proof obligations and the recovery units), `bindings` (adapter identities with each node's config, targets, principals and credential handles and classes, never credential material), `conformance` (per-adapter operation, predicate and executable support, the three linted checks and every finding) and `repairs` (one per finding, then one per missing executable, all `user_action`). No adapter `invoke` is reachable from any command; it is reachable only through the transaction core.

The legacy skills-config bridge (`release_bridge`, #124 D13) is two pure functions: `plan_legacy_release` proposes a `release` from a legacy `deploy` member, or a stable adoption question where the forge-only profile cannot represent it, and `project_legacy_deploy` renders the member-scoped `deploy` projection of a profile. The adoption sweep (`adopt_planning.legacy_binding_operations`, #148 D30) is its one writer, so during the bridge the legacy `deploy` member is generated, not edited.

## Release adapters

An adapter is a module with `describe`, `inspect` and `invoke`; `release_adapter.REGISTRY` is the closed mapping of adapter names to modules and `release_adapter.DESCRIPTORS` the descriptors built from it at import, so a malformed descriptor or one whose `name` differs from its registry key fails the import, and an unknown adapter name is a grammar violation (#124 D7, D19). `inspect` returns a closed effect or predicate `Observation` and `invoke` the closed `InvokeResult` `{result, error_class, reference}`: `result` is `accepted`, `rejected` or `unknown`, `error_class` is null exactly when `accepted`, and there is no `succeeded` because only the core's later inspection can say an effect landed (D7; #85, #206). `release_adapter.core_binding(adapter, compiled, alias)` projects an adapter onto the shapes the transaction core accepts: it refuses an implementation whose name or descriptor digest differs from the one the compiled profile pins, refuses any request whose `operation`, `target` or `config` is not exactly a compiled node of its alias (D24), and validates every result it returns, adding no retry or ordering policy.

The forge adapter (`forge_adapter`, D8) declares `pr_merge` as `unsupported` with reason `target_cas_unproven`, so a profile that names it is a grammar violation, and carries `tag` and `release`, both `index` mode, irreversible and create-if-absent. `inspect` reads with `gh api` and `gh pr view` only, with `GITHUB_TOKEN` and `GH_TOKEN` removed from the child so the keyring credential answers, under one collection budget; it reads a tag from its own ref and object, never from a Release's `target_commitish`. `invoke` applies the steps of spec section 7 in order and stops at the first refusal: request shape (an unsupported operation is `unsupported_operation`, bad parameters `invalid_input`, with no child process), the working checkout (`git rev-parse --show-toplevel`, D23), same repository (`origin` and its one push URL must each be a `github.com` URL in the `git@github.com:`, `https://github.com/` or `ssh://git@github.com/` spelling, and they and `gh api repos/<slug> --jq .full_name` all name `target.repository`), containment of the commit in the target branch (`tag`), the local annotated tag (reused at the same commit, created when absent, refused otherwise; D25), then the rendered command and the guard. A failed read before the mutation is `rejected` with `transient_transport` or `provider_unavailable`, because nothing was mutated. There are two mutation spellings: `git push origin refs/tags/<tag>` and `gh release create <tag> --repo <slug> --verify-tag --title "<title>" --notes-file <file>`, where `--verify-tag` refuses to create a tag and the notes file is a mode-0600 temporary removed afterwards. Before the one mutation the command text is passed to `claude-bash-lifecycle-guard`, by name on `PATH`, as a `{tool_name, tool_input.command, cwd}` Bash payload; a non-zero exit, timeout or missing guard is `authorization_denied` (D9). The mutation is never retried and the target is never read after it: `already exists` (git) or `HTTP 422` (gh) is `precondition_failed`, a mutation binary that cannot be spawned is `rejected` with `provider_unavailable`, because no child ran and nothing was applied (D23), and a timeout or any other non-zero exit is `unknown` with `transient_transport`, which the core resolves by inspection (D9, D11).

`tests/fixtures/forge-adapter-spellings.json` is the one list of provider spellings: `tests/forge_world.py` builds its fake `gh`, `git` and `claude-bash-lifecycle-guard` from it, and `tests/test_forge_adapter.py` pins the adapter to it, so the world and the adapter cannot disagree about a spelling (D12, D22). `tests/test_release_adapter_core.py` drives the real `TransactionStore` through `core_binding` and shows that an `accepted` invoke which never lands is recorded and then observed `absent` by a second inspection (AC8).

## guard-policy

`guard-policy compile --base <path> --output <path>` compiles the lifecycle guard's policy from the fleet registry (issue 126). It reads the base policy, the registry (`agent_platform.read_registry`, an absent one being the empty fleet) and each registered project's contract on its registered branch of `origin`, through `adopt_verify.remote_source` with the resolver run in process (issue 126 D13); it never reads the checkout's working tree, index or local branches. Its only repository writes are the remote-tracking refs of the branches it reads and the fetched objects. The base policy must be an object with exactly the five trusted members `authorized_owners`, `integration_bases`, `git_bin`, `gh_bin` and `jq_bin`, where the owners and branches are non-empty strings and the three tools are absolute paths; anything else, an unreadable file included, is the cause `base_invalid`.

A project earns a derived row only when twelve steps all hold in this run and the guard can load the row, and the first of those to fail names the reason code of its refusal. `derive` runs steps 1 to 10: the registered root is a git repository (`root_unavailable`); `origin`'s fetch url and its single push url name one `github.com` slug, spelt as `github_remote.github_slug` reads it and never case-folded (`origin_unproven`, issue 126 D9); `origin` yields a default branch and the contract's branch (`branch_unresolved` for `adopt.registration.remote_default_unknown` and `adopt.registration.integration_branch_unresolved`, `fetch_failed` for every other `AdoptError`); the resolver accepts that contract (`contract_unresolved`, with its repair id in the detail). `target_profiles` runs steps 5 to 8 on the resolved snapshot: the contract's project id is the registered one (`identity_mismatch`), its tracker is the `github` repository named by the slug (`tracker_mismatch`), it has a `github_repository` release target (`no_forge_target`), and every such target names the slug and the default branch (`target_mismatch`); each selected profile then compiles through `release_profile.compile_profile` (`profile_inadmissible`). Step 9 requires the contract's integration and default branches to be the branch read and `origin`'s default (`branch_mismatch`), and step 10 that `gh api repos/<slug> --jq .full_name` answers the slug (`provider_unproven`). `compile_policy` runs steps 11 and 12 over the projects that passed: a slug derived by more than one is `duplicate_repository` for each, and a slug that is also a key of the base `integration_bases` is `literal_conflict`: that project gets no row and the literal row stays in the base policy (issue 377 D5). A project that passed all twelve is then refused `name_unsupported` when `unsupported_name` finds its slug or either of its branches outside the shapes the guard's `load_compiled_policy` demands of a derived row: git and the contract grammar take a branch such as `dev+ci`, and the guard drops the whole compiled policy over one such row, which removes every derived row and blocks nothing the base policy allows (issue 377 D4). The guard is a standalone file the package cannot import, so `guard_policy` restates its two shapes as `GUARD_SLUG` and `GUARD_REF_NAME`, and a guard-suite test holds them to the built guard by loading a policy compiled from a fleet that has such a branch.

A row is `{default_branch, integration_branch, evidence}`, and the evidence is identity only (issue 126 D11): the project id, the digest of the registry entry (`canonical.telemetry_digest`), the pinned `ref` and `commit`, the contract's blob id at that commit, the provider's `full_name` and each compiled profile's `id`, `version` and `digest`. No resolved snapshot and no contract body is persisted. The written document has exactly two members, the rows under `derived_repositories` and `derivation`: `{schema_version, platform_version, registry_digest}`, where `schema_version` is 2 and the digest is `null` when no registry file exists. The lifecycle guard reads its trusted members (`authorized_owners`, `integration_bases` and the three tools) from the base policy only and takes nothing but a row's two branches from this file.

The three outcomes are the exit statuses. Exit 0 (`complete`) means every entry derived and the file was written. Exit 1 (`written_with_refusals`) means the file was written without the rows of the refused projects, one stderr line each. Exit 2 (`refused`) means no policy could be compiled, so the previous file is removed whatever it held: a missing file or a parent that is not a directory counts as removed, and any other failure to remove it is appended to the cause's detail without replacing the cause. The cause is one of `base_invalid`, `registry_invalid`, `platform_unavailable`, `output_unwritable` (issue 126 D14) or `internal`, which carries the exception's type and message. The write is atomic (`agent_platform.write_atomically`), so a reader sees the old file or the new one. The stdout report is one line of sorted-key JSON: `schema_version`, `outcome`, `derived` (the sorted slugs), `refused` (`project_id`, `root`, `reason_code` and a `detail` cut to 240 characters) and `cause` (`null` or `{reason_code, detail}`).

`guard-policy derive --repository <slug>` re-derives one repository's row (issue 377). It reads the registry, runs steps 1 and 2 for every entry and steps 3 to 10 only for the entries whose `origin` names the slug, so an entry naming another repository is never fetched and never asks the provider; then it runs step 11 and the name check among those entries. It prints one line of JSON with the keys `schema_version` (1), `repository` (the argument), `outcome`, `row`, `refused` and `cause`. The outcomes are `derived` (exit 0, `row` is the row `compile` would write), `refused` (exit 1, no row; `refused` lists the entries that name the slug and have none, and is empty when no entry names it) and `unavailable` (exit 2, `cause` is `{reason_code, detail}` with `registry_invalid`, `platform_unavailable` or `internal`). It writes no file beyond the fetched objects and remote-tracking refs, reads no base policy and never reports `literal_conflict`. The lifecycle guard runs it as its row check.

Every child of the identity steps, the two `git remote get-url` reads and the `gh api` read, runs by name with `cwd` at the registered root, stdin at `/dev/null`, `GIT_TERMINAL_PROMPT=0`, `GH_PROMPT_DISABLED=1`, a 30-second timeout and `GITHUB_TOKEN` and `GH_TOKEN` removed, so `gh` answers with the keyring credential (issue 126 D7); the fetch and the listing are bounded at the same 30 seconds. A timeout or a missing executable is a failed read. A failed read puts its reason in the refusal's detail (`timed out`, the executable error, or `exit <n>` with the child's stderr), and a `gh` answer other than the slug puts the name it gave. `tests/test_guard_policy.py` drives the commands as `python -m agent_tools.guard_policy compile` and `derive` over `tests/guard_policy_world.py`, and calls two functions directly for the checks no command input reaches: `target_profiles` on a hand-built snapshot for the one step the release grammar hides (issue 126 D10, D15), and `unsupported_name` on a hand-built row for the slug, because `github_remote.github_slug` already reads no slug the guard would refuse.
