# agent_tools — the agent helper package

Agent-workflow Python is moving into one standard-library package, `agent_tools`, under `python/` (with its `pyproject.toml`).

## Package and launchers

`lib/agent-tools.nix` builds it into one Python environment, import-checks every module so that a broken import fails `just build`, and holds the command table.

Each row becomes a `~/.agents/bin/<command>` launcher, which unsets the `NIX_PYTHON*` variables and runs `python3 -I -m agent_tools.<module>` from that environment, so nothing on `PYTHONPATH` or in the working directory can shadow the store copy; `just agent-installed-skill-tests` proves it.

## Review packaging and feasibility

`review-package` and `review-feasibility` use the package command table; their source entry points are `python -m agent_tools.review_package` and `python -m agent_tools.review_feasibility`.

Actual production and generic projection share packing and the external `artifact-budget` policy queried by PATH; projection binds its policy identity.

`review-feasibility project` reads committed plans and authenticated Git history without mutating them, while `validate-result` checks closed canonical v3 results and producer exits.

Actual production also calls external `sdd-workspace` by PATH.

## `verified-tree`

`verified-tree` records a passing run of the declared verification against the git tree it verified (what a Git-backed build sees: the index's entries with tracked files' working-tree edits applied, built in a temporary index, so an untracked file is outside it until committed) as `verified-tree.json` in the worktree's own git directory; `verified-tree check` answers `verified` only for that same tree under the same verification ids, which is how sdd's final gate lets ship skip a rerun (#263).

## `launch-scope`

`launch-scope` (#276) contains a lifecycle agent's long commands: `launch-scope exec` checks that the launch (or worker) is live, runs the command in a new session whose processes carry `AGENT_LAUNCH_SCOPE=<repo-scope>/<run-id>/<action-id>/<nonce>` (`<repo-scope>` is a hash of the registry's real path, so another repository's launch with the same run and action ids is never touched), and kills whatever the command left behind when it returns, while `launch-scope reap --action-id` (an owner, before its exit write) and `reap --sweep` (the orchestrate-issues stop pass, for every non-current launch of the run) kill the marked processes, and the process groups those processes prove, recorded in a host-local registry under the ledger repository's git common dir at `agent-launch/<run-id>/<action-id>/`; on darwin an Apple platform binary (`/bin`, `/usr/bin`) exposes no environment, so an orphaned group holding only such processes is never proved and survives a sweep.

`launch-scope scratch` (#277) prints the launch's one scratch root, a `launch-scope-*` directory under the system temp directory that the owner and its workers share, recorded as `scratch.json` in the launch's registry directory; once a reap finds the launch's processes gone it force-removes every worktree registered inside that root, present or missing, and deletes the root, never running a repository-wide `git worktree prune` (#277 D10); and every reap reports the registered worktrees outside the main checkout and outside every recorded root as `unattributed_worktrees`, deleting none of them.

## `lane-triage`

`lane-triage evaluate --repo-root <root> --input -` (#279) reads an owner's triage record on stdin, reads `bindings.workflow.light_lane` (an optional `resolve-project` member; absent or `null` means unsupported) through `agent_tools.resolve_project.resolve`, the one public function that composes exactly what `resolve-project resolve` prints, and prints the verdict `{hits, lane, mode}` without writing anything: `lane` is `light` only when no signal is `hit` or `doubt` and no predicted path matches a `risk_paths` glob, an absent or `null` member exits 2 with `light_lane_unsupported`, and `from-issue` Phase 0 records the verdict while every attempt still runs full.

## `sdd-gate`

`sdd-gate review PLAN_FILE --skill-dir DIR --task N [--standards PATH]... [--repo-root R --run-id I --action-id A --worker-id W]` (#353) gates one sdd task's evidence and renders the reviewer's dispatch brief, so a controller dispatches by a file path instead of composing the brief. `--standards` (repeatable) names a project standards index; the three lifecycle identity flags are all given or all absent, and `--worker-id` goes with them. Any other shape prints `sdd-gate: invalid invocation` on stderr, nothing on stdout, and exits 2. The task's base is the commit in the plan ledger's `Task <N>: dispatched (base <sha>)` line, which `sdd-gate next` writes; the head is the current checkout's `HEAD`, read once.

`review` runs seven steps in order and stops at the first that fails, naming it as `step`: `ledger` (the workspace `sdd-workspace` prints holds a `progress.md` whose header names this plan and which records exactly one base for the task), `release-worker` (under a lifecycle identity only, `workflow-state release-worker --event returned`), `review-package` (build the package for `base..head` with `review-package`, or reuse an existing one), `validate-report` (the artifact-budget authority validates the report, which must be `complete` or `decompose_required` and name this package root), `budget-check` (an independent `artifact-budget check` says `within_budget`), `metrics-match` (that check's metrics equal the report's) and `render-brief` (fill `task-reviewer-prompt.md` from `--skill-dir` and write `task-<N>-review-dispatch.md` in the workspace atomically).

A package is never deleted or overwritten. A fresh one saves its validated report beside it as `review-<base7>..<head7>.report.json`, for either state; an existing root is reused only when its manifest's `range` is exactly the base and head and that saved report exists, otherwise `review-package` refuses, so a repeated call is safe.

Stdout is one compact JSON object and a newline. Ready, exit 0: `command`, `outcome` (`ready`), `task`, `brief_path`, `base_sha`, `head_sha`, `manifest_root`, `metrics` and `standards` (the documents the brief quotes). Refused: `command`, `outcome` (`refused`), `step`, `gate`, `detail` (one line of at most 300 characters naming the cause, with the tail of a failed child's stderr where it has one, never artifact content), `report` and `completed_steps` (the steps that ran and passed, in order). `gate` is `decompose_required` (exit 3, with the validated report in `report`) for a package that must be split, `failed` (exit 2) for every other refusal of `review-package` to `metrics-match`, and `null` (exit 2) elsewhere; `report` is `null` unless `gate` is `decompose_required`, and no brief file exists after a refusal unless an earlier call wrote it.

`sdd-gate next PLAN_FILE --skill-dir DIR [--standards PATH]... [--completed N [--parked K]] [--task M [--context-file PATH]] [--delivery-base SHA] [--repo-root R --run-id I --action-id A]` closes task `N`, opens task `M` or both, and renders the implementer's dispatch brief. At least one of `--completed` and `--task` is required and both may be given; `--parked` goes with `--completed` and `--context-file` with `--task`; `N`, `K` and `M` are positive integers, `SHA` is a full 40-hex commit id, and the identity flags are all three or none. There is no `--worker-id` (the command registers the worker itself) and no stdin flag. Any other shape is the same `sdd-gate: invalid invocation`.

`next` runs up to eleven steps in order and stops at the first that fails; a step that does not apply to the call does not run and is not listed in `completed_steps`: `ledger` (the ledger is this plan's, its recorded delivery base and `--delivery-base` agree and at least one exists, the completed task has a `dispatched` line, the task to dispatch has at most one; nothing is written until every read has passed, and then the delivery base is recorded if new), `ledger-complete` (with `--completed`), `mark-progress` (under an identity: `workflow-state mark-progress`, and a non-zero exit or an unreadable reply reports `"refused"` without stopping the call), `review-package`, `validate-report`, `budget-check` and `metrics-match` (the same package gate as `review`, over the cumulative range delivery base to `HEAD`), `task-brief` (the installed `task-brief` command copies the task's plan member into the workspace), `prepare-brief` (record the task's base if new, then render the brief once in memory), `register-worker` (under an identity: `workflow-state register-worker`) and `write-brief` (`task-<M>-implementer-dispatch.md`, atomically). A ledger that cannot be read or appended to is refused at the step that needs it (`ledger`, `ledger-complete`), except that the `Delivery gate:` line is refused at `metrics-match` with gate `failed` and that step is not listed as passed. A worker is registered only after the brief has rendered; a failed brief write releases the worker it registered with `release-worker --event stopped` before the refusal is printed, and when that release fails too the refusal's `detail` names the worker and the command to run first.

The ledger gains only four line shapes, one write each and never the same line twice: `Delivery base: <sha40>`; `Task <N>: complete (commits <base7>..<head7>, review clean)` (or `, <K> parked)`); `Delivery gate: <base40>..<head40> root_bytes=<n> total_bytes=<n> file_count=<n> largest_member_bytes=<n>`; and `Task <M>: dispatched (base <sha40>)`. `review` and `next` read `dispatched` and `next` also reads `Delivery base`; `workflow-state resume-pack` reads `complete`. A repeated call writes nothing new.

Ready, exit 0, in this key order: `command` (`next`), `outcome` (`ready`), `completed`, `task`, `brief_path`, `report_path` (`task-<M>-report.md` in the workspace), `base_sha` (the task's base), `worker_id`, `mark_progress` (`skipped` without an identity, else the `workflow-state` outcome or `refused`), `delivery` (`base_sha`, `head_sha`, `manifest_root`, `metrics`) and `standards`; the members that do not apply to the call are `null` (`[]` for `standards` without `--task`). Refusals and exit codes are `review`'s.

## adopt-project

`adopt-project plan` asks two kinds of open question: `project-id`, answered by declaring exactly one remote or authoring a contract with the project id, and `candidate-class` (#340), one per tracked or targeted-ignored agent path that no classification row settles (none covers it, or a targeted-ignored one it covers resolves outside the repository or cannot be read), keyed by its `subject` (the path) and carrying the one `value` the question accepts: `archive-history` for a tracked path, which plans a `git mv` to `.agents/knowledge/archive/adopted/<path>`, `retain-product` for an ignored one, and `null`, no answer, for a secret-shaped tracked path, which stays open until a central classification row covers it or it leaves the repository, or for a tracked symlink resolving outside the repository, which stays open until it leaves the repository; `plan --answer QUESTION SUBJECT VALUE` (repeatable, order-independent) settles a `candidate-class` question, refusing the first violation as `adopt.decisions.invalid_answer` (an id other than `candidate-class`, a subject answered twice, or a value other than the offered one) or `adopt.decisions.unmatched_answer` (a subject that is not an undecided candidate of this inspection), checking each answer in `(id, subject, value)` order and changing nothing on a refusal; the answers enter `decisions.answered` and therefore `plan_id`, and `apply --plan-id` re-applies them from the stored plan (refusing a malformed `decisions.answered` as `adopt.plan.malformed`), so the plan id, not an `apply` flag, authenticates them.

`adopt-project plan` rewrites relative Markdown link targets across its moves (#345): outbound in every Markdown file a `git-mv` moves, inbound in every other tracked Markdown file (a regular `.md`/`.markdown` blob at the base revision, strict UTF-8, not secret-shaped; a `generated_file` projection target is left to its regeneration). `agent_tools.adopt_links` owns the grammar — inline links and images on one line and reference definitions, outside fenced code, code spans and link titles — and resolves a target against the tracked paths of a tree, never the filesystem: a target is relative unless it is empty, starts with `#` or `/`, carries a URL scheme or holds a backslash, and it resolves when its percent-decoded path, joined to the containing directory, names a tracked file or a directory inside the root. The rewritten bytes come from the plan's base revision, each changed file is a `write-file` at the path the file has after the moves and placed before the projection regenerations, and a rewritten target keeps its anchor or query, title, angle brackets and trailing slash, and its leading `./` unless the new path climbs out with `../`; a bare target is percent-encoded and an angle target encodes only `%`, `#`, `?`, `<`, `>` and line breaks, and gains a leading `./` when its path would otherwise open with a URL scheme (`urn:x.md`), so the emitted path names the same file and stays relative; a link that already fails to resolve, a URL and a link the moves leave correct stay byte-identical. The plan document and the adoption evidence record carry `link_rewrites` (`inbound` and `outbound` link counts and sorted files, `unrewritable` `path`/`target` entries and an `already_broken` count), which is the seventh input of `plan_id`. The ready gate `no-unrewritable-link` (`adopt.link.unrewritable`) keeps the plan `draft` when a link targets a file the plan deletes or a directory that no longer exists after the moves and whose files did not all move, by the same relative tails, under one new directory, and `apply`'s commit gate `no-new-broken-link` (`adopt.gate.no-new-broken-link`), before `cold-clone-resolves`, fails when any Markdown file in the index has more non-resolving relative links, each side counted against its own tree, than its pre-move counterpart at `HEAD` (a file with no counterpart is compared with zero); because the verification commands and a `pre-commit` hook run after it, the same count over the commit against its parent is proved again once the commit exists, and a failure there refuses `adopt.commit.new_broken_link` with the worktree and branch retained. Prose mentions of moved paths, inline HTML, root-relative targets and non-Markdown files are never rewritten.

## Transaction core

`agent_tools.transaction_core` is the transaction core's library surface, with no command-table row, and whose first caller is `workflow-state`, which mints one created-only *run transaction* per attempt run in `<ledger root>/.superpowers/attempt-transactions/` through `agent_tools.attempt_identity` (pure rules) and `agent_tools.attempt_store` (store root, mint lock, binding and `migrate`'s rows) and finds it by the read-only `TransactionStore.lookup` (#337): slice 1 (#204) holds caller-rooted transaction state under a closed schema and lifecycle, slice 2 (#205) adds fenced custody — a lease authority over concurrency keys in `agent_tools.transaction_custody`, epoch-fenced writes, and evidence and grant admissibility derived from the fence — and slice 3 (#206) adds the administrative protocol — a durable write intent before every external call, inspection before any retry, and an automatic-retry budget — in `agent_tools.transaction_invocation`; slice 4 (#207) then adds an immutable proof plan compiled at creation (`agent_tools.transaction_plan`), core-collected obligations, and one convergence cohort (at most three attempts) that `settle_proof` alone seals into `succeeded` or parks as `proof_rejected` or `proof_did_not_converge`, never rolling back (`agent_tools.transaction_proof`); slice 5 (#208) adds an immutable recovery plan compiled at creation beside the proof plan (`agent_tools.transaction_recovery_plan`), rollback anchors verified in `ready` before publication, `abandoned` only while no action has had an effect, and `begin_recovery`, `settle_recovery` and `roll_forward` as the only ways into `recovering`, into `rolled_back` and to a linked child transaction (`agent_tools.transaction_recovery`); slice 6 (#209) writes a permanent, content-addressed terminal receipt under the store root's `receipts/` and reads it back before the one `state.json` write that enters any terminal, which ends with a `receipt_sealed` event naming it, then re-reads that receipt on every load (`agent_tools.transaction_receipt`), and makes `dispose_failed` the only way into `failed`: it takes a fresh grant and one closed ground, and it yields an `effects_unobservable` qualifier with per-key hazard markers only when a human grant at the transaction's authority class asserts an observability ground (`agent_tools.transaction_disposition`), with the `transaction-state/v6` validator and snapshot fold in `agent_tools.transaction_history`, over the durable-file primitives in `agent_tools.transaction_storage`.

The [#117 attempt-lifecycle decision](../.agents/artifacts/specs/2026-09-20-issue-117-attempt-lifecycle-first-consumer-design.md) selects attempts as the transaction core's first consumer and ship-release second.

The decision governs the planned single-store migration, immutable subject/identity, fenced custody and terminal evidence, and maps the already-delivered agent-slot admission (#150) and delivery contracts, remainders and authorization continuity (#151/#171) onto that core.

The decision is an architecture decision: runtime core delivery belongs to the open #123/#125, and the lifecycle paths and behavior that `home/common/agent-skills/README.md` describes remain the shipped implementation until that cutover.

## Release profiles

The authored `release` member of `.agents/project.json` is required and has two forms (#124 D1): `"unsupported"`, or `{"profiles": {<profile-id>: <profile>}}` with exactly that member and a non-empty map. Two tiers judge a profile. The grammar (`release_profile.grammar_violations`) runs inside `resolve-project resolve`: every violation is `invalid_contract` with a `contract.release.*` repair, and a profile that names an adapter outside the closed registry (`release_adapter.REGISTRY`) or an operation the adapter does not support is a grammar violation, never a lookup fallback (D7). Admissibility (`release_profile.admissibility_findings`, D3) runs over a grammar-valid profile only: it reports every finding of its four rules (`observation_deadline`, `rolled_back_reachable`, `restore_anchor`, `core_plans`) as `{rule, pointer, reason, detail}`, and the same function feeds `capabilities.release`, which is `unsupported` for `"unsupported"`, `blocked` with `release_profile_inadmissible` for the first inadmissible profile, `blocked` with `release_adapter_unavailable` when a bound adapter's declared executable is not on `PATH`, and `available` otherwise (D23). `compile_profile` returns a deep-frozen `ResolvedReleaseProfile` or raises `ProfileInadmissible`, and its `digest` covers the authored profile and the bound adapters' identities only (D5, D23). `bind_candidate(compiled, candidate)` takes only a `ResolvedReleaseProfile` and returns the exact inputs of `TransactionStore.create` (`proof`, `recovery`, `concurrency_keys`, `subject`), so the core recompiles what the profile lowered (D5, D20).

`release profile inspect <profile-id> [--repo-root PATH]` (#124 D15, D18) prints one compact sorted-key JSON `ReleaseProfileInspection` and exits 0 whether the profile is admissible or not, because diagnosis never mutates (#69). It is read-only: no adapter is invoked, nothing is written, no network is used, and the only child process is `git rev-parse HEAD` in the project root under a 10-second bound (a failure reports `source_revision: null`). It resolves the project as `resolve-project resolve` does, so a resolver refusal reaches the caller byte for byte with exit 2; `"unsupported"` is `release_unsupported` (repair `release.profile.declare`) and an unknown id is `profile_unknown` (repair `release.profile.unknown`), both exit 2. The report has exactly seven members: `schema_version`, `subject` (project, root, revision and installed platform), `profile` (id, version, digest, target, per-node deadlines, limits, `admissible`), `graphs` (the ordered publication and activation nodes, the handoff, the derived and authored proof obligations and the recovery units), `bindings` (adapter identities with each node's config, targets, principals and credential handles and classes, never credential material), `conformance` (per-adapter operation, predicate and executable support, the three linted checks and every finding) and `repairs` (one per finding, then one per missing executable, all `user_action`). No adapter `invoke` is reachable from any command; it is reachable only through the transaction core.

The legacy skills-config bridge (`release_bridge`, #124 D13) is two pure functions: `plan_legacy_release` proposes a `release` from a legacy `deploy` member, or a stable adoption question where the forge-only profile cannot represent it, and `project_legacy_deploy` renders the member-scoped `deploy` projection of a profile. The adoption sweep (`adopt_planning.legacy_binding_operations`, #148 D30) is its one writer, so during the bridge the legacy `deploy` member is generated, not edited.

## Release adapters

An adapter is a module with `describe`, `inspect` and `invoke`; `release_adapter.REGISTRY` is the closed mapping of adapter names to modules and `release_adapter.DESCRIPTORS` the descriptors built from it at import, so a malformed descriptor or one whose `name` differs from its registry key fails the import, and an unknown adapter name is a grammar violation (#124 D7, D19). `inspect` returns a closed effect or predicate `Observation` and `invoke` the closed `InvokeResult` `{result, error_class, reference}`: `result` is `accepted`, `rejected` or `unknown`, `error_class` is null exactly when `accepted`, and there is no `succeeded` because only the core's later inspection can say an effect landed (D7; #85, #206). `release_adapter.core_binding(adapter, compiled, alias)` projects an adapter onto the shapes the transaction core accepts: it refuses an implementation whose name or descriptor digest differs from the one the compiled profile pins, refuses any request whose `operation`, `target` or `config` is not exactly a compiled node of its alias (D24), and validates every result it returns, adding no retry or ordering policy.

The forge adapter (`forge_adapter`, D8) declares `pr_merge` as `unsupported` with reason `target_cas_unproven`, so a profile that names it is a grammar violation, and carries `tag` and `release`, both `index` mode, irreversible and create-if-absent. `inspect` reads with `gh api` and `gh pr view` only, with `GITHUB_TOKEN` and `GH_TOKEN` removed from the child so the keyring credential answers, under one collection budget; it reads a tag from its own ref and object, never from a Release's `target_commitish`. `invoke` applies the steps of spec section 7 in order and stops at the first refusal: request shape (an unsupported operation is `unsupported_operation`, bad parameters `invalid_input`, with no child process), the working checkout (`git rev-parse --show-toplevel`, D23), same repository (`origin` and its one push URL must each be a `github.com` URL in the `git@github.com:`, `https://github.com/` or `ssh://git@github.com/` spelling, and they and `gh api repos/<slug> --jq .full_name` all name `target.repository`), containment of the commit in the target branch (`tag`), the local annotated tag (reused at the same commit, created when absent, refused otherwise; D25), then the rendered command and the guard. A failed read before the mutation is `rejected` with `transient_transport` or `provider_unavailable`, because nothing was mutated. There are two mutation spellings: `git push origin refs/tags/<tag>` and `gh release create <tag> --repo <slug> --verify-tag --title "<title>" --notes-file <file>`, where `--verify-tag` refuses to create a tag and the notes file is a mode-0600 temporary removed afterwards. Before the one mutation the command text is passed to `claude-bash-lifecycle-guard`, by name on `PATH`, as a `{tool_name, tool_input.command, cwd}` Bash payload; a non-zero exit, timeout or missing guard is `authorization_denied` (D9). The mutation is never retried and the target is never read after it: `already exists` (git) or `HTTP 422` (gh) is `precondition_failed`, a mutation binary that cannot be spawned is `rejected` with `provider_unavailable`, because no child ran and nothing was applied (D23), and a timeout or any other non-zero exit is `unknown` with `transient_transport`, which the core resolves by inspection (D9, D11).

`tests/fixtures/forge-adapter-spellings.json` is the one list of provider spellings: `tests/forge_world.py` builds its fake `gh`, `git` and `claude-bash-lifecycle-guard` from it, and `tests/test_forge_adapter.py` pins the adapter to it, so the world and the adapter cannot disagree about a spelling (D12, D22). `tests/test_release_adapter_core.py` drives the real `TransactionStore` through `core_binding` and shows that an `accepted` invoke which never lands is recorded and then observed `absent` by a second inspection (AC8).
