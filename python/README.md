# agent_tools — the agent helper package

Agent-workflow Python is moving into one standard-library package, `agent_tools`, under `python/` (with its `pyproject.toml`).

## Package and launchers

`lib/agent-tools.nix` builds it into one Python environment, import-checks every module so that a broken import fails `just build`, and holds the command table.

Each row becomes a `~/.agents/bin/<command>` launcher, which unsets the `NIX_PYTHON*` variables and runs `python3 -I -m agent_tools.<module>` from that environment, so nothing on `PYTHONPATH` or in the working directory can shadow the store copy; `just agent-installed-skill-tests` proves it.

## Review packaging and feasibility

`review-package` and `review-feasibility` use the package command table; their source entry points are `python -m agent_tools.review_package` and `python -m agent_tools.review_feasibility`.

Actual production and generic projection share packing and the external `artifact-budget` policy queried by PATH; projection binds its policy identity.

When one file diff is larger than the review-package member limit, actual production replaces it with a bounded generated-evidence entry if that entry fits the limit and the file is an auto-generated EF Core migration designer (`ef-core-migration-designer`) or a file the range deletes outright (`whole-file-deletion`: the base blob's identity and line count, and a null head); any other oversized file diff stays whole, and the package is `decompose_required`.

`review-feasibility project` reads committed plans and authenticated Git history without mutating them, while `validate-result` checks closed canonical v3 results and producer exits.

Actual production also calls external `sdd-workspace` by PATH.

## `verified-tree`

`verified-tree` records a passing run of the declared verification against the git tree it verified (what a Git-backed build sees: the index's entries with tracked files' working-tree edits applied, built in a temporary index, so an untracked file is outside it until committed) as `verified-tree.json` in the worktree's own git directory (#263). Both verbs read the worktree's own `bindings.workflow.verification`, `bindings.workflow.verification_conditions` and `bindings.vcs.integration_branch` through `agent_tools.resolve_project.resolve` with `verification` required, and a refusal exits 2 as `verified-tree: resolve-project refused: <code> <repair_id>`. `verified-tree check` prints `{run, skipped, status, tree}`: `run` is the declared ids, in order, that have no condition or whose condition matches the change, and `skipped` is the rest as `{id, reason}`. It answers `verified` only for that same tree with a record whose ids equal `run`, which is how sdd's final gate lets ship skip a rerun. `check` also persists the plan it printed (`tree` and `run`) as `verified-tree-plan.json` beside the record. `verified-tree record --tree <id>` first compares the tree (a moved tree exits 3 `tree_changed`), then records the persisted `run` only when `check` persisted a plan for that tree and the plan recomputed now has the same `run`; otherwise it exits 2 writing no record, so a moved `origin/<integration_branch>` cannot turn an id the caller skipped into a recorded pass, and a skipped id never reads as passed. `record` consumes the persisted plan once it has read it, recorded or not, and a `check` of a tree whose plan is still pending narrows it to the ids both plans run and never widens it, so a second caller's `check` in the same worktree cannot make the first caller record an id it skipped; both verbs touch the plan under an exclusive lock on `verified-tree-plan.lock`.

`verification_conditions` (issue 437) is an optional `resolve-project` member; absent or `null` means no id is conditional. It maps a `workflow.verification` id to `{"when_changed": [<glob>, ...], "skip_reason": "<text>"}`, with exactly those two members. `when_changed` is a non-empty list of globs under the `light_lane.risk_paths` rules: repository-relative, canonically spelled, and matched with `fnmatch.fnmatchcase`, so `*` crosses `/`. `skip_reason` is a non-empty string, reported verbatim. At least one declared id must stay unconditional. The change is every path `git diff-tree -r --no-renames` names between `git merge-base HEAD refs/remotes/origin/<integration_branch>` and the verified tree, so a rename counts as both of its paths and a deletion counts. It is computed only when some id is conditional, and then a missing ref or merge base is exit 2, never a skip.

## `launch-scope`

`launch-scope` (#276) contains a lifecycle agent's long commands: `launch-scope exec` checks that the launch (or worker) is live, runs the command in a new session whose processes carry `AGENT_LAUNCH_SCOPE=<repo-scope>/<run-id>/<action-id>/<nonce>` (`<repo-scope>` is a hash of the registry's real path, so another repository's launch with the same run and action ids is never touched), and kills whatever the command left behind when it returns, while `launch-scope reap --action-id` (an owner, before its exit write) and `reap --sweep` (the orchestrate-issues stop pass, for every non-current launch of the run) kill the marked processes, and the process groups those processes prove, recorded in a host-local registry under the ledger repository's git common dir at `agent-launch/<run-id>/<action-id>/`; on darwin an Apple platform binary (`/bin`, `/usr/bin`) exposes no environment, so an orphaned group holding only such processes is never proved and survives a sweep.

`launch-scope scratch` (#277) prints the launch's one scratch root, a `launch-scope-*` directory under the system temp directory that the owner and its workers share, recorded as `scratch.json` in the launch's registry directory; once a reap finds the launch's processes gone it force-removes every worktree registered inside that root, present or missing, and deletes the root, never running a repository-wide `git worktree prune` (#277 D10); and every reap reports the registered worktrees outside the main checkout and outside every recorded root as `unattributed_worktrees`, deleting none of them.

## `lane-triage`

`lane-triage evaluate --repo-root <root> --input -` (#279) reads an owner's triage record on stdin, reads `bindings.workflow.light_lane` (an optional `resolve-project` member; absent or `null` means unsupported) through `agent_tools.resolve_project.resolve`, the one public function that composes exactly what `resolve-project resolve` prints, and prints the verdict `{hits, lane, mode}` without writing anything: `lane` is `light` only when no signal is `hit` or `doubt` and no predicted path matches a `risk_paths` glob, an absent or `null` member exits 2 with `light_lane_unsupported`, and `from-issue` Phase 0 records the verdict while every attempt still runs full.

## `agent-workflow-tests` runner

`just agent-workflow-tests` hands its curated member list to `agent_tools.suite_runner` (issue 436; source entry `python -m agent_tools.suite_runner`, no command-table row). The runner runs each member in its own process from its working directory, with the recipe's environment: a `.py` member as `python -m unittest -v <path>`, and a `.sh` member as `bash <path>`. At most `--jobs N` members run at once. The default, 4, is a fixed value, not one derived from the CPU count: the suite is CPU-bound, the hosted CI runner has 4 vCPUs, and several agents may verify on one host. In parallel mode each member's stdout and stderr are captured together and printed as one block when it exits, from `suite-runner: begin <member>` to `suite-runner: end <member> passed|failed exit=<code> <seconds>s`. A `suite-runner: start <member>` line marks each launch, so a run cut off by a time limit names the members still running. `--jobs 1` is serial mode: members run one at a time with stdin, stdout and stderr passed straight through, for a hang or a `breakpoint()`. A member passes only on exit 0. Unittest's exit 5 for a module that ran no tests, a death by signal (`exit=signal-<n>`) and a failure to launch (`exit=launch-error`) all fail it, and every member still runs after a failure. Every completed run ends with a timing table, slowest first with ties in list order, then one `suite-runner: failed <member>` line per failure and a `summary` line. Exit 0 means every member passed and 1 that one failed. Exit 2 is a usage error, raised before anything starts: a bad `--jobs`, no members, a duplicate, a member that is missing, is not a file or lies outside the working directory, or a suffix other than `.py` or `.sh`. Exit 130 is an interrupt: the runner starts nothing more, prints `suite-runner: interrupted, waiting for running members`, waits for those members and prints no report. A test that shares state with another test process is fixed by giving it its own temporary location, never by a serial-exemption list, a retry or a lock.

## `context-meter`

`context-meter` (issue 424; `python -m agent_tools.context_meter`) is a `PreToolUse` hook, the second command hook of the Bash entry that `home/common/claude-code/default.nix` registers beside the lifecycle guard (timeout 10 s, no arguments; see `home/common/claude-code/README.md` § Context meter). Claude Code runs it before every Bash call with the call as JSON on stdin; it reads `tool_name`, `tool_input.command`, `session_id`, `agent_id` (absent for a main session) and `transcript_path`, and prints either nothing or one JSON object with `hookSpecificOutput.hookEventName` `PreToolUse` plus `updatedInput` and `additionalContext`, or a `systemMessage`. Input that is not JSON, not a Bash call, or has no string command prints nothing.

**Measurement.** A subagent's context is read from `subagents/agent-<agent_id>.jsonl` in the directory named for the session, beside `transcript_path`; a main session reads `transcript_path` itself and skips records marked `isSidechain`, which belong to its subagents. Both ids must be plain identifiers (`[A-Za-z0-9][A-Za-z0-9_-]{0,127}`), so no id can steer the path. Only the last 1 MiB (`WINDOW_BYTES`) of the file is read, dropping the partial first line; the newest `assistant` record whose model is not `<synthetic>` and whose usage sums above 0 gives the context, `input_tokens + cache_read_input_tokens + cache_creation_input_tokens`, the same sum `agent-costs` counts as a call's context. A usage field that is negative, boolean or not an integer makes that record count as 0. A missing or unreadable transcript, no usable record in the window, or an unusable id leaves the context unmeasured, with the reason in the message. A session's first tool call is always unmeasured, because Claude Code runs `PreToolUse` before that turn's usage record reaches the transcript, so the meter fails open there (spec D20).

**Rewrite.** `context_meter_commands` lexes the command with a small shell subset (quotes, escapes, line continuations, comments, control and redirection operators, the IO-number rule) and finds each `workflow-state progress` invocation, however the helper is addressed (its last path component is `workflow-state`). It recognises the two adjacent words at any position, not only where a command starts, so a wrapped call (`timeout 60 workflow-state progress …`, `launch-scope exec … -- workflow-state progress …`) is measured, and unquoted data words that spell a progress call (`echo workflow-state progress --context-tokens 1`) are rewritten too, with the measured note shown (spec D21). A command outside the subset (a heredoc, an unterminated quote, a trailing backslash, or a double-quoted interior holding an unescaped `$(` or backtick) is left alone; a progress call among them passes through unchanged with the message `could not be tokenised`. In each invocation the rewrite deletes every spelling of `--context-tokens` that argparse accepts, from the full option down to `--context-t`, with `=` or a separate value and before any `--`, skipping the words of redirections, and inserts one `--context-tokens <n>` right after `progress`. It splices the original text, so every other byte survives, and the ceiling and headroom flags (`--context-ceiling`, `--context-headroom`, the turn pair) are never touched. The result is emitted only when it is proved: the rewritten command must lex to exactly the original words minus the removed ones plus the inserted pair (`context_meter_commands.proved`). A removal is also refused as unprovable when a removed word is glued to a following `(`, backtick or redirection operator (deleting it would fuse a substitution or redirection into a new word), when a bare spelling is followed by `(` or a backtick, or by redirections and then a word not starting with `-` (bash takes `--context-tokens >/dev/null 5` as the value `5`), or when the invocation's simple command ends at an opening `(` or backtick (`--repo-root $(pwd) …` continues past a substitution the subset cannot see; a backtick closes rather than opens when an odd number of backticks precede the invocation); the call then passes through unchanged with the message `the rewrite failed its proof`. An unmeasured context removes the agent's value and inserts nothing.

The four fixed texts, each with its reason:

- Measured: `additionalContext` says the call carries `--context-tokens <n>`, measured from the agent's transcript, so the agent knows the value is not its own.
- Unmeasured: `additionalContext` says the call carries no `--context-tokens`, and a `systemMessage` names the reason, so a missing figure is never taken for zero.
- Unchanged: a `systemMessage` names why a progress call was left as written (not tokenisable, or failed its proof), so the user sees that the measured value is absent.
- Crossing: `additionalContext` tells an owner its context and the threshold and to run its phase gate (`workflow-state progress` for its last completed phase, with truthful booleans, then obey its action) at the next safe point; it says the notice is not repeated.

**Owners and the crossing.** An agent becomes an owner when one of its calls is a registering call: `workflow-state progress` or `workflow-state mark-progress`, or `sdd-gate`, with an `--action-id` (bare or `=`) in the same simple command. For an owner every Bash call reads the transcript, an untokenisable one included (such a call never registers an owner); a call from an agent with no state file that registers nothing and holds no progress invocation reads nothing and writes nothing. The threshold is `phase_budget.crossing_threshold(current(), phase)`, 200,000 for every phase unless `AGENT_PHASE_BUDGET` overrides it, where `phase` is the owner's recorded phase (`null` reads as the base threshold). The record shape is in State below. A call holding a `workflow-state progress` invocation sets `phase` to the last such invocation's `--phase` plus one when that value is a decimal integer and the sum is at most 8, and a registering `workflow-state mark-progress` or `sdd-gate` sets it to 6 while it is `null`; the update is applied under the lock before the crossing is decided. The crossing text names the threshold used. A measurement below it clears the owner's `notified` flag; the first measurement at or above it sets the flag and makes the crossing text due, unless the same call is a progress call the meter rewrote to carry the measurement (a proved rewrite of a measured context), which reports the context itself; a progress call left unchanged gets the crossing text with its own `systemMessage` kept in the same output; later measurements at or above it are not due until one falls below again. An unmeasured call changes nothing.

**State.** `~/.agents/state/context-meter/<session_id>.main.json`, or `<session_id>.agent-<agent_id>.json` for a subagent, holds exactly `{"notified": <bool>, "owner": true, "phase": <integer 0 to 8 or null>}`, which is the only form the hook writes; a record written before `phase` existed, exactly `{"notified": <bool>, "owner": true}`, is accepted and read as `phase: null`; the directory is created `0700` and the file `0600`. An empty file is an owner being registered. Each update is a read-decide-write under an exclusive `flock` with no timeout, so hooks of parallel tool calls from one owner serialise on the lock, which is held only for that sequence. Any other content in the file, a repeated key included, is an error (the hook exits 1, below). State files are never pruned.

**`phase_budget`.** `agent_tools.phase_budget` is the one home of the phase-gate budget, the frozen `PhaseBudget` (turn ceiling 120, turn headroom 2, context headroom 10,000, hand-off threshold 200,000, optional per-phase `phase_thresholds`, and the replay-only `guard` and `cap`) and `select_phase_action`. `workflow-state progress` leaves its four budget flags at `None` and resolves them from `current()`: an explicit flag wins, and otherwise the context ceiling is `handoff_threshold(budget, --phase + 1)` plus the default headroom, so the gate reads the threshold of the phase being entered, as the meter does. `current()` is read once per process: it is the default budget unless `AGENT_PHASE_BUDGET` holds a spec (`threshold=N`, `threshold:<a>-<b>=N`; `parse` also takes `guard` and `cap` for the replay), which raises when invalid. The variable exists for evaluation arms; production never sets it.

**Exit codes.** `0` after printing nothing or one object; `1` with a traceback on stderr when stdin cannot be read, the state file is malformed or the lock or write fails, which Claude Code treats as a non-blocking error, so the call runs as the agent wrote it. It never exits `2` and never prints `permissionDecision`, `decision` or `continue`.

## `sdd-gate`

`sdd-gate review PLAN_FILE --skill-dir DIR --task N [--standards PATH]... [--repo-root R --run-id I --action-id A --worker-id W]` (#353) gates one sdd task's evidence and renders the reviewer's dispatch brief, so a controller dispatches by a file path instead of composing the brief. `--standards` (repeatable) names a project standards index; the three lifecycle identity flags are all given or all absent, and `--worker-id` goes with them. Any other shape prints `sdd-gate: invalid invocation` on stderr, nothing on stdout, and exits 2. The task's base is the commit in the plan ledger's `Task <N>: dispatched (base <sha>)` line, which `sdd-gate next` writes; the head is the current checkout's `HEAD`, read once.

`review` runs seven steps in order and stops at the first that fails, naming it as `step`: `ledger` (the workspace `sdd-workspace` prints holds a `progress.md` whose header names this plan and which records exactly one base for the task), `release-worker` (under a lifecycle identity only, `workflow-state release-worker --event returned`), `review-package` (build the package for `base..head` with `review-package`, or reuse an existing one), `validate-report` (the artifact-budget authority validates the report, which must be `complete` or `decompose_required` and name this package root), `budget-check` (an independent `artifact-budget check` says `within_budget`), `metrics-match` (that check's metrics equal the report's) and `render-brief` (fill `task-reviewer-prompt.md` from `--skill-dir` and write `task-<N>-review-dispatch.md` in the workspace atomically).

A package is never deleted or overwritten. A fresh one saves its validated report beside it as `review-<base7>..<head7>.report.json`, for either state; an existing root is reused only when its manifest's `range` is exactly the base and head and that saved report exists, otherwise `review-package` refuses, so a repeated call is safe.

Stdout is one compact JSON object and a newline. Ready, exit 0: `command`, `outcome` (`ready`), `task`, `brief_path`, `base_sha`, `head_sha`, `manifest_root`, `metrics` and `standards` (the documents the brief quotes). Refused: `command`, `outcome` (`refused`), `step`, `gate`, `detail` (one line of at most 300 characters naming the cause, with the tail of a failed child's stderr where it has one, never artifact content), `report` and `completed_steps` (the steps that ran and passed, in order). `gate` is `decompose_required` (exit 3, with the validated report in `report`) for a package that must be split, `failed` (exit 2) for every other refusal of `review-package` to `metrics-match`, and `null` (exit 2) elsewhere; `report` is `null` unless `gate` is `decompose_required`, and no brief file exists after a refusal unless an earlier call wrote it.

`sdd-gate next PLAN_FILE --skill-dir DIR [--standards PATH]... [--completed N [--parked K]] [--task M [--context-file PATH]] [--delivery-base SHA] [--repo-root R --run-id I --action-id A]` closes task `N`, opens task `M` or both, and renders the implementer's dispatch brief. At least one of `--completed` and `--task` is required and both may be given; `--parked` goes with `--completed` and `--context-file` with `--task`; `N`, `K` and `M` are positive integers, `SHA` is a full 40-hex commit id, and the identity flags are all three or none. There is no `--worker-id` (the command registers the worker itself) and no stdin flag. Any other shape is the same `sdd-gate: invalid invocation`.

`next` runs up to eleven steps in order and stops at the first that fails; a step that does not apply to the call does not run and is not listed in `completed_steps`: `ledger` (the ledger is this plan's, its recorded delivery base and `--delivery-base` agree and at least one exists, the completed task has a `dispatched` line, the task to dispatch has at most one; nothing is written until every read has passed, and then the delivery base is recorded if new), `ledger-complete` (with `--completed`), `mark-progress` (under an identity: `workflow-state mark-progress`, and a non-zero exit or an unreadable reply reports `"refused"` without stopping the call), `review-package`, `validate-report`, `budget-check` and `metrics-match` (the same package gate as `review`, over the cumulative range delivery base to `HEAD`), `task-brief` (the installed `task-brief` command copies the task's plan member into the workspace), `prepare-brief` (record the task's base if new, then render the brief once in memory), `register-worker` (under an identity: `workflow-state register-worker`) and `write-brief` (`task-<M>-implementer-dispatch.md`, atomically). A ledger that cannot be read or appended to is refused at the step that needs it (`ledger`, `ledger-complete`), except that the `Delivery gate:` line is refused at `metrics-match` with gate `failed` and that step is not listed as passed. A worker is registered only after the brief has rendered; a failed brief write releases the worker it registered with `release-worker --event stopped` before the refusal is printed, and when that release fails too the refusal's `detail` names the worker and the command to run first. Every `next --task` call under an identity registers a fresh worker, so before `register-worker` it reads the task's existing brief and refuses, at that step, while `workflow-state check-worker` reports the worker that brief names as live: the owner releases it and calls again (a brief with no worker line, or a worker that is not live, changes nothing).

The ledger gains only four line shapes, one write each and never the same line twice: `Delivery base: <sha40>`; `Task <N>: complete (commits <base7>..<head7>, review clean)` (or `, <K> parked)`); `Delivery gate: <base40>..<head40> root_bytes=<n> total_bytes=<n> file_count=<n> largest_member_bytes=<n>`; and `Task <M>: dispatched (base <sha40>)`. `review` and `next` read `dispatched` and `next` also reads `Delivery base`; `workflow-state resume-pack` reads `complete`. A repeated call writes nothing new.

Ready, exit 0, in this key order: `command` (`next`), `outcome` (`ready`), `completed`, `task`, `brief_path`, `report_path` (`task-<M>-report.md` in the workspace), `base_sha` (the task's base), `worker_id`, `mark_progress` (`skipped` without an identity, else the `workflow-state` outcome or `refused`), `delivery` (`base_sha`, `head_sha`, `manifest_root`, `metrics`) and `standards`; the members that do not apply to the call are `null` (`[]` for `standards` without `--task`). Refusals and exit codes are `review`'s.

## `orchestrate-control`

`orchestrate-control start --repo-root R [N ... | --label L | --milestone M] [--run-id I]` (#403) opens an orchestrate-issues session: it names the issue set, creates or re-enters the run and prints the session object the skill carries. `R` is absolute, and exactly one of the issue numbers (positive integers, no sign or leading zero), `--label` and `--milestone` is given; any other shape prints `orchestrate-control: invalid invocation` on stderr, nothing on stdout, and exits 2.

`start` runs four steps in order and stops at the first that refuses, naming it as `step`: `bindings` (resolve the project in process with `agent_tools.resolve_project.resolve` and read `bindings.workflow.orchestration`, `bindings.tracker` and `bindings.vcs.worktree`; a missing or mistyped member refuses naming its pointer and nothing is defaulted), `route` (`workflow-state host-route --route claude-code`), `issues` and `bootstrap` (`workflow-state init-run`). Every `workflow-state` reply passes `artifact-budget validate-report --boundary workflow-response` before any field of it is read, and every JSON the command reads rejects duplicate keys and non-finite constants. `issues` takes the explicit numbers in the caller's order (a repeated number refuses) or sweeps the open issues of a label or milestone with the bound tracker CLI (`issue list --repo <slug> --state open ... --json number --limit 1000`, GitHub only), ascending; an empty set, or a listing that reached the 1000-issue limit, refuses. `bootstrap` runs `init-run --issue-set` with the session's numbers joined by `-` in session order, which mints the run or answers the first reusable one; with `--run-id` it runs `init-run --run-id`, which re-enters an existing run and never creates one. A set whose key is too long for `init-run` refuses at `bootstrap`: mint that run with `workflow-state init-run --creation-key` and re-enter it with `start --run-id`.

Stdout is one compact JSON object and a newline. Ready, exit 0: `{"command":"start","outcome":"ready","session":{interface_version,run_id,issues,human_directed,source}}`, where `source` is `{kind:"explicit_user",reference:"invocation:/orchestrate-issues <numbers>"}` for explicit numbers (`human_directed` true) and `{kind:"standing_repository",reference:"sweep:label:<L>"}` or `sweep:milestone:<M>` for a sweep (`human_directed` false). A host that does not support the route, exit 0: `{"command":"start","outcome":"unsupported","route":<the validated host_route>}`, with no run created. Refused, exit 2: `{command,outcome:"refused",step,detail,completed_steps,response}`, where `detail` is one line of at most 300 characters (with the tail of a failed child's stderr where it has one) and `response` is `null`.

`orchestrate-control step --repo-root R --input -` gathers the facts for a session's issues and runs one `workflow-state control` round over them. `R` is absolute and `--input` is `-`; stdin is one strict JSON object, exactly `{session, first_sweep, owners, contracts_due, refused_contracts}`, and anything else (a member missing or added, a duplicate key, a `session` that is not the `session` member `start` printed, a number outside the session, a repeated number, an owner observation whose `issue` is not the session's) is an invalid invocation. `session` is the `session` member `start` printed, which the adapter carries unchanged. `first_sweep` is true on the first call of a run or a re-entry, `owners` the owner observations to hand `control` on this call, and `contracts_due` and `refused_contracts` are the members of the previous ready object of those names: the adapter passes them back, because the command holds no state between calls (one adapter process calls `step` serially per run, as the ledger is the only shared state).

`step` runs eight steps in order and stops at the first that refuses, naming it as `step`. `bindings` resolves the project again on every call, so a contract edited between calls is read. `bootstrap` runs `init-run --run-id` for the session's run and requires that run in the answer. `tracker` (GitHub only) asks the bound tracker CLI for each session issue's state and its blockers, one GraphQL call per 100 issues: an issue that is missing, not an issue, neither open nor closed, or has more blockers (or a blocker with more labels) than one page lists refuses, an open blocker outside the bound repository refuses, and an open blocker labelled `wayfinder:research`, `wayfinder:prototype`, `wayfinder:grilling` or `wayfinder:task` is a decision blocker, any other an open blocker. `forge` lists the repository's pull requests in one paginated, uncapped call and matches them to the session issues by head branch (`<prefix>issue-<N>-...`, same-repository only, the newest wins); a listing whose `--slurp` array holds no page (a repository with no pull request still answers one page, which is no refusal), that is incomplete, or that holds a merged pull request with no 40-hex merge commit refuses. `worktrees` reads `git worktree list` and the local branches: an issue with a recorded worktree reports its path and a state (`absent`, `matching_issue_branch` or `mismatch`; a registration git lists as `prunable`, whose checkout lost its `.git`, is not live and never matches), any other issue the first free candidate path `<root>/<prefix>issue-<N>-orchestrated[-2..-9]`, free meaning no such path, registered worktree (a `prunable` one included) or branch (with or without the prefix), no path recorded for any requirement of the run (the session's issues or not), and no path already taken as an earlier issue's candidate in this call; none free refuses. `contracts` builds, before the first call, a delivery pair for each issue that needs one (below). `control` makes one or two calls (below) and requires the reply to be this run's interface-3 control response. `project` checks that every action kind is in the closed set (`spawn`, `resume`, `retry`, `delivery_remainder`, `delivery_contract`, `wait`, `finalize`), then makes one dispatch entry per `spawn`, `resume`, `retry` and `delivery_remainder` action in returned order: `{action_id, launch_kind, issue, attempt, owner, worktree, handoff_path, owner_object, resume_pack}`, where `owner_object` is the owner object as `artifact-budget validate-report --boundary workflow-response` prints it (a `delivery_remainder` action verbatim; the others the action less `id` and `kind`, plus `action_id`, `launch_kind`, `kind: "owner"`, `interface_version: 2`, `ledger_repo_root` and `run_id`), and `resume_pack` is the `workflow-state resume-pack` text for a `resume` and null for the rest, or when that child fails. Any other failure in `project` refuses with the id of the action it could not project and no dispatches.

`contracts` builds a pair with `workflow-state build-delivery --repo-root R --kind contract --input -` (stdin `{issue, worktree, source_kind, source_reference}`, the worktree being the issue's recorded path, else its candidate) for each session issue, once per call and in session order, that is in `contracts_due`, or, when `first_sweep`, has a bootstrap requirement with a null `contract_digest`; an issue in `refused_contracts` is never built. A builder that exits 2 with no output has refused that issue: the line it printed is that issue's entry in `contract_refusals` (`{issue, detail}`, in build order), the issue joins `refused_contracts`, and the call goes on without a pair for it. Any other builder outcome (another exit, a non-JSON or other-shaped output, an exit 2 that printed output) refuses at `contracts`. The pairs go into the first `control` request as `delivery_contracts` and `authorization_intents`; every other per-issue member is empty.

`control` is called with `owners` as given. Each `control` request carries `human_directed` true only when the session's `human_directed` and `first_sweep` are both true, the chained second call of such a step included, and false otherwise, so an explicit session's direction is spent on its first sweep and a record that parks on a gated cause later in the session waits for the next invocation (issue 458 D4). When the reply's only action is `delivery_contract` it is a request for contracts and is chained, at most once: the listed issues not yet built or refused are built (a builder failure here refuses at `control`, not `contracts`), and when any listed issue has a pair `control` is called a second and last time with the same facts, `owners` empty (the observations ride the first call only) and the pair of each issue whose first-reply summary asks for a contract and has one. A reply with any dispatch or other action is never followed by a second call. A failure of the second call, including a reply that is not this run's control response, refuses at `control` carrying the first reply as `response`. The reply the second call returns is final.

Ready, exit 0: `{"command":"step","outcome":"ready","run_id","control_calls":1|2,"response","dispatches","contracts_due","refused_contracts","contract_refusals","ends_run"}`. `response` is the final control reply; `contracts_due` the issues its summaries still ask a contract for, less the refused ones, ascending; `refused_contracts` the previous list plus this call's refusals, ascending; and `ends_run` is true when the reply's only action is `delivery_contract` and every issue it lists is refused, since no build will ever answer it. A refusal is the same object `start` prints: `response` is the latest validated control reply once `control` has answered (so a refusal at `project`, or in the second call, carries one) and null before.

The command writes no file; its only writes are `workflow-state`'s own ledger writes under the ledger repository's `.superpowers/`. A dispatch that `control` reserved before a later refusal is not undone: it stays in the ledger until its own deadline expires. The `orchestrate-issues` skill drives every run through `start` and `step` (#404).

Every tracker-CLI child runs with this process's environment less each name in `bindings.tracker.credential_env.unset_before_invocation`. The command writes no file and holds no lock.

## `cache-proxy`

`cache-proxy --port N [--upstream URL] [--keepalive] [--reorder]` (#422) is a loopback pass-through from Claude Code to the Anthropic API: it binds `127.0.0.1` only and, without `--keepalive` or `--reorder`, forwards each request's method, path, query and body bytes and each response's status, headers and body unchanged (only `Host` is rewritten and hop-by-hop headers are dropped; nothing is added, decoded or retried), re-chunks an unsized (streamed) response one upstream read at a time, and holds one keep-alive upstream connection per client connection. `GET /_proxy/health` answers `{"service":"cache-proxy","status":"ok"}` without being forwarded or logged. An upstream that fails before responding gets the client a `502` Anthropic error envelope; one that fails mid-body gets the client connection closed without the terminating chunk. stderr carries one JSON line per request (`method`, `path`, `status`, `upstream_conn`, `ttfb_ms`, `duration_ms`, `bytes`, `outcome`, plus `error` and up to 4 KiB of an upstream error body), never a header value; an exception no request step expected (a client reset on an idle connection) is one `handler_error` line with `error`, never a traceback. `bytes` counts the body bytes written to the client, a reply the proxy makes itself (a `502` or a rejection envelope) included; a `HEAD` reply ends after its headers, so it logs 0. Known limitation: without `--keepalive` the client's `Accept-Encoding` is forwarded verbatim (with it, every request whose outcome is not `untracked` is sent with `Accept-Encoding: identity`, below) and bodies are never decoded, so an upstream 4xx/5xx body that arrives compressed (for example gzip) is logged as `error_body` decoded as UTF-8 with replacement characters, not as readable text; the client still receives it unchanged. The service that runs it and the `claude` wrapper that routes through it are in `home/common/claude-code/README.md`.

`--keepalive` (#423, `agent_tools.cache_keepalive`) keeps a subagent conversation's prompt cache warm while it is idle, by replaying its last request with `max_tokens=1` (the replay is the one fact 2 of `docs/spikes/cache-proxy-spike.md` measured to refresh the 5-minute cache entry). A conversation is a pair of the `X-Claude-Code-Session-Id` and `x-claude-code-agent-id` headers, and each `POST /v1/messages` the proxy is about to forward is sorted into one of seven outcomes. `untracked` (not a messages `POST`, or no session header), `main` (no agent header: the main conversation) and `unparsed` (the body is not a strict JSON object, or arrives with a `Content-Encoding`) are not candidates; `no_tail_mark` (the last message carries no `cache_control`), `ttl_1h` (some mark asks `ttl` `1h`) and `thinking_budget` (`thinking.type` is `enabled`) are subagent requests that are left alone as well; and `tracked` is a subagent request that can be replayed. A `tracked` request whose response starts 2xx becomes its conversation's candidate (a newer one replaces an older one; a candidate is held for at most 64 conversations, and the 65th evicts the one whose last client request is oldest); a later 2xx `unparsed`, `ttl_1h` or `thinking_budget` request clears it, and `main` and `no_tail_mark` requests leave it as it is. Every request with an outcome other than `untracked` is forwarded with `Accept-Encoding: identity`, and its response chunks are tapped, after they have been written to the client, by an incremental SSE reader that keeps the final `stop_reason`; the bytes the client gets are unchanged. A session counts as active for a candidate when one of its conversations has a request in flight (under 60 minutes old), is pending a tool (its last 2xx response completed with `stop_reason` `tool_use`, under 60 minutes ago, and it has sent nothing since), or has sent a request since the candidate's last touch; pings never count. A tick every 5 s finds each candidate untouched for 270 s (the touch is the upstream send time of its last 2xx `tracked` request or ping). It ends the conversation with `ceiling` when 60 minutes have passed since its last client request, with `session_idle` when the session is not active, and otherwise sends the ping. A ping travels on a fresh upstream connection (never a client's) with a 30 s socket timeout and is never retried; its response is read to the end, its usage logged, and the bytes discarded. The whole exchange is also bounded by that 30 s from the ping's send time, checked on the keepalive's clock between reads and enforced by a wall-clock watchdog that shuts the ping connection's socket, so a read still blocked ends too, the response's headers and chunk framing included: once it has passed, the read stops, no usage is parsed, the connection is closed and the `ping` line reads `upstream_error` with `error` `ping exceeded 30.0 s`, so a response that keeps trickling bytes cannot hold a ping, or its conversation's credentials, in flight. Only a 2xx ping whose body was read whole (outcome `complete`) becomes the new touch; any other result (a non-2xx status, an upstream error such as a timeout or a connection failure, a body cut short of its declared length, or the overall bound) ends the conversation with `ping_failed`, and a ping superseded by a newer client request while in flight changes nothing. The ping keeps the candidate's headers, `Accept-Encoding: identity` and a recomputed `Content-Length` included, and its body is the candidate's with `max_tokens` set to `1` and nothing else changed. The candidate's headers, `authorization` among them, are held in process memory only, from its 2xx response start until it is cleared, replaced or ended; they are never logged or written anywhere, and a proxy restart forgets every conversation. A client request that arrives after at least one ping ends that idle period with `resumed`; the other end reasons are `ceiling`, `session_idle`, `ping_failed` and `evicted`. With the flag, the `listening` line gains `"keepalive":true`, and each `request` line that reached the keepalive gains `keepalive` (the outcome), and, unless it is `untracked`, `conversation` (12 hex digits of the `telemetry_digest` of the session and agent, never a header value) and the `stop_reason` the tap saw. A request rejected while its body was read (`411`, `400`) and the health path carry none of these. Three events are new: `ping` (`conversation`, `model`, `idle_s`, `status`, `ttfb_ms`, `duration_ms`, `outcome`, `usage` and, on failure, `error` and up to 4 KiB of an error body), `keepalive_end` (`conversation`, `reason`, `pings` and `idle_s`) and `keepalive_error` (`stage` `observe`, `track`, `tick` or `send`, and `error`). A keepalive bug never blocks traffic: an exception from `observe`, a track call, `tick` or `send` is one `keepalive_error` line, the request carries `"keepalive":"untracked"`, and the scheduler keeps running. When `observe` raises, the request is forwarded exactly as it would be without the flag; when a later track call raises, the track is dropped and the request continues untracked, its headers already sent as the track gave them (`Accept-Encoding: identity`); a dropped track is still told its request is done (unless `done` itself raised), so its flight never keeps the session active. Without the flag no keepalive object exists, no thread runs, and every byte sent upstream and every log line is as described above.

`--reorder` (#429, `agent_tools.subagent_prefix`) reorders a Claude Code subagent's first user message so that two subagents of one type share a cached start-up prefix. A `POST` to `/v1/messages` (any query) with a non-empty `x-claude-code-agent-id` is parsed as strict JSON (a duplicate key or `NaN` is `unparsed`); every other request is `not_subagent` and is never parsed, and so is a body whose `system[0]` is not a text block starting `x-anthropic-billing-header:` with `cc_is_subagent=true` among its `;`-separated fields. A request with no assistant message is a first request, and its agent id is registered when it is reordered (in memory, at most 4,096 ids, oldest out first, forgotten on restart); a later request is reordered only when its id is registered, so a forked subagent, which carries its parent's first message, passes as `unregistered`. The reorder needs `messages[0]` to be a user message of text blocks: attachments (text starting `<system-reminder>`), budget lines (whole text `<total_tokens>N tokens left</total_tokens>`, `N` digits or `Infinite`) and exactly one other block, the prompt, which is not first. Only its last block may carry a `cache_control`, and the body's marks (on `tools`, `system`, each message block after its inner content, then a top-level one) number at most four, are objects with a `ttl` of `5m` (the default) or `1h`, and never grow longer in prefix order; anything else is `shape`. The output keeps every block before the prompt and every attachment after it in order, then the prompt, then the budget lines that followed it, and a mark on the original last block moves to the new last block. With fewer than four marks, the block just before the prompt gains `{"type":"ephemeral"}` with the `ttl` of the nearest mark after it, else of the nearest before it, else none (`applied`); with four, nothing is added (`applied_at_cap`). No existing mark is retimed or removed, and the billing header is never changed. A reordered body is re-encoded as compact UTF-8 JSON in its key order, with every `Content-Length` value replaced; every other outcome forwards the client's bytes and headers. The transform runs after the upstream headers are assembled and before the keepalive's observation, so a keepalive candidate and its pings carry the reordered body. With the flag, the `listening` line gains `"reorder":true` and each `request` line that reached the transform gains `reorder`: `applied`, `applied_at_cap`, `not_subagent`, `unregistered`, `unparsed`, `shape` or `error`. A request rejected while its body was read (`411`, `400`) and the health path carry none. An exception from the transform, or an outcome outside that set, forwards the original bytes and headers and is logged at once as a `reorder_error` line with `method`, `path` and `error`. Without the flag no transform object exists, and every byte sent upstream and every log line is as described above.

## adopt-project

`adopt-project plan` asks four kinds of open question: `project-id`, answered by declaring exactly one remote or authoring a contract with the project id, and `candidate-class` (#340), one per tracked or targeted-ignored agent path that no classification row settles (none covers it, or a targeted-ignored one it covers resolves outside the repository or cannot be read), keyed by its `subject` (the path) and carrying the one `value` the question accepts: `archive-history` for a tracked path, which plans a `git mv` to `.agents/knowledge/archive/adopted/<path>`, `retain-product` for an ignored one, and `null`, no answer, for a secret-shaped tracked path, which stays open until a central classification row covers it or it leaves the repository, or for a tracked symlink resolving outside the repository, which stays open until it leaves the repository; `plan --answer QUESTION SUBJECT VALUE` (repeatable, order-independent) settles a `candidate-class` question, refusing the first violation as `adopt.decisions.invalid_answer` (an id other than `candidate-class`, `path-reference`, `reference-policy` or `reference-format`, a subject answered twice, or a value other than the offered one) or `adopt.decisions.unmatched_answer` (a subject that is not an undecided candidate, a path occurrence or a reference policy of this inspection, by the answered id), checking each `candidate-class`, `path-reference` and `reference-policy` answer in `(id, subject, value)` order, then the `reference-format` answers in `(subject, value)` order, and changing nothing on a refusal; the answers enter `decisions.answered` and therefore `plan_id`, and `apply --plan-id` re-applies them from the stored plan (refusing a malformed `decisions.answered` as `adopt.plan.malformed`), so the plan id, not an `apply` flag, authenticates them. The third and fourth kinds, `path-reference` and `reference-policy`, are described below; `--answer` settles them through the same flag, pass and refusals. A fourth answerable id, `reference-format`, opens no question and so is not one of the kinds above: its subject is a file class, its value a command id of the contract, and it is checked after every other answer, so its subject must be the class of a file the other answers edit (`adopt.decisions.unmatched_answer` otherwise) and its value must be a command the contract declares (`adopt.decisions.invalid_answer` otherwise, as for a subject answered twice); the plan document publishes the answer as the `command` of its class's row in `reference_formatting`, which enters `plan_id` as its tenth input.

`adopt-project plan` rewrites relative Markdown link targets across its moves (#345): outbound in every Markdown file a `git-mv` moves, inbound in every other tracked Markdown file (a regular `.md`/`.markdown` blob at the base revision, strict UTF-8, not secret-shaped; a `generated_file` projection target is left to its regeneration). `agent_tools.adopt_links` owns the grammar — inline links and images on one line and reference definitions, outside fenced code, code spans and link titles — and resolves a target against the tracked paths of a tree, never the filesystem: a target is relative unless it is empty, starts with `#` or `/`, carries a URL scheme or holds a backslash, and it resolves when its percent-decoded path, joined to the containing directory, names a tracked file or a directory inside the root. The rewritten bytes come from the plan's base revision, each changed file is a `write-file` at the path the file has after the moves and placed before the projection regenerations, and a rewritten target keeps its anchor or query, title, angle brackets and trailing slash, and its leading `./` unless the new path climbs out with `../`; a bare target is percent-encoded and an angle target encodes only `%`, `#`, `?`, `<`, `>` and line breaks, and gains a leading `./` when its path would otherwise open with a URL scheme (`urn:x.md`), so the emitted path names the same file and stays relative; a link that already fails to resolve, a URL and a link the moves leave correct stay byte-identical. The plan document and the adoption evidence record carry `link_rewrites` (`inbound` and `outbound` link counts and sorted files, `unrewritable` `path`/`target` entries and an `already_broken` count), which is the seventh input of `plan_id`. The ready gate `no-unrewritable-link` (`adopt.link.unrewritable`) keeps the plan `draft` when a link targets a file the plan deletes or a directory that no longer exists after the moves and whose files did not all move, by the same relative tails, under one new directory, and `apply`'s commit gate `no-new-broken-link` (`adopt.gate.no-new-broken-link`), before `cold-clone-resolves`, fails when any Markdown file in the index has more non-resolving relative links, each side counted against its own tree, than its pre-move counterpart at `HEAD` (a file with no counterpart is compared with zero); because the verification commands and a `pre-commit` hook run after it, the same count over the commit against its parent is proved again once the commit exists, and a failure there refuses `adopt.commit.new_broken_link` with the worktree and branch retained. Prose mentions of moved paths, inline HTML and root-relative targets are never rewritten, and a path literal in a non-Markdown file is left to the `path-reference` question.

`adopt-project plan` asks about every path literal in a tracked non-Markdown text file that names something its moves relocate (https://github.com/fagenorn/nix-config/issues/350), and edits nothing without an answer. `agent_tools.adopt_references` scans the base revision's regular, non-Markdown, non-secret blobs that git judges text and that decode as strict UTF-8, found by one `git grep` for the first path segment of each move source (the depth reading described below has a read set of its own), leaving out `.agents/artifacts/`, `.agents/knowledge/archive/` (each tested on the base path, so a file under them is editable only by the adoption that moves it) and the files adoption itself may write (the contract, `.gitignore`, the runtime sentinel, a legacy binding config and a `generated_file` projection target). A token is a run of characters bounded by whitespace or one of `"`, `'`, `` ` ``, `,`, `;`, `:`, `=`, `(`, `)`, `<`, `>`, `|`, `&`, `#`, `!`, read as an optional leading `./` or `/`, a path up to its first glob segment and a tail; it is an occurrence when it contains `/` or is the whole content of a quoted string, and a reading of it (the plain one here, the pattern and variable ones below) gives a path that names a file or directory of the base tree, where a move source is that path or lies under it, so `.claude/` counts when `.claude/specs` moves. A moved file, or a directory whose members all moved by the same relative tails under one new directory, has a single successor; a path that survives or dissolves maps to the successors of its wholly moved subtrees, carried only for an empty, `/` or `/**` tail. An occurrence that no answer decides (its own, or its policy's, below) opens a `path-reference` question unless its policy's question is open; the question is keyed by its `subject`, `<path>:<line>:<column>`, with an `answers` list and no recommended value: `extend`, offered when the token is a quoted element of a bracketed, braced or parenthesised sequence (it follows `[`, `{`, `,`, a `(` that does not open a call, or the start of its line, and ends the line or precedes `,`, `]`, `)` or `}`) or the only content of its line after indentation and an optional `- `, adds one quoted element or one copied line per successor beside the literal; `rewrite`, offered for a single successor, replaces the token; `retain`, always offered, leaves the file as it is. `plan --answer path-reference SUBJECT VALUE` settles one, after any `candidate-class` answers, whose moves the references are derived from; an unknown subject refuses `adopt.decisions.unmatched_answer` and a repeated subject or a value the occurrence does not offer refuses `adopt.decisions.invalid_answer`. An open reference keeps the plan `draft` through `no-open-decisions`; no gate and no `verify` check is added. Each file with an `extend` or `rewrite` answer is one `write-file` after the Markdown link rewrites and before the projection regenerations, in the same commit as the moves, unless another file is left at its `target` (below). The plan document and the adoption evidence record carry `path_references`, one row per occurrence sorted by path, line and column (`subject`, `path`, `line`, `column`, `literal`, `answers`, `answer`, `additions`, `replacement`, `target`, `policy`, `decided_by`; `answer` is the effective answer), which enters `plan_id` as its eighth input, and the record's `decisions_accepted` lists the answers. A variable is never followed to its definition (the one exception is the depth reading's Python names, below), a regular-expression spelling is read only as the pattern reading below describes, a path joined to a variable is read only as the variable reading below describes, and outside the variable reading a joined path is not resolved as a whole (a quoted segment that alone names a path of the tree is still an occurrence), URLs and bare unquoted single words are not recognised, and an unquoted element of a YAML flow sequence that shares its line with other flow-sequence text (a bracket, a comma or another element) is never offered `extend` (one that touches its bracket is no occurrence at all); one alone on its line counts as the only content of its line.

A file the plan moves is read like any other, at its base path, and edited at its destination (https://github.com/fagenorn/nix-config/issues/372). An occurrence's `path` and `subject` stay the base path; its row's `target` is the file's destination, or its own path when the plan does not move it. An edited moved file is one `write-file` at its `target`, after its `git-mv` and in the same commit, with `before` the hash of the base bytes. A path that more than one file of the base tree is left at (two moves onto it, or one move onto a tracked file that stays) gets no such write, whatever the answers: the rows keep their answers, and two moves onto one path keep the plan `draft` through `no-existing-destination`. `apply` treats such a write like any other: it recomputes the plan from the stored answers, applies the operations the plan lists, and then runs the formatting step below over the edited files.

Every occurrence in a moved file belongs to one policy, whose subject is `<tree>:<class>`. The tree is the path of the classification row that moved the file, or the candidate's own path for an `archive-history` answer; the class is the lower-cased text from the last dot of the file name, or `-` for a name with no such suffix (a dotfile included). A file the plan does not move has no policy. The `reference-policy` question has seven members: `id`, `subject`, `answers` (`rewrite` and `retain`, never `extend`), `value`, `basis`, `impact` and `recommendation`. `value` comes from a closed table: `rewrite` for the classes `.py`, `.sh`, `.bash`, `.zsh`, `.nix`, `.yaml`, `.yml`, `.toml`, `.js`, `.mjs`, `.cjs` and `.ts`; `retain` for `.json`, `.jsonl`, `.ndjson`, `.csv`, `.tsv`, `.txt` and `.log`; null for every other class. The recommendation is printed and never applied: nothing is edited without an answer. The class of an occurrence the variable reading made is `<file class>/variable`, so its policy is `<tree>:<class>/variable`: its `reference-policy` question's `value` is null, being outside the table, and a `<tree>:<class>` answer never decides it, so `.claude/notes:.sh` and `.claude/notes:.sh/variable` are two questions and answering one leaves the other open. In a file the plan does not move, a variable-joined occurrence has no policy and opens an ordinary `path-reference` question. Its `path_references` row has the same members as any other, and its `literal` shows the variable. The class of a depth occurrence (https://github.com/fagenorn/nix-config/issues/380, below) is `<file class>/depth`, so its policy is `<tree>:<class>/depth`: its `reference-policy` question's `value` is null, and neither a `<tree>:<class>` nor a `<tree>:<class>/variable` answer ever decides it. A lock file is its own class (`uv.lock` is `.lock`, so `.lock/depth`), and a manifest's policy is never paired with its lock file's.

An occurrence is decided by its own `path-reference` answer; else by its policy's answer when the occurrence offers that value; else by none, so a `rewrite` policy leaves an occurrence that offers no `rewrite` open, and `extend` is never a policy answer. A policy opens its question while it is unanswered and at least one of its occurrences has no answer of its own; during that time its occurrences open no question of their own, though they stay listed in `path_references` and can still be answered one by one. Once the policy is answered, each occurrence still without an effective answer opens a `path-reference` question. The open questions are ordered by id as in `QUESTION_IDS`, the `reference-policy` ones by subject. `plan --answer reference-policy SUBJECT VALUE` is checked after the other two ids: a subject that is the policy of no occurrence of this inspection refuses `adopt.decisions.unmatched_answer`, and a value outside `rewrite` and `retain` or a subject answered twice refuses `adopt.decisions.invalid_answer`. The `reference-format` answers are checked after it (below).

Each `path_references` row carries `target`, `policy` (null for a file the plan does not move) and `decided_by` (`occurrence`, `policy` or null), and the plan document and the adoption evidence record carry `reference_policies`, one row per policy that has an occurrence, sorted by subject, which enters `plan_id` as its ninth input. A row has thirteen members: `subject`, `tree`, `class`, `recommended`, `answer` (the policy's answer or null), `files` (distinct base paths), `occurrences`, `rewritable` (occurrences that offer `rewrite`), `rewritten`, `retained` and `extended` (occurrences decided with that answer, whoever decided it), `open` (occurrences no answer decides) and `overridden` (occurrences their own answer decides). The human view adds one `policy <subject>: ...` line per row after the `references:` line and an `open reference-policy <subject> (answers: ..., recommended: ...): ...` line per open policy. A plan stored before this contract no longer equals its re-derivation, so `apply` refuses it and the operator plans again.

A token that the plain reading does not make an occurrence is read a second time as a regular-expression spelling, only when it starts with `^` or holds `\.` (also `\\.`, as a TOML or JSON string spells it). The reading takes the anchor `^`, one escape for the whole token, an optional `/` prefix, the path decoded segment by segment (the escape replaced by `.`) up to its first empty, glob or backslash-bearing segment, and the rest verbatim as the tail. The forms offered keep the anchor, the escape and the tail, and a carried form exists only for a successor made of letters, digits, `_`, `-`, `.` and `/`. Not read: an end anchor, character classes, groups, alternation and a `./` prefix inside a pattern. The plain reading decides alone whenever it yields an occurrence. The `git grep` prefilter keeps one limit: a file is scanned only when it holds the first path segment of a move source as written, so an escaped first segment with an interior dot (`foo\.bar` for `foo.bar`) is not found.

In a file of a shell class, `.sh`, `.bash` or `.zsh` (the class of the file's base path), a token that neither the plain nor the pattern reading makes an occurrence is read a third time, as a variable-joined path (https://github.com/fagenorn/nix-config/issues/376). The reading takes a prefix `$name/` or `${name}/` at the start of the token, `name` being a letter or `_` and then letters, digits and `_`; the path is the longest leading run of non-empty segments after it that hold neither a glob character nor a `$`, and the rest is the tail. The carried form is the prefix, the successor and the tail, and it must be one token that reads back to the successor; such an occurrence offers `rewrite` (for a single successor with a carried form) and `retain`, never `extend`. Not read: positional and special parameters, parameter expansions, a variable that is not at the start of the token and a second variable before the path. A `$(...)/path` is already a plain root-anchored occurrence, because `(`, `)` and the backtick delimit tokens.

A file the plan moves is read a fourth time, for the relative climbs that leave its moved tree (https://github.com/fagenorn/nix-config/issues/380). The depth reading has its own read set: the moved files that a second `git grep` for `..` and `__file__`, limited to the trees of the moves (each named both as a `:(literal)` pathspec and plainly, so a `GIT_LITERAL_PATHSPECS`, `GIT_GLOB_PATHSPECS`, `GIT_NOGLOB_PATHSPECS` or `GIT_ICASE_PATHSPECS` environment finds the same files), returns, under the filters of the prefilter's files (regular, non-Markdown, non-secret, not excluded, not under a record home, strict UTF-8). A blob both searches return is read once, a file the plan does not move is never read for climbs, and the plain, pattern and variable readings stay limited to the files of the first search. The tree root is the group directory the file moves with, or, for a file the plan archives, the file's own directory; a climb's landing point is the directory it ends at from the file's directory, or the repository root when it climbs past it. A text climb is a token with at least one `/` made of an optional `./`, one or more `..` segments and a rest that is empty or starts with `/`, taken from the file's own directory; a bare `..` and a rest that holds a `..` segment are not read. In a `.py` file the reading also takes Python parent-count chains as climbs with no target text. An anchor is `Path(__file__)` or `pathlib.Path(__file__)`, with at most one `.resolve()` or `.absolute()`, which stands for the file; or a name bound at column 0 by `NAME = <that>` (which stands for the file) or `NAME = <that>.parent` (which stands for its directory), with an optional `: Path` or `: pathlib.Path` annotation and a trailing comment, and bound nowhere else in the file, at any indentation, by assignment, `for`, `as`, `del`, `global`, `nonlocal`, a keyword argument, a mention in a `def` or `lambda` header (a parameter) or a mention in a target list: followed on its line by `,`, `)` or `]` and then by an assignment's `=` that no bracket opened on that line encloses (`NAME, b = …`, `(a, NAME) = …`, `*NAME, b = …`), inside a bracketed run holding no bracket and no `=`, over lines too, directly followed by an assignment's `=`, between a `for` and its `in` (a comprehension's too), or inside a bracketed run after `as`. Headers and target lists are read loosely, so any mention there counts and the name is not followed. A chain is zero or more `.parent` then at most one `.parents[N]`, with `N` a decimal literal, at least one of them and no whitespace, and it climbs one level per `.parent` and `N + 1` for the index, from the file's directory (a chain on the file itself has one level less). Not read: `os.path` calls, `Path.cwd()`, a name chained from another name, a binding inside a function or class, a name bound more than once, a chain continued by `.parent` after its end, a chain with whitespace or a non-literal index, and a chain that overlaps an occurrence another reading made in the file or a text climb the depth reading itself accepted there. A climb is an occurrence when its landing point is a proper ancestor of the tree root, or above the repository root, and the same climb from the destination's directory ends elsewhere. A text climb whose base target (its rest joined to the landing point) is back inside the tree root, which moves with the file, is an occurrence only when its unchanged spelling, taken from the destination's directory, misses the target's successor (the directory the tree root is left at, joined to the target's path below the root), as for `../../research/data.txt` in `.claude/research/tool/config.toml` when `.claude/research` is filed under `.agents/artifacts/specs`; such an occurrence offers `retain` alone. It offers `rewrite`, which shifts the climb's height by the difference between the depths of the destination's and the base directories (the `.parents[N]` index, or the number of `.parent`s, for a chain), only when the landing point is above the repository root or an ancestor of the destination's directory, the base target names no moved path and is not back inside the tree root, and the shifted form is valid (at least one level, and a non-negative index); `retain` is always offered and `extend` never. Climbs in Markdown, which the link rewrites own, and in files the plan does not move are not read.

A tracked `.claude/settings.json` is classified `legacy-native-store` and `retain-product`, so classification opens no `candidate-class` question for it and plans no relocation of it; it appears in the plan's `evidence` and in the record's `sources` with `after` null. The path literals inside it are ordinary occurrences: each may open a `path-reference` question, and an `extend` or `rewrite` answer produces one in-place `write-file` of the settings file.

`plan --answer reference-format <class> <command-id>` declares a formatter for a file class (https://github.com/fagenorn/nix-config/issues/376) and opens no question. The answers are validated after all the others, in `(subject, value)` order: a repeated subject, or a value that is no `bindings.commands` key of the authored contract (always, when there is no contract), refuses `adopt.decisions.invalid_answer`, and a class that no settled answer edits refuses `adopt.decisions.unmatched_answer`. The plan document and the adoption evidence record carry `reference_formatting`, one `{class, command, files}` row, sorted by class, for each class with a file the `path-reference` answers edit, `files` being the edited files' destination paths and `command` the class's answer or null; Markdown link rewrites, the contract, the records and the projections never appear in it. The rows are the tenth input of `plan_id`, so a plan stored before this change no longer equals its re-derivation and `apply` refuses it as stale. The human view prints one `format <class>: <n> files, command <id or none>` line per row. `apply` runs the step once, after every operation has executed and matched its `after` and before the commit gates, so the gates judge the formatted tree: it takes its own `resolve` of the worktree, and for each row with a command runs that command's `argv` followed by the row's files as absolute worktree paths, in row order, at the entry's `cwd`, output captured and no timeout, as a verification command is run, then stages the row's files. A plan with no `reference-format` answer formats nothing and makes no extra `resolve`. The step then proves the formatter stayed on the files it was given: for every other path some operation targets, the last operation naming it still produces its published `after` (a moved file that a later write edits is judged by the write), and for a path whose `after` is a `git-object:` hash, as a move-only destination's is, the bytes on disk must also hash to it as `git add` would store them (a symlink as its link text), so an unstaged edit is caught; every formatted file must remain a regular file and not a symlink. Before any command runs, a file of a row with a command that is the source of a `regenerate-projection` operation for a `generated_file` projection refuses `adopt.format.failed`, naming the file, the two paths compared after `posixpath.normpath` so a source spelled with `./` or a repeated `/` is still matched: the projection was regenerated from the unformatted bytes, and regenerating it again would change a planned `after`. A `managed_import` projection's source may be formatted, since its managed line names only the source's path. A failure refuses `verification_failed` with `adopt.format.failed` (a formatted projection source, the worktree resolves to no command set, the id is no command of it, the command cannot start, exits non-zero, or a file cannot be staged; a command that cannot start is named in the message with its launch error, and one that exits non-zero with its exit status and the last 2000 characters of its stderr) or `adopt.format.unplanned_content` (a confinement check), pointer `/reference_formatting`, with the worktree and branch retained and every commit gate recorded `not_run`. A formatter that changes some other tracked file or leaves an untracked one is refused by the `worktree-status-matches-operations` gate, which this step does not duplicate. A formatted file's `write-file` keeps the hash of the planned, unformatted bytes as its published `after`, and `verify` is unchanged. The command must take file paths as trailing arguments, rewrite them in place, format whole files, and leave no untracked, unignored file.

`adopt-project verify --register` reads one pinned commit of the remote and nothing from the checkout (https://github.com/fagenorn/nix-config/issues/363). It lists `origin` once, fetches its default branch into `refs/remotes/origin/<branch>`, pins and exports that commit and resolves the contract there; a resolving contract that names another branch `origin` lists is the one hop, fetched, pinned, exported and confirmed the same way, and every check then reads the one pinned commit, the fetched objects and those remote-tracking refs being the only repository writes. The default branch's contract stays the authority when it resolves: `--integration-branch NAME` equal to the branch it names (or to the default branch when it names none) changes nothing, and any other operand refuses. The operand takes effect only when that contract does not resolve (it is accepted only with `--register` and at most once, refusing `adopt.verify.integration_branch_without_register` and `adopt.verify.integration_branch_repeated` as `adopt_failure`): the named branch must be listed by `origin`, must not be the default branch, and its own contract must resolve and name it, with no further hop. A run that selects its branch this way carries a `branch_override` object (`branch`, `default_branch` and `reason`, whose one value is `default_contract_unresolved`) in the report and in its registry entry, and in no other run; a later registration of the project that did not need the operand drops it from the entry, another project's registration leaves it, and a repeated operand registration writes the same bytes. The report `schema_version` stays 2 and the registry `schema_version` 1, and no reader decides anything from the member. Every operand that the remote or the branch's contract does not confirm refuses `not_integrated` with `adopt.registration.integration_branch_unresolved`; a pinned commit with no adoption evidence record refuses `not_integrated` with `adopt.registration.not_integrated`, and when the default contract did not resolve and no operand was given its message names `--integration-branch`.

## Transaction core

`agent_tools.transaction_core` is the transaction core's library surface, with no command-table row, and whose first caller is `workflow-state`, which mints one created-only *run transaction* per attempt run in `<ledger root>/.superpowers/attempt-transactions/` through `agent_tools.attempt_identity` (pure rules) and `agent_tools.attempt_store` (store root, mint lock, binding and `migrate`'s rows) and finds it by the read-only `TransactionStore.lookup` (#337): slice 1 (#204) holds caller-rooted transaction state under a closed schema and lifecycle, slice 2 (#205) adds fenced custody — a lease authority over concurrency keys in `agent_tools.transaction_custody`, epoch-fenced writes, and evidence and grant admissibility derived from the fence — and slice 3 (#206) adds the administrative protocol — a durable write intent before every external call, inspection before any retry, and an automatic-retry budget — in `agent_tools.transaction_invocation`; slice 4 (#207) then adds an immutable proof plan compiled at creation (`agent_tools.transaction_plan`), core-collected obligations, and one convergence cohort (at most three attempts) that `settle_proof` alone seals into `succeeded` or parks as `proof_rejected` or `proof_did_not_converge`, never rolling back (`agent_tools.transaction_proof`); slice 5 (#208) adds an immutable recovery plan compiled at creation beside the proof plan (`agent_tools.transaction_recovery_plan`), rollback anchors verified in `ready` before publication, `abandoned` only while no action has had an effect, and `begin_recovery`, `settle_recovery` and `roll_forward` as the only ways into `recovering`, into `rolled_back` and to a linked child transaction (`agent_tools.transaction_recovery`); slice 6 (#209) writes a permanent, content-addressed terminal receipt under the store root's `receipts/` and reads it back before the one `state.json` write that enters any terminal, which ends with a `receipt_sealed` event naming it, then re-reads that receipt on every load (`agent_tools.transaction_receipt`), and makes `dispose_failed` the only way into `failed`: it takes a fresh grant and one closed ground, and it yields an `effects_unobservable` qualifier with per-key hazard markers only when a human grant at the transaction's authority class asserts an observability ground (`agent_tools.transaction_disposition`), with the `transaction-state/v6` validator and snapshot fold in `agent_tools.transaction_history`, over the durable-file primitives in `agent_tools.transaction_storage`.

From schema 9 `workflow-state` also holds attempt custody in the core ([design spec](../.agents/artifacts/specs/2026-10-10-issue-338-fenced-custody-receipts-design.md)). Each implementation attempt has one custody transaction, created under the creation key `attempt-custody/v1:<run>:<issue>:<attempt>` with the closed subject schema `attempt-custody/v1` (run, issue, attempt, worktree, prior, `bound_launch`), the authority class `attempt-custody` and the single concurrency key `attempt-worktree:<path>`, so one live worktree has one holder across runs. A launch is a custody span whose executor is the launch's action id (`<issue>:<attempt>:<launch>`), so the key's epoch is the launch generation; the lease's validity is the attempt's budget window (`deadline_at`), and `renew(custody, ttl_ms=…)` is the one in-place renewal, used when `declare-lane` re-bases that deadline (a transaction parked longer than the core's parked-custody window quiesces under `renew` instead of renewing). `agent_tools.attempt_custody` holds the pure rules, the closed subject and the settle planner, which turns one ledger attempt, its custody transaction and its lease record into ordered core operations; `agent_tools.attempt_store` applies the plan to `TransactionStore` under the store lock. The settle step runs inside `commit_state`: the core is brought to the ledger's state first, the ledger is published, and the seal of each issue's latest attempt is applied last, so a core refusal leaves the ledger untouched and an interrupted seal is completed by a later write, after a reap when its span has lapsed by then. The subject's worktree is fixed at creation, and a live attempt that the ledger records at another worktree is refused as a `custody projection mismatch`. A verdict that records no merge (`stopped` or `failed`, from the owner, a refusal or a supersession) seals the transaction `abandoned` with a receipt that lists its stops and owner results; a synthesized stop (`stalled`, `expiry`) parks it and never seals. A `merged` attempt, or a failed one over a recorded merge, seals `succeeded` once its issue's delivery transaction has (next paragraph); one whose issue has no installed contract has no delivery proof and stays unsealed, and so does one whose delivery never completes. The helper-facing contract (schema 9, fencing, late results) is in `home/common/agent-skills/README.md` § Attempt custody and fencing.

From schema 10 the control plane decides from the store ([design spec](../.agents/artifacts/specs/2026-10-11-issue-339-control-plane-cutover-design.md)). Each installed delivery contract has one *delivery transaction*, created under the key `attempt-delivery/v1:<issue>:<contract digest>:<n>` with the closed subject `attempt-delivery/v1` (run, issue, contract digest, contract), the authority class `attempt-delivery`, the single concurrency key `attempt-delivery:<run>:<issue>`, a proof plan with one required `event` obligation per postcondition the contract marks `required`, and a journal: every delivery object of the ledger as an `event` evidence entry `<kind>:<id>` holding its canonical text, appended under a short span of the executor `delivery:<issue>`. A delivery remainder has *remainder custody*, a custody transaction under `attempt-custody/v1:<run>:<issue>:r<n>` with the closed subject `remainder-custody/v1` and the same worktree key as its source attempt, planned by the attempt rows. A held owner claim is the *claim entry* on the launch's open span, `admission-claim:<action id>:<epoch>`, so the span closing releases it and control counts a launch's slots from its open claimed span, falling back to the ledger's `admission` block for the controller's own slots, for a live launch without such a span and, for the `host_capacity` gate, for a launch the store has no view of. A write that adds a release other than a refusal moves every custody transaction parked for `suspended:host_capacity` back to `created` with the `capacity_released` transition, which is how the next sweep sees the gate open; an `owner_unavailable` release closes the launch's span in its own write. When the delivery is complete the delivery transaction seals `succeeded` (its receipt's evaluations are the required postconditions with their observations), and each unsealed custody transaction of that issue then seals `succeeded` under a span of the executor `<issue>:<attempt or r<n>>:seal`, after one `delivery-receipt` evidence entry citing the delivery receipt's digest. A delivery object, owner result or reconciled merge that reaches a sealed transaction is recorded as a *supplement* with `record_post_terminal` and never changes the receipt. `agent_tools.attempt_identity`, `agent_tools.attempt_custody` and `agent_tools.attempt_delivery` are pure and import no skill script (the delivery model's canonical-text function is passed in); `agent_tools.attempt_store` and `agent_tools.attempt_delivery_store` apply their plans to `TransactionStore`, and no `transaction_*` module changed for it.

The [#117 attempt-lifecycle decision](../.agents/artifacts/specs/2026-09-20-issue-117-attempt-lifecycle-first-consumer-design.md) selects attempts as the transaction core's first consumer and ship-release second.

The decision governs the planned single-store migration, immutable subject/identity, fenced custody and terminal evidence, and maps the already-delivered agent-slot admission (#150) and delivery contracts, remainders and authorization continuity (#151/#171) onto that core.

The decision is an architecture decision, and its runtime is the code described above: #123 delivered the core, and #125 moves the attempt lifecycle onto it in three packages, run identity (#337), attempt custody and receipts (#338) and the control-plane cutover (#339). `workflow-state` still writes each run's ledger, whose attempt fields are the projection of the custody transactions, and `home/common/agent-skills/README.md` holds the helper-facing contract of that lifecycle.

## Release profiles

The authored `release` member of `.agents/project.json` is required and has two forms (#124 D1): `"unsupported"`, or `{"profiles": {<profile-id>: <profile>}}` with exactly that member and a non-empty map. A profile's `publication` is `"none"` or `{"actions": [...]}` with at least one action, and a profile with `"publication": "none"` is a publication-free profile (#368 D1, D2): it declares its target, requirements and bindings like any other and passes the same same-repository rule. The grammar holds it to three further rules: its `activation` must be `"none"` (anything else is one `contract.release.invalid` violation, and the activation is then judged no further), its `proof.obligations` must be `[]` (a non-empty list is one `contract.release.invalid` violation and each obligation is still judged), and it can name no recovery unit, because the existing rule that a recovery key names no action or unit reports each entry as `contract.release.reference_unknown` (#368 D11). Two tiers judge a profile. The grammar (`release_profile.grammar_violations`) runs inside `resolve-project resolve`: every violation is `invalid_contract` with a `contract.release.*` repair, and a profile that names an adapter outside the closed registry (`release_adapter.REGISTRY`) or an operation the adapter does not support is a grammar violation, never a lookup fallback (D7). While any profile exists, the grammar's `contract.release.deploy_conflict` refuses a `capabilities.deploy` other than `unsupported` at `/capabilities/deploy/support` (#124 D1), unless `bindings.deploy.adapter` is a registered adapter and no profile authors `activation` as an object: a deploy watch through a registered adapter then coexists with profiles while one activation authority remains (issue 465 D4). `resolve-project` holds such a binding, whatever its support, to `command: null` (`contract.deploy.command_conflict`), a descriptor with exactly one inspectable activation-mode operation (`contract.deploy.adapter_unwatchable`), a `config` that passes that operation's closed schema (`contract.deploy.config_invalid`, one violation per problem) and a GitHub tracker (`contract.deploy.tracker_not_github`); a supported one needs no `command`, and it is `available` when every executable the descriptor declares resolves on `PATH`, else `blocked` with `release_adapter_unavailable` (issue 465 D3). An unregistered adapter such as `railway` keeps a free-form `config` and a required `command`. Admissibility (`release_profile.admissibility_findings`, D3) runs over a grammar-valid profile only: it reports every finding of its four rules (`observation_deadline`, `rolled_back_reachable`, `restore_anchor`, `core_plans`) as `{rule, pointer, reason, detail}`, and the same function feeds `capabilities.release`, which is `unsupported` for `"unsupported"`, `blocked` with `release_profile_inadmissible` for the first inadmissible profile, `blocked` with `release_adapter_unavailable` when a bound adapter's declared executable is not on `PATH`, and `available` otherwise (D23); it is also `unsupported` when no profile declares a publication, before any admissibility or executable check, and otherwise that logic runs over all profiles, publication-free ones included (#368 D4). `compile_profile` returns a deep-frozen `ResolvedReleaseProfile` or raises `ProfileInadmissible`, and its `digest` covers the authored profile and the bound adapters' identities only (D5, D23). A publication-free profile compiles to empty graphs, read through `release_profile.phase_nodes`, the one post-grammar reader of a phase's authored nodes. `bind_candidate(compiled, candidate)` takes only a `ResolvedReleaseProfile` and returns the exact inputs of `TransactionStore.create` (`proof`, `recovery`, `concurrency_keys`, `subject`), so the core recompiles what the profile lowered (D5, D20). It refuses a compiled profile with no publication node with `ValueError` naming the profile, before it reads the candidate, so a publication-free profile never reaches `TransactionStore.create` (#368 D3), and `release_adapter.core_binding` over such a profile has no compiled node, so it refuses every request for it (#368 D8).

The resolved snapshot has a fifth member, `release`, derived rather than authored (#368 D5): `{"targets": [...]}`, where `release.targets` is built by `release_profile.release_targets` from the authored `release` member alone, so a profile that fails admissibility is listed all the same. It is `{"targets": []}` for `"unsupported"`. Otherwise it holds one entry per `bindings.targets` handle of every profile, ordered by profile id and then handle: `profile`, `adapter` (the registered adapter the target's alias binds), `target` (the normalized target, with `handle` and `kind`) and `operations` (the sorted, duplicate-free operations the profile's publication actions and activation units run against that handle). Every target of a publication-free profile is listed with an empty `operations` (#368 D6). The other four members of the snapshot are unchanged by it.

`release profile inspect <profile-id> [--repo-root PATH]` (#124 D15, D18) prints one compact sorted-key JSON `ReleaseProfileInspection` and exits 0 whether the profile is admissible or not, because diagnosis never mutates (#69); a publication-free profile is reported with exit 0, empty `publication` and `activation` graphs and an empty `handoffs` list (#368 D7). It is read-only: no adapter is invoked, nothing is written, no network is used, and the only child process is `git rev-parse HEAD` in the project root under a 10-second bound (a failure reports `source_revision: null`). It resolves the project as `resolve-project resolve` does, so a resolver refusal reaches the caller byte for byte with exit 2; `"unsupported"` is `release_unsupported` (repair `release.profile.declare`) and an unknown id is `profile_unknown` (repair `release.profile.unknown`), both exit 2. The report has exactly seven members: `schema_version`, `subject` (project, root, revision and installed platform), `profile` (id, version, digest, target, per-node deadlines, limits, `admissible`), `graphs` (the ordered publication and activation nodes, the handoff, the derived and authored proof obligations and the recovery units), `bindings` (adapter identities with each node's config, targets, principals and credential handles and classes, never credential material), `conformance` (per-adapter operation, predicate and executable support, the three linted checks and every finding) and `repairs` (one per finding, then one per missing executable, all `user_action`). No adapter `invoke` is reachable from any command; it is reachable only through the transaction core.

`release deploy inspect --commit <sha> [--repo-root PATH]` (issue 465 D5) is the deploy read that ship-release Phase 5 polls. A `--commit` that is not 40 lowercase hex characters is `parameters_invalid` (repair `release.deploy.commit_invalid`). It then resolves the project as `resolve-project resolve --require deploy` does, so a refusal, `capability_unavailable` for an unsupported or blocked deploy included, reaches the caller byte for byte. A `bindings.deploy.adapter` outside the registry is `deploy_adapter_unregistered` (repair `release.deploy.adapter_unregistered`), because that binding's command is the deploy reader. All three exit 2 before any read. Otherwise it removes every name in `bindings.tracker.credential_env.unset_before_invocation` from its own environment (D10) and calls the registered adapter's `inspect` for its watch operation. The request has the tracker's `repo_slug` and the default branch as a `github_repository` target, the commit as the candidate, and `bindings.deploy.config` as the config. It prints the observation as compact sorted-key JSON and exits 0 whatever the outcome, and it keeps no state between calls.

The legacy skills-config bridge (`release_bridge`, #124 D13) is two pure functions: `plan_legacy_release` proposes a `release` from a legacy `deploy` member, or a stable adoption question where the forge-only profile cannot represent it, and `project_legacy_deploy` renders the member-scoped `deploy` projection of a profile. The adoption sweep (`adopt_planning.legacy_binding_operations`, #148 D30) is its one writer, so during the bridge the legacy `deploy` member is generated, not edited.

## Release adapters

An adapter is a module with `describe`, `inspect` and `invoke`; `release_adapter.REGISTRY` is the closed mapping of adapter names to modules and `release_adapter.DESCRIPTORS` the descriptors built from it at import, so a malformed descriptor or one whose `name` differs from its registry key fails the import, and an unknown adapter name is a grammar violation (#124 D7, D19). `inspect` returns a closed effect or predicate `Observation` and `invoke` the closed `InvokeResult` `{result, error_class, reference}`: `result` is `accepted`, `rejected` or `unknown`, `error_class` is null exactly when `accepted`, and there is no `succeeded` because only the core's later inspection can say an effect landed (D7; #85, #206). `release_adapter.core_binding(adapter, compiled, alias)` projects an adapter onto the shapes the transaction core accepts: it refuses an implementation whose name or descriptor digest differs from the one the compiled profile pins, refuses any request whose `operation`, `target` or `config` is not exactly a compiled node of its alias (D24), and validates every result it returns, adding no retry or ordering policy.

The forge adapter (`forge_adapter`, D8) declares `pr_merge` as `unsupported` with reason `target_cas_unproven`, so a profile that names it is a grammar violation, and carries `tag` and `release`, both `index` mode, irreversible and create-if-absent. `inspect` reads with `gh api` and `gh pr view` only, with `GITHUB_TOKEN` and `GH_TOKEN` removed from the child so the keyring credential answers, under one collection budget; it reads a tag from its own ref and object, never from a Release's `target_commitish`. `invoke` applies the steps of spec section 7 in order and stops at the first refusal: request shape (an unsupported operation is `unsupported_operation`, bad parameters `invalid_input`, with no child process), the working checkout (`git rev-parse --show-toplevel`, D23), same repository (`origin` and its one push URL must each be a `github.com` URL in the `git@github.com:`, `https://github.com/` or `ssh://git@github.com/` spelling, and they and `gh api repos/<slug> --jq .full_name` all name `target.repository`), containment of the commit in the target branch (`tag`), the local annotated tag (reused at the same commit, created when absent, refused otherwise; D25), then the rendered command and the guard. A failed read before the mutation is `rejected` with `transient_transport` or `provider_unavailable`, because nothing was mutated. There are two mutation spellings: `git push origin refs/tags/<tag>` and `gh release create <tag> --repo <slug> --verify-tag --title "<title>" --notes-file <file>`, where `--verify-tag` refuses to create a tag and the notes file is a mode-0600 temporary removed afterwards. Before the one mutation the command text is passed to `claude-bash-lifecycle-guard`, by name on `PATH`, as a `{tool_name, tool_input.command, cwd}` Bash payload; a non-zero exit, timeout or missing guard is `authorization_denied` (D9). The mutation is never retried and the target is never read after it: `already exists` (git) or `HTTP 422` (gh) is `precondition_failed`, a mutation binary that cannot be spawned is `rejected` with `provider_unavailable`, because no child ran and nothing was applied (D23), and a timeout or any other non-zero exit is `unknown` with `transient_transport`, which the core resolves by inspection (D9, D11).

The GitHub Actions deploy-watch adapter (`actions_health_adapter`, issue 465 D2) is registered as `github-actions-health`. Its one operation, `deploy`, is `publication_triggered`, `unsupported` for `invoke` with reason `bridge_watch_only` and supported for `inspect`, so no profile can bind it yet and its `invoke` refuses every request with `unsupported_operation` and no child process. Its closed config is `workflow`, `branch`, `services`, `health_url` and `health_commit_field`, all required; `services` is the `string_list` config type, a non-empty list of unique non-empty strings. `release_adapter.watch_operation(descriptor)` names a descriptor's single inspectable activation-mode operation, or returns `None` when there is none or more than one. `inspect` answers `parameters_invalid` unless the request carries a `github_repository` target of exactly `kind`, `repository` and `branch`, a 40-lowercase-hex candidate `commit`, and a config whose `branch` equals the target's and whose `health_url` is `http` or `https` with a host. It then makes at most two reads under one 30-second budget. The first is `gh run list --repo <repository> --workflow <workflow> --branch <branch> --limit 5 --json databaseId,status,conclusion,headSha,headBranch,createdAt`, run by name with the caller's environment unchanged: the adapter strips no variable, and `release deploy inspect` applies `bindings.tracker.credential_env` (D10). The second, made only when the newest run at the candidate on that branch is completed, is one `GET <health_url>` that follows no redirect, reads at most 65,536 bytes and loads the body strictly through the `canonical` hooks (D8). Runs are ordered newest first by `createdAt`, which must be an ISO 8601 time with an offset (D14), and a commit matches when it is 7 to 40 hex characters and the candidate starts with it, case-insensitively (D7). The outcome follows the spec's classification table (D6): `absent` (`run_absent`); `in_progress` (`run_in_progress`); `satisfied` (`deployed`) only for a `success` run whose health commit matches; `diverged` (`superseded`) for a completed, unsatisfied run that a run at another commit followed; otherwise `diverged` (`health_commit_mismatch`, `silent_rollback` or `run_failed`) or `unknown` (`health_unreachable` or `health_payload_invalid`). A failed run-list read is `unknown` with `lookup_failed`, `lookup_timeout`, `executable_missing` or `payload_invalid` and the bounded stderr in `facts.detail`. Every effect observation's `facts` hold `runs` (each `{id, status, commit, branch, createdAt}`, newest first), `run`, `health` and the configured `services`. `tests/actions_world.py` is its fake `gh`, which logs token visibility, and loopback HTTP server.

`tests/fixtures/forge-adapter-spellings.json` is the one list of provider spellings: `tests/forge_world.py` builds its fake `gh`, `git` and `claude-bash-lifecycle-guard` from it, and `tests/test_forge_adapter.py` pins the adapter to it, so the world and the adapter cannot disagree about a spelling (D12, D22). `tests/test_release_adapter_core.py` drives the real `TransactionStore` through `core_binding` and shows that an `accepted` invoke which never lands is recorded and then observed `absent` by a second inspection (AC8).

## guard-policy

`guard-policy compile --base <path> --output <path>` compiles the lifecycle guard's policy from the fleet registry (issue 126). It reads the base policy, the registry (`agent_platform.read_registry`, an absent one being the empty fleet) and each registered project's contract on its registered branch of `origin`, through `adopt_verify.remote_source` with the resolver run in process (issue 126 D13); it never reads the checkout's working tree, index or local branches. It reads each branch at the commit `origin` lists for it, through `adopt_verify.SourceReader`: `adopt_inspection.pin_listed` fetches the branch only when the checkout lacks that commit, and `contract_export.export_contract` exports the contract and its projection files (`resolve_project.projection_paths`) sparsely, with no tree inventory. Its only repository writes are the remote-tracking refs of the branches it fetched and the fetched objects. The base policy must be an object with exactly the five trusted members `authorized_owners`, `integration_bases`, `git_bin`, `gh_bin` and `jq_bin`, where the owners and branches are non-empty strings and the three tools are absolute paths; anything else, an unreadable file included, is the cause `base_invalid`.

A project earns a derived row only when twelve steps all hold in this run and the guard can load the row, and the first of those to fail names the reason code of its refusal. `derive` runs steps 1 to 10: the registered root is a git repository (`root_unavailable`); `origin`'s fetch url and its single push url name one `github.com` slug, spelt as `github_remote.github_slug` reads it and never case-folded (`origin_unproven`, issue 126 D9); `origin` yields a default branch and the contract's branch (`branch_unresolved` for `adopt.registration.remote_default_unknown` and `adopt.registration.integration_branch_unresolved`, `fetch_failed` for every other `AdoptError`); the resolver accepts that contract (`contract_unresolved`, with its repair id in the detail). `target_profiles` runs steps 5 to 8 on the resolved snapshot: the contract's project id is the registered one (`identity_mismatch`), its tracker is the `github` repository named by the slug (`tracker_mismatch`), it has a `github_repository` release target (`no_forge_target`), and every such target names the slug and the default branch (`target_mismatch`); each selected profile then compiles through `release_profile.compile_profile` (`profile_inadmissible`). Step 9 requires the contract's integration and default branches to be the branch read and `origin`'s default (`branch_mismatch`), and step 10 that `gh api repos/<slug> --jq .full_name` answers the slug (`provider_unproven`). `compile_policy` runs steps 11 and 12 over the projects that passed: a slug derived by more than one is `duplicate_repository` for each, and a slug that is also a key of the base `integration_bases` is `literal_conflict`: that project gets no row and the literal row stays in the base policy (issue 377 D5). A project that passed all twelve is then refused `name_unsupported` when `unsupported_name` finds its slug or either of its branches outside the shapes the guard's `load_compiled_policy` demands of a derived row: git and the contract grammar take a branch such as `dev+ci`, and the guard drops the whole compiled policy over one such row, which removes every derived row and blocks nothing the base policy allows (issue 377 D4). The guard is a standalone file the package cannot import, so `guard_policy` restates its two shapes as `GUARD_SLUG` and `GUARD_REF_NAME`, and a guard-suite test holds them to the built guard by loading a policy compiled from a fleet that has such a branch.

A row is `{default_branch, integration_branch, evidence}`, and the evidence is identity only (issue 126 D11): the project id, the digest of the registry entry (`canonical.telemetry_digest`), the pinned `ref` and `commit`, the contract's blob id at that commit, the provider's `full_name` and each compiled profile's `id`, `version` and `digest`. No resolved snapshot and no contract body is persisted. The written document has exactly two members, the rows under `derived_repositories` and `derivation`: `{schema_version, platform_version, registry_digest}`, where `schema_version` is 2 and the digest is `null` when no registry file exists. The lifecycle guard reads its trusted members (`authorized_owners`, `integration_bases` and the three tools) from the base policy only and takes nothing but a row's two branches from this file.

The three outcomes are the exit statuses. Exit 0 (`complete`) means every entry derived and the file was written. Exit 1 (`written_with_refusals`) means the file was written without the rows of the refused projects, one stderr line each. Exit 2 (`refused`) means no policy could be compiled, so the previous file is removed whatever it held: a missing file or a parent that is not a directory counts as removed, and any other failure to remove it is appended to the cause's detail without replacing the cause. The cause is one of `base_invalid`, `registry_invalid`, `platform_unavailable`, `output_unwritable` (issue 126 D14) or `internal`, which carries the exception's type and message. The write is atomic (`agent_platform.write_atomically`), so a reader sees the old file or the new one. The stdout report is one line of sorted-key JSON: `schema_version`, `outcome`, `derived` (the sorted slugs), `refused` (`project_id`, `root`, `reason_code` and a `detail` cut to 240 characters) and `cause` (`null` or `{reason_code, detail}`).

`guard-policy derive --repository <slug>` re-derives one repository's row (issue 377). It reads the registry, runs steps 1 and 2 for every entry and steps 3 to 10 only for the entries whose `origin` names the slug, so an entry naming another repository is never fetched and never asks the provider; then it runs step 11 and the name check among those entries. It prints one line of JSON with the keys `schema_version` (1), `repository` (the argument), `outcome`, `row`, `refused` and `cause`. The outcomes are `derived` (exit 0, `row` is the row `compile` would write), `refused` (exit 1, no row; `refused` lists the entries that name the slug and have none, and is empty when no entry names it) and `unavailable` (exit 2, `cause` is `{reason_code, detail}` with `registry_invalid`, `platform_unavailable` or `internal`). It reads each branch the same way `compile` does (the listed commit, fetched only when absent, and the sparse `contract_export` of the contract and its projection files), so it writes no file beyond the fetched objects and the remote-tracking refs of the branches fetched, reads no base policy and never reports `literal_conflict`. The lifecycle guard runs it as its row check.

Every child of the identity steps, the two `git remote get-url` reads and the `gh api` read, runs by name with `cwd` at the registered root, stdin at `/dev/null`, `GIT_TERMINAL_PROMPT=0`, `GH_PROMPT_DISABLED=1`, a 30-second timeout and `GITHUB_TOKEN` and `GH_TOKEN` removed, so `gh` answers with the keyring credential (issue 126 D7); the fetch and the listing are bounded at the same 30 seconds. A timeout or a missing executable is a failed read. A failed read puts its reason in the refusal's detail (`timed out`, the executable error, or `exit <n>` with the child's stderr), and a `gh` answer other than the slug puts the name it gave. `tests/test_guard_policy.py` drives the commands as `python -m agent_tools.guard_policy compile` and `derive` over `tests/guard_policy_world.py`, and calls two functions directly for the checks no command input reaches: `target_profiles` on a hand-built snapshot for the one step the release grammar hides (issue 126 D10, D15), and `unsupported_name` on a hand-built row for the slug, because `github_remote.github_slug` already reads no slug the guard would refuse.

## agent-costs

`agent-costs` (`just agent-costs`; source entry `python -m agent_tools.agent_costs`) reports agent token spend per issue from the Claude Code transcripts under `~/.claude/projects`, and with `--format json` projects one `agent-cost-record` (Codex rollouts too, with `--strata`). Its dollar figures apply list prices per model ID from `agent_tools.model_pricing`: comparative telemetry, not billing data.

Issue 421 corrected the Opus-class row from $15 input / $75 output per million tokens to $5 / $25, with cache writes at 2× input for the 1-hour TTL and 1.25× for 5 minutes and reads at 0.1×, so dollar figures from before and after that change are not comparable; token counts and the record's shape (`schema_version` 1) are unchanged.

**Per-model pricing (issue 432).** `agent_tools.model_pricing` is the one price table: a row per model ID (input, output, 5-minute write, 1-hour write and cache read, dollars per million tokens) from <https://platform.claude.com/docs/en/about-claude/pricing>, fetched 2026-10-25. An ID equal to a row's ID, or to it plus a `-<8 digits>` date suffix, takes that row. Any other ID takes the newest row of the family its name contains (Opus 5.5, Sonnet 5.5, Haiku 5.5, Fable 5.1), and an ID that names no family, or none, takes Opus 5.5; both count as approximate calls. Haiku 5.5 switches to its second tier when a request's prompt (input plus cache reads plus cache writes) is over 100,000 tokens, and `<synthetic>` costs nothing. `cost_by_family` still groups by `model_family`, whose `opus` key holds Opus, Fable and unrecognised models, but each call is priced by its own model, so dollar figures from before this change, which priced Opus 5.5 at the Opus 5 row, are not comparable with later ones; token counts and the record's shape are unchanged. `agent_tools.transcript_calls` is the shared transcript reader, which the cache report and the owner report read through (`read_transcript`, `Call`, `is_death`) and which also keeps each call's tool inputs, each tool result's text and size, and the notes a `PreToolUse:Bash` hook attached to a tool use. The cache report's last line before `NOTE:` is `Pricing: <source URL> (<date>); <n> calls priced approximately`.

`--report cache` (issue 421; `agent_tools.agent_cache_report`) prints a cache report in place of the per-issue tables, which the default `--report issues` prints unchanged. It is text only: `--format json`, `--project`, `--artifacts`, `--strata` other than `claude`, one event bound without the other, a bound without an offset, or an `--events-since` not before `--events-before` is a usage error (exit 2, nothing on stdout), as is `--context-threshold` with the per-issue report. With `--events-since/--events-before` a call counts when its earliest record timestamp lies in `[since, before)`, transcripts last modified before `since` are skipped and `--days` is ignored; without them `--days` selects transcripts by file mtime and every call in them counts. The report prints a header naming the window, three tables each capped at `--top` rows with a line saying how many it dropped, and the comparative-telemetry note; a run that selects no transcript exits `no transcripts in window`, and one whose transcripts hold no counting call exits `no calls in window`.

A call is one `message.id` of a transcript (else `requestId`, else `uuid`), each usage field taken as its maximum over the call's records; its context is `input_tokens + cache_read_input_tokens + cache_creation_input_tokens`, and a message whose context is 0 is no call. A cache death is a counting call that started more than the TTL less 10 s after its predecessor's last record (1 h for a main session's transcript, 5 min for a subagent's), whose predecessor's context exceeded 5,000 tokens, and whose cache creation exceeds half that context. Its cause is the tool of the last result, between the two calls, of one of the predecessor's own tool uses (`child dispatch` for `Agent` or `Task`, `long foreground command` for `Bash`, `other tool` otherwise), a result marked `toolEndsTurn` excepted; without one, the first other user record between them decides (`hand-back after end of turn` for a `peer` origin with `handback: true`, `task notification after end of turn` for a `task-notification` origin, `message after end of turn` for any other), and with neither it is `unclassified`. The deaths table shows each agent type and cause with its count, median gap and premium, `min(cache creation, predecessor context)` at the call's write price, weighted by its own 1-hour/5-minute split, less the read price; a totals line splits subagent and main-session deaths.

The reread table shows, per agent type, the transcripts with a counting call, the summed `max(0, cache_read_input_tokens − T)` of their counting calls at the read price, where `T` is `--context-threshold` (default 120,000), and the median, p90 and maximum of each transcript's largest counting-call context; every median and p90 is the sorted value at the position `p/100 × (n − 1)` rounded half to even, so the median of four peaks is the third. The start-up table shows, per subagent type, the subagents whose first call counts, the median cache write and read of that call, and the median character count of the `rendered` content of the first `skill_listing`, `instructions`, `mcp_instructions_delta`, `deferred_tools_delta`, `agent_listing_delta` and `environment` attachment recorded before the second call, over the subagents that carried one (`-` when none did). A subagent's agent type is the `agentType` of its sibling `.meta.json` (`unknown` without one), and a main session's is `main`.

**Owner report (issue 432).** `--report owners` (`agent_tools.agent_owner_report`) prints dollars per delivered issue by lineage, by arm and for fresh-owner boots, as text or with `--format json` as one `agent-owner-report` document (`schema_version` 1). It takes `--days`, `--projects-dir`, `--top` and `--events-since/--events-before`, which count only the calls that start inside the window (a transcript's gaps, deaths and phases are still read over all its calls); it refuses `--project`, `--artifacts`, `--context-threshold`, `--strata` other than `claude` and `--eval-results`/`--eval` without each other, each as a usage error (exit 2).

*Owner.* A transcript is an owner's when one of its Bash calls holds a `workflow-state progress`, a `workflow-state mark-progress` or an `sdd-gate` invocation (read through `context_meter_commands.invocations`) carrying both `--run-id` and `--action-id`; its run ID is that `--run-id` and its action ID an opaque string. Its issue, attempt, remainder and launch come, per field and in this order, from a JSON reply of its own for that run (`phase_gate`, a `workflow-state finish` reply or a `direct-owner` reply of `kind: owner`: `issue` and `custody.{attempt, remainder, launch}`, else a top-level `attempt`), from the `--issue`/`--attempt` of its `progress` and `suspend` calls, and from another owner transcript of the same run with the same action ID. A reply is the first JSON object of the tool result's text; text after it is ignored, and a result that does not start with an object has none. An owner left without an issue counts in `unattributed.unresolved_owners`, and its spend and its descendants' spend count as unattributed.

*Lineage and descendants.* One lineage per `(run_id, issue)`, its launches ordered by attempt, then remainder (an attempt's own launches before its remainders'), then launch ordinal, each unknown last, then first call time: a launch ordinal counts within one attempt or remainder, so a retry's launches follow every launch of the attempt before it. Every other transcript is attributed to the nearest owner on its way up: its parent is the subagent transcript named by its `.meta.json` `parentAgentId` in the same session, or the session's root transcript when it names none. A transcript that reaches no owner is unattributed, and the footer shows the count and the dollars. `owner_dollars` is the lineage's owner transcripts' calls, each priced at its model's row for its prompt size; `total_dollars` adds its descendants.

*Delivered.* A live lineage is delivered when a transcript of it, owner or descendant, ran `workflow-state finish` and got a reply whose `kind` is `delivery_complete` for that `run_id` and `issue`. An eval trial is delivered when its results row's `verdict` is `PASS`.

*Calls and phases.* A call is a death by the cache report's rule. Its phase is the `--phase` of the transcript's first progress call for every call up to and including it (6 when the first registering call is an `sdd-gate` or `mark-progress`), and `n + 1` after a progress call reporting `n`. A child is out from the call that dispatched it (`Agent` or `Task`, matched to the child's `.meta.json` `toolUseId`) until its last call ends; a long child wait is a gap over 300 s between two calls with a child out across it, counted once per gap. A gate call is a progress call, a measured one when a `PreToolUse:Bash` hook note on its tool use holds the context meter's measured-note prefix, and `phase7_entered` when a `progress --phase 6` call got a `phase_gate` reply. A fresh owner's boot runs from its first call through its registering call, or through the last call before the first with a child out when that comes earlier (a dispatched child is the owner's first unit of work, which the replay's observed increments already carry), and a boot with a call outside the event window is in no boots table, boot model or calibration; its slimmable tokens are the context growth after each boot call, split across the call's tool results by size, that came from reading another task's `.tasks/task-<n>.md` (the resumed task is the `--task` of the first `sdd-gate review`), a `ship-handoff.md` before Phase 7, or a persisted output file named after `saved to: ` in such a result.

*Eval grouping.* `--eval-results PATH --eval SKILL:ID` takes the rows of the results file whose `skill` and `id` match. A row's transcripts are the sessions whose project directory name equals its `workdir` with every non-alphanumeric character replaced by `-`, or starts with that and a `-`; the mtime window does not apply. Only a row with `claude_exit` 0 is a sample: it becomes one lineage row (its lineages merged: sums, the highest peak, any Phase 7 entry) in the arm `<first 12 characters of tree_rev>/<policy or default>`, with its `trial` and `verdict`. Any other row, a timeout or a kill whatever its `verdict`, forms no lineage and is listed in `interrupted` as `{trial, tree_rev, claude_exit}`. A `claude_exit` 0 row that yields no lineage (its `workdir` matches no session, or no owner of its sessions resolved an issue) is an evidence gap too: it is listed in `unmatched` with the same three keys, never dropped from the counts silently. Live lineages are all in the arm `live`.

*Document.* `lineages` rows hold exactly `key, run_id, issue, arm, trial, verdict, direct, launches, handoffs, boots, deaths, long_child_waits, peak_context, owner_dollars, total_dollars, delivered, phase_reached, phase7_entered, gate_calls, measured_gate_calls, help_calls, absolute_path_calls` (`phase_reached` counts a progress call that got a `phase_gate` reply as `--phase + 1`). `arms` rows hold `arm, n, delivered, dollars_per_delivered, sd, undelivered_dollars, peak_p50, peak_p90`: dollars per delivered issue is all spend of the arm, undelivered included, divided by its delivered rows (`null` for none), and `sd` the sample standard deviation of `total_dollars` over delivered rows (`null` below two). `boots` rows hold `phase_group` (`0-5` or `6-7`, by the registering call's phase), `count, b_p50, b_p90, start_p50, calls_p50, slimmable_p50`. `simulated` and `calibration` are an empty list and `null` unless `--policy` or `--sweep` fills them (see *Replay*); `interrupted` and `unmatched` are lists of `{trial, tree_rev, claude_exit}` (`unmatched` is empty for live lineages), `pricing` is `{source, date, approximate_calls}`, `unattributed` is `{transcripts, dollars, unresolved_owners}`. The text output prints the lineage, arm and boot tables, the simulated-arms and calibration tables (each `(none: pass --policy or --sweep)` without a replay), and a footer with `Pricing: …`, the unattributed spend, the interrupted-trial and unmatched-trial counts, the replay's bias note when there are simulated rows, and `NOTE: ` plus the comparative-telemetry disclaimer.

*Replay (issue 432).* `--policy NAME=SPEC` (repeatable; a duplicate name, or `baseline`, is a usage error) and `--sweep` (`agent_tools.agent_owner_replay`) replay every lineage in scope under a hand-off policy; both are usage errors without `--report owners`, and a bad SPEC is a usage error too. A SPEC is comma-separated items: the `phase_budget` knobs `threshold=<tokens>`, `threshold:<a>-<b>=<tokens>`, `guard=<tokens>` and `cap=<n>`, and the replay's own `boot=observed|slim`, `keepalive=off|on`, `help=keep|drop` and `threshold=never` (no hand-off at all, which excludes any other `threshold` item; the SPEC's other knobs are still checked). Knobs a SPEC does not name keep the pre-issue-432 policy (`ORIGIN`: 110,000 in every phase, no guard, no cap, observed boots, keepalive off, help calls kept), whatever `PhaseBudget`'s defaults are; `BASELINE` is that policy and every saving is measured against its replay. The identity replay (`observed`) is each lineage's calls as priced plus its descendants' dollars, and the calibration table checks it against the lineage totals.

The shift model undoes each observed `handoff` relaunch first, in every arm: the outgoing owner's calls after its first call that answered `handoff` (context `C`) and the fresh owner's calls before its registering call (context `R`) are dropped, and the remaining calls join the outgoing owner with `C - R` of context added back; a hand-off joins only the next launch of the same chain and the same attempt or remainder, and any other transfer starts a new owner. An arm then hands off at the phase gates (`select_phase_action` re-decides each observed gate with the arm's threshold for the next phase; the guard never applies there) and mid-phase at the first Bash call with no Agent child out at or after a Bash call whose context reaches `crossing_threshold`, so the crossing call itself hands off when it has no child out (only Bash calls are measured: a latch notifies once per crossing and re-arms at a Bash call below it; an owner is measured from the call after its registering call). A simulated hand-off at context `C` prices the outgoing call, then `h` overhead calls at `C`, the relauncher's wake call and a boot of `m` calls growing linearly from `S` to `B`, the modelled end of a boot of the phase the fresh owner works in (the phase after the gate's at a gate, the call's own mid-phase), and every later call loses `C - B` of context, taken from its cache read first; this `B` is the boot end of *Calls and phases*, which falls before the registering call when a child goes out earlier, so it is not the undo's `R`. A hand-off owner is a subagent: its writes are 5-minute writes, and a call that the observed root made more than 290 s after the call before it, when that call's replayed context was above 5,000 tokens, becomes a cache death. A root revives an observed subagent death within 3,590 s, and `keepalive=on` revives every death and adds `⌈gap/270⌉ − 1` cache-read pings. `help=drop` removes the `progress --help` calls and their growth. `boot=slim` lowers every boot's `B` (and an observed boot's growth) by its slimmable tokens. `cap=n` skips a hand-off while `n` simulated hand-offs have happened since the last `mark-progress` outcome `advanced` or the last gate of a higher phase than any before it. `S`, `m(p)`, `B(p)`, the slimmable median, `h` and the boot output are medians over the observed boots and hand-offs, and a value the corpus lacks takes `S = 29,000`, `m = 20`, `h = 6`, the other group's `B` and then 98,000, or 0 slimmable, each listed in the calibration `defaults`.

The keep rule (D8) reads the per-lineage saving of the baseline replay over the arm's: an arm is kept when there are two or more lineages, the mean saving is above 0 and the one-sided 90% lower bound `mean − 1.2816·sd/√n` is above 0. `--sweep` is the coordinate pass of D18: `boot=slim`; the thresholds 90,000 to 200,000 (the cheapest is compared with 110,000, and the 16-arm per-phase grid follows when the median Phase 6-7 `B` differs from the Phase 0-5 one by more than 25%; `threshold=never` is an `info` row, never chosen); the guard (20,000 to 60,000), the cap (1 to 3) and `help=drop`, each at the choices so far; `keepalive=on` for information; and a `final` step that prices each chosen candidate alone against `BASELINE` and one `combined` row over exactly those that kept alone. A step's candidate is `chosen` only when it keeps against the step's simpler arm; a step row's saving is against that simpler arm, and a `policy` or `final` row's against `BASELINE`. A `simulated` row has exactly `arm, step, spec, dollars_per_delivered, mean_saving, lower_bound, share_saving, handoffs_per_issue, deaths_per_issue, peak_p90, verdict` (`baseline`, `chosen`, `not chosen`, `keep`, `reject` or `info`) and `live_confirmation_required`, true when the arm hands off more per issue than the baseline. `calibration` holds `identity_matches`, `identity_max_error`, the observed and modelled dollars of each observed fresh-owner boot by `phase_group`, and the fitted `model`. Known bias: the model keeps observed increments after a hand-off and cannot see a fresh owner's later re-reads, so it favours hand-offs (D18), and an arm that hands off more than the baseline is kept only if the live arm confirms it.

**Boot report (issue 448).** `--report boot` (`agent_tools.agent_boot_report`) splits the context of each owner boot the owner report finds into twelve buckets, as text or with `--format json` as one `agent-boot-report` document (`schema_version` 1). It takes `--days`, `--projects-dir`, `--top` and `--events-since/--events-before` (with the owner report's window rule), and refuses `--project`, `--artifacts`, `--strata` other than `claude`, `--policy`, `--sweep`, `--eval-results`/`--eval` and `--context-threshold`, each as a usage error (exit 2) with nothing on stdout. `--projects-dir` is repeatable here, as `[LABEL=]PATH`: a value is labelled when it fullmatches `([A-Za-z0-9][A-Za-z0-9._-]*)=(.+)` (`ROOT_LABEL`) and is otherwise a bare path, which takes the local short hostname (`socket.gethostname()` up to its first dot); a labelled or bare path is read after `~` expansion. With no `--projects-dir` the root is `~/.claude/projects`, under the short hostname. The label `all` is reserved for the pooled host, and a label given twice is a usage error; any other report refuses a second `--projects-dir`, or a labelled one, as a usage error too. Each root gets its own `agent_owner_report.collect` call, so no lineage spans two hosts: two roots whose sessions share a run ID and issue give two lineages, each with its own first launch. A root that is not a directory exits 1 with `no transcript root at <root>`, before any root is read. Another host's transcripts are read from a read-only copy of its `~/.claude/projects` placed in the task's scratch (issue 448, D15, D18), never from the repository, and labelled with that host's name.

*Boots and cohorts.* A boot is the owner report's (`boot_facts`/`boot_slice`): `b` is the context of its last call and `start` the context of its first. A boot is `fresh` when its launch is not the first of its lineage or its launch ordinal is 2 or more, else `spawned`; its `phase_group` is the owner report's (`0-5` or `6-7`), and the groups table has one set of rows per host label, in argument order, then the pooled host `all`, by cohort and by phase group with `all` pooling both; a row with no boots is omitted. The `all` rows are means over the pooled boots, never means of the hosts' means.

*Attribution.* Call 0 is split from the transcript's request records: the last `api-request-shape` record and the last `api-request` record before it. Harness characters are the shape's system texts plus every text block of the request's tail blobs that is in a `system`-role message or starts with `<system-reminder>`, and prompt characters are the other text blocks; each is divided by the fixed 2.44 characters per token and rounded, and `tool_schemas` is what remains of call 0's context (unclamped). A boot with no such pair of records, or whose transcript cannot be opened, is `unsplit`: it is counted per host and left out of `boots` and every table. What a later call added is every chunk between it and the call before it: each tool result (its full text length), the meta user message of each Skill call (`skill_bodies`, keyed by the skill), each text block of a tail blob of an `api-request` record whose hash the boot has not counted (call 0's included) as `harness` and each `tool_addition` block as `tool_schemas` (its compact JSON length), and the characters a new shape record's tool list has beyond the last one, as `tool_schemas`. A blob of an `assistant`-role message (the earlier call's output) adds nothing, nor does a text block equal to a Skill meta message between the two calls, nor a `tool_result` block. The chunks are classified, and the reads, `saved to: ` origins, counted hashes and tool-list size updated, whatever the growth. A call's growth over the call before it is `unexplained` when it is not positive; otherwise it is `assistant` up to the earlier call's output tokens, and the rest is split across the chunks by character share in integer floors, the first largest chunk taking the remainder, or is `unexplained` when the chunks hold no characters. A call whose chunks hold more than 2,000 characters and that shares a positive rest also feeds `observed_chars_per_token`, those characters over the tokens they were given, summed over every such call of every host and rounded to two places, which is reported next to the fixed one and never used.

*Buckets.* `tool_schemas, harness, prompt, skill_bodies, skill_files, plan_reads, resume_reads, rereads, other_reads, commands, assistant, unexplained`, which sum to `b`. A tool result takes the first rule that holds: a `Read` of a path an earlier result named after `saved to: ` takes that result's bucket; a call with read keys, every one read before, is `rereads`; a result holding a `resume_pack`, or an `owner` object of interface version 2, is `resume_reads`; the first read path that is a skill file (two or more components under its last `skills` component) is `skill_files`, keyed by the path after that component, else any plan path (a `.tasks/task-<n>.md`, a `plans/*.md` other than an acceptance record, or a `progress.md` under `.superpowers/sdd`) is `plan_reads`, else any read is `other_reads`; a `Skill` call is `skill_bodies`, keyed by its skill; everything else is `commands`. A read key is a `Read`'s `(path, offset, limit)` or, for a `Bash` command that `lex` accepts, each file operand (a word other than an option, a `head`/`tail` `-n`/`-c` value or the program of `sed`, `awk` or `jq`, that holds a `/` or ends in an extension, joined to the `cd` directory) of `cat`, `sed`, `head`, `tail`, `nl`, `awk`, `jq` or `less` with the words of that command, after heredoc bodies and redirections are dropped and `NAME=value` and `cd` are applied.

*Document.* The keys are exactly `kind, schema_version, window, hosts, chars_per_token, observed_chars_per_token, unsplit, boots, groups`. `hosts` holds `{label, root}`, `unsplit` maps a host label to its count, and `observed_chars_per_token` is `null` when no call qualified. A boot row holds exactly `host, transcript, run_id, issue, cohort, phase_group, calls, start, b, buckets, skills, skill_files`, where `skills` and `skill_files` split the two buckets of the same names by skill and by file. A group row holds exactly `host, cohort, phase_group, count, b_mean, b_without_schemas_mean, buckets`, the means being per boot.
