# agent_tools — the agent helper package

Agent-workflow Python is moving into one standard-library package, `agent_tools`, under `python/` (with its `pyproject.toml`).

## Package and launchers

`lib/agent-tools.nix` builds it into one Python environment, import-checks every module so that a broken import fails `just build`, and holds the command table.

`home/common/agent-tools/default.nix` applies that builder once per home configuration as the `agentTools` module argument, which agent-skills and claude-code consume. The installed-layout check pins the built system closure to one agent_tools package build, every agent-tools launcher to one Python environment, and that environment's imports to the closure's package build. `just agent-installed-skill-tests` passes `AGENT_TOOLS_SYSTEM_RESULT` to the check.

Each row becomes a `~/.agents/bin/<command>` launcher, which unsets the `NIX_PYTHON*` variables and runs `python3 -I -m agent_tools.<module>` from that environment, so nothing on `PYTHONPATH` or in the working directory can shadow the store copy; `just agent-installed-skill-tests` proves it. Every agent-workflow helper is a module of the package, and each command-table row is its only install route.

## artifact-budget

`artifact-budget` measures a skill artifact root against the policy and validates a producer phase report; the design, grill-with-docs, writing-plans and handoff skills call it by bare name. Its commands are `check --kind {design-spec,implementation-plan,handoff} --root PATH --format json` (exit 0 within budget, 3 over budget, 2 refused) and `validate-report --boundary producer --input PATH|-` (exit 0 with the canonical report, 2 refused). `--policy` defaults to `~/.agents/share/artifact-budget-policy.json`.

## issue-branch

`issue-branch --repo-root <path> --issue <n>` prints the branch a delivery of issue `<n>` works on, as one JSON line `{adopted, branch, derived, worktree_path}` (issue 748). `derived` renders `bindings.vcs.branch_pattern` with the title slug: at most 6 ASCII words and 40 characters, cut at a word boundary, `untitled` when empty. After `git fetch origin` it re-adopts an earlier branch of the issue: a local or origin branch that fully matches the pattern with the issue number filled in and only `<slug>` as a wildcard. A pattern without both placeholders, or with them adjacent, re-adopts only the derived name, and the integration and default branches never count. Order: the derived branch, else the head of the lowest-numbered open same-repository PR, else the newest commit. `worktree_path` is `<worktree.root>/<worktree.prefix><branch>` under the project root. Exit 2 refuses (`resolver_refused`, `tracker_unsupported`, `derived_is_protected`), exit 1 is a `forge_failed` or `git_failed` failure; both write `{"error": {code, detail}}` to stderr.

## `lane-triage`

`lane-triage evaluate --repo-root <root> --input -` (#279) reads an owner's triage record on stdin, reads `bindings.workflow.light_lane` (an optional `resolve-project` member; absent or `null` means unsupported) through `agent_tools.resolve_project.resolve`, the one public function that composes exactly what `resolve-project resolve` prints, and prints the verdict `{hits, lane, mode}` without writing anything: `lane` is `light` only when no signal is `hit` or `doubt` and no predicted path matches a `risk_paths` glob, an absent or `null` member exits 2 with `light_lane_unsupported`, and the owner's Phase 0 records the verdict while every attempt still runs full.

## `agent-workflow-tests` runner

`just agent-workflow-tests` hands its curated member list to `agent_tools.suite_runner` (issue 436; source entry `python -m agent_tools.suite_runner`, no command-table row). The runner runs each member in its own process from its working directory, with the recipe's environment plus two git configuration entries and the run's bytecode cache: a `.py` member as `python -m unittest -v <path>`, and a `.sh` member as `bash <path>`. The entries, `maintenance.auto=false` and `gc.auto=0` (issue 496), are appended to `GIT_CONFIG_PARAMETERS` in the form `git -c` exports (`member_environment`), because otherwise a commit or a fetch in a test's repository starts a detached `git maintenance run --auto`, which creates `.git/objects/maintenance.lock` while the test reads that repository. Every git command that inherits a member's environment, at any depth, reads them as if given `git -c maintenance.auto=false -c gc.auto=0`: they win over an inherited entry, a test's own `GIT_CONFIG_COUNT` entry and any config file for the same key, a test's other count entries still apply, and a `git -c` option a command adds comes after them and wins. They do not reach a process started with an environment built from scratch or with its own `GIT_CONFIG_PARAMETERS`, nor the receive-pack of a push to a local repository, which git starts with every `GIT_CONFIG_*` variable removed, so that receiving repository still runs automatic maintenance. The bytecode cache (issue 499) is one directory per run. Before the first member starts, the runner creates a `suite-runner-pycache-*` directory in the default temporary directory, sets `PYTHONPYCACHEPREFIX` to it, replacing an inherited value, and drops an inherited `PYTHONDONTWRITEBYTECODE` (`member_environment`). Every Python process that inherits a member's environment, at any depth, writes the bytecode of the source modules it imports there, under each source's absolute path, and reads what an earlier process of the same run wrote instead of compiling again. Parallel writers need no coordination: CPython writes each file under a temporary name and renames it into place, and skips a write it cannot make. The prefix redirects every bytecode lookup, the standard library's included, so a run compiles the standard-library source modules its processes import instead of reading the interpreter's own bytecode, and its later processes read that result. A script run as a main file is compiled on every start. The runner removes the directory when the run ends, after the report, after an interrupted run has waited for its members, or on an error, and a failure to remove it is raised, never ignored. The cache does not reach a process started with an environment built from scratch, nor one run with `-I` or `-E`, which ignores both variables and keeps Python's default bytecode behaviour, and a descendant still running after the run ends may recreate part of the removed directory. CPython takes a cached file as current while its source's modification time, in whole seconds, and its size match, so a test that rewrites an importable source in place to the same size within one second and then imports it in a new process gives that process its own `PYTHONPYCACHEPREFIX` directory. Outside the runner, as in a direct `python -m unittest` run, a test's Python children that inherit its environment write bytecode beside their sources where those are writable, as the test process itself does; the checkout ignores `__pycache__/`. At most `--jobs N` members run at once. The default (issue 604) is `SUITE_RUNNER_JOBS` when that variable is set and non-empty, else `min(8, CPUs - 2)` with a floor of 1 (also when the CPU count is unknown); an explicit `--jobs` wins over both, and a bad `SUITE_RUNNER_JOBS` is a usage error (exit 2). The suite is CPU-bound and its CPU time does not change with the job count, so more jobs buy wall time: on a 10-CPU Mac the full suite took 923 s at 4 jobs and 473 s at 8, all members passing. Two CPUs stay free for the host, and the cap of 8 stops a large machine from oversubscribing its disk and git. A host shared by several agents verifying at once sets `SUITE_RUNNER_JOBS` lower, and the hosted CI job sets it to 4, the vCPUs of its runner, in `.github/workflows/ci.yaml`. In parallel mode members start longest-first (LPT, issue 604) so a long member is not left to the end: the order comes from `python/agent_tools/suite_timings.json`, a committed map of member path to wall seconds taken from a full run's timing table, with members it does not name starting first in list order, ties in list order, and a missing or malformed file meaning list order. Serial mode keeps list order, and the report stays in list order for ties. Refresh the file from a run's `suite-runner: <wall>s wall ... <member>` rows when the suite's shape changes; a stale file only costs wall time. In parallel mode each member's stdout and stderr are captured together and printed as one block when it exits, from `suite-runner: begin <member>` to `suite-runner: end <member> passed|failed exit=<code> <seconds>s`. A `suite-runner: start <member>` line marks each launch, so a run cut off by a time limit names the members still running. `--jobs 1` is serial mode: members run one at a time with stdin, stdout and stderr passed straight through, for a hang or a `breakpoint()`. A member passes only on exit 0. Unittest's exit 5 for a module that ran no tests, a death by signal (`exit=signal-<n>`) and a failure to launch (`exit=launch-error`) all fail it, and every member still runs after a failure. Every completed run ends with a timing table, slowest first with ties in list order, of one `suite-runner: <wall>s wall <cpu>s cpu passed|failed <member>` row per member, then one `suite-runner: failed <member>` line per failure and `suite-runner: summary members=<n> passed=<p> failed=<f> jobs=<N> wall=<seconds>s cpu=<seconds>s`. A row's CPU figure is the member's child CPU time: the user plus system seconds in the resource usage that `os.wait4` returns when the runner reaps the member. That covers the member's own process and every descendant that it, or a descendant in between, waited for, such as the `git` and `python -m agent_tools.…` processes a test runs. A descendant still running when the member exits, or never waited for, is not counted, and a member that failed to launch shows `0.0`. The summary's `cpu=` adds up the members' unrounded figures and never the runner's own CPU, so rounding can make it differ from the sum of the printed rows. A member whose CPU is close to its wall time, or above it when its descendants ran at once, was computing. One far below it was waiting, for I/O, a sleep or a CPU it could not get. Set `cpu=` against `wall=` times the CPUs the run could use, the smaller of `--jobs` and the host's CPUs. Near it, every slot was computing and the CPUs were saturated; well below it, the members were waiting on something else. A module whose CPU grows from a `--jobs 1` run to a parallel one ran on slower, shared CPUs. Exit 0 means every member passed and 1 that one failed. Exit 2 is a usage error, raised before anything starts: a bad `--jobs`, no members, a duplicate, a member that is missing, is not a file or lies outside the working directory, or a suffix other than `.py` or `.sh`. Exit 130 is an interrupt: the runner starts nothing more, prints `suite-runner: interrupted, waiting for running members`, waits for those members and prints no report. A test that shares state with another test process is fixed by giving it its own temporary location, never by a serial-exemption list, a retry or a lock.

## `cache-proxy`

`cache-proxy --port N [--upstream URL] [--keepalive] [--reorder]` (#422) is a loopback pass-through from Claude Code to the Anthropic API: it binds `127.0.0.1` only and, without `--keepalive` or `--reorder`, forwards each request's method, path, query and body bytes and each response's status, headers and body unchanged (only `Host` is rewritten and hop-by-hop headers are dropped; nothing is added, decoded or retried), re-chunks an unsized (streamed) response one upstream read at a time, and holds one keep-alive upstream connection per client connection. `GET /_proxy/health` answers `{"service":"cache-proxy","status":"ok"}` without being forwarded or logged. An upstream that fails before responding gets the client a `502` Anthropic error envelope; one that fails mid-body gets the client connection closed without the terminating chunk. stderr carries one JSON line per request (`method`, `path`, `status`, `upstream_conn`, `ttfb_ms`, `duration_ms`, `bytes`, `outcome`, plus `error` and up to 4 KiB of an upstream error body), never a header value; an exception no request step expected (a client reset on an idle connection) is one `handler_error` line with `error`, never a traceback. `bytes` counts the body bytes written to the client, a reply the proxy makes itself (a `502` or a rejection envelope) included; a `HEAD` reply ends after its headers, so it logs 0. Known limitation: without `--keepalive` the client's `Accept-Encoding` is forwarded verbatim (with it, every request whose outcome is not `untracked` is sent with `Accept-Encoding: identity`, below) and bodies are never decoded, so an upstream 4xx/5xx body that arrives compressed (for example gzip) is logged as `error_body` decoded as UTF-8 with replacement characters, not as readable text; the client still receives it unchanged. The service that runs it and the `claude` wrapper that routes through it are in `home/common/claude-code/README.md`.

`--keepalive` (#423, `agent_tools.cache_keepalive`) keeps a subagent conversation's prompt cache warm while it is idle, by replaying its last request with `max_tokens=1` (the replay is the one fact 2 of `docs/spikes/cache-proxy-spike.md` measured to refresh the 5-minute cache entry). A conversation is a pair of the `X-Claude-Code-Session-Id` and `x-claude-code-agent-id` headers, and each `POST /v1/messages` the proxy is about to forward is sorted into one of seven outcomes. `untracked` (not a messages `POST`, or no session header), `main` (no agent header: the main conversation) and `unparsed` (the body is not a strict JSON object, or arrives with a `Content-Encoding`) are not candidates; `no_tail_mark` (the last message carries no `cache_control`), `ttl_1h` (some mark asks `ttl` `1h`) and `thinking_budget` (`thinking.type` is `enabled`) are subagent requests that are left alone as well; and `tracked` is a subagent request that can be replayed. A `no_tail_mark` request is a *side request* (Claude Code's forks and side queries look like this), and a request with any other outcome but `untracked` is a *thread request*, its conversation's own turn. A side request counts as session activity only while it is in flight: whatever its `stop_reason`, it never clears or sets its conversation's pending tool, ends an idle period, restarts the ceiling, moves the eviction order or supersedes a ping in flight. A `tracked` request whose response starts 2xx becomes its conversation's candidate (a newer one replaces an older one; a candidate is held for at most 64 conversations, and the 65th evicts the one whose last thread request is oldest); a later 2xx `unparsed`, `ttl_1h` or `thinking_budget` request clears it, and `main` and `no_tail_mark` requests leave it as it is. Every request with an outcome other than `untracked` is forwarded with `Accept-Encoding: identity`, and its response chunks are tapped, after they have been written to the client, by an incremental SSE reader that keeps the final `stop_reason`; the bytes the client gets are unchanged. A session counts as active for a candidate when one of its conversations has a request in flight (under 60 minutes old, side requests included), is pending a tool (the 2xx response to its newest thread request completed with `stop_reason` `tool_use`, under 60 minutes ago), or has sent a thread request since the candidate's last touch; pings never count. A conversation's *last reply* is the `stop_reason` the tap read from the 2xx response to its newest thread request once that response completed; it has none while that response streams, or when the response was not 2xx, was cut short or carried no `stop_reason` the tap could read, and a side request never sets or clears it. A tick every 5 s finds each candidate untouched for 270 s (the touch is the upstream send time of its last 2xx `tracked` request or ping). It ends the conversation with `ceiling` when 60 minutes have passed since its last thread request, with `session_idle` when the session is not active, with `end_turn_cap` when its last reply was `end_turn` and its idle period already holds at least two pings (`END_TURN_PINGS`; the pings sent since its last thread request, those sent while that reply streamed included), checked in that order, and otherwise sends the ping. A ping travels on a fresh upstream connection (never a client's) with a 30 s socket timeout and is never retried; its response is read to the end, its usage logged, and the bytes discarded. The whole exchange is also bounded by that 30 s from the ping's send time, checked on the keepalive's clock between reads and enforced by a wall-clock watchdog that shuts the ping connection's socket, so a read still blocked ends too, the response's headers and chunk framing included: once it has passed, the read stops, no usage is parsed, the connection is closed and the `ping` line reads `upstream_error` with `error` `ping exceeded 30.0 s`, so a response that keeps trickling bytes cannot hold a ping, or its conversation's credentials, in flight. Only a 2xx ping whose body was read whole (outcome `complete`) becomes the new touch; any other result (a non-2xx status, an upstream error such as a timeout or a connection failure, a body cut short of its declared length, or the overall bound) ends the conversation with `ping_failed`, and a ping superseded by a newer thread request of its conversation while in flight changes nothing. The ping keeps the candidate's headers, `Accept-Encoding: identity` and a recomputed `Content-Length` included, and its body is the candidate's with `max_tokens` set to `1` and nothing else changed. The candidate's headers, `authorization` among them, are held in process memory only, from its 2xx response start until it is cleared, replaced or ended; they are never logged or written anywhere, and a proxy restart forgets every conversation. A thread request that arrives after at least one ping ends that idle period with `resumed`; the other end reasons are `ceiling`, `session_idle`, `end_turn_cap`, `ping_failed` and `evicted`. With the flag, the `listening` line gains `"keepalive":true`, and each `request` line that reached the keepalive gains `keepalive` (the outcome), and, unless it is `untracked`, `conversation` (12 hex digits of the `telemetry_digest` of the session and agent, never a header value) and the `stop_reason` the tap saw. A request rejected while its body was read (`411`, `400`) and the health path carry none of these. Three events are new: `ping` (`conversation`, `model`, `idle_s`, `status`, `ttfb_ms`, `duration_ms`, `outcome`, `usage` and, on failure, `error` and up to 4 KiB of an error body), `keepalive_end` (`conversation`, `reason`, `pings` and `idle_s`) and `keepalive_error` (`stage` `observe`, `track`, `tick` or `send`, and `error`). A keepalive bug never blocks traffic: an exception from `observe`, a track call, `tick` or `send` is one `keepalive_error` line, the request carries `"keepalive":"untracked"`, and the scheduler keeps running. When `observe` raises, the request is forwarded exactly as it would be without the flag; when a later track call raises, the track is dropped and the request continues untracked, its headers already sent as the track gave them (`Accept-Encoding: identity`); a dropped track is still told its request is done (unless `done` itself raised), so its flight never keeps the session active. Without the flag no keepalive object exists, no thread runs, and every byte sent upstream and every log line is as described above.

`--reorder` (#429, `agent_tools.subagent_prefix`) reorders a Claude Code subagent's first user message so that two subagents of one type share a cached start-up prefix. A `POST` to `/v1/messages` (any query) with a non-empty `x-claude-code-agent-id` is parsed as strict JSON (a duplicate key or `NaN` is `unparsed`); every other request is `not_subagent` and is never parsed, and so is a body whose `system[0]` is not a text block starting `x-anthropic-billing-header:` with `cc_is_subagent=true` among its `;`-separated fields. A request with no assistant message is a first request, and its agent id is registered when it is reordered (in memory, at most 4,096 ids, oldest out first, forgotten on restart); a later request is reordered only when its id is registered, so a forked subagent, which carries its parent's first message, passes as `unregistered`. The reorder needs `messages[0]` to be a user message of text blocks: attachments (text starting `<system-reminder>`), budget lines (whole text `<total_tokens>N tokens left</total_tokens>`, `N` digits or `Infinite`) and exactly one other block, the prompt, which is not first. Only its last block may carry a `cache_control`, and the body's marks (on `tools`, `system`, each message block after its inner content, then a top-level one) number at most four, are objects with a `ttl` of `5m` (the default) or `1h`, and never grow longer in prefix order; anything else is `shape`. The output keeps every block before the prompt and every attachment after it in order, then the prompt, then the budget lines that followed it, and a mark on the original last block moves to the new last block. With fewer than four marks, the block just before the prompt gains `{"type":"ephemeral"}` with the `ttl` of the nearest mark after it, else of the nearest before it, else none (`applied`); with four, nothing is added (`applied_at_cap`). No existing mark is retimed or removed, and the billing header is never changed. A reordered body is re-encoded as compact UTF-8 JSON in its key order, with every `Content-Length` value replaced; every other outcome forwards the client's bytes and headers. The transform runs after the upstream headers are assembled and before the keepalive's observation, so a keepalive candidate and its pings carry the reordered body. With the flag, the `listening` line gains `"reorder":true` and each `request` line that reached the transform gains `reorder`: `applied`, `applied_at_cap`, `not_subagent`, `unregistered`, `unparsed`, `shape` or `error`. A request rejected while its body was read (`411`, `400`) and the health path carry none. An exception from the transform, or an outcome outside that set, forwards the original bytes and headers and is logged at once as a `reorder_error` line with `method`, `path` and `error`. Without the flag no transform object exists, and every byte sent upstream and every log line is as described above. `agent_tools.model_pricing` is the per-model price table that `agent_tools.keepalive_pings` prices pings with, and `python -m agent_tools.keepalive_pings end-turn-cap` is the measurement behind the verify check `keepalive-end-turn-cap` (issue 502).

## adopt-project

`adopt-project plan` asks four kinds of open question: `project-id`, answered by declaring exactly one remote or authoring a contract with the project id, and `candidate-class` (#340), one per tracked or targeted-ignored agent path that no classification row settles (none covers it, or a targeted-ignored one it covers resolves outside the repository or cannot be read), keyed by its `subject` (the path) and carrying the one `value` the question accepts: `archive-history` for a tracked path, which plans a `git mv` to `.agents/knowledge/archive/adopted/<path>`, `retain-product` for an ignored one, and `null`, no answer, for a secret-shaped tracked path, which stays open until a central classification row covers it or it leaves the repository, or for a tracked symlink resolving outside the repository, which stays open until it leaves the repository; `plan --answer QUESTION SUBJECT VALUE` (repeatable, order-independent) settles a `candidate-class` question, refusing the first violation as `adopt.decisions.invalid_answer` (an id other than `candidate-class`, `path-reference`, `reference-policy` or `reference-format`, a subject answered twice, or a value other than the offered one) or `adopt.decisions.unmatched_answer` (a subject that is not an undecided candidate, a path occurrence or a reference policy of this inspection, by the answered id), checking each `candidate-class`, `path-reference` and `reference-policy` answer in `(id, subject, value)` order, then the `reference-format` answers in `(subject, value)` order, and changing nothing on a refusal; the answers enter `decisions.answered` and therefore `plan_id`, and `apply --plan-id` re-applies them from the stored plan (refusing a malformed `decisions.answered` as `adopt.plan.malformed`), so the plan id, not an `apply` flag, authenticates them. The third and fourth kinds, `path-reference` and `reference-policy`, are described below; `--answer` settles them through the same flag, pass and refusals. A fourth answerable id, `reference-format`, opens no question and so is not one of the kinds above: its subject is a file class, its value a command id of the contract, and it is checked after every other answer, so its subject must be the class of a file the other answers edit (`adopt.decisions.unmatched_answer` otherwise) and its value must be a command the contract declares (`adopt.decisions.invalid_answer` otherwise, as for a subject answered twice); the plan document publishes the answer as the `command` of its class's row in `reference_formatting`, which enters `plan_id` as its tenth input.

`adopt-project plan` rewrites relative Markdown link targets across its moves (#345): outbound in every Markdown file a `git-mv` moves, inbound in every other tracked Markdown file (a regular `.md`/`.markdown` blob at the base revision, strict UTF-8, not secret-shaped; a `generated_file` projection target is left to its regeneration). `agent_tools.adopt_links` owns the grammar — inline links and images on one line and reference definitions, outside fenced code, code spans and link titles — and resolves a target against the tracked paths of a tree, never the filesystem: a target is relative unless it is empty, starts with `#` or `/`, carries a URL scheme or holds a backslash, and it resolves when its percent-decoded path, joined to the containing directory, names a tracked file or a directory inside the root. The rewritten bytes come from the plan's base revision, each changed file is a `write-file` at the path the file has after the moves and placed before the projection regenerations, and a rewritten target keeps its anchor or query, title, angle brackets and trailing slash, and its leading `./` unless the new path climbs out with `../`; a bare target is percent-encoded and an angle target encodes only `%`, `#`, `?`, `<`, `>` and line breaks, and gains a leading `./` when its path would otherwise open with a URL scheme (`urn:x.md`), so the emitted path names the same file and stays relative; a link that already fails to resolve, a URL and a link the moves leave correct stay byte-identical. The plan document and the adoption evidence record carry `link_rewrites` (`inbound` and `outbound` link counts and sorted files, `unrewritable` `path`/`target` entries and an `already_broken` count), which is the seventh input of `plan_id`. The ready gate `no-unrewritable-link` (`adopt.link.unrewritable`) keeps the plan `draft` when a link targets a file the plan deletes or a directory that no longer exists after the moves and whose files did not all move, by the same relative tails, under one new directory, and `apply`'s commit gate `no-new-broken-link` (`adopt.gate.no-new-broken-link`), before `cold-clone-resolves`, fails when any Markdown file in the index has more non-resolving relative links, each side counted against its own tree, than its pre-move counterpart at `HEAD` (a file with no counterpart is compared with zero); because the verification commands and a `pre-commit` hook run after it, the same count over the commit against its parent is proved again once the commit exists, and a failure there refuses `adopt.commit.new_broken_link` with the worktree and branch retained. Prose mentions of moved paths, inline HTML and root-relative targets are never rewritten, and a path literal in a non-Markdown file is left to the `path-reference` question.

`adopt-project plan` asks about every path literal in a tracked non-Markdown text file that names something its moves relocate (https://github.com/fagenorn/nix-config/issues/350), and edits nothing without an answer. `agent_tools.adopt_references` scans the base revision's regular, non-Markdown, non-secret blobs that git judges text and that decode as strict UTF-8, found by one `git grep` for the first path segment of each move source (the depth reading described below has a read set of its own), leaving out `.agents/artifacts/`, `.agents/knowledge/archive/` (each tested on the base path, so a file under them is editable only by the adoption that moves it) and the files adoption itself may write (the contract, `.gitignore`, the runtime sentinel, a legacy binding config and a `generated_file` projection target). A token is a run of characters bounded by whitespace or one of `"`, `'`, `` ` ``, `,`, `;`, `:`, `=`, `(`, `)`, `<`, `>`, `|`, `&`, `#`, `!`, read as an optional leading `./` or `/`, a path up to its first glob segment and a tail; it is an occurrence when it contains `/` or is the whole content of a quoted string, and a reading of it (the plain one here, the pattern and variable ones below) gives a path that names a file or directory of the base tree, where a move source is that path or lies under it, so `.claude/` counts when `.claude/specs` moves. A moved file, or a directory whose members all moved by the same relative tails under one new directory, has a single successor; a path that survives or dissolves maps to the successors of its wholly moved subtrees, carried only for an empty, `/` or `/**` tail. An occurrence that no answer decides (its own, or its policy's, below) opens a `path-reference` question unless its policy's question is open; the question is keyed by its `subject`, `<path>:<line>:<column>`, with an `answers` list and no recommended value: `extend`, offered when the token is a quoted element of a bracketed, braced or parenthesised sequence (it follows `[`, `{`, `,`, a `(` that does not open a call, or the start of its line, and ends the line or precedes `,`, `]`, `)` or `}`) or the only content of its line after indentation and an optional `- `, adds one quoted element or one copied line per successor beside the literal; `rewrite`, offered for a single successor, replaces the token; `retain`, always offered, leaves the file as it is. `plan --answer path-reference SUBJECT VALUE` settles one, after any `candidate-class` answers, whose moves the references are derived from; an unknown subject refuses `adopt.decisions.unmatched_answer` and a repeated subject or a value the occurrence does not offer refuses `adopt.decisions.invalid_answer`. An open reference keeps the plan `draft` through `no-open-decisions`; no gate and no `verify` check is added. Each file with an `extend` or `rewrite` answer is one `write-file` after the Markdown link rewrites and before the projection regenerations, in the same commit as the moves, unless another file is left at its `target` (below). The plan document and the adoption evidence record carry `path_references`, one row per occurrence sorted by path, line and column (`subject`, `path`, `line`, `column`, `literal`, `answers`, `answer`, `additions`, `replacement`, `target`, `policy`, `decided_by`; `answer` is the effective answer), which enters `plan_id` as its eighth input, and the record's `decisions_accepted` lists the answers. A variable is never followed to its definition (the one exception is the depth reading's Python names, below), a regular-expression spelling is read only as the pattern reading below describes, a path joined to a variable is read only as the variable reading below describes, and outside the variable reading a joined path is not resolved as a whole (a quoted segment that alone names a path of the tree is still an occurrence), URLs and bare unquoted single words are not recognised, and an unquoted element of a YAML flow sequence that shares its line with other flow-sequence text (a bracket, a comma or another element) is never offered `extend` (one that touches its bracket is no occurrence at all); one alone on its line counts as the only content of its line.

A file the plan moves is read like any other, at its base path, and edited at its destination (https://github.com/fagenorn/nix-config/issues/372). An occurrence's `path` and `subject` stay the base path; its row's `target` is the file's destination, or its own path when the plan does not move it. An edited moved file is one `write-file` at its `target`, after its `git-mv` and in the same commit, with `before` the hash of the base bytes. A path that more than one file of the base tree is left at (two moves onto it, or one move onto a tracked file that stays) gets no such write, whatever the answers: the rows keep their answers, and two moves onto one path keep the plan `draft` through `no-existing-destination`. `apply` treats such a write like any other: it recomputes the plan from the stored answers, applies the operations the plan lists, and then runs the formatting step below over the edited files.

Every occurrence in a moved file belongs to one policy, whose subject is `<tree>:<class>`. The tree is the path of the classification row that moved the file, or the candidate's own path for an `archive-history` answer; the class is the lower-cased text from the last dot of the file name, or `-` for a name with no such suffix (a dotfile included). A file the plan does not move has no policy. The `reference-policy` question has seven members: `id`, `subject`, `answers` (`rewrite` and `retain`, never `extend`), `value`, `basis`, `impact` and `recommendation`. `value` comes from a closed table: `rewrite` for the classes `.py`, `.sh`, `.bash`, `.zsh`, `.nix`, `.yaml`, `.yml`, `.toml`, `.js`, `.mjs`, `.cjs` and `.ts`; `retain` for `.json`, `.jsonl`, `.ndjson`, `.csv`, `.tsv`, `.txt` and `.log`; null for every other class. The recommendation is printed and never applied: nothing is edited without an answer. The class of an occurrence the variable reading made is `<file class>/variable`, so its policy is `<tree>:<class>/variable`: its `reference-policy` question's `value` is null, being outside the table, and a `<tree>:<class>` answer never decides it, so `.claude/notes:.sh` and `.claude/notes:.sh/variable` are two questions and answering one leaves the other open. In a file the plan does not move, a variable-joined occurrence has no policy and opens an ordinary `path-reference` question. Its `path_references` row has the same members as any other, and its `literal` shows the variable. The class of a depth occurrence (https://github.com/fagenorn/nix-config/issues/380, below) is `<file class>/depth`, so its policy is `<tree>:<class>/depth`: its `reference-policy` question's `value` is null, and neither a `<tree>:<class>` nor a `<tree>:<class>/variable` answer ever decides it. A lock file is its own class (`uv.lock` is `.lock`, so `.lock/depth`), and a manifest's policy is never paired with its lock file's.

An occurrence is decided by its own `path-reference` answer; else by its policy's answer when the occurrence offers that value; else by none, so a `rewrite` policy leaves an occurrence that offers no `rewrite` open, and `extend` is never a policy answer. A policy opens its question while it is unanswered and at least one of its occurrences has no answer of its own; during that time its occurrences open no question of their own, though they stay listed in `path_references` and can still be answered one by one. Once the policy is answered, each occurrence still without an effective answer opens a `path-reference` question. The open questions are ordered by id as in `QUESTION_IDS`, the `reference-policy` ones by subject. `plan --answer reference-policy SUBJECT VALUE` is checked after the other two ids: a subject that is the policy of no occurrence of this inspection refuses `adopt.decisions.unmatched_answer`, and a value outside `rewrite` and `retain` or a subject answered twice refuses `adopt.decisions.invalid_answer`. The `reference-format` answers are checked after it (below).

Each `path_references` row carries `target`, `policy` (null for a file the plan does not move) and `decided_by` (`occurrence`, `policy` or null), and the plan document and the adoption evidence record carry `reference_policies`, one row per policy that has an occurrence, sorted by subject, which enters `plan_id` as its ninth input. A row has thirteen members: `subject`, `tree`, `class`, `recommended`, `answer` (the policy's answer or null), `files` (distinct base paths), `occurrences`, `rewritable` (occurrences that offer `rewrite`), `rewritten`, `retained` and `extended` (occurrences decided with that answer, whoever decided it), `open` (occurrences no answer decides) and `overridden` (occurrences their own answer decides). The human view adds one `policy <subject>: ...` line per row after the `references:` line and an `open reference-policy <subject> (answers: ..., recommended: ...): ...` line per open policy. A plan stored before this contract no longer equals its re-derivation, so `apply` refuses it and the operator plans again.

A token that the plain reading does not make an occurrence is read a second time as a regular-expression spelling, only when it starts with `^` or holds `\.` (also `\\.`, as a TOML or JSON string spells it). The reading takes the anchor `^`, one escape for the whole token, an optional `/` prefix, the path decoded segment by segment (the escape replaced by `.`) up to its first empty, glob or backslash-bearing segment, and the rest verbatim as the tail. The forms offered keep the anchor, the escape and the tail, and a carried form exists only for a successor made of letters, digits, `_`, `-`, `.` and `/`. Not read: an end anchor, character classes, groups, alternation and a `./` prefix inside a pattern. The plain reading decides alone whenever it yields an occurrence. The `git grep` prefilter keeps one limit: a file is scanned only when it holds the first path segment of a move source as written, so an escaped first segment with an interior dot (`foo\.bar` for `foo.bar`) is not found.

In a file of a shell class, `.sh`, `.bash` or `.zsh` (the class of the file's base path), a token that neither the plain nor the pattern reading makes an occurrence is read a third time, as a variable-joined path (https://github.com/fagenorn/nix-config/issues/376). The reading takes a prefix `$name/` or `${name}/` at the start of the token, `name` being a letter or `_` and then letters, digits and `_`; the path is the longest leading run of non-empty segments after it that hold neither a glob character nor a `$`, and the rest is the tail. The carried form is the prefix, the successor and the tail, and it must be one token that reads back to the successor; such an occurrence offers `rewrite` (for a single successor with a carried form) and `retain`, never `extend`. Not read: positional and special parameters, parameter expansions, a variable that is not at the start of the token and a second variable before the path. A `$(...)/path` is already a plain root-anchored occurrence, because `(`, `)` and the backtick delimit tokens.

A file the plan moves is read a fourth time, for the relative climbs that leave its moved tree (https://github.com/fagenorn/nix-config/issues/380). The depth reading has its own read set: the moved files that a second `git grep` for `..` and `__file__`, limited to the trees of the moves (each named both as a `:(literal)` pathspec and plainly, so a `GIT_LITERAL_PATHSPECS`, `GIT_GLOB_PATHSPECS`, `GIT_NOGLOB_PATHSPECS` or `GIT_ICASE_PATHSPECS` environment finds the same files), returns, under the filters of the prefilter's files (regular, non-Markdown, non-secret, not excluded, not under a record home, strict UTF-8). A blob both searches return is read once, a file the plan does not move is never read for climbs, and the plain, pattern and variable readings stay limited to the files of the first search. The tree root is the group directory the file moves with, or, for a file the plan archives, the file's own directory; a climb's landing point is the directory it ends at from the file's directory, or the repository root when it climbs past it. A text climb is a token with at least one `/` made of an optional `./`, one or more `..` segments and a rest that is empty or starts with `/`, taken from the file's own directory; a bare `..` and a rest that holds a `..` segment are not read. In a `.py` file the reading also takes Python parent-count chains as climbs with no target text. An anchor is `Path(__file__)` or `pathlib.Path(__file__)`, with at most one `.resolve()` or `.absolute()`, which stands for the file; or a name bound at column 0 by `NAME = <that>` (which stands for the file) or `NAME = <that>.parent` (which stands for its directory), with an optional `: Path` or `: pathlib.Path` annotation and a trailing comment, and bound nowhere else in the file, at any indentation, by assignment, `for`, `as`, `del`, `global`, `nonlocal`, a keyword argument, a mention in a `def` or `lambda` header (a parameter) or a mention in a target list: followed on its line by `,`, `)` or `]` and then by an assignment's `=` that no bracket opened on that line encloses (`NAME, b = …`, `(a, NAME) = …`, `*NAME, b = …`), inside a bracketed run holding no bracket and no `=`, over lines too, directly followed by an assignment's `=`, between a `for` and its `in` (a comprehension's too), or inside a bracketed run after `as`. Headers and target lists are read loosely, so any mention there counts and the name is not followed. A chain is zero or more `.parent` then at most one `.parents[N]`, with `N` a decimal literal, at least one of them and no whitespace, and it climbs one level per `.parent` and `N + 1` for the index, from the file's directory (a chain on the file itself has one level less). Not read: `os.path` calls, `Path.cwd()`, a name chained from another name, a binding inside a function or class, a name bound more than once, a chain continued by `.parent` after its end, a chain with whitespace or a non-literal index, and a chain that overlaps an occurrence another reading made in the file or a text climb the depth reading itself accepted there. A climb is an occurrence when its landing point is a proper ancestor of the tree root, or above the repository root, and the same climb from the destination's directory ends elsewhere. A text climb whose base target (its rest joined to the landing point) is back inside the tree root, which moves with the file, is an occurrence only when its unchanged spelling, taken from the destination's directory, misses the target's successor (the directory the tree root is left at, joined to the target's path below the root), as for `../../research/data.txt` in `.claude/research/tool/config.toml` when `.claude/research` is filed under `.agents/artifacts/specs`; such an occurrence offers `retain` alone. It offers `rewrite`, which shifts the climb's height by the difference between the depths of the destination's and the base directories (the `.parents[N]` index, or the number of `.parent`s, for a chain), only when the landing point is above the repository root or an ancestor of the destination's directory, the base target names no moved path and is not back inside the tree root, and the shifted form is valid (at least one level, and a non-negative index); `retain` is always offered and `extend` never. Climbs in Markdown, which the link rewrites own, and in files the plan does not move are not read.

A tracked `.claude/settings.json` is classified `legacy-native-store` and `retain-product`, so classification opens no `candidate-class` question for it and plans no relocation of it; it appears in the plan's `evidence` and in the record's `sources` with `after` null. The path literals inside it are ordinary occurrences: each may open a `path-reference` question, and an `extend` or `rewrite` answer produces one in-place `write-file` of the settings file.

`plan --answer reference-format <class> <command-id>` declares a formatter for a file class (https://github.com/fagenorn/nix-config/issues/376) and opens no question. The answers are validated after all the others, in `(subject, value)` order: a repeated subject, or a value that is no `bindings.commands` key of the authored contract (always, when there is no contract), refuses `adopt.decisions.invalid_answer`, and a class that no settled answer edits refuses `adopt.decisions.unmatched_answer`. The plan document and the adoption evidence record carry `reference_formatting`, one `{class, command, files}` row, sorted by class, for each class with a file the `path-reference` answers edit, `files` being the edited files' destination paths and `command` the class's answer or null; Markdown link rewrites, the contract, the records and the projections never appear in it. The rows are the tenth input of `plan_id`, so a plan stored before this change no longer equals its re-derivation and `apply` refuses it as stale. The human view prints one `format <class>: <n> files, command <id or none>` line per row. `apply` runs the step once, after every operation has executed and matched its `after` and before the commit gates, so the gates judge the formatted tree: it takes its own `resolve` of the worktree, and for each row with a command runs that command's `argv` followed by the row's files as absolute worktree paths, in row order, at the entry's `cwd`, output captured and no timeout, as a verification command is run, then stages the row's files. A plan with no `reference-format` answer formats nothing and makes no extra `resolve`. The step then proves the formatter stayed on the files it was given: for every other path some operation targets, the last operation naming it still produces its published `after` (a moved file that a later write edits is judged by the write), and for a path whose `after` is a `git-object:` hash, as a move-only destination's is, the bytes on disk must also hash to it as `git add` would store them (a symlink as its link text), so an unstaged edit is caught; every formatted file must remain a regular file and not a symlink. Before any command runs, a file of a row with a command that is the source of a `regenerate-projection` operation for a `generated_file` projection refuses `adopt.format.failed`, naming the file, the two paths compared after `posixpath.normpath` so a source spelled with `./` or a repeated `/` is still matched: the projection was regenerated from the unformatted bytes, and regenerating it again would change a planned `after`. A `managed_import` projection's source may be formatted, since its managed line names only the source's path. A failure refuses `verification_failed` with `adopt.format.failed` (a formatted projection source, the worktree resolves to no command set, the id is no command of it, the command cannot start, exits non-zero, or a file cannot be staged; a command that cannot start is named in the message with its launch error, and one that exits non-zero with its exit status and the last 2000 characters of its stderr) or `adopt.format.unplanned_content` (a confinement check), pointer `/reference_formatting`, with the worktree and branch retained and every commit gate recorded `not_run`. A formatter that changes some other tracked file or leaves an untracked one is refused by the `worktree-status-matches-operations` gate, which this step does not duplicate. A formatted file's `write-file` keeps the hash of the planned, unformatted bytes as its published `after`, and `verify` is unchanged. The command must take file paths as trailing arguments, rewrite them in place, format whole files, and leave no untracked, unignored file.

`adopt-project verify --register` reads one pinned commit of the remote and nothing from the checkout (https://github.com/fagenorn/nix-config/issues/363). It lists `origin` once, fetches its default branch into `refs/remotes/origin/<branch>`, pins and exports that commit and resolves the contract there; a resolving contract that names another branch `origin` lists is the one hop, fetched, pinned, exported and confirmed the same way, and every check then reads the one pinned commit, the fetched objects and those remote-tracking refs being the only repository writes. The default branch's contract stays the authority when it resolves: `--integration-branch NAME` equal to the branch it names (or to the default branch when it names none) changes nothing, and any other operand refuses. The operand takes effect only when that contract does not resolve (it is accepted only with `--register` and at most once, refusing `adopt.verify.integration_branch_without_register` and `adopt.verify.integration_branch_repeated` as `adopt_failure`): the named branch must be listed by `origin`, must not be the default branch, and its own contract must resolve and name it, with no further hop. A run that selects its branch this way carries a `branch_override` object (`branch`, `default_branch` and `reason`, whose one value is `default_contract_unresolved`) in the report and in its registry entry, and in no other run; a later registration of the project that did not need the operand drops it from the entry, another project's registration leaves it, and a repeated operand registration writes the same bytes. The report `schema_version` stays 2 and the registry `schema_version` 1, and no reader decides anything from the member. Every operand that the remote or the branch's contract does not confirm refuses `not_integrated` with `adopt.registration.integration_branch_unresolved`; a pinned commit with no adoption evidence record refuses `not_integrated` with `adopt.registration.not_integrated`, and when the default contract did not resolve and no operand was given its message names `--integration-branch`.

`adopt-project migrate --migration ID [--repo-root R]` executes one manifest `migrations` entry on the checkout in place (https://github.com/fagenorn/nix-config/issues/579). `agent_tools.adopt_migrate.MIGRATIONS` maps an id to a pure executor, and an id the manifest lists without an executor, or an executor the manifest does not list, refuses `adopt.migration.unknown`. The contract's `schema_version` must equal the entry's `from_schema` (`adopt.migration.not_applicable` otherwise, which is also what a second run over a migrated tree gets). `bindings-deploy.retire` returns a deep copy of the contract with `schema_version` 2, no `bindings.deploy`, no `capabilities.deploy` and the platform interval `[max(min_inclusive, 1.2.0), 3.0.0)`, every other member keeping its authored order, and refuses `adopt.migration.deploy_in_use` at the first of `/bindings/deploy/adapter`, `/bindings/deploy/command` and `/capabilities/deploy/support` that keeps the watch alive. Before any write it refuses `adopt.migration.path_outside_checkout` for a touched path that resolves outside the checkout (a symlinked directory included, checked with `adopt_inspection.contained_relative`) `adopt.migration.symlink_target` for a touched file that is itself a symbolic link (the projection writer would replace it with a regular file and the byte restore would not bring the link back), and `adopt.migration.unreadable` for a touched file that exists but cannot be read, since no backup of it could be restored. It then reads the bytes of `.agents/project.json`, `AGENTS.md` and `CLAUDE.md`, writes the contract with the serialiser `apply` uses for an amended authored file, runs the resolver children `write-projections` and `resolve` through `run_resolver`, and prints `{"migration": ID, "written": [...]}` with the sorted repository-relative paths whose bytes changed. Both children run in the resolver of this process's store environment, so a host whose installed manifest does not admit the target schema refuses `adopt.migration.result_invalid`, carrying the child's `error.code` and `repair_id` in `violations[0].message`. This is the one place `adopt-project` rewrites a file it already wrote: on a refusal after the write, every byte is restored (and each file's timestamps), so the tree is as before. Every refusal exits 2 with the adopt error envelope. It never stages, commits or fetches and writes no other file; the operator commits.

## Platform deprecations

A `deprecations` entry of `platform-manifest.json` is closed on exactly `id`, `kind`, `subject`, `since`, `successor` and `migration` (https://github.com/fagenorn/nix-config/issues/580). `id`, `subject`, `successor` and `migration` are non-empty strings and `id` is distinct across entries; `kind` is `project_file` (the `subject` is a repository-relative POSIX path a project may hold: not absolute, no backslash, no empty, `.` or `..` segment), `platform_behavior` (the `subject` names shipped platform behaviour; nothing per project) or `project_schema` (the `subject` is a decimal project schema version: digits only, no sign, no leading zero; anything else is `subject_not_schema_version`); `since` is strict SemVer `MAJOR.MINOR.0` with `MINOR >= 1`, because deprecation begins only in a minor. A violation refuses the manifest as `resolver_failure` with the repair id `platform.manifest.deprecations.<not_array|not_object|member_missing|member_unexpected|not_string|duplicate_id|kind_unknown|since_not_minor|subject_not_relative_path|subject_not_schema_version>`. That each `since` is at most `platform_version` and shares its major is pinned on the committed file by `CommittedManifestTest`, not by the validator. A `removals` entry is closed on the same six members under the same member rules, with the repair ids `platform.manifest.removals.<...>` of the list above, and a removal `id` that is also a deprecation `id` is `platform.manifest.removals.still_deprecated` at `/removals/<n>/id`. A manifest that removes nothing keeps `removals: []`.

`resolve-project platform-status` republishes `platform.deprecations` verbatim and adds `deprecated_uses` to the `project` block and to each `fleet` row: the ascending ids of the `project_file` entries whose `subject` exists under that root by `os.lstat` (a dangling symlink counts) and of the `project_schema` entries whose `subject` equals the `schema_version` of that root's `.agents/project.json` read as JSON, or `null` when the root is not a directory, a subject cannot be inspected, or a `project_schema` entry is declared and the contract file is missing, unreadable or carries a non-integer version (only ENOENT and ENOTDIR mean absent; EACCES or EIO never read as a clean report). It is presence, not git tracking, because the command starts no child process, so an untracked or ignored copy is still reported. It never changes `compatible`, `reason_code`, `repair_id` or the exit code, and `resolve` never reads it. `removed_uses` (`resolve_project.removed_uses`, issue 579 P2) applies exactly those rules to `removals`, in the `project` block and in every fleet row. The report is interface version 3 (`PLATFORM_STATUS_SCHEMA_VERSION`).

`resolve-project platform-status --manifest PATH` (issue 579 P7) judges against the manifest at `PATH` instead of the installed one: it is loaded and validated by the installed loader's rules, `platform.manifest_path` is `PATH` resolved, and a missing or invalid `PATH` refuses `resolver_failure` exactly as a broken installed manifest does. Without the flag nothing changes but the added `removed_uses`. The cutover preflight runs the candidate's own code this way against the candidate's own manifest.

Platform `2.0.0` declares `deprecations: []` and carries the five removals of `1.1.0` and `1.2.0` as `removals`, byte-identical to the entries that main declared (https://github.com/fagenorn/nix-config/issues/579): `legacy-skills-config` (`project_file`, `.claude/skills.config.json`, successor `resolve-project resolve`), `legacy-skills-config-writer` (`platform_behavior`, the `adopt-project` legacy binding config rewrite, successor `resolve-project resolve`), `bindings-deploy` (`project_schema`, subject `1`, successor `release profile activation`), `release-deploy-inspect` (`platform_behavior`, `release deploy inspect`, successor `release profile activation`) and `release-bridge-planning` (`platform_behavior`, the `adopt-project` `release_bridge` legacy deploy planning, successor release profiles in `.agents/project.json`). None of the five has a code path any more: `.claude/skills.config.json` is no longer read or written, project schema 1 is refused as `unsupported_schema`, `release deploy inspect` is no `release` subcommand and `release_bridge` is not a module. The one migration kept is `bindings-deploy.retire`, from schema 1 to 2.

The migration `bindings-deploy.retire`, per project root R:

1. `bindings.deploy.adapter` is `none` and `capabilities.deploy.support` is `unsupported`.
2. `adopt-project migrate --migration bindings-deploy.retire --repo-root R`.
3. Commit `.agents/project.json` and the regenerated projections.
4. `removed_uses` no longer lists `bindings-deploy`.

## Project schema 2

Platform 2.0.0 supports project schema 2 only (`project_schema_versions` is `[2]`, `resolved_schema_version` is 2) and declares the migration `bindings-deploy.retire` from schema 1 to 2 (https://github.com/fagenorn/nix-config/issues/579). Schema 2 is schema 1 without the deploy watch: `bindings.deploy` and `capabilities.deploy` are not members of it, so an authored one is refused like any member outside the schema, and the resolved snapshot has neither. A schema-1 contract is refused `unsupported_schema` with reason `project_schema_unsupported`, and `adopt-project plan` routes it as `migration_required` with the `bindings-deploy.retire` step. The projection header records the contract's own schema, so a schema-2 contract's `AGENTS.md` says `(project schema 2)`. ## Transaction core

`agent_tools.transaction_core` is the transaction core's library surface, with no command-table row, and whose caller is the release driver: slice 1 (#204) holds caller-rooted transaction state under a closed schema and lifecycle, slice 2 (#205) adds fenced custody — a lease authority over concurrency keys in `agent_tools.transaction_custody`, epoch-fenced writes, and evidence and grant admissibility derived from the fence — and slice 3 (#206) adds the administrative protocol — a durable write intent before every external call, inspection before any retry, and an automatic-retry budget — in `agent_tools.transaction_invocation`; slice 4 (#207) then adds an immutable proof plan compiled at creation (`agent_tools.transaction_plan`), core-collected obligations, and one convergence cohort (at most three attempts) that `settle_proof` alone seals into `succeeded` or parks as `proof_rejected` or `proof_did_not_converge`, never rolling back (`agent_tools.transaction_proof`); slice 5 (#208) adds an immutable recovery plan compiled at creation beside the proof plan (`agent_tools.transaction_recovery_plan`), rollback anchors verified in `ready` before publication, `abandoned` only while no action has had an effect, and `begin_recovery`, `settle_recovery` and `roll_forward` as the only ways into `recovering`, into `rolled_back` and to a linked child transaction (`agent_tools.transaction_recovery`); slice 6 (#209) writes a permanent, content-addressed terminal receipt under the store root's `receipts/` and reads it back before the one `state.json` write that enters any terminal, which ends with a `receipt_sealed` event naming it, then re-reads that receipt on every load (`agent_tools.transaction_receipt`), and makes `dispose_failed` the only way into `failed`: it takes a fresh grant and one closed ground, and it yields an `effects_unobservable` qualifier with per-key hazard markers only when a human grant at the transaction's authority class asserts an observability ground (`agent_tools.transaction_disposition`), with the `transaction-state/v6` validator and snapshot fold in `agent_tools.transaction_history`, over the durable-file primitives in `agent_tools.transaction_storage`.

The [#117 attempt-lifecycle decision](../.agents/artifacts/specs/2026-09-20-issue-117-attempt-lifecycle-first-consumer-design.md) selects attempts as the transaction core's first consumer and ship-release second.

The decision governs the planned single-store migration, immutable subject/identity, fenced custody and terminal evidence, and maps the already-delivered agent-slot admission (#150) and delivery contracts, remainders and authorization continuity (#151/#171) onto that core.

The decision is an architecture decision, and its runtime is the code described above: #123 delivered the core, and #125 moved the attempt lifecycle onto it. That lifecycle and the helpers that wrote it are retired (issue 689); the release driver is the core's caller.

## Release profiles

The authored `release` member of `.agents/project.json` is required and has two forms (#124 D1): `"unsupported"`, or `{"profiles": {<profile-id>: <profile>}}` with exactly that member and a non-empty map. A profile's `publication` is `"none"` or `{"actions": [...]}` with at least one action, and a profile with `"publication": "none"` is a publication-free profile (#368 D1, D2): it declares its target, requirements and bindings like any other and passes the same same-repository rule. The grammar holds it to three further rules: its `activation` must be `"none"` (anything else is one `contract.release.invalid` violation, and the activation is then judged no further), its `proof.obligations` must be `[]` (a non-empty list is one `contract.release.invalid` violation and each obligation is still judged), and it can name no recovery unit, because the existing rule that a recovery key names no action or unit reports each entry as `contract.release.reference_unknown` (#368 D11). Two tiers judge a profile. The grammar (`release_profile.grammar_violations`) runs inside `resolve-project resolve`: every violation is `invalid_contract` with a `contract.release.*` repair, and a profile that names an adapter outside the closed registry (`release_adapter.REGISTRY`) or an operation the adapter does not support is a grammar violation, never a lookup fallback (D7). Admissibility (`release_profile.admissibility_findings`, D3) runs over a grammar-valid profile only: it reports every finding of its four rules (`observation_deadline`, `rolled_back_reachable`, `restore_anchor`, `core_plans`) as `{rule, pointer, reason, detail}`, and the same function feeds `capabilities.release`, which is `unsupported` for `"unsupported"`, `blocked` with `release_profile_inadmissible` for the first inadmissible profile, `blocked` with `release_adapter_unavailable` when a bound adapter's declared executable is not on `PATH`, and `available` otherwise (D23); it is also `unsupported` when no profile declares a publication, before any admissibility or executable check, and otherwise that logic runs over all profiles, publication-free ones included (#368 D4). `compile_profile` returns a deep-frozen `ResolvedReleaseProfile` or raises `ProfileInadmissible`, and its `digest` covers the authored profile and the bound adapters' identities only (D5, D23). A publication-free profile compiles to empty graphs, read through `release_profile.phase_nodes`, the one post-grammar reader of a phase's authored nodes. `bind_candidate(compiled, candidate)` takes only a `ResolvedReleaseProfile` and returns the exact inputs of `TransactionStore.create` (`proof`, `recovery`, `concurrency_keys`, `subject`), so the core recompiles what the profile lowered (D5, D20). A profile with a node that consumes the `merge` candidate member (`release_profile.binds_merge`, issue 554 D2) needs the candidate to carry `merge: {pr, base_tip}`, a positive integer and 40 lowercase hex digits. `bind_candidate` binds that member, beside `version` and `commit`, into the subject's `candidate` and into the `candidate` of every unit of the consuming node's adapter alias, and into every `publication_triggered` activation unit too, which watches what publication released (issue 555 D6, amending issue 554 D15 for that mode); a schema-2 contract has neither `bindings.deploy` nor `capabilities.deploy`, so a profile's activation unit is the only deploy watch. Any other profile refuses a candidate that carries it (issue 554 D15). The grammar refuses, as `contract.release.invalid` at its `adapter`, a node of that same registered adapter on another alias, so no `tag` or `release` runs without the `merge` it must target. It refuses a compiled profile with no publication node with `ValueError` naming the profile, before it reads the candidate, so a publication-free profile never reaches `TransactionStore.create` (#368 D3), and `release_adapter.core_binding` over such a profile has no compiled node, so it refuses every request for it (#368 D8).

The resolved snapshot has a fifth member, `release`, derived rather than authored (#368 D5): `{"targets": [...]}`, where `release.targets` is built by `release_profile.release_targets` from the authored `release` member alone, so a profile that fails admissibility is listed all the same. It is `{"targets": []}` for `"unsupported"`. Otherwise it holds one entry per `bindings.targets` handle of every profile, ordered by profile id and then handle: `profile`, `adapter` (the registered adapter the target's alias binds), `target` (the normalized target, with `handle` and `kind`) and `operations` (the sorted, duplicate-free operations the profile's publication actions and activation units run against that handle). Every target of a publication-free profile is listed with an empty `operations` (#368 D6). The other four members of the snapshot are unchanged by it.

`release profile inspect <profile-id> [--repo-root PATH]` (#124 D15, D18) prints one compact sorted-key JSON `ReleaseProfileInspection` and exits 0 whether the profile is admissible or not, because diagnosis never mutates (#69); a publication-free profile is reported with exit 0, empty `publication` and `activation` graphs and an empty `handoffs` list (#368 D7). It is read-only: no adapter is invoked, nothing is written, no network is used, and the only child process is `git rev-parse HEAD` in the project root under a 10-second bound (a failure reports `source_revision: null`). It resolves the project as `resolve-project resolve` does, so a resolver refusal reaches the caller byte for byte with exit 2; `"unsupported"` is `release_unsupported` (repair `release.profile.declare`) and an unknown id is `profile_unknown` (repair `release.profile.unknown`), both exit 2. The report has exactly seven members: `schema_version`, `subject` (project, root, revision and installed platform), `profile` (id, version, digest, target, per-node deadlines, limits, `admissible`), `graphs` (the ordered publication and activation nodes, the handoff, the derived and authored proof obligations and the recovery units), `bindings` (adapter identities with each node's config, targets, principals and credential handles and classes, never credential material), `conformance` (per-adapter operation, predicate and executable support, the three linted checks and every finding) and `repairs` (one per finding, then one per missing executable, all `user_action`). Adapter `invoke` is reachable only through `release transaction run`, which drives the transaction core.

A liveness check on an activated unit is an authored obligation with `semantic: liveness`, `form: snapshot`, `predicate: agent_running` and the `launchd-agent` alias as `collector`, usually depending on `derived:running_subject_identity:<unit>`. Its `parameters.parameters` restates the unit's `action`, `operation`, normalized `target` and `config` (#124 D24); `tests/fixtures/release/argus-shaped-profile.json` is the worked example.

## Release adapters

An adapter is a module with `describe`, `inspect` and `invoke`; `release_adapter.REGISTRY` is the closed mapping of adapter names to modules and `release_adapter.DESCRIPTORS` the descriptors built from it at import, so a malformed descriptor or one whose `name` differs from its registry key fails the import, and an unknown adapter name is a grammar violation (#124 D7, D19). `inspect` returns a closed effect or predicate `Observation` and `invoke` the closed `InvokeResult` `{result, error_class, reference}`: `result` is `accepted`, `rejected` or `unknown`, `error_class` is null exactly when `accepted`, and there is no `succeeded` because only the core's later inspection can say an effect landed (D7; #85, #206). `release_adapter.core_binding(adapter, compiled, alias)` projects an adapter onto the shapes the transaction core accepts: it refuses an implementation whose name or descriptor digest differs from the one the compiled profile pins, refuses any request whose `operation`, `target` or `config` is not exactly a compiled node of its alias (D24), and validates every result it returns, adding no retry or ordering policy.

The forge adapter (`forge_adapter`, D8) carries `pr_merge` (`materialize`, `pointer_cas`, supported since issue 554 D4, `candidate_members` `["merge"]`) and `tag` and `release`, both `index` mode, irreversible and create-if-absent. `inspect` reads with `gh api` and `gh pr view` only, with `GITHUB_TOKEN` and `GH_TOKEN` removed from the child so the keyring credential answers, under one collection budget; it reads a tag from its own ref and object, never from a Release's `target_commitish`. `invoke` applies the steps of spec section 7 in order and stops at the first refusal: request shape (an unsupported operation is `unsupported_operation`, bad parameters `invalid_input`, with no child process), the working checkout (`git rev-parse --show-toplevel`, D23), same repository (`origin` and its one push URL must each be a `github.com` URL in the `git@github.com:`, `https://github.com/` or `ssh://git@github.com/` spelling, and they and `gh api repos/<slug> --jq .full_name` all name `target.repository`), containment of the commit in the target branch (`tag`), the local annotated tag (reused at the same commit, created when absent, refused otherwise; D25), then the rendered command and the guard. A failed read before the mutation is `rejected` with `transient_transport` or `provider_unavailable`, because nothing was mutated. There are three mutation spellings: `git push origin refs/tags/<tag>`, `gh release create <tag> --repo <slug> --verify-tag --title "<title>" --notes-file <file>` and `gh pr merge <pr> --repo <slug> --merge --match-head-commit <commit>`, where `--verify-tag` refuses to create a tag and the notes file is a mode-0600 temporary removed afterwards. Before the one mutation the command text is passed to `claude-bash-lifecycle-guard`, by name on `PATH`, as a `{tool_name, tool_input.command, cwd}` Bash payload; a non-zero exit, timeout or missing guard is `authorization_denied` (D9). The mutation is never retried and the target is never read after it: for `tag` and `release`, `already exists` (git) or `HTTP 422` (gh) is `precondition_failed`, while a failed `pr_merge` is `unknown` (issue 554 D6), a mutation binary that cannot be spawned is `rejected` with `provider_unavailable`, because no child ran and nothing was applied (D23), and a timeout or any other non-zero exit is `unknown` with `transient_transport`, which the core resolves by inspection (D9, D11).

The `pr_merge` operation binds the candidate's `merge` member, `{pr, base_tip}`, beside `version` and `commit`; its expected head is `candidate.commit`, so `candidate` is exactly `{version, commit, merge}` for it, while `tag` and `release` take `{version, commit}` or the same with `merge` (issue 554 D4). After the same-repository step `invoke` makes four precondition reads, and a miss in any of them is `rejected` with `precondition_failed` before the guard and the merge (issue 554 D6, D13): the protection floor on `target.branch`, which needs a 200 answer with `strict` true, non-empty required contexts and enforced admins, else `protection_floor_unmet: <member>` naming the first of `unprotected`, `inaccessible`, `strict`, `required_contexts` and `enforce_admins`; the repository's `delete_branch_on_merge`, which must print `false`, else `head_auto_delete_on`; the pull request, which must be `OPEN` on `target.branch` at `candidate.commit`, else `pr_not_open: <STATE>`, `pr_base_mismatch: <base>` or `pr_head_mismatch: <oid>`; and the base tip, which must equal `merge.base_tip`, else `base_moved: <tip>`. A read that fails is `rejected` with `transient_transport` on a timeout and `provider_unavailable` otherwise. The rendered spelling is `gh pr merge <pr> --repo <slug> --merge --match-head-commit <commit>`, and it never renders `--admin`, `--auto`, `--delete-branch`, `--squash`, `--rebase` or a subject (issue 554 D5, D17). Exit 0 is `accepted` with the pull request URL as its reference; a timeout or any non-zero exit is `unknown` with `transient_transport`, whatever stderr says, and the core settles it by inspection. `inspect` reads what it read before, adds `strict` to `facts.protection`, and is `satisfied` only when the merge commit's parents are exactly `[merge.base_tip, candidate.commit]` (issue 554 D7). With `candidate.merge`, `tag` and `release` judge an existing tag against the release PR's merge commit, whose parents must be exactly `[base_tip, commit]`, else `tag_target_mismatch`; `tag` invoke refuses `release PR not merged as bound`, then checks that merge commit's containment, fetches `refs/heads/<branch>` and tags it, while without `merge` both are unchanged (issue 554 D8, D17).

The GitHub Actions deploy-watch adapter (`actions_health_adapter`, issue 465 D2) is registered as `github-actions-health` at contract version 1.1.0. Its one operation, `deploy`, is a supported, watch-only `publication_triggered` activation unit a release profile can bind (issue 555 D3): `invoke` refuses every request with `unsupported_operation` (reference `deploy: watch_only`) and no child process, and it answers the `running_subject_identity` predicate. Its closed config is `workflow`, `branch`, `services`, `health_url` and `health_commit_field`, all required; `services` is the `string_list` config type, a non-empty list of unique non-empty strings. The target is a `github_repository` of `kind`, `repository` and `branch` with one optional `handle`, the name the compiled profile carries and `CoreBinding` forwards; a `handle` that is not a non-empty string is `parameters_invalid`. The candidate is exactly `{commit}`, `{version, commit}` or `{version, commit, merge}`, where `merge` is `{pr, base_tip}`. The released commit is `candidate.commit`, or, with a `merge`, the merge commit of that release PR (issue 555 D6): `gh pr view <pr> --json state,baseRefName,mergeCommit`, then for `MERGED` one `gh api repos/<slug>/git/commits/<oid>`, all under the one budget. `OPEN` is `absent` (`release_unmerged`); `CLOSED`, another base branch or parents other than `[merge.base_tip, candidate.commit]` is `diverged` (`release_merge_mismatch`); any other state or a malformed `mergeCommit` or parents list is `unknown` (`payload_invalid`); and a failed read is `unknown` with the run-list read statuses. An unresolved merge reads neither the run list nor the health URL. Every effect observation's `facts.released` is the released commit, or `None` when unresolved. `running_subject_identity` makes no run-list read: it reads the merge (when bound) and one health URL, and is `satisfied` (`running`) when the health commit names the released commit, `unsatisfied` (`subject_mismatch`) when it does not, and otherwise `unknown` (`identity_unobservable`); every non-`satisfied` answer for that predicate, including a malformed request, stays in `DERIVED_REASONS["running_subject_identity"]`, and any other predicate name is `unknown` (`predicate_unsupported`). `release_adapter.watch_operation(descriptor)` names a descriptor's single inspectable `publication_triggered` operation, or returns `None` when there is none or more than one. `inspect` answers `parameters_invalid` unless the request carries a target and candidate of the shapes above, with a 40-lowercase-hex candidate `commit`, a `vMAJOR.MINOR.PATCH` `version` when present, and a config of exactly the five members, whose `string` members are non-empty and free of control characters, whose `services` is a non-empty list of unique non-empty strings, whose `branch` equals the target's, and whose `health_url` parses with `urllib.parse.urlsplit` and is `http` or `https` with a host. It then makes at most two reads under one 30-second budget. The first is `gh run list --repo <repository> --workflow <workflow> --branch <branch> --limit 5 --json databaseId,status,conclusion,headSha,headBranch,createdAt`, run by name with the caller's environment unchanged: the adapter strips no variable, and the release driver applies `bindings.tracker.credential_env` (D10). The second, made only when the newest run at the candidate on that branch is completed, is one `GET <health_url>` that follows no redirect, reads at most 65,536 bytes and loads the body strictly through the `canonical` hooks (D8). Runs are ordered newest first by `createdAt`, which must be an ISO 8601 time with an offset (D14), and a commit matches when it is 7 to 40 hex characters and the candidate starts with it, case-insensitively (D7). The outcome follows the spec's classification table (D6): `absent` (`run_absent`); `in_progress` (`run_in_progress`); `satisfied` (`deployed`) only for a `success` run whose health commit matches; `diverged` (`superseded`) for a completed, unsatisfied run that a run at another commit followed; otherwise `diverged` (`health_commit_mismatch`, `silent_rollback` or `run_failed`) or `unknown` (`health_unreachable` or `health_payload_invalid`). A failed run-list read is `unknown`, with `facts.detail` bounded to 240 characters: `lookup_failed` carries the stderr of a non-zero exit, or `gh could not be started: <error>` when the operating system refuses the argument list; `lookup_timeout` carries an empty detail; `executable_missing` carries the operating-system error; and `payload_invalid` carries the stderr when stdout is not JSON, or the first shape violation (for example `run 0 headSha is not 40 hex characters`) when the JSON is not the closed run-list shape. Every effect observation's `facts` hold `runs` (each `{id, status, commit, branch, createdAt}`, newest first), `run`, `health`, the configured `services` and `released`. `tests/actions_world.py` is its fake `gh`, which logs token visibility, and loopback HTTP server.

The Railway deploy-watch adapter (`railway_deploy_adapter`, issue 582) is registered as `railway-deploy` at contract version 1.0.0, a second watch-only adapter beside `github-actions-health`. Its one operation, `deploy`, is a supported `publication_triggered` activation unit; `invoke` refuses every request with `unsupported_operation` (reference `deploy: watch_only`) and no child process, and it answers the `running_subject_identity` predicate. Its target is a `github_repository` (`kind`, `repository`, `branch`, plus the compiled `handle`), so the released commit resolves through `release_merge` exactly as above (issue 555 D6), and its closed config is `project`, `environment` and `services` (a non-empty `string_list`), all required. Its executables are `gh` and `railway`. Under one 30-second budget and the caller's environment, `inspect` runs `railway status --json` first, whose linked project `name` must equal `config.project` and which must list an environment named `config.environment` (else `unknown`, `project_mismatch`), then `railway deployment list --service <s> --environment <env> --json` once per service in config order. Each service is classified newest first by `createdAt`, then `id`, in this order: no deployment at the released commit on the target branch is `absent` (`deployment_absent`); a serving (`SUCCESS` or `SLEEPING`) deployment newer than the matched one is `diverged` (`superseded`), before the matched status is read; `QUEUED`, `WAITING`, `INITIALIZING`, `BUILDING`, `DEPLOYING` or `NEEDS_APPROVAL` is `in_progress` (`deployment_in_progress`); `SUCCESS` or `SLEEPING` is `satisfied` (`deployed`); `SKIPPED` is `satisfied` (`skipped`) only when the commit's GitHub check runs are all green and the serving deployment is the immediately older row at the released commit's first parent, otherwise `unknown` (`skip_unexplained`) or, after a failed check, `diverged` (`skipped_after_ci_failure`); `FAILED` or `CRASHED` is `diverged` (`silent_rollback` with an older serving deployment, else `deployment_failed`); `REMOVED` or `REMOVING` is `diverged` (`removed`); any other status is `unknown` (`status_unrecognized`). The services aggregate with the precedence `diverged`, `unknown`, `in_progress`, `absent`, `satisfied`, and the reason is the first service's, in config order, at the winning outcome. `running_subject_identity` is `satisfied` (`running`) when every service is deployed or a benign skip, `unknown` (`identity_unobservable`) when any service is unobservable, and otherwise `unsatisfied` (`subject_mismatch`). The driver waits on `in_progress` and `absent` within the unit's `observation_deadline_ms` and parks `attention_required` past it, so an absent deployment is never a success. `tests/railway_world.py` is its fake `gh` and `railway`.

The codesigned-artifact adapter (`codesigned_artifact_adapter`, issue 547) is registered as `codesigned-artifact`. Its one operation, `install`, is `materialize`, `in_place` and `supported`, with both non-spend effect classes and no recovery operation. It answers `publication_visible` and not `running_subject_identity`. The `installed_bundle` target carries a `~/`-relative `path`, and the closed config is `source`, `identity_prefix`, `identity_env` and `adhoc_fallback`. `invoke` signs with the hash of the `identity_env` value when set, else of the first listed identity starting with `identity_prefix`, else ad hoc only when `adhoc_fallback` is true; an env value that matches nothing never falls back. It refuses uid 0, refuses an install path with an existing component between `$HOME` and its parent that is a symlink or not a directory before any write, which `inspect` reports `diverged`/`target_unexpected` (issue 547 D26), and stages and signs a copy in `.<name>.release-staging` before renaming it onto the install path (issue 547 D20). A failure before the first rename is `rejected` and leaves the install path as it was, and a rename that fails after the old bundle moved is `unknown` (issue 547 D15). It stamps `AgentReleaseVersion` and `AgentReleaseCommit` into the staged `Contents/Info.plist`, and `inspect` classifies by the issue 547 spec's table. It never builds: it installs what the checkout holds when HEAD is the candidate and no tracked file changed, and cannot prove the bundle was built from that commit (issue 547 D9). `tests/host_world.py` fakes `security` and `codesign` behind a fake-only `PATH`.

The launchd-agent adapter (`launchd_agent_adapter`, issue 547) is registered as `launchd-agent`. Its one operation, `activate`, is `local_apply`, `in_place` and `supported`, with both non-spend effect classes, and it answers `agent_running` and `running_subject_identity`. The `launchd_gui_agent` target carries a `label` matching `[A-Za-z0-9][A-Za-z0-9._-]{0,127}`; the domain is always `gui/<uid>` and the plist always `~/Library/LaunchAgents/<label>.plist`, so a profile cannot name another, and uid 0 is refused. ## Release driver

`release transaction status|preview|run|abandon` (`release_driver`, #128 D3) drives one release of a project through the transaction core. Each verb takes `[--profile P] [--repo-root R]`; `preview` and `run` also take `[--commit C --version V --title T --notes-file F]`, and `run` takes `--confirm TOKEN` once per token. The four candidate flags are all absent (no candidate) or all present: some absent refuses `candidate_required` naming them, and a notes file that cannot be read as UTF-8 refuses `candidate_invalid`. The candidate is `{version, commit, title, notes}`; for a profile that consumes `merge`, the driver adds `merge: {pr, base_tip}`, which it observes itself (issue 554 D3).

**Entry and gates (spec §1; D1, D13, D15, D19, D26).** The command resolves the project as `resolve-project resolve --require release` does, so a resolver refusal reaches the caller byte for byte with exit 2 (divergence 4). Then `--repo-root` must be a main checkout, read from the filesystem with no git child: its `.git` is a real directory, which is the common dir, else `not_main_checkout`. `run` and `abandon` also refuse `cwd_mismatch` unless the nearest ancestor of the working directory holding a `.git` entry is `--repo-root`. Selection picks `--profile` when given (an unknown id is `profile_unknown`), else the sole profile whose `publication` is not `"none"`, else refuses `profile_ambiguous` listing the ids, or `profile_unknown` when none publishes; a profile the compiler refuses is `profile_inadmissible`. `preview` and `run` then refuse the first shape problem, and `status` reports it in its `shape` member instead: `merge_not_declared` (integration and default branches differ and no `materialize` action merges them; repair `release.profile.merge_unsupported`) and `anchors_unsupported` (a `restorable` recovery unit; repair `release.profile.anchor_unbound`).

**Store and reservation (§2; D4, D16).** The store is a `TransactionStore` at `<git common dir>/agent-release/store`; only `run` creates it, and it and its parent `agent-release` are mode `0700`. A transaction's creation key is `release/v1:<project id>:<profile id>:<n>`, `n` from 1; the current release is the last key found by probing `lookup` for `n = 1, 2, ...`, and the probe stops at the first key that is not indexed or whose transaction has no `state.json` (a create that died before writing it), so that key is created again. A new release takes `n + 1` only when the current one is terminal, and refuses `version_reserved` when any earlier transaction not `abandoned` holds the candidate's version (an `abandoned` one never published it). While one is nonterminal the verbs work on it: a candidate is refused `release_in_flight`, a release created under another profile digest than the current compiled profile's refuses `profile_drift` (restore that profile or abandon the release), and `preview` shows mode `resume`. The store is host-local; a concurrent `run` that loses on creation or custody refuses `release_busy`.

**Verification (§3; D5, D22).** For a profile that consumes `merge`, `release_verification.observe_merge` first reads the one open PR from `<owner>:<integration>` into the default branch, the default branch's tip and `compare/<base_tip>...<commit>`, under its own 30-second budget. It refuses `release_pr_missing`, `release_pr_stale`, `release_pr_behind` or `verification_unavailable`, and `preview` then reads no receipt and shows `verification` null (issue 554 D3). In mode `new`, `release_verification.observe` makes the three `gh api` reads its docstring lists under one 30-second budget with `GITHUB_TOKEN` and `GH_TOKEN` removed from the child, and returns a `release-verification/v1` receipt. `candidate_stale` and `verification_unavailable` come from the reads, `verification_failed` and `verification_pending` from the receipt's `result`. Before `create`, `run` raises each as a refusal, so a red or unfinished CI reserves no version; `preview` carries it in its own document (D18). Once the transaction exists, `run` records the receipt as one `event` evidence entry, `verification:<digest>`, before the transaction advances to `ready`. A resumed release re-observes its stored candidate and parks `attention_required` unless that passes.

**Preview, `plan_digest` and tokens (§4; D6, D17, D18).** `preview` creates nothing and calls no adapter; its only provider calls are the verification reads and, for a profile that consumes `merge`, the merge reads, in mode `new`. It prints `{schema_version, mode, profile, plan_digest, candidate, verification, actions, confirmations, runnable, refusal}`, each `actions` entry carrying `phase` (`publication` or `activation`; the digest still selects only `name, operation, mode, effect, target`), where `candidate` is `{version, commit, title, merge}` and `merge` is null without one and exits 0 when `runnable`, else 3 with the reason in `refusal`. `plan_digest` is `telemetry_digest` of the profile digest, the next ordinal, the candidate (notes as their digest, and its `merge`), the verification result with its per-context conclusions and the ordered actions in mode `new`, and of the transaction id and the proof plan digest in mode `resume`. One confirmation is listed per `irreversible` action not last seen `satisfied`, with token `<action>:<first 12 hex of telemetry_digest([plan_digest, action, next attempt, next acquisition ordinal])>`, so a retry, a re-acquisition or a changed input yields a new token and an unchanged one prints the same.

**Run (§5; D6, D7, D14, D20, D21).** `run` re-derives the plan as `preview` does and writes nothing until it passes: a refused plan raises its refusal, a token outside the recomputed set refuses `confirmation_stale`, and a missing one `confirmation_required` (all-or-nothing). It then creates the transaction (mode `new`), acquires custody as executor `release-driver` with a 900000 ms TTL and issues one grant per token (`release-irreversible`, actor `operator`, kind `human`) and, when the plan has a non-irreversible action, `release-scope:<acquisition ordinal>` (`release-scope`). It renews custody before each phase and each action, so a lapsed lease refuses and propagates. A `attention_required` release first advances back to `parked_from`. It drives `awaiting_verification`, `ready`, `publishing`, `published`, then `activating` or, with no activation, records the `activation-not-applicable` evidence entry (divergence 1) and goes to `proving`, where it collects every required obligation and every optional one whose collector supports its predicate (an optional unsupported one is never collected), starts one cohort, collects its members and settles. Each action is inspected, an `irreversible` one is invoked only under a valid grant for its token of this attempt, and one `InvocationRefused` or an `absent` or `diverged` result parks `attention_required`. After an invoke whose result was not `accepted`, the park reason is `<name>: <status> after <result> <error_class>: <reference>`, read from the action's latest `invocation_returned` event, so `status` shows, for example, `protection_floor_unmet: enforce_admins` (issue 554 D12). An activation unit of mode `publication_triggered` (a deploy watch, issue 555 D4, D5) is inspected and never invoked: `satisfied` goes on to proving; `absent`, `in_progress` or `unknown` is `wait` while now minus the first `action_declared` stamp is at most the node's `observation_deadline_ms`, and past it parks `<name>: <status> past <deadline> ms: <reference>`; `diverged` parks `<name>: diverged: <reference>`, `<reference>` being the latest inspection's reason and references (an `absent` one names no run). The result is `{schema_version, transaction_id, state, next, actions, receipt_digest}`, `actions` being `{name, status, attempts}`, with `next` one of `done` (terminal `succeeded`), `confirm` (an irreversible action has no valid grant), `wait` (an action is `in_progress` or `unknown`, or a watch is pending inside its deadline, or the proof cohort is still open) or `attention` (parked). Exit is 0 for any recorded progress. Custody is released on every normal return of `run` that does not end terminal and never in a `finally`, so a raised effect leaves it to lapse at its TTL (D21). Every adapter is reached through one router over per-alias `core_binding`s, so tests enter fixture adapters only as `registry` entries.

**Abandon (§5; D14).** `abandon` acquires custody and advances the current nonterminal release to `abandoned` with external state `known`, printing `{schema_version, transaction_id, state}`. With no nonterminal release it refuses `no_release`, and it refuses `abandon_refused` when the core does, which it does once any action had an effect. It releases custody on that refusal.

**Status (§7; D3, D25).** `status` reads only and prints `{schema_version, profile, shape, legacy, release}`; `release` is null with no transaction and otherwise `{transaction_id, ordinal, state, parked_from, reason, version, commit, actions, grants, evidence_ids, terminal, receipt, hazard_markers}`. `reason` is the latest transition's reason when the state is `attention_required`, an `actions` entry is `{name, phase, operation, effect, status, attempts, reference}`, a grant is `{grant_id, authority_class, valid}`, and `terminal` and `receipt` are the core's views, null until terminal.

**Refusals (D18).** A driver refusal prints `{"error": {"code", "repair_id", "detail"}}` (`repair_id` null where none is named) and exits 3; a resolver refusal is untouched with exit 2, and any other failure keeps the `release` command's `resolver_failure` envelope.

**Legacy state (§6; D8).** `agent_tools.release_cutover.classify` reads `.superpowers/workflows/ship-release/state.json` without following a symlink and imports no field. It is `absent` when the file is missing; `unreadable` when it is a symlink or not a regular file, larger than 65536 bytes, not valid UTF-8 JSON (duplicate keys and non-finite constants included), not an object, or its keys are not exactly `headSha`, `pr`, `prUrl`, `mergeSha`, `tag`, `releaseUrl`, `deployState`, or a field has another type than the previous schema's (`headSha` and `deployState` strings, `pr` null or an integer, the other four null or strings); `completed` when `releaseUrl` is set, or `tag` is set with `pr` null, and `deployState` is `done` or `none`; and `in_flight` otherwise. `preview` and `run` refuse `legacy_release_in_flight` (repair `release.legacy.finish`) for `in_flight` and `unreadable`, before any shape gate; the detail names the class and path, and removing such a file is the user's decision, never the driver's. `status` reports the `{class, path}` dict as its `legacy` member and never refuses; `abandon` is not gated. In mode `new` only, `run` calls `retire` after the confirmation checks and the store is made, immediately before `create`, which unlinks a `completed` file (any other class raises `ValueError`), and its document gains `legacy: "deleted"`; otherwise `legacy` is null. A resumed `run` never retires, and nothing from the file reaches the store.

## guard-policy

`guard-policy compile --base <path> --output <path>` compiles the lifecycle guard's policy from the fleet registry (issue 126). It reads the base policy, the registry (`agent_platform.read_registry`, an absent one being the empty fleet) and each registered project's contract on its registered branch of `origin`, through `adopt_verify.remote_source` with the resolver run in process (issue 126 D13); it never reads the checkout's working tree, index or local branches. It reads each branch at the commit `origin` lists for it, through `adopt_verify.SourceReader`: `adopt_inspection.pin_listed` fetches the branch only when the checkout lacks that commit, and `contract_export.export_contract` exports the contract and its projection files (`resolve_project.projection_paths`) sparsely, with no tree inventory. Its only repository writes are the remote-tracking refs of the branches it fetched and the fetched objects. The base policy must be an object with exactly the five trusted members `authorized_owners`, `integration_bases`, `git_bin`, `gh_bin` and `jq_bin`, where the owners and branches are non-empty strings and the three tools are absolute paths; anything else, an unreadable file included, is the cause `base_invalid`.

A project earns a derived row only when twelve steps all hold in this run and the guard can load the row, and the first of those to fail names the reason code of its refusal. `derive` runs steps 1 to 10: the registered root is a git repository (`root_unavailable`); `origin`'s fetch url and its single push url name one `github.com` slug, spelt as `github_remote.github_slug` reads it and never case-folded (`origin_unproven`, issue 126 D9); `origin` yields a default branch and the contract's branch (`branch_unresolved` for `adopt.registration.remote_default_unknown` and `adopt.registration.integration_branch_unresolved`, `fetch_failed` for every other `AdoptError`); the resolver accepts that contract (`contract_unresolved`, with its repair id in the detail). `target_profiles` runs steps 5 to 8 on the resolved snapshot: the contract's project id is the registered one (`identity_mismatch`), its tracker is the `github` repository named by the slug (`tracker_mismatch`), it has a `github_repository` release target (`no_forge_target`), and every such target names the slug and the default branch (`target_mismatch`); each selected profile then compiles through `release_profile.compile_profile` (`profile_inadmissible`). Step 9 requires the contract's integration and default branches to be the branch read and `origin`'s default (`branch_mismatch`), and step 10 that `gh api repos/<slug> --jq .full_name` answers the slug (`provider_unproven`). `compile_policy` runs steps 11 and 12 over the projects that passed: a slug derived by more than one is `duplicate_repository` for each, and a slug that is also a key of the base `integration_bases` is `literal_conflict`: that project gets no row and the literal row stays in the base policy (issue 377 D5). A project that passed all twelve is then refused `name_unsupported` when `unsupported_name` finds its slug or either of its branches outside the shapes the guard's `load_compiled_policy` demands of a derived row: git and the contract grammar take a branch such as `dev+ci`, and the guard drops the whole compiled policy over one such row, which removes every derived row and blocks nothing the base policy allows (issue 377 D4). The guard is a standalone file the package cannot import, so `guard_policy` restates its two shapes as `GUARD_SLUG` and `GUARD_REF_NAME`, and a guard-suite test holds them to the built guard by loading a policy compiled from a fleet that has such a branch.

A row is `{default_branch, integration_branch, required_checks, evidence}`. `required_checks` is the contract's `bindings.vcs.merge.required_checks` (below), read from the resolved snapshot of the pinned contract as the two branches are, sorted, or `[]` when the contract declares none; the guard's loader accepts exactly the entries the resolver accepts, so `unsupported_name` does not check them. The evidence is identity only (issue 126 D11): the project id, the digest of the registry entry (`canonical.telemetry_digest`), the pinned `ref` and `commit`, the contract's blob id at that commit, the provider's `full_name` and each compiled profile's `id`, `version` and `digest`. No resolved snapshot and no contract body is persisted. The written document has exactly two members, the rows under `derived_repositories` and `derivation`: `{schema_version, platform_version, registry_digest}`, where `schema_version` is 3 and the digest is `null` when no registry file exists. The lifecycle guard reads its trusted members (`authorized_owners`, `integration_bases` and the three tools) from the base policy only and takes nothing but a row's two branches and its required checks from this file.

The three outcomes are the exit statuses. Exit 0 (`complete`) means every entry derived and the file was written. Exit 1 (`written_with_refusals`) means the file was written without the rows of the refused projects, one stderr line each; when every registered project was refused and the file already held a derived row, the outcome is `kept_previous` instead and the file is left byte-identical (issue 470: a shell that cannot reach the forge refuses every project, and the guard re-derives a row before it trusts it anyway). Any argument after the fixed ones reaches `compile`, so `claude-guard-policy --help` prints usage and writes nothing. Exit 2 (`refused`) means no policy could be compiled, so the previous file is removed whatever it held: a missing file or a parent that is not a directory counts as removed, and any other failure to remove it is appended to the cause's detail without replacing the cause. The cause is one of `base_invalid`, `registry_invalid`, `platform_unavailable`, `output_unwritable` (issue 126 D14) or `internal`, which carries the exception's type and message. The write is atomic (`agent_platform.write_atomically`), so a reader sees the old file or the new one. The stdout report is one line of sorted-key JSON: `schema_version`, `outcome`, `derived` (the sorted slugs), `refused` (`project_id`, `root`, `reason_code` and a `detail` cut to 240 characters) and `cause` (`null` or `{reason_code, detail}`).

`guard-policy derive --repository <slug>` re-derives one repository's row (issue 377). It reads the registry, runs steps 1 and 2 for every entry and steps 3 to 10 only for the entries whose `origin` names the slug, so an entry naming another repository is never fetched and never asks the provider; then it runs step 11 and the name check among those entries. It prints one line of JSON with the keys `schema_version` (2), `repository` (the argument), `outcome`, `row`, `refused` and `cause`. The outcomes are `derived` (exit 0, `row` is the row `compile` would write), `refused` (exit 1, no row; `refused` lists the entries that name the slug and have none, and is empty when no entry names it) and `unavailable` (exit 2, `cause` is `{reason_code, detail}` with `registry_invalid`, `platform_unavailable` or `internal`). It reads each branch the same way `compile` does (the listed commit, fetched only when absent, and the sparse `contract_export` of the contract and its projection files), so it writes no file beyond the fetched objects and the remote-tracking refs of the branches fetched, reads no base policy and never reports `literal_conflict`. The lifecycle guard runs it as its row check.

Every child of the identity steps, the two `git remote get-url` reads and the `gh api` read, runs by name with `cwd` at the registered root, stdin at `/dev/null`, `GIT_TERMINAL_PROMPT=0`, `GH_PROMPT_DISABLED=1`, a 30-second timeout and `GITHUB_TOKEN` and `GH_TOKEN` removed, so `gh` answers with the keyring credential (issue 126 D7); the fetch and the listing are bounded at the same 30 seconds. A timeout or a missing executable is a failed read. A failed read puts its reason in the refusal's detail (`timed out`, the executable error, or `exit <n>` with the child's stderr), and a `gh` answer other than the slug puts the name it gave. `tests/test_guard_policy.py` drives the commands as `python -m agent_tools.guard_policy compile` and `derive` over `tests/guard_policy_world.py`, and calls two functions directly for the checks no command input reaches: `target_profiles` on a hand-built snapshot for the one step the release grammar hides (issue 126 D10, D15), and `unsupported_name` on a hand-built row for the slug, because `github_remote.github_slug` already reads no slug the guard would refuse.

`bindings.vcs.merge.required_checks` (issue 552) is an optional `resolve-project` member beside `strategy` and `delete_branch`; absent or `null` means the project declares no required checks, and the resolver never inserts it, so the project schema version stays 1. A present value is a non-empty list of distinct non-empty strings, each the exact name GitHub shows for a check (a check run's `name` or a commit status's `context`), with no character restricted. A value that is not a list is `contract.vcs.not_list`, an empty list `contract.vcs.empty_required_checks`, an entry that is not a non-empty string `contract.vcs.not_string` at that entry's pointer, and a repeated entry `contract.vcs.duplicate_required_check` at its second occurrence's pointer. The snapshot passes the member through unchanged.

## fallback-audit

`fallback-audit` (issue 579 P8) holds the two checks #130 runs after activation. `ladders [--repo-root R] [--manifest PATH]` reads the tracked files under `ENTRY_PATHSPECS` (`git ls-files`, so untracked files, `.agents/artifacts/**`, `**/tests/**`, `**/evals/**` and the module itself are never scanned) and reports each `(path, line, marker_id)` hit of an `INVENTORY_MARKERS` literal or of a removal subject of kind `project_file` or `platform_behavior` in the manifest (`--manifest`, else the repository's committed `platform-manifest.json`). `NON_LADDER_SITES` is the closed exemption table, and it belongs to nix-config: it applies only when the root's `.agents/project.json` declares `project.id` `fagenorn/nix-config` (`NON_LADDER_PROJECT_ID`, read through `resolve_project.declared_facts`), so another project's audit has no exemption rows and no `stale_exemption` finding, and a root whose contract is missing or unreadable has none either (#763). A row `(path, marker_id, reason)` moves every hit of exactly that marker in exactly that path to `exempt`, and a row with no hit is itself a finding, `stale_exemption:<marker_id>`, and a tracked entry file that cannot be read is a finding `unreadable_input` (never exempt), because a scan that skipped a file proves nothing. A row needs a reason that says why the hit is not a route; rewording code to dodge a literal is never a fix. It then runs the fail-closed probe, `resolve-project resolve` on a fresh git repository, which must exit 2 with an `error.code` in `resolve_project.ERROR_CODES`. It prints one JSON line `{findings, exempt, probe, clean}` and exits 0 when clean, 1 when not.

`traces --since T [--claude-root P] [--codex-root P]` (T is RFC 3339 with an offset) reads its own transcripts: every `*.jsonl` under each root recursively (subagent transcripts and Codex's dated rollouts included), skipping a file whose mtime is before T. Each line must parse to an object, and a call record with a missing or unparseable `timestamp` is not dropped silently; both add to `skipped_lines`. A call is a Claude `Bash` `tool_use`, or a Codex `function_call` of a shell tool, an `exec` `custom_tool_call` or a `local_shell_call`; usage is never read. Each call after T whose text holds the literal of `release-deploy-inspect`, `resolve-bindings` or `legacy-skills-config` is an execution carrying its first 200 characters, so the owner can discount a mere search for the literal. Exit 0 with none, 1 with any, 2 on usage or an unopenable file.

## agent-run-profile

`agent-run-profile` (`just agent-run-profile`; source entry `python -m agent_tools.run_profile`) profiles Workflow run directories (`journal.jsonl`, `agent-<id>.jsonl`, `agent-<id>.meta.json`) given as arguments, printing phase totals, the costliest agents, label families and a per-issue table as text or, with `--json`, one JSON document with the keys `incomplete`, `runs`, `phases`, `agents`, `families`, `issues`; `--top N` (default 15) caps agents and families.

Fresh tokens are input plus cache creation plus output, with cache reads reported separately. Usage is deduplicated per message id (the per-field maximum) and tool calls per tool_use id. A label's family drops its numeric parts. For a label in a batch phase (`Intake`, `Deliver`, `Land`) the first numeric part of the label names the issue; any other agent takes the first explicit `issue #N` of its first prompt, else its first bare `#N` that is not a pull request (`PR #N`), skipping the workflow harness's user-request relay. An agent's model is the meta file's `model`, else the commonest model recorded in its transcript's assistant messages, else `?`. A transcript or journal that cannot be read in full, or that holds a line that is not a JSON object (truncated, not UTF-8), is listed under `incomplete` (a table in text mode) and on stderr as `incomplete evidence:` lines, and the command exits 1; the totals then omit what could not be read. Exit 2 is a usage error or a run directory that does not exist; an absent journal or meta file is normal. Issues are keyed by the run's repository slug from its setup result. An issue is listed only once a `close-out` agent for it returned `released: true`, and its planner calls count its `plan`, `plan-revise` and `plan-rules-revise` agents.
