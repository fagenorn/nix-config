# agent_tools — the agent helper package

Agent-workflow Python is moving into one standard-library package, `agent_tools`, under `python/` (with its `pyproject.toml`).

## Package and launchers

`lib/agent-tools.nix` builds it into one Python environment, import-checks every module so that a broken import fails `just build`, and holds the command table.

`home/common/agent-tools/default.nix` applies that builder once per home configuration as the `agentTools` module argument, which agent-skills and claude-code consume. The installed-layout check pins the built system closure to one agent_tools package build, every agent-tools launcher to one Python environment, and that environment's imports to the closure's package build. `just agent-installed-skill-tests` passes `AGENT_TOOLS_SYSTEM_RESULT` to the check.

Each row becomes a `~/.agents/bin/<command>` launcher, which unsets the `NIX_PYTHON*` variables and runs `python3 -I -m agent_tools.<module>` from that environment, so nothing on `PYTHONPATH` or in the working directory can shadow the store copy; `just agent-installed-skill-tests` proves it. Every agent-workflow helper is a module of the package, and each command-table row is its only install route.

## artifact-budget

`artifact-budget` measures a skill artifact root against the policy and validates a producer phase report; the design, grill-with-docs, writing-plans and handoff skills call it by bare name. Its commands are `check --kind {design-spec,implementation-plan,handoff} --root PATH --format json` (exit 0 within budget, 3 over budget, 2 refused) and `validate-report --boundary producer --input PATH|-` (exit 0 with the canonical report, 2 refused). `--policy` defaults to `~/.agents/share/artifact-budget-policy.json`.

## issue-branch

`issue-branch --repo-root <path> --issue <n>` prints the branch a delivery of issue `<n>` works on, as one JSON line `{adopted, branch, derived, worktree_path}` (issue 748). `derived` renders `bindings.vcs.branch_pattern` with the title slug: at most 6 ASCII words and 40 characters, cut at a word boundary, `untitled` when empty. After `git fetch origin` it re-adopts an earlier branch of the issue: a local or origin branch that fully matches the pattern with the issue number filled in and only `<slug>` as a wildcard. A pattern without both placeholders, or with them adjacent, re-adopts only the derived name, and the integration and default branches never count. Order: the derived branch, else the head of the lowest-numbered open same-repository PR, else the newest commit. `worktree_path` is `<worktree.root>/<worktree.prefix><branch>` under the project root. Exit 2 refuses (`resolver_refused`, `tracker_unsupported`, `derived_is_protected`), exit 1 is a `forge_failed` or `git_failed` failure; both write `{"error": {code, detail}}` to stderr.

## `lane-triage`

`lane-triage evaluate --repo-root <root> --input -` (#279) reads an owner's triage record on stdin, reads `bindings.workflow.light_lane` (an optional `resolve-project` member; absent or `null` means unsupported) through `agent_tools.resolve_project.resolve`, the one public function that composes exactly what `resolve-project resolve` prints, and prints the verdict `{hits, lane, mode}` without writing anything: `lane` is `light` only when no signal is `hit` or `doubt` and no predicted path matches a `risk_paths` glob, an absent or `null` member exits 2 with `light_lane_unsupported`, and the owner's Phase 0 records the verdict while every attempt still runs full.

## `agent-workflow-tests` runner

`just agent-workflow-tests` hands its curated member list to `agent_tools.suite_runner` (issue 436; source entry `python -m agent_tools.suite_runner`, no command-table row). The runner runs each member in its own process from its working directory, with the recipe's environment plus two git configuration entries and the run's bytecode cache: a `.py` member as `python -m unittest -v <path>`, and a `.sh` member as `bash <path>`. The entries, `maintenance.auto=false` and `gc.auto=0` (issue 496), are appended to `GIT_CONFIG_PARAMETERS` in the form `git -c` exports (`member_environment`), because otherwise a commit or a fetch in a test's repository starts a detached `git maintenance run --auto`, which creates `.git/objects/maintenance.lock` while the test reads that repository. Every git command that inherits a member's environment, at any depth, reads them as if given `git -c maintenance.auto=false -c gc.auto=0`: they win over an inherited entry, a test's own `GIT_CONFIG_COUNT` entry and any config file for the same key, a test's other count entries still apply, and a `git -c` option a command adds comes after them and wins. They do not reach a process started with an environment built from scratch or with its own `GIT_CONFIG_PARAMETERS`, nor the receive-pack of a push to a local repository, which git starts with every `GIT_CONFIG_*` variable removed, so that receiving repository still runs automatic maintenance. The bytecode cache (issue 499) is one directory per run. Before the first member starts, the runner creates a `suite-runner-pycache-*` directory in the default temporary directory, sets `PYTHONPYCACHEPREFIX` to it, replacing an inherited value, and drops an inherited `PYTHONDONTWRITEBYTECODE` (`member_environment`). Every Python process that inherits a member's environment, at any depth, writes the bytecode of the source modules it imports there, under each source's absolute path, and reads what an earlier process of the same run wrote instead of compiling again. Parallel writers need no coordination: CPython writes each file under a temporary name and renames it into place, and skips a write it cannot make. The prefix redirects every bytecode lookup, the standard library's included, so a run compiles the standard-library source modules its processes import instead of reading the interpreter's own bytecode, and its later processes read that result. A script run as a main file is compiled on every start. The runner removes the directory when the run ends, after the report, after an interrupted run has waited for its members, or on an error, and a failure to remove it is raised, never ignored. The cache does not reach a process started with an environment built from scratch, nor one run with `-I` or `-E`, which ignores both variables and keeps Python's default bytecode behaviour, and a descendant still running after the run ends may recreate part of the removed directory. CPython takes a cached file as current while its source's modification time, in whole seconds, and its size match, so a test that rewrites an importable source in place to the same size within one second and then imports it in a new process gives that process its own `PYTHONPYCACHEPREFIX` directory. Outside the runner, as in a direct `python -m unittest` run, a test's Python children that inherit its environment write bytecode beside their sources where those are writable, as the test process itself does; the checkout ignores `__pycache__/`. At most `--jobs N` members run at once. The default (issue 604) is `SUITE_RUNNER_JOBS` when that variable is set and non-empty, else `min(8, CPUs - 2)` with a floor of 1 (also when the CPU count is unknown); an explicit `--jobs` wins over both, and a bad `SUITE_RUNNER_JOBS` is a usage error (exit 2). The suite is CPU-bound and its CPU time does not change with the job count, so more jobs buy wall time: on a 10-CPU Mac the full suite took 923 s at 4 jobs and 473 s at 8, all members passing. Two CPUs stay free for the host, and the cap of 8 stops a large machine from oversubscribing its disk and git. A host shared by several agents verifying at once sets `SUITE_RUNNER_JOBS` lower, and the hosted CI job sets it to 4, the vCPUs of its runner, in `.github/workflows/ci.yaml`. In parallel mode members start longest-first (LPT, issue 604) so a long member is not left to the end: the order comes from `python/agent_tools/suite_timings.json`, a committed map of member path to wall seconds taken from a full run's timing table, with members it does not name starting first in list order, ties in list order, and a missing or malformed file meaning list order. Serial mode keeps list order, and the report stays in list order for ties. Refresh the file from a run's `suite-runner: <wall>s wall ... <member>` rows when the suite's shape changes; a stale file only costs wall time. In parallel mode each member's stdout and stderr are captured together and printed as one block when it exits, from `suite-runner: begin <member>` to `suite-runner: end <member> passed|failed exit=<code> <seconds>s`. A `suite-runner: start <member>` line marks each launch, so a run cut off by a time limit names the members still running. `--jobs 1` is serial mode: members run one at a time with stdin, stdout and stderr passed straight through, for a hang or a `breakpoint()`. A member passes only on exit 0. Unittest's exit 5 for a module that ran no tests, a death by signal (`exit=signal-<n>`) and a failure to launch (`exit=launch-error`) all fail it, and every member still runs after a failure. Every completed run ends with a timing table, slowest first with ties in list order, of one `suite-runner: <wall>s wall <cpu>s cpu passed|failed <member>` row per member, then one `suite-runner: failed <member>` line per failure and `suite-runner: summary members=<n> passed=<p> failed=<f> jobs=<N> wall=<seconds>s cpu=<seconds>s`. A row's CPU figure is the member's child CPU time: the user plus system seconds in the resource usage that `os.wait4` returns when the runner reaps the member. That covers the member's own process and every descendant that it, or a descendant in between, waited for, such as the `git` and `python -m agent_tools.…` processes a test runs. A descendant still running when the member exits, or never waited for, is not counted, and a member that failed to launch shows `0.0`. The summary's `cpu=` adds up the members' unrounded figures and never the runner's own CPU, so rounding can make it differ from the sum of the printed rows. A member whose CPU is close to its wall time, or above it when its descendants ran at once, was computing. One far below it was waiting, for I/O, a sleep or a CPU it could not get. Set `cpu=` against `wall=` times the CPUs the run could use, the smaller of `--jobs` and the host's CPUs. Near it, every slot was computing and the CPUs were saturated; well below it, the members were waiting on something else. A module whose CPU grows from a `--jobs 1` run to a parallel one ran on slower, shared CPUs. Exit 0 means every member passed and 1 that one failed. Exit 2 is a usage error, raised before anything starts: a bad `--jobs`, no members, a duplicate, a member that is missing, is not a file or lies outside the working directory, or a suffix other than `.py` or `.sh`. Exit 130 is an interrupt: the runner starts nothing more, prints `suite-runner: interrupted, waiting for running members`, waits for those members and prints no report. A test that shares state with another test process is fixed by giving it its own temporary location, never by a serial-exemption list, a retry or a lock.

## agent-run-profile

`agent-run-profile` (`just agent-run-profile`; source entry `python -m agent_tools.run_profile`) profiles Workflow run directories (`journal.jsonl`, `agent-<id>.jsonl`, `agent-<id>.meta.json`) given as arguments, printing phase totals, the costliest agents, label families and a per-issue table as text or, with `--json`, one JSON document with the keys `incomplete`, `runs`, `phases`, `agents`, `families`, `issues`; `--top N` (default 15) caps agents and families.

Fresh tokens are input plus cache creation plus output, with cache reads reported separately. Usage is deduplicated per message id (the per-field maximum) and tool calls per tool_use id. A label's family drops its numeric parts. For a label in a batch phase (`Intake`, `Deliver`, `Land`) the first numeric part of the label names the issue; any other agent takes the first explicit `issue #N` of its first prompt, else its first bare `#N` that is not a pull request (`PR #N`), skipping the workflow harness's user-request relay. An agent's model is the meta file's `model`, else the commonest model recorded in its transcript's assistant messages, else `?`. A transcript or journal that cannot be read in full, or that holds a line that is not a JSON object (truncated, not UTF-8), is listed under `incomplete` (a table in text mode) and on stderr as `incomplete evidence:` lines, and the command exits 1; the totals then omit what could not be read. Exit 2 is a usage error or a run directory that does not exist; an absent journal or meta file is normal. Issues are keyed by the run's repository slug from its setup result. An issue is listed only once a `close-out` agent for it returned `released: true`, and its planner calls count its `plan`, `plan-revise` and `plan-rules-revise` agents.
