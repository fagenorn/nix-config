# ADR-project-contract-019 — Adoption moves hints and turns hand-written entry files into the bootstrap source

- **Status:** accepted
- **Decided in:** #1468 (per #1413)

## Context

Adoption left `.claude/hints/` where it was, so the delivery phases, which read `.agents/knowledge/hints/`, never saw an adopted project's hints. It rewrote every inbound relative link, including those in accepted records that must keep their citations, and it overwrote hand-written entry files with generated ones. This decision makes adoption move the hints, keep point-in-time records as they are, and report a hint no phase reads.

## Decision

**D1. Hints are a canonical move.** The `.claude/hints` classification row is `move-canonical` into `.agents/knowledge/hints`, the directory `agent_tools.delivery.hint_phases.HINT_DIR` names, so every tracked hint is a `git-mv` that keeps its history. A hint that is ignored by git stays recorded and retained, because `git mv` cannot move an untracked file.

**D2. A `paths.hints` binding follows the move, file or directory.** `amended_contract` maps each `paths.hints` string through the plan's relocations by prefix: a value equal to a relocated group, or under it, takes the group's target in place of that prefix. `.claude/hints` becomes `.agents/knowledge/hints` and `.claude/hints/planning.md` becomes `.agents/knowledge/hints/planning.md`, so a declared `knowledge.hints` capability stays `available` after apply.

**D3. An unread hint is an open item, never a gate.** `plan.open_items` is present only when non-empty: one `{"id": "hint-without-reader", "path": <new path>}` per moved hint whose path under the hint directory is not a name in `hint_phases.HINT_FILES` (a file in a subdirectory always qualifies), sorted by path. It is outside the plan id, because it is a pure function of the evidence and moves the plan id already covers, and it is not a ready gate, because a gate would change the `checks` of every evidence record and block a plan on something adoption cannot repair. The human view prints `open item hint-without-reader: <path>`.

**D4. Point-in-time records keep their citations (bar B9).** A path with an `adr` component, or under `.agents/knowledge/archive/` or `.agents/artifacts/`, is a point-in-time record. It is never an inbound link-rewrite source: the planner skips it before counting, so it adds no rewrite, no `unrewritable` row and no `already_broken` count, and `no-new-broken-link` does not judge it unless a `git-mv` moved it. A moved record keeps its outbound rewrite, because its links would otherwise break where it now sits.

**D5. What counts as hand-written.** Only a regular-mode blob at the base revision counts, read as strict UTF-8. An `AGENTS.md` counts unless its text starts with the generated-header prefix (`GENERATED_HEADER_TEMPLATE` up to `{source}`). A `CLAUDE.md` counts when its text minus every line equal to `@.agents/instructions/bootstrap.md` is not whitespace-only. A non-UTF-8 candidate refuses the plan as `adopt_failure`/`adopt.entry.undecodable`. A plan with neither a contract nor a draft converts nothing. A stale generated `AGENTS.md` (header kept) is regenerated, not converted. A candidate that would convert must have the same index record as its base record; a staged deletion or a staged edit refuses the plan as `dirty_worktree`/`adopt.worktree.dirty`.

**D6. The source text.** The parts are the source's base text (after its link rewrite, when the moves rewrite it), then one block per converted file in the order `AGENTS.md`, `CLAUDE.md`. A block is `<!-- adopted from <path> -->` and a newline, then the authored text ending in a newline. The parts are joined by a newline, which leaves one blank line between them. A block whose authored text equals an earlier part's text exactly is skipped. The source is written only when its final bytes differ from its base bytes (or it is absent at base); when a conversion is planned, that one write replaces the link write for the source.

**D7. The projections.** `CLAUDE.md` gets a `write-file` of exactly `@.agents/instructions/bootstrap.md` and a newline; `AGENTS.md` is left to its `regenerate-projection`. When a conversion is planned, a declared projection with the same `target` as an entry projection must have the same `kind` and `source` (its `id` may differ), and an entry projection with no declared target is appended unless its `id` is already declared. Any mismatch refuses the plan as `adopt_failure`/`adopt.entry.projection_conflict` at `/projections/<index>`. Converted evidence entries get the action `convert-to-source` with target `.agents/instructions/bootstrap.md`. Every scratch resolution of the final contract (the `--contract-draft` and conformance resolutions) runs on a tree that also holds the planned source bytes.

**D8. Links and imports fail closed.** When a conversion is planned, a relative Markdown link in the source's final text cannot be correct both at `.agents/instructions/` and in the generated root `AGENTS.md`, and `no-new-broken-link` would refuse it at apply. Each such link is therefore an `unrewritable` row, which keeps the plan `draft` through `no-unrewritable-link`: links in the source's base text (path the source, target after the link rewrite) and in each block (path the entry file). A Claude `@path` import in a `CLAUDE.md` block would resolve from `.agents/instructions/` instead of the file's directory, so each import whose path is neither absolute nor `~`-rooted is an `unrewritable` row too.

**D9. A nested entry file joins the source and is deleted.** After the two root files, every tracked `AGENTS.md` or `CLAUDE.md` below the root, sorted by path, converts the same way (D5, D6, D8): its authored text is a block of the source, its evidence entry gets `convert-to-source`, and the plan holds one `delete-file` for it, which is `destructive`, so `apply` refuses it without `--acknowledge-deletions`. A path qualifies when it is a regular file, is not an agent path or secret-shaped, is neither the `target` nor the `source` of a declared projection, and is unclassified or under a `retain-product` row that is not `product-source` (so `.github/AGENTS.md` converts and `home/common/agent-guidance/AGENTS.md` does not). A link to a deleted nested file is `unrewritable`, so the plan stays `draft`. Declaring the nested file as a projection was rejected: a nested `AGENTS.md` rendered from the one source would repeat the root text to Codex, and a nested `managed_import` would keep its text out of the source.

**D10. One home for the two templates.** `GENERATED_HEADER_TEMPLATE` and `MANAGED_IMPORT_TEMPLATE` move verbatim to `agent_platform`, and `resolve_project` binds the same names to them, so adoption reads the header prefix and the managed line without importing the resolver (D26).

**D11. The commit proves the conversion.** After the commit, when the plan converts, apply checks that the committed source and `CLAUDE.md` hash to their operations' `after` and that the resolver's `check-projections` on an export of the commit reports every projection `unchanged`. Otherwise it refuses `verification_failed`/`adopt.commit.conversion_unproved` and retains the worktree, as the other post-commit proofs do. This closes the gap a `pre-commit` hook leaves, because `prove_commit_content` compares path names only.

## Consequences

A project whose entry files or source hold relative links, or whose `CLAUDE.md` holds relative imports, stays `draft` until it removes them. A declared entry projection with another kind or source, or with an entry projection's id on another target, refuses the plan.
