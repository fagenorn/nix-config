# ADR-delivery-025 — A new test is a unittest id the merge base lacks, run alone in a scratch worktree at the merge base

The `revert-check` step (issue 1534) needs to tell new tests from source and to run one test; no decision fixed either. A new test is a `test*` method of a top-level class that reaches `TestCase` through classes of its own file or of a file it imports a base from, in a `.py` file the change adds or modifies, whose id `<module>.<Class>.<method>` the file at the merge base lacks; every other changed file is source. The check checks the merge base out into a scratch directory (no registered worktree), writes the head version of each file holding a new test over it, refusing a symlink, and runs each new test once as `python -m unittest <id>` from the scratch root, each on a fresh checkout. The path puts the scratch root, then the parent of each top-level package tracked there, ahead of the inherited `PYTHONPATH`, whose entries inside the run's worktree are dropped, so the reverted source is what the test imports. Where the host has a sandbox that starts (`sandbox-exec`, `bwrap`) the test runs under it with the run's worktree, the repository's git directories and every worktree the repository lists (the main checkout and so the other runs' worktrees) unwritable, since a changed `chdir` leaves a test's absolute paths intact. When a test ends or times out, every process below its watcher and every process carrying its random environment token (a daemon handed to init by a double fork keeps it) is killed; a daemon that clears its environment escapes, which the check does not contain. Exit 0 is a test that still passes. This fits the engine fixture project and this repository, both Python `unittest`; another stack's tests are not recognised, so such a change lists none. Rejected: the implementer's reply naming its tests (a claim, not a reading of the diff), a per-test command in the project contract (no binding exists) and running whole changed test files (old tests would count as new).
