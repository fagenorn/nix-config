# ADR-system-004 — Host activation runs only through the console's Activate

- **Status:** accepted; amended by ADR-console-072
- **Decided in:** #1193

## Context

ADR-console-043 put one line at the head of the Work column when a merged console change is not active on this host, and told the owner to run `just switch` in a checkout. ADR-project-contract-007 and ADR-guard-011 let a contract name its production commands, and the guard then refuses them in an agent session unless they go through the release profile. This repository's `nix-activate` is `just switch`, and the release profile is the wrong path for it: a host activation is not a release. Left as it was, the owner read a line that named a command, and ran it in a terminal outside the console. This decision makes the console's own service the one place a host activation is run, from the line itself, and has the guard say so.

## Decision

- **D1, the contract member.** A contract's production section may name one of its changing commands as its console activation: an optional string, `production.console_activation`, holding one id of `production.changes.commands`. It is allowed only in the rules form, and the snapshot carries it only when it is authored. This repository's own contract is not changed here: declaring `nix-activate` as production and naming it as the console activation is issue 1206's.
- **D2, the derived row.** The derived row's `production` member carries `console_activation` only when it is declared, and `DERIVATION_SCHEMA_VERSION` becomes 6, as 4 added production and 5 added key files and MCP tools.
- **D3, the guard sentence.** For the rule whose id is the row's `console_activation` the refusal is ``<argv> changes the production of <slug> (production rule <id>), so it runs only through the console's Activate, on the line that says a console change is not active on this host.`` Every other rule, MCP tool and key file keeps the release-profile sentence of ADR-guard-011 D8.
- **D4, the build is the shown commit.** The activation builds the commit the line shows, not the checkout's working tree, and writes nothing to the checkout. The runner keeps one clone of its own, `activation-tree` in the console's state directory, made on the first run with `git clone --no-checkout`. Each run fetches the checkout's `refs/remotes/origin/*` into it, checks the commit out detached and cleans the tree, then runs the contract's command there, in the command's `cwd` relative to the project root. The flake in the clone is a clean git tree at the commit, so its `self.rev` is the commit. There is no `git worktree add` and no `git worktree prune`. The line no longer says the checkout is behind, so `local_behind` and its text are retired.
- **D5, what success is.** A run succeeded when the command's recorded exit is 0 and the host's configuration revision (`nixos-version --configuration-revision`, `darwin-version` on darwin) equals the commit. The flake sets `system.configurationRevision` from `self.rev`. The revision alone never decides: `/run/current-system` already points at the new generation while switch-to-configuration can still fail.
- **D6, the run outlives the console.** A page activation restarts the console's own unit, because the line shows only for a console change, which changes the launcher and the unit's `ExecStart`, and `systemd.user.startServices` is true. On Linux the command therefore runs in its own transient user scope, as the manager does, which the unit's `KillMode=control-group` does not reach. Inside the scope a `record` wrapper runs the command and writes its exit to `activation.result` in the state directory. `nixos-rebuild` runs switch-to-configuration in its own system unit and waits for it, so the command's exit is the switch's. `activation.started` logs the tree's name. A restarted console resumes waiting on a started run and settles it from the recorded exit and the host's revision. A console that stops never ends the run and appends nothing for it.
- **D7, the page write.** `POST /api/activate` is a page write (ADR-console-008), with a JSON body of at most 4096 bytes, `{"commit"}`, forty lowercase hex digits. A body that is not that object is `400` `bad activation`. A refusal on its merits is `409` with one of four reasons, checked in this order: `nothing to activate`, `an activation is already running`, `that commit is no longer the tip of origin's integration branch` (the body's commit is not the shown reading's commit, or not a fresh tip read), and `the tip of origin's integration branch could not be read`. The token and origin refusals are the page-write guard's. A started run answers an empty `204`.
- **D8, what the line is.** The line still appears only for a merged console change (ADR-console-043 D1). A non-console change shows none, and so is not activated from the page. On darwin the unit's `PATH` holds no `just`, so a run there fails and the line says why.
- **D9, the outcome stays.** An outcome line stays while the reading's commit equals the outcome's commit, or for 24 hours after the run finished while nothing newer is pending. A newer pending commit replaces it.
- **D10, one run at a time.** The claim is held from admission until the run's whole process tree is gone, not until its first process exits. The tree is the scope's cgroup on Linux, read with `systemctl --user show --property=ActiveState`, else the process group. A failed read of the tree counts as alive. Past the run's time limit the console signals the whole tree (SIGTERM, then SIGKILL after 5 seconds) and still waits for it to be gone.

## Consequences

- The rollout has a window. This change cannot activate itself: the console running before the first switch has no Activate. This repository's contract stays unchanged here (issue 1206) so that a host whose installed resolver predates `console_activation` still resolves it until it is switched; declaring the member earlier would make every resolve-project entry on main fail on a host that has not been switched, ADR-project-contract-007 having accepted that refusal for a new member. Until issue 1206 lands, `activation_run.activation_command` refuses this repository (the project contract names no command for the console to activate), so Activate fails on this host with that reason, and the verify check for this change can be met only after issue 1206. The guard names the console's Activate only for a repository whose contract declares the member.
- Issue 1206 then declared `nix-activate` as production in this repository's contract, with `console_activation` naming it, once the host ran a resolver that knows the member. The guard policy is recompiled on the host (`guard-policy compile`), after which the guard refuses the activation recipe in every agent session and names the console's Activate.
- Darwin is a known limit (D8): the unit's `PATH` holds no `just`, so a darwin run fails with its reason. The line is still tied to console changes: a change to nix, docs or another module does not show it, and is activated outside the page.
- The run is in its own user scope and outlives the console's restart (D6). The restarted console settles it from its recorded exit, not from a process it no longer holds.
- A process the console's user cannot signal, such as root under `sudo`, keeps the claim held until it exits on its own (D10). The line reads running meanwhile and no second activation can start.
- ADR-console-043 D2 still holds: the activation clones from the checkout into the console's state directory and writes nothing to the checkout, with no worktree registration and no prune (D4).
- Amended: ADR-console-043 D4 and D5, because the line now carries an action and no longer names `just switch` or the checkout; ADR-console-008, which gains the twenty-second page write; ADR-guard-011 D8 and D9, because for the console-activation rule the refusal names the console's Activate and the release profile is not its approved path; and ADR-project-contract-007, whose production section gains the optional `console_activation` member.
