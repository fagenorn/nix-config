# ADR-console-089 — A question session reads the console's own records of its project

- **Status:** accepted
- **Decided in:** #1271

## Context

The owner asked a project what costs the most tokens per issue, and the session answered that nothing records spend. The console does keep it: its spend view reads the transcripts into memory (ADR-console-049), its log holds each project's delivery and activation rows, and its folds hold the sprints and the held checks. The session reaches none of that, because ADR-console-058 admits only Read, Grep, Glob and a few commands, and the console's state is not in the project's folder. ADR-console-058 D6 and ADR-console-065 fixed the session this ADR extends. Handing it the records means handing it a file in the console's own state directory, which also holds the event log, the page token and every other question's records, and ADR-console-058 leaves Read, Grep and Glob unconfined.

## Decision

**D1. The records file.** For each accepted question the console writes one JSON document of that project's records, in the settings directory beside the question's settings file as `<question id>.records.json`, mode 0600 in the 0700 directory, and removes it with the settings file once the session ends. It holds only the asked project's content.

**D2. The hook confines reads of the console's state.** The hook refuses every read of the console's state directory except the question's own records file. It covers every Read path, every word and attached option value of an admitted Bash command (a bundled short flag before the value included, as in `-wS<path>`), and every entry a Grep or Glob may traverse, with symlinks followed, `..` refused after a wildcard, and a search past `WALK_LIMIT` entries refused. The profiles share one transcript store, and a transcript keeps every tool result, so the transcript stores are confined the same way: another question's records would otherwise stay readable there after their file is removed. This amends ADR-console-058 D6 and its consequence "Reads are not confined" for the console's own state. Containment is judged by filesystem identity, the (st_dev, st_ino) of the path or an existing ancestor, as well as by spelling, and the records file is admitted by identity, so a case alias on a case-insensitive volume is confined like its own spelling; an identity that cannot be read is a denial. One part of a transcript store stays readable: the session's own saved tool output, `<store>/<slug>/<session id>/tool-results/`, which the client writes for a command's output too large to show inline and tells the model to Read; the session id is the one in the hook's own document, so another session's output stays confined. A search walks every directory by identity, compares each with the console's state and the stores (a second mount of one is refused), trusts no subtree (a link into the Nix store is walked like any other), and refuses a search it cannot fully list, so an unreadable directory is a refusal and not a gap.

**D3. The contents and their sources.** The document holds the spend view's `project_items` for the project (runs, issues, phases and sprints, in tokens and estimated dollars), the project's retained `delivery.seen` rows and the activation rows of its root, its sprints and held checks from the console's folds (a held check is an inbox item whose reason starts `verify-` or is the review reason), and for each delivery run whether it is `live`. A path can be registered to another project later, so the records count only what was observed under the project's own ownership of its root: activation rows at or before the newest point at which a different project stopped owning the root, and spend days up to that point's date, are left out. Retention keeps the newest activation rows whatever their age, so it also keeps every `project.registered` row and each `project.unregistered` row that ends a retained registration: the evidence of who owned a root lasts as long as the activation rows that name it. A log pruned before that rule may lack them, so activation rows at or before the project's own earliest retained registration at its root are left out too. `live` follows the desk's own ownership rule: the run's session is known, not ended, and its repository root maps to the project. The service gathers the records once per accepted question, in its job, after the contract's reach resolves and before the session starts.

**D4. Issue attribution.** Spend is attributed to an issue only from runs whose issues are exactly that issue; a run that named several issues is listed under each issue's `shared_runs` and adds to none of their tokens, so the figures never count a run twice. Every figure comes from the asked project's own columns, because a run id is unique only within a project.

**D5. The prompt names the file.** The prompt tells the session where the file is, what it holds and when to read it, and asks it to name the file under Read when it used it. This amends ADR-console-065 D7.

**D6. Permissions are unchanged.** Read is already admitted, so no allow rule is added; the settings directory also holds the records file. This amends ADR-console-058 D5.

**D7. A failed gathering is a failed answer.** If gathering the records raises, the question is answered once, `failed`, with the reason "the console's records could not be gathered: <Type>: <message>", one stderr line `console: project_question_records_failed <question id> <Type>: <message>`, and no session is started. Nothing new is appended to the log: the question still writes exactly its asked and answered rows.

**D8. Spend is null before the first spend read.** Until the console's first spend poll there is no view, so the document's `spend` is null and the rest is written, and the prompt says so.

**D9. A request key makes a question asked once.** A question request may carry `request_key`, 32 lowercase hex digits (`REQUEST_KEY`); any other value is a bad request. The service asks a key once per project: a key already on a folded question of the project returns that question's id and appends, counts and dispatches nothing, and the same key on another project is a separate question. The check runs under the ingest lock after the unregistered and question checks and before the follow-up check, so a re-sent keyed follow-up is not refused as a follow-up to an unanswered thread. The key is in the asked row's payload only when one is given, the fold keeps it only when it is well formed, and the published view's question carries it (null when absent). The POST answers 204 with no body, so the key is how a client that must judge exactly the question it asked finds it again, and a retry never starts a second paid session. A keyed question also appends a receipt row, `project_question.keyed` (`request_key`, `question_id`), in the same append, which retention never removes: the question's own rows go at 90 days and the receipt does not, so a retry of the same key after that still returns the question's id and starts nothing. A request without a key behaves and writes exactly as before.

**D10. The fixed question check.** A verify check, `question_check`, asks one project three fixed questions on this host's console and passes only when each answer read its own records: what shipped and what is live in the last 7 days; what costs the most time or tokens per issue and whether the backlog holds an improvement; and why production run NAME (else the most recent failed production run) failed. It posts through the page's write route, so a run that posts starts up to three read-only sessions and its verify check is `effects: paid`. Each question is posted under a `request_key` (D9) saved in a state file before the POST, so a retry finds the question it asked instead of asking again, and a question is judged only through its own key: another question of the same text is never judged. The saved keys belong to one revision, the commit the check runs at; verify-pending runs it at the block's merge commit once the deployment holds, so when the saved revision differs the keys are dropped and answers to an earlier revision's questions are never judged. An answered question is grounded iff its answer is non-blank and its Read section names the question's own `<question id>.records.json` as a complete file name, however the prompt's path formats write it (backquoted, in a list, with a line suffix); another question's file, a backup or a missing Read section is ungrounded. One run waits within itself up to 480 seconds for the answers to settle. Stdout is one JSON line of status and verdicts and holds no question text, answer or console text; the answers, each answer section and any refusal text go only to the result file, mode 0600 in a 0700 directory. Exit 0 met, 1 not met, 75 not yet, 2 a usage or setup error.

## Considered Options

- A Bash route printing the records: it needs a new admitted argv, for a copy the session's Read reaches anyway.
- An MCP tool: ADR-console-058 D4 rules MCP out.
- A console HTTP read: the session has no tool to reach it.
- Leaving reads unconfined: another question's records, the event log and the page token would be one Glob away.

## Consequences

- Transcripts and checkouts outside the console's state stay readable, as before; a question's own saved tool output is readable too.
- A declared read-only command is the project's own declaration: the hook confines which files a session reads, and does not sandbox what a declared command writes.
- A project whose root contains the console's state directory has its whole-root searches refused, and so does a project tree holding a symlink into that directory, a directory it cannot list or more than `WALK_LIMIT` entries; a checkout whose `result` link leads into a large Nix closure has its whole-root searches refused until a narrower path is named.
- A hard link made outside the session is not detected, and the session itself cannot make links.
- Spend stays out of the log (ADR-console-049); the file is a copy that lives for one question.
- Related: ADR-console-049, ADR-console-058, ADR-console-059, ADR-console-065.
