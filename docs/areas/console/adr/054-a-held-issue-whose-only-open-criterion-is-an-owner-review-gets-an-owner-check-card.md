# ADR-console-054 — A held issue whose only open criterion is an owner review gets an owner check card

- **Status:** accepted; amended in #1186 (D8)
- **Decided in:** #1113

## Context

A delivery run that has finished its work holds its issue with the `needs-verification` label until every acceptance criterion is ticked. When the only criteria still open are `[human]` reviews and the runner has posted no prompt, nothing on the page tells the owner: ADR-console-012 D7 raises an item only from a live runner prompt, so a held issue with none raises no item. #1091 sat in that state. This decision gives such an issue a card the owner can answer from the page, through the write path the other owner checks use.

## Decision

**D1. The read.** A second search, after the one of ADR-console-003, asks for open items carrying the `needs-verification` label, 25 a page and the last 100 comments each, at most four calls. It is lenient where the first is strict: held issues stay open and labelled until the runner verifies them, so their number and comments only grow, and a read that failed on them would lose every owner card of the repository. When it is still paging after its fourth call it keeps the nodes it read, and a held issue with more comments than the 100 read raises no card; a node the first search already returned is read once, from the first search. An Issue node also reads `authorAssociation`, `body` and `labels(first: 100)`; a node without them reads as it did before.

**D2. Which issues.** An issue is read for review cards when it carries `needs-verification`, its author association is OWNER or MEMBER, and it has no live trusted runner prompt, answered or not. A runner prompt keeps its own card (ADR-console-012); the review card never stands beside it.

**D3. Which criteria.** The criteria are the checkbox lines of the first `Acceptance criteria` heading section of the body, outside code fences. One card is raised per unticked `[human]` criterion (less D8), and only when no unticked `[evidence]` or untagged criterion remains: the owner is asked only when the owner's review is all that is left. An unticked `[code]` box counts as met, because the hold step never ticks it, and an unticked `[note]` criterion blocks nothing. A bullet may be followed by any run of spaces or tabs before its box. A fence opens and closes with up to three spaces of indent beyond the content column of the list item that holds it, and may open right after the list marker (`- ~~~`), so a fenced example nested under a checkbox is never a criterion; a fence ends with its list item, at the first non-blank line indented less than the item's content column. A heading inside a list item (indented to the item's content column) belongs to that item and does not end the section; only a heading outside every list item does. A `[human]` criterion that a check of the held `verify` block names (the `ac` of a check, `AC<n>` for the criterion's 1-based index, compared case-insensitively, read from the newest block of a trusted comment) raises no card, because the runner asks it when its check comes due and the owner is not asked twice; the same rule is checked again at the write (D5).

**D4. The card.** It is an owner check card of kind `owner-review`, reason `held-review`, with the key `<slug>#<issue>/ac<n>`. It is headed by the criterion's text cut before its first measured tail (whitespace, any dash, whitespace, `measured:`, case-insensitive; the whole text stays with the card and is what the pictures are read from), then without any word that names a PNG file or a folder (a `.png` name, or a word with a `/` that starts with `/`, `~/`, `./` or `../` or ends with `/`, and has no `://`; `light/dark`, `and/or` and `1440/480` stay) and without the connecting words (`in`, `under`, `at`, `on`, `from`, `of`, `into`, `by`, `to`, `and`, `or`) left hanging before one, so the card never shows a bare path in its heading or in the digest line; the pictures and missing lines of ADR-console-045 and ADR-console-047 are read from the whole text. Its thumbnails read Before ahead of the After of the same width, whatever order the files are named in. Its answers are Approve and Not yet. Approve asks for no typed confirmation, and the five-second undo of ADR-console-010 applies.

**D5. The write.** The answer is `POST /api/check-answer`, as for every owner check. Approve reads the issue again as the owner and edits its body so that only that criterion's box is ticked (the tick of ADR-console-010, made on the issue body instead of a prompt comment). It is refused when the issue is closed, when the label or the criterion is gone, when another blocking criterion is open, when a live runner prompt has appeared, or a check of the held verify block now names the criterion, since the poll built the card (the comments are read again before either write), or when the criterion's text changed since the page read it; a criterion already ticked is left alone. Not yet posts one owner comment holding the note, never a verify block, and ticks nothing; it is refused on the same grounds.

**D6. Not a runner prompt.** The card has no comment id and no prompt marker. Answering it never writes the runner's answer block, and the runner's hold still decides what happens to the issue once the criterion is ticked.

**D7. The page change is held for the owner.** This is a change to how the page looks. The delivery makes before and after PNG screenshots of the review card at 1440 and 480 px, and the pull request merges only after the owner approves them.

**D8. An approved look answers its look marker.** A criterion whose line is a look marker (issue 1138) raises no card when a trusted (OWNER or MEMBER) live `agent:look` marker of the issue, the latest for its pull request and head, answers `approved` and that pull request reads merged with that head as its head commit. The check is one REST read `repos/<slug>/pulls/<n>` per approved pull request and head, made only for an issue that would otherwise raise a look-marker card, outside D1's four calls, with the stop asked before each. An approval of another head, a `changes` answer, an untrusted or ended marker, an unmerged pull request or a failed read keeps the card. The write (D5) does not check it again, so an Approve on a card read before the approval ticks the box the approval answers.

## Consequences

- The read makes one more search, for the held issues, and parses their bodies. Past four pages of held issues the rest raise no card until the runner verifies some; the owner search and its owner cards are never lost to them.
- The tick does not close the issue or touch its labels; the runner's hold still decides that.
- GitHub has no conditional update of an issue body, so an issue edited by someone else between the read and the write may lose that edit; the version check narrows the exposure to the criterion line.
- ADR-console-003's search and ADR-console-012 D7's rule of no item without a live prompt are amended.
- An issue held before landings ticked its look marker costs one pull request read per poll until its box is ticked.
- Related: ADR-console-003, ADR-console-010, ADR-console-012, ADR-console-045, ADR-console-047.
