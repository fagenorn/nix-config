# Claude Code module

## Settings

The `env` of the generated `~/.claude/settings.json` sets `BASH_MAX_TIMEOUT_MS` to `3600000` (60 minutes), the ceiling for an explicit Bash timeout, so an agent can run `just build` or `just agent-workflow-tests` in the foreground under a timeout above its duration (#261); `BASH_DEFAULT_TIMEOUT_MS` is left unset, so a command with no explicit timeout keeps the host's 120 s default.

`skillOverrides` hides twelve skills from the model's skill listing, each set to `user-invocable-only`, so `/<name>` still runs it (issue 425): the bundled `artifact-design`, `artifact-diagramming`, `artifact-capabilities` and `dataviz`, keyed by their bare names, and the claude.ai-synced `docx`, `pptx`, `xlsx`, `pdf`, `google-workspace`, `morning`, `import-memory` and `skill-creator`, keyed by their full `anthropic-skills:<name>` names. Claude Code matches a synced skill's full name before its bare one, so a user or project skill that shares a bare name stays listed. A plugin's skills ignore user-level overrides and leave the listing only when their plugin is disabled, so the skill-creator kept listed is the plugin's `skill-creator:skill-creator` and the hidden one is the claude.ai copy. The three Artifact skills are registered only in sessions that have the Artifact tool, so their entries take effect only there. `tests/test_claude_code_installed.py`, run by `just agent-installed-skill-tests`, checks the map and `enabledPlugins` in the built settings.

The generated settings set `statusLine` to the `owner-actions statusline` store launcher (issue 624) on every host. It shows `owner N (oldest Xd)` for the cwd's repo only when that repo is in the fleet registry and has open issues or PRs labelled `owner-action` or `agent:human-required`, followed by `, answered M` for the issues whose decision prompt is fully ticked and waits for a run (`owner-answered`; `answered M` alone when nothing else needs the owner), and is blank otherwise. It never calls the network and refreshes its cache through a detached `owner-actions refresh`; the contract is in [`python/README.md`](../../../python/README.md) § owner-actions.

## Allow surface and lifecycle guard

Use `just show-claude-settings` to build and print the settings JSON (failing unless discovery finds exactly one artifact); its 28-entry allow surface allows the lifecycle helpers `workflow-state`, `artifact-budget` and `ship-delivery`, the `verification-observe` adapter and the `forge-issue` filer, outright, bare and as `~/.agents/bin/…`, and hands five lifecycle verbs (`git push`, `gh pr create`, `git branch -d`, `gh pr merge`, `gh release create`), and the raise-label rule below, to a fail-closed `PreToolUse` hook. That hook's Python is `home/common/claude-code/lifecycle_guard.py`, a standard-library-only file that imports nothing from `agent_tools`: the registered command is a store wrapper that clears `NIX_PYTHON*` and runs it under `python3 -I` with `--base-policy` naming the store base policy, `--policy` naming the compiled policy at `~/.agents/state/guard/policy.json`, a path fixed at evaluation time from the configured home directory, and `--derive-bin` naming the store row check (the terms and their producers are under `## Guard policy`), so an owner change never touches the source. `just build` fails when the guard source or the base policy cannot load, because the wrapper's build check runs the guard as registered on a harmless payload that has no repository-bound verb. A bad base policy blocks every Bash call, while a bad compiled policy contributes no row (`## Guard policy`). The hook splits the command into shell segments, tokenises each one, and adjudicates a verb **wherever a simple command starts** — after `(`/`{`/`` ` ``/`$(`/a `case` arm, after `!`/`time`/`then`/`do`, and behind `command`/`env`/`sudo`-style wrappers, stepping over their option arguments (`env -u NAME`, `sudo -u user`, attached and long forms included) — comparing *token values*, so `git  push`, `git<TAB>push` and `"git" push` all count. A word whose basename is `git` starts a git invocation (a git word that is not a `push` or `branch -d` is judged by `## Transmitting git invocations`): with no global option, or one `-C <dir>`, the word after them is its subcommand (`push`, or `branch` then `-d`), and with any other global option a `push` or `branch -d` anywhere among its words counts; a word whose basename is `gh` counts when its first two words are `pr merge`, `pr create`, `release create` or `release new`, or when a flag comes before the path's second word and both path words occur in order, so `gh --repo a/b pr merge 1` counts and `gh pr view 1 --json mergeable` does not (issue 400). Such an invocation is refused before any repository lookup, its problem ending `run git and gh by name, and carry a directory only as git -C <dir>` and followed by the accepted-forms clause (`## Adjudicated verbs`), when its program is named by a path, or it carries a git global option other than one `-C`, a repeated `-C`, or a `-C` directory holding whitespace, a quote or a shell-active character, or when its run reaches a shell substitution, expansion or grouping before its verb is certain: a git run still inside its global options or carrying a global option other than `-C`, whose value the walk cannot bound (`git -c k=$(…) push …`), or a gh run carrying a flag or ending before its third word (`gh pr --repo $(…) merge …`); then the verb's words among the rest of the command's words count, across segment boundaries, so `git -C $(pwd | cat) push …` blocks, also when a segment it crosses is judged on its whole text as evaluator source or an `env -S` payload (`git -C $(sh -c pwd | cat) push …`), and the reason names that invocation continuing past the substitution (issue 400 D15, D18, D19); a word taken as a `-C` value is an argument of git, never a program; a gh flag between the path words is left to the verb's grammar. A mention that is one quoted token (`echo "gh pr merge …"`), a comment, or a heredoc body the guard reads exactly is not a command and never triggers it. The guard reads a heredoc exactly only when its delimiter is a bare word without quotes, backslashes, `$` or backticks, one single-quoted span, or one double-quoted span without a shell-active character, and, under a bare-word delimiter, the body holds no `$`, backtick or backslash (the shell runs substitutions there); any other heredoc (ANSI-C `$'EOF'`, locale `$"EOF"`, mixed quoting, escapes, an expanding body) makes the command unparseable, so a verb anywhere in its text, body included, is refused (issue 651). Everything the tokeniser cannot vouch for is refused rather than waved through: an unparseable command, shell source handed to an evaluator (`eval`/`sh -c`, matched by basename, so `/bin/sh -c` too), a segment in which `env` takes `-S`/`--split-string` (judged on its whole text, since env appends the remaining words to the split command), and a guarded verb sitting in a non-command position (an argument to `xargs`, `timeout`, …) all block. In such raw text a verb counts when its words occur in order, the first by basename, with the text read twice (words split at whitespace, quotes and shell-active characters; and again with quotes and backslashes deleted, since the shell glues the pieces into one word) and an attached `-S` payload read as a word, and it also counts when its words joined by one space occur as a substring of the text or of the text with quotes and backslashes deleted, so `sh -c 'git -C x push …'`, `sh -c "g''it push …"`, `env -Sgit push …`, `eval "${CMD:-git push …}"` and `sh -c "git branch -df x"` block too. Bare `Agent` remains inert under `defaultMode = "auto"`; verify the built artifact and guard with `tests/test_claude_permission_guard.py`, which takes the built settings through `CLAUDE_SETTINGS_PATH` and the built base policy through `CLAUDE_GUARD_BASE_POLICY_PATH`, runs under `python3 -m unittest` with `python/` on `PYTHONPATH`, and passes a fixture compiled policy and a stub row check on every invocation, so it never reads this host's compiled policy or fleet registry (three tests, `test_a_compiled_policy_round_trips_through_the_guard`, `test_a_compiled_policy_loads_whatever_branch_names_the_fleet_carries` and `test_an_arcwave_shaped_project_is_judged_by_its_compiled_row`, run `guard-policy derive` from source as the row check over a fixture fleet, and `test_the_row_check_never_sees_a_hostile_shell_environment` runs the built `claude-guard-row-check` with `HOME` at an empty fixture fleet). The same Bash `PreToolUse` entry also holds a second command hook, the context meter (`## Context meter`), which never grants or denies.

## Detaching words

Before any of that, and before its policy loads, the hook refuses the detaching words `nohup`, `setsid` and `disown` in every repository (#278), naming the Bash tool's `run_in_background: true` and `launch-scope exec` as the routes. Since issue 656 it reads no shell syntax for this. A command is refused when one of the words appears as a whole word in its raw text, in any case. A whole word has no ASCII letter, digit, `_` or `-` after it, and none before it except `c` or `s`, which covers env's attached `-S` and `su -c`; a `$` and one digit, `!`, `@` or `*` before it also bound it (`$1nohup`), and a `-` default-value operator does too (`${x:-nohup}`, `${x-nohup}`, whatever the parameter, `${@:-nohup}` and `${a[0]:-nohup}` included, and with the word rebuilt as the deletion copy below rebuilds it, `${x:-no''hup}` and `${x:-'n'ohup}`). The same test runs on a copy of the text with backslash-newlines deleted, then every `$` before a quote and every `\`, `'`, `"`, `{`, `}` and `,` (`no''hup`, `no$''hup`, `no{,}hup`). The refusal names the earliest hit. Only two read-only forms are admitted, each read in the issue-418 word grammar with every option enumerated. One is a single plain `grep` or `rg` call that holds the word only in its search pattern. An option outside the table refuses the admission, such as `-f`, `--files`, or rg's `--pre`, `--hostname-bin` and `-z`. The other is one `gh issue|pr create|comment` call, optionally after the `unset GITHUB_TOKEN && ` scrub, that holds the word only in a quoted `--title`/`-t`/`--body`/`-b` value, with no other options than `--repo`, `--base` and `--head`. Any other mention, a heredoc body, a comment, `nohup.out` and a word handed to `xargs` or `timeout` are refused; a trailing `&` passes, and so does a slugged branch or worktree name such as `issue-7-refuse-nohup`. A commit message that names a word is refused; reword it or use `git commit -F`. Accepted residuals, none of them seen:
- a word assembled at run time (`${a}hup`, `$(printf …)`, a variable);
- a glob (`noh?p`);
- an ANSI-C escape (`$'\x6eohup'`);
- a brace expansion with a non-empty other alternative (`{no,x}hup`);
- a word glued to a letter other than `c`/`s` as an attached option value a program runs.

## Transmitting git invocations

Issue 655. A git invocation that could transmit refs and is not an admitted lifecycle form is refused as a push. `push` and `branch -d` keep the recognition above and its messages; every other `git` word, and every word whose basename starts with `git-`, is judged by `git_transmit_problem` and refused as `lifecycle guard: unsafe push: <problem>; accepted: <push forms>; optional prefix: …`. The guard never reads git configuration, so an alias is refused by its name, not by what it resolves to. The refusal comes after the lifecycle-grammar check (a command that also holds a lifecycle verb keeps its grammar refusal) and before any repository context is built, so no git, gh or row-check child runs.

What is refused:
- A global option outside `GIT_GLOBAL_OPTIONS`, a closed table of each option and the number of words it takes (an attached `=value` counts only for the one-word long options). `-c`, `--config-env`, `--exec-path=<dir>` and any unknown option are refused for every subcommand, because a `-c` value such as `core.pager`, `core.fsmonitor` or `core.sshCommand` runs a command from any of them. This moved `git -c core.pager=cat diff` from admitted to refused.
- A subcommand outside `GIT_LOCAL_SUBCOMMANDS`, a closed list of the subcommands that cannot transmit refs: an alias (repository, global or `-c` config), an external `git-<name>` program, a transport (`send-pack`, `http-push`, `subtree`) and the subcommands that run a caller-supplied command (`submodule`, `bisect`, `filter-branch`, `difftool`, `mergetool`).
- A `git-<name>` program in any spelling (`git-push`, `/usr/libexec/git-core/git-send-pack`, `git-lfs`), since one on `PATH` is an alias by another spelling. An argument such as a branch or path named `git-<x>` is refused too, inside an otherwise admitted lifecycle command as well, once its grammar check has passed; this workflow's branches start with `issue-`.
- A git run cut by an opening operator (`(`, `{`, or a backtick with an even number of backtick tokens before the git word in its segment) before its subcommand is certain: no subcommand word remains, or the subcommand is the last word and may be glued to the substitution (`` git add`echo -x` `` runs the alias `add-x`). `git $(printf p) origin x` and `git -C $(pwd) status` are refused; `(git status)`, `` `git status` ``, `echo $(which git)` and `git log $(printf HEAD) -1` pass.
- A bare git word (no subcommand after its global options) whose subcommand the shell supplies from elsewhere: at an argument position in a command where a pipe comes before it or a redirection (`<`, `<<`, `<<<`) appears anywhere, whichever segment or grouping the pipe or redirection belongs to (`echo p origin t | xargs git`, `echo p | { true; xargs git; }`, `{ xargs git; } <<< 'push …'`, `exec <f; xargs git`, a pipe followed by a newline, also inside evaluator text), whether the git word is plain, the last word `"$(which git)"` or `${G:-git}` (the brace forms `${G-git}` and `${G:=git}` too), and a git word that is the output of an unglued `$(…)` or backtick substitution that words follow (`$(echo git) p origin t`, `xargs $(echo git) p`, a substitution that ends the segment before it closes, and the quoted `"$(which git)" push …`). `which git`, `brew install git`, `echo $(which git)` and `xargs git status` pass; so does `x="$(which git)" y`, whose output is assigned. The accepted cost is `ps aux | grep git`, `echo $(which git) status` and a `which git` that follows a pipe or shares a command with a redirection; write `grep '[g]it'`.
- A command option hidden from the option scan: the scan also reads a word that holds an expansion and does not start with `-` (`"${X:---exec=sh p.sh}"`, a `-` after one of `:=+?-` starts a candidate), and the words that follow the operator which cut the run (`git rebase $(x) --exec …`).
- `git config` naming `core.hooksPath` (issue 672 D8): any later word of the invocation, the words after an operator in the same segment included, that equals `core.hookspath` or starts with `core.hookspath=`, compared lowercase, so the get, set and unset spellings, `--global`, `--local`, `--file` and `git config set`/`unset` all refuse as `git config naming core.hooksPath would change which hook judges a push; read it with git rev-parse --git-path hooks`. Any other key passes, `git config --get core.hooksPathX` included. `--no-verify` and `-n` on `git push` stay refused as an unsafe push form.
- Clearing the agent session marker (issue 672 D3), in every repository: a segment refuses with `clearing or unsetting CLAUDECODE would hide the agent session from the pre-push hook` when a non-operator token assigns `CLAUDECODE` in any position (a prefix, a standalone assignment, an `export`/`declare`/`typeset`/`local`/`readonly` argument), when a token is exactly `CLAUDECODE`, `-uCLAUDECODE` or `--unset=CLAUDECODE` (`unset [-v]`, `export -n`, `declare +x`, `env -u`), when an `env` word has `-`, `-i`, `--ignore-environment` (or a prefix of it) or a short cluster holding `i` among its options, when an `env` unset option names it in any spelling (`-u CLAUDECODE`, `-vuCLAUDECODE`, `--unset CLAUDECODE`, an abbreviation such as `--unse=CLAUDECODE`), or when an `exec` word has a cluster holding `c`; the same tests apply to evaluator text, so `sh -c 'unset CLAUDECODE; …'` and `sh -c 'env -i ./push.sh'` refuse. A read (`$CLAUDECODE`) never refuses. The accepted cost is that a bare-word mention such as `printenv CLAUDECODE` refuses too; write `echo $CLAUDECODE` instead.

The same rule judges a git word at a command position, at an argument position and in raw text. At an argument position it is `git_argument_problem`, whatever runs the word (`xargs git p`, `timeout 5 git p`, `find -exec git p`); the guard keeps no list of runners. Evaluator text (`eval`, `sh -c`), `env -S` text and unparseable or untokenisable text is split at `;`, `&`, `|` and newlines, and each piece's raw words, in both quote readings, are walked from every raw git word: one whose text ends in `git` after nothing or after `/`, `:`, `=`, `+`, `?` or `-`, so `${X:-git} p` is caught. The reason such a refusal reports is the evaluator's or the `env -S` one. The accepted cost is mention false positives, as for lifecycle verbs: `rg -n git README.md`, `echo git p` and `nix-shell -p git jq` are refused. Write a mention so that no word is a bare `git` followed by a non-local word (`rg -n '[g]it' README.md`, `echo 'git p'`); a `git` followed by nothing (`which git`, `brew install git`) passes.

Spellings of a git word that the shell resolves are read too: the word after `$` (`$'git' p`, which tokenises to `$git`), a line continuation (`git\<newline> p` is `git p`, in tokenised and raw text alike), a variable the command itself assigns a git word (`G=git; $G p`, `export G=/usr/bin/git; "$G" p`, `${G} p`) or the output of a substitution that holds one (`G=$(which git); $G p`), a name that `hash` or `alias` binds to git (`hash g=/usr/bin/git; g p`, `alias g=git; g p`), zsh's `=git p` expansion of the command's path (one leading `=` is stripped), the braced default `${G:-git} p` at any position, and a git word inside a double-quoted `$(…)` or backtick substitution, refused as `a command substitution inside a quoted word cannot be validated` when its text would be refused as raw text. A command that has an evaluator at a command position is also scanned as a whole, heredoc bodies included, because that evaluator may read its source from stdin (`echo 'git p origin t' | sh`, `sh <<'EOF'`). Evaluator text carries the same spellings: names it assigns itself or inherits from the command (`sh -c 'G=git; $G p'`, `G=git; sh -c '$G p'`), and a third, quote-aware reading of each piece in which a quoted global-option operand is one word (`sh -c 'git -C "/tmp status" p origin t'`) and a word holding several words is read again as text.

Residuals, none closed: a runner that takes its words from a file (`xargs -a args.txt git`), a variable assigned an option elsewhere in the command (`X=--exec=sh; git rebase $X`), and a command word the guard cannot resolve to git from the command's own text: a variable built from pieces (`G=g; H=it; $G$H p`) or set by `read`, `printf -v`, `declare -n`, `set --` or the environment, and an ANSI-C escape that spells a letter (`$'g\x69t' p`); channels that run a file the agent must first write, no different from running that file (`sh /tmp/p.sh`): git configuration files (`git config core.pager …` then `git log`, hooks, `core.fsmonitor`, credential helpers), `PATH`, `HOME` and `XDG_CONFIG_HOME` assigned outside a git prefix, merge strategy programs (`-s <name>` runs `git-merge-<name>` from `PATH`), `source`d environment files, variables set by `read`, `printf -v` or `declare -n`, `ext::` remote URLs (git's default `protocol.ext.allow` is `never`), and `gh` aliases.

Further residual classes: stdin fed to a fed command through an fd-numbered redirection (`0<<<`, `0<file`, `exec 0<`) or a zsh coprocess; a fed git after an empty substitution or unset expansion between the feeder and git (`xargs $(true) git`); git spelled through a braced default glued to literal text (`${G:-g}it`, `g${G:-i}t`). These deliberate obfuscations are out of scope for the text guard and are covered by the planned git pre-push hook.

**Command-running options.** An allowlisted subcommand is still refused when it carries an option whose value git runs as a command, from `GIT_COMMAND_OPTIONS`: `archive --exec`, `clone --upload-pack`/`-u`/`--config`/`-c`/`--template`, `fetch`/`pull --upload-pack`, `grep --open-files-in-pager`/`-O`, `init --template`, `ls-remote --upload-pack`/`-u` and `rebase --exec`/`-x`. `git_command_option` matches a `--` word by its part before any `=` when that part has three or more characters and a spelling of the subcommand starts with it (git accepts `--exe` and `--upload`), and a short word when any letter of its cluster is a short spelling (`-ix`, `-Osh`). Every word after the subcommand is scanned, an option value or an operand after `--` included, so a lookalike can only refuse more. The check runs inside `git_transmit_problem`, so it applies at a command position, an argument position and in raw text alike.

**Environment assignments.** An assignment that hands git a command or other configuration is refused as a push in two places. (a) Every assignment before a git word, up to the last operator (`X=1 git …`, `env X=1 git …`, `timeout 5 env X=1 git …`), must name a variable in `GIT_ASSIGNMENT_ALLOWED` (tracing, author and committer identity, pathspec switches, locale, `TZ`, `TERM` and similar); `PATH`, `HOME`, `GIT_SEQUENCE_EDITOR`, `GIT_SSH_COMMAND`, `GIT_EXEC_PATH` and every `GIT_CONFIG_*` name are not in it. (b) Anywhere in the command, including `export` and `declare` arguments, a standalone assignment, and the raw text of an evaluator or quoted substitution, a name starting with `GIT_` that is not allowlisted, or one of `GIT_COMMAND_VARIABLES` (`EDITOR`, `VISUAL`, `PAGER`), is refused. Residuals, none closed: `PATH` and `HOME` assigned outside a git prefix, a value set by `read`, `printf -v` or `declare -n`, and a `source`d file that assigns one.

## Adjudicated verbs

The verbs it does adjudicate are validated against the live repository: `git push` only as `git push [-u] origin <branch>` onto a non-default branch with no force/delete/mirror flags, no refspecs and no namespaced refs (`refs/heads/main` and `heads/main` name the default branch too; the two exceptions are the tag-push and remote-deletion arms below), `gh pr create` only as the exact `--repo/[--draft]/--base/--head/--title/--body` form (issue 671: `--draft` stands right after `--repo <slug>`, in both body spellings, and nowhere else), with no shell-active character outside quotes (issue 386, so an unquoted title cannot redirect or brace-expand) (or, issue 386, with `--body-file <path>` in place of `--body`, only when that PR creation is the whole command after any scrub prefix, the path absolute, free of whitespace, shell-active characters and `..`, outside `/dev/` and `/proc/` (case-folded) before and after resolution, and resolving, case-folded, outside the working tree, which fails closed when the tree cannot be read; this is a placement check that refuses obvious in-tree paths, not a guarantee about the file's content, which any earlier command or concurrent process can still have written) whose repo is the target repository's slug and whose base is `origin/HEAD`'s branch, `git branch -d <branch>` (guarded globally, in every repo), and `gh pr merge <n> --repo <target repository slug> --merge [--subject "<subject>"] [--match-head-commit <sha>] --delete-branch`, flags in that order, `<sha>` one separate word of exactly 40 lowercase hex characters (issue 402) that must also be the PR's head commit (the mergeability check below, issue 476), or, in a repository with a declared integration branch, the release arm: the same form without `--delete-branch`, only the integration branch merged into the default branch, gated on a fully green check rollup instead of forge protection, optionally behind a credential-scrub prefix (issue 400), spelled exactly `unset N && `, `unset N M && `, `env -u N ` or `env -u N -u M ` with single spaces and `N`, `M` distinct members of the credential-name set `GITHUB_TOKEN`, `GH_TOKEN` (`unset GITHUB_TOKEN && ` is the spelling derived from `bindings.tracker.credential_env.unset_before_invocation`'s exhaustive credential-name list), stripped from the start of the whole command so the remainder is still judged whole and nothing else can chain; `git push` and `gh pr create` take the `env -u` spellings at the start of their own segment (the `unset` spelling is an earlier segment there), `git branch -d` takes none, and any other `env` option or assignment, `--`, `--unset=` or attached `-uN` spelling, repeated name or doubled space leaves the text whole for the grammar to refuse; the four repository-bound verbs (every one but `git branch -d`) additionally require the repository to be inside standing authorization, which means its owner is in the base policy's `authorized_owners` or the repository itself has a derived row that the row check confirmed in this invocation, and merging further requires an open PR based on the default branch (or the repository's declared integration branch, which comes from a literal base-policy `integration_bases` row or from a confirmed derived row whose two branches differ); a default-branch base additionally demands live protection with at least one required status check and admin enforcement on the feature arm (or, where the forge answers that the repository's plan cannot protect the branch, the plan-gated floor below), while a declared integration base is deliberately exempt from the protection demand — it is the development-pace branch, and its CI gate stays in the shipping flow's wait-for-checks. `git push` and `git branch -d` also take one `git -C <dir>` directly after `git` (issue 400), `<dir>` one unquoted word without whitespace, quotes or shell-active characters, a relative one joined to the payload `cwd` without normalisation: the guard strips it to the canonical command and builds a push's repository context — origin slug, `origin/HEAD`, the derived-row lookup and row check, and the tag lookup — from that directory, one context per distinct directory in a command under the one invocation deadline, while branch deletion checks only its spelling; an unresolvable directory is an unknown repository, refused as outside standing authorization. The merge's own `gh` lookups run with `GITHUB_TOKEN`/`GH_TOKEN` scrubbed from their environment, so they authenticate via the gh keyring credential (whose reach covers every authorized owner) rather than any ambient environment token, which gh would prefer and which may be narrower; a machine with no keyring auth fails closed at the lookup. There is no defer path: once the hook adjudicates a verb it is validated-and-allowed or blocked, never handed back to the allowlist unexamined, and every uncertainty (unknown repo, unresolvable default branch, child timeout, non-zero or unparseable output) blocks. The guarantee is only as wide as that segment tokeniser — it approximates bash rather than being bash — which is why it refuses whatever it cannot parse, and why `tests/test_claude_permission_guard.py` carries an adversarial table (one case per class of "the parser and the shell might disagree") that any change to the guard must keep green. Every accepted spelling has one home, `FORM_TABLE` in `lifecycle_guard.py` (issue 402), each operation's forms in its template notation (`<slot>` one word, `"<slot>"` one free-text word that may begin with `-`, a slot closing a literal word, `[…]` an optional group led by its flag, a parenthesised note never matched) with three properties — whole-text characters (push and branch deletion), exact spelling (merge and release creation: single spaces, double-quoted free text) and scrub prefix (every operation but branch deletion) — compiled first on every invocation inside the unexpected-failure handler, so a template that does not compile refuses every Bash call with exit 2 and fails `just build`; one shared matcher judges each canonical command against its operation's forms in table order, and `canonical_text` reads the scrub-prefix property.

The **remote-deletion arm** (issue 458) is the push verb's third form, judged after the tag and branch arms: exactly `git push origin --delete refs/heads/<branch>`, with the push verb's whole-text character rule, credential-scrub prefixes and one `git -C <dir>`. The `refs/heads/` literal is the point: git resolves a bare `--delete <name>` against the remote's refs and deletes a tag when only a tag matches, while the qualified name can only be a branch, so the bare spelling stays refused (`missing refs/heads/<branch>`). After standing authorization the value takes the branch arm's name rule (so `refs/heads/refs/heads/x` is a namespaced ref), then needs a resolvable `origin/HEAD`, and the default branch and the repository's declared integration branch are refused as `unsafe push: refusing to delete the permanent branch <branch>`. The arm reads no forge state: GitHub itself refuses to delete a protected branch, and the delivery's ship stage runs the deletion only after verifying the merge and seeing `git ls-remote --heads origin <branch>` non-empty.

The **effective push URL** (issue 655) is checked on every push arm, after `ownership_problem` and after the form matches, before the tag, branch or remote-deletion arm runs. The guard runs `git -C <dir> remote get-url --push --all origin` (`PUSH_URL_LOOKUP`) in the judged directory and in the hook's own environment, so the git configuration that applies to the push is the one the lookup reads (D13). git applies `remote.origin.pushurl`, `url.<base>.insteadOf` and `url.<base>.pushInsteadOf` itself; the guard never reimplements the rewriting. Every URL the lookup prints (`--all` lists each `pushurl` entry, and git pushes to all of them) must parse as a GitHub URL (`git@github.com:`, `ssh://git@github.com/`, `https://github.com/` or `http://github.com/`, one optional trailing `.git`) whose owner/name slug equals the repository the guard judged; a URL that is not GitHub, or names another repository, is refused as `unsafe push: origin's push URL <url> does not name <owner/name>`. A lookup that times out is refused as `unsafe push: push URL lookup timed out`, and one that cannot start, exits non-zero or prints nothing as `unsafe push: cannot resolve origin's push URL`. Each is a state refusal with no accepted-forms clause, since no rewording of the command changes it; a push whose text matches no form keeps its text refusal with accepted forms, whatever the push URL. PR creation, merge, release creation and branch deletion never run the lookup.

The forge adapter's two mutations are adjudicated too (#124, D9/D10). The **tag-push arm** sits inside the push verb and is judged before the branch arm: argv exactly `git push origin refs/tags/<tag>` with `<tag>` a SemVer `vMAJOR.MINOR.PATCH` (no leading zeros), standing authorization, and `git cat-file -t refs/tags/<tag>` (the base policy `git`, in the push's target directory: its `git -C` directory, else the payload `cwd`) printing exactly `tag`, so only an existing annotated tag is pushed; any other namespaced push keeps its refusal, except the remote-deletion arm's qualified `refs/heads/<branch>`, and the branch arm, including the legacy `git push origin <tag>`, is unchanged. **Release creation** (`gh release create`, operation `release`, label "release creation") is judged on the whole command like the merge, behind the same optional credential-scrub prefix: exactly `gh release create <tag> --repo <detected slug> --verify-tag --title "<title>" --notes-file <path>`, flags in that order and nothing before or after, a SemVer `<tag>`, standing authorization, a title that passes the same free-text check as `--subject`, and an absolute `<path>` without whitespace or any shell-active character. `--target`, `--draft`, `--prerelease` and every other flag are refused, and so is gh's alias `gh release new` (it routes to the same arm, whose grammar spells `create`). The feature arm of `gh pr merge` also refuses `--delete-branch` when the PR's head is the default branch or the repository's declared integration branch (`unsafe merge: --delete-branch would delete the permanent branch <head>`), judged after the PR lookup and before any protection lookup, and a head that is missing, null, empty or not a string is refused as `cannot read the PR head branch` (#116 D5). The guard is on `PATH` as `claude-bash-lifecycle-guard` (`home.packages`) so the adapter and the resolver find it by name; the registered hook path is unchanged. The spelling fixture `tests/fixtures/forge-adapter-spellings.json` drives both the adapter suite and the guard's allowed-row table; the guard never reads it at run time. The shape fixture `tests/fixtures/guarded-command-shapes.json` (#351) lists the push (remote deletion included), merge and branch-delete forms the delivery's ship stage spells and the dressed shapes agents reach for, each with the guard's verdict bare, behind `unset GITHUB_TOKEN && ` and behind `env -u GITHUB_TOKEN `; only the guard suite's shape table in `tests/test_claude_permission_guard.py` reads it (no skill-text check reads it any more, so a ship-stage spelling is not checked against it), and the guard never reads it either; its `invocation_shapes` section (issue 400) holds the guard-only rows. `form_values` (issue 402) is guard-only too: one value per guard placeholder, from which the guard suite fills and runs every form a refusal prints.

The **mergeability check** (issue 476) reads two more facts from the same PR lookup, whose `--json` field list is `state,baseRefName,headRefName,headRefOid,mergeStateStatus,url,statusCheckRollup`. Each merge arm runs it after its own shape judgment (the feature arm's permanent-head refusal, the release arm's integration-into-default check) and before its first gate (the feature arm's integration-base exemption and protection lookup, the release arm's rollup predicate), so a PR merged onto a declared integration base meets it before the exemption. A `mergeStateStatus` of exactly `BEHIND` is refused first, as `unsafe merge: the PR is behind its base <base>; repair: sync the branch with <base>, push it and wait for its required checks before merging`; then, only when the command carries `--match-head-commit`, a value other than the PR's `headRefOid` is refused as `unsafe merge: --match-head-commit <given> is not the PR head commit <headRefOid>; merge only a head you reviewed`. Any other non-empty merge state passes, `UNKNOWN`, `BLOCKED`, `DIRTY` and `UNSTABLE` included, and the check reads no protection setting. A `mergeStateStatus` that is missing, not a string or empty is refused as `cannot read the PR merge state`, and, with the flag, a `headRefOid` that is not 40 lowercase hex characters as `cannot read the PR head commit`; without the flag `headRefOid` is neither read nor demanded. GitHub stays the authority: it still compares `--match-head-commit` atomically with the merge and enforces its own up-to-date rule, which closes the window between this check and the merge.

The **plan-gated floor** (issue 552) replaces that protection demand for one answer only. When the feature arm's protection read of the default branch exits non-zero, the guard parses its stdout, gh's response body, and never its stderr: the **plan-gated answer** is a JSON object whose `status` is the string `403` and whose `message` is exactly `Upgrade to GitHub Pro or make this repository public to enable this feature.`. Only with that answer, and only when the repository's confirmed derived row declares at least one required check (a row with a problem, a literal `integration_bases` row and a repository without a row declare none), is the merge judged by the floor; every other non-zero answer (a 404 `Branch not protected`, a 403 for missing admin rights or a rate limit, a body that is not JSON, the plan-gated answer without declared checks) keeps `protection lookup failed: <diagnostic>`, and a timeout or a readable protection object keeps its verdict. The floor starts no child and reads only the PR lookup's facts, and the first failure is the verdict: the merge must carry `--match-head-commit`, which the mergeability check has held to the PR's `headRefOid`, so the rollup judged is the head GitHub merges (`unsafe merge: <base> cannot be protected on this repository's plan, so the merge must carry --match-head-commit with the reviewed PR head`); `statusCheckRollup` must be a list of objects, each a `CheckRun` with a string `name` or a `StatusContext` with a string `context` (`unsafe merge: cannot read the PR check rollup`); then each declared check, in row order, must be named exactly by at least one entry (`unsafe merge: <base> cannot be protected on this repository's plan, and the declared required check <name> is missing from the PR's check rollup`), and every entry naming it must be green (`unsafe merge: <base> cannot be protected on this repository's plan, and the declared required check <name> is not green (<observed>)`, the first non-green entry as `CheckRun <status>/<conclusion>` or `StatusContext <state>`, a fact that is not a string shown as `none`). Entries naming no declared check are ignored. Green has one home, from which the release arm's jq predicate is rendered: a `CheckRun` whose `status` is `COMPLETED` and whose `conclusion` is `SUCCESS`, `SKIPPED` or `NEUTRAL`, or a `StatusContext` whose `state` is `SUCCESS`. The floor is weaker than forge protection, because nothing stops a merge made outside the guard; a forge that later protects the branch answers the read with exit 0, and the protection demand governs again with no contract change. `test_an_argus_shaped_project_merges_under_the_plan_gated_floor` drives the floor end to end, with `guard-policy derive` run from source as the row check over a fixture fleet.

A refusal that lies in the command's text (each recognition refusal, a form the matcher refuses, a slot value, a merge arm while another arm remains) reads `lifecycle guard: unsafe <operation>: <problem>; accepted: <form>[; or <form>…]; optional prefix: unset GITHUB_TOKEN && | env -u GITHUB_TOKEN`, and branch deletion, which takes no prefix, omits the last clause. The forms come from `FORM_TABLE` in table order: before any PR lookup the whole table, except that the merge's release form, noted `(only <integration> into <default>)`, is listed only where the repository declares an integration branch distinct from its resolved default branch, and after the lookup only the arm the PR admits, none when its head is a permanent branch no arm fits. With a repository context `<slug>` becomes the detected slug and, once the default branch resolved, `<base>` one alternative per authorized base, and the note names both branches (`only dev into main`); every other slot stays a placeholder, and a recognition refusal, which builds no context, fills nothing and lists the merge's feature form alone. The clause's two spellings stand for the whole accepted prefix set (`unset N && `, `unset N M && `, `env -u N `, `env -u N -u M `, `N` and `M` distinct members of `GITHUB_TOKEN`, `GH_TOKEN`). A refusal of the repository or the forge state (authorization and row problems, an unresolvable default branch, a default-branch push, a permanent-branch deletion, head equal to base, a tag that is not an existing annotated tag, every PR, protection and rollup lookup or predicate failure, a PR behind its base, a `--match-head-commit` that is not the PR head, every plan-gated floor refusal, an unreadable PR merge state or head commit, timeouts, the invocation deadline) names only its problem, since no spelling would pass there.

A **lifecycle command** (issue 418) is admitted only in an allowlist grammar, checked before any other judgement once a lifecycle verb is found: `[unset GITHUB_TOKEN && ][cd <dir> && ]<verb> <args>`, where the scrub is one `unset` or `env -u` spelling of the credential names (its exact spelling is left to the verb's grammar), `<verb>` is `git push`, `git branch -d`, `gh pr create`, `gh pr merge` or `gh release create` (`git -C <dir>` before `push` or `branch -d`), and every word is plain (`[A-Za-z0-9_./:@%+=,-]`, not beginning with `=`, zsh's `=cmd` expansion), single-quoted, or double-quoted without `$`, a backtick, a backslash or `!` (so an owner's ship stage and the forge adapter's double-quoted text still passes), separated by spaces or tabs. Anything else (another segment or operator, a redirection, an expansion, a glob, a comment, a newline outside quotes, a quote glued to a word, a wrapper or assignment) refuses that verb as `unsafe <operation>: <first thing outside the grammar>; a lifecycle verb runs only alone, as ...` with its accepted forms. So the only directory change left is that leading `cd`: push and PR creation run in the directory it names when it is spelled `cd <dir> && ` with single spaces and `<dir>` is absolute with no `..` component (relative names follow `CDPATH`, and `..` is logical for `cd`), else they refuse with the `CD_PRELUDE_PROBLEM` text (`the directory the verb runs in cannot be resolved: ...`); a `git -C` directory joins onto it, and an absolute one stands alone. Merge, release creation and branch deletion are judged on the whole command and so still take no prelude. Residual: an alias or function defined in an earlier call or a startup file, and zsh `AUTO_CD`, can still move the directory unseen.

A **named repository** (issue 418): a PR creation or merge whose `--repo` names a repository other than its directory's, and which has a derived row in the compiled policy, is judged against that repository from its row, with no checkout read: the context is built from the slug, runs no `git` child, and takes the row's `default_branch` as the base once the row check confirms the row. A row the check does not confirm refuses with that row problem and never falls back to the directory. Without a row for the slug, the directory's refusal (`--repo ... is not the current repository ...`) stands. `--body-file` there fails closed (`cannot resolve the working tree to check --body-file against`), because there is no working tree to place the file against. Release creation and pushes stay judged against their directory.

## Pre-push hook

`lifecycle_guard.py --mode pre-push -- <remote> <url>` is the guard's second entry mode (issue 672), run by git itself as a `pre-push` hook, so the judgement does not depend on how a push is spelled: an alias, an `xargs` feed or a `git` reached through a wrapper all arrive at the hook as the same facts, the real push URL git resolved and one line per ref update on stdin. The hook reads those facts only as the text mode's push forms (`PRE_PUSH_FORMS`, pinned equal to the ids of `FORM_TABLE["push"]`) and judges them through the predicates the text mode shares (`push_url_slug_problem`, `push_arm_problem`, `branch_target_problem`, `annotated_tag_problem`), over the same base policy, compiled policy and row check, so no push rule is written twice: a branch deleted is `delete`, a branch created or fast-forwarded is `branch`, a tag created is `tag` (its tag object is the pushed sha), and a forced update, a moved or deleted tag and any other ref namespace match no form and are refused. The order is standing authorization, then the push URL, then each ref line in the order git handed them, and the first refusal wins; empty stdin admits once the repository checks pass, and a line that is not four space-separated fields, whose two shas are not hex of equal length 40 or 64, or that lacks its newline is refused as `cannot read the refs git handed the pre-push hook`. The hook judges only an agent session, one whose environment holds a non-empty `CLAUDECODE` (Claude Code exports it to every Bash child); outside one it judges nothing and no compiled policy or row check is read. git exports repository-local variables to hooks (`GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE` and the rest of `git rev-parse --local-env-vars`), which would make the row check's own `git` read the pushing repository in every registered root, so `pre_push_main` reads that list with the base policy's `git` and removes the names from the row check's environment only, in every session. Every other `git` query the judgement makes (the repository's origin and default branch, the fast-forward and tag checks) keeps the original environment, so the repository git was told to push from, by `GIT_DIR` or `--git-dir`, is the one judged wherever the hook's cwd is, including a work tree without a `.git` and another checkout; the chained hook gets the original environment too. A lookup that fails, times out or prints nothing refuses. A refused ref prints `lifecycle guard pre-push: unsafe push: <problem>` on stderr, with the text mode's problem wording, and exits 1, which aborts the push; a malformed invocation, a bad base policy or an unreadable variable list prints `lifecycle guard pre-push: <reason>` and exits 1, and the base policy loads first in both modes, so an invalid store policy refuses every push just as it blocks every Bash call. This hook is the authoritative check and the text guard stays the first line (O1): it refuses early, with accepted forms, what the hook would refuse late. `tests/test_git_pre_push_hook.py` runs real `git push` through the hook against `agent_tools.push_fixture`, a hermetic fixture whose fake ssh carries `git@github.com:<slug>.git` to a local bare repository and whose environment drops every inherited `GIT_*` variable, so no rewrite in the host's own git configuration can reach a network. **What it does not stop (residual).** The hook catches mistaken spellings (an alias, an `xargs` feed, a wrapper), not a deliberate bypass, and one indirection is enough for that. It judges only when `CLAUDECODE` is non-empty and the text guard reads only the Bash command text, so a push hidden in a script file written with the unguarded Write tool and run as `sh ./push.sh` is never seen by the text guard. That script can run `git push --no-verify` or `git -c core.hooksPath=/dev/null push`, which skip the hook, or `unset CLAUDECODE` first, which leaves it nothing to judge. A launcher that starts the child with the variable gone (`sudo`, `nix-shell --pure`, `subprocess.run(..., env={})`) does the same, and a `core.hooksPath` key built by expansion or a git config file edited directly means the managed hook does not run. The text guard's refusal to strip the marker catches the plain spelling only. The protection that holds against a deliberate bypass is branch protection on the default branch (`just protect-main`, the required checks), not this hook.

**Chaining and git-lfs (D5).** A global `core.hooksPath` disables every per-repository hook, so the hook judges first and then chains: after an admitted agent judgement, and always outside an agent session, `chain_pre_push` runs `<git-common-dir>/hooks/pre-push` when it is a regular, executable file whose `realpath` differs from that of the hook git is running (a repository hook linking to the managed one cannot recurse). The common directory is used, not the per-worktree one, so a linked worktree runs the main repository's hook. The chained hook gets git's argv, the identical stdin bytes, the original environment from before the D10 scrub and the hook's own stdout, stderr and cwd, and its exit status becomes the push's (a signal death is 1); a refused agent push runs no repository hook and no git-lfs. When git cannot answer the two `rev-parse` queries (non-zero, timed out or empty) the hook prints `lifecycle guard pre-push: cannot locate the repository's own hooks` and exits 1. The other managed hooks are the POSIX shim `git-hooks/chain-hook`, one copy per hook name with `@git@` and `@gitlfs@` filled in at build time, which applies the same rule from `basename "$0"` and starts no process but `git` and `realpath` before it execs. git-lfs installs its hooks into `git rev-parse --git-path hooks`, which is now the read-only store directory, so when no repository hook runs, `pre-push`, `post-checkout`, `post-commit` and `post-merge` run `<git-lfs> <name> <args>` with the same stdin for an LFS repository (a repository hook takes precedence, as git-lfs never overwrites one), and the fallback is off when the LFS binary is empty. A repository counts as an LFS repository when `<git-common-dir>/lfs` is a directory or `git config --get lfs.storage` prints a value, since `lfs.storage` keeps the objects elsewhere (the shim and `chain_pre_push` apply the same rule). A repository `pre-push` hook that is executable text with no `#!` line runs through `/bin/sh`, as git retries it on an exec format error. Four hook names get no shim, so a repository's own hook of that name does not run: `push-to-checkout` (when present it replaces git's built-in check), `fsmonitor-watchman` (invoked by path through `core.fsmonitor`), and `reference-transaction` and `post-index-change` (git fires them on routine ref and index writes, a cost every repository on every host would pay). Two residuals: installers that honour `core.hooksPath` (`pre-commit install` refuses, lefthook writes into the store) must target `<git-common-dir>/hooks`, which a human can do as `GIT_CONFIG_GLOBAL=/dev/null <installer>` and the chain then finds; and a repository-local `core.hooksPath` (husky, git-hooks.nix) overrides the global one, so the managed hook does not run there. `git lfs install` inside a repository cannot write the store directory, and no longer needs to.

**Installation.** `default.nix` builds the store directory `agent-git-hooks` (`agentGitHooks`): the `pre-push` wrapper and one chain shim for each name in `agentGitHookNames`, and sets `programs.git.settings.core.hooksPath` to it in the shared `home/common` module, so every host, darwin and Linux, carries the setting with no host or platform condition (O4). The wrapper is the `claude-bash-lifecycle-guard` exec line with `--mode pre-push`, the LFS binary (when `programs.git.lfs` is enabled) and git's `--` arguments appended, so it shares the guard's interpreter, source and three policy arguments (`--base-policy`, `--policy`, `--derive-bin`); `tests/test_claude_code_installed.py` pins that equality. The derivation's build check fails `just build` on a shim that fails the shell dry run, on a `pre-push` that exits non-zero in a scratch repository outside an agent session with empty stdin, or on a missing hook name. git re-reads its configuration on every invocation, so a session's next push after a switch already uses the new path. Residual (D5): an installer that honours `core.hooksPath` cannot install into the read-only store directory, so it must target `<git-common-dir>/hooks`, where the chain finds it. Test fixtures that push to a local remote run git with `GIT_CONFIG_GLOBAL=/dev/null`, because on a switched host the managed hook judges every push an agent session's test makes.

## The raise label

The hook also refuses an agent adding the `instruction-budget-raise` label (#294): in a command that mentions that label, case-insensitively, a `gh` invocation in any position whose `--add-label` value contains it is blocked, in every repository and before any other verb is judged, and an unparseable command, `eval`/`sh -c` source or a quoted `$(…)`/backtick substitution that mentions the label blocks too, while other labels, `--remove-label` and quoted mentions pass. This catches mistakes and is not enforcement: Codex has no hook, and `gh api`, GraphQL and `curl` are outside the guard, so the protection that holds is the required `Instruction Budget` check plus the user seeing the label on the PR (`.agents/knowledge/rejections/ungated-agent-merges.md`).

## Guard policy

The guard reads two policy files with disjoint closed schemas, and a loader refuses a file with any other key set (issue 377 D1). The **base policy** is a store file, `claude-bash-lifecycle-guard-base-policy.json`, built from `lifecycleGuardBasePolicy` in `default.nix`: an object with exactly `authorized_owners`, `integration_bases`, `git_bin`, `gh_bin` and `jq_bin`, which are the literal `authorizedOwners` and `integrationBases` rows (an `integration_bases` row exists only for a repository that is not a registered project, and the built set is currently empty) and the store paths of `git`, `gh` and `jq`. The **compiled policy** is the user state file `~/.agents/state/guard/policy.json`: an object with exactly `derived_repositories` and `derivation`. A **derived row** is an entry of the compiled policy's `derived_repositories`, keyed by the exact repository slug, `{default_branch, integration_branch, required_checks, evidence}`, where `required_checks` is the sorted list of check names the project's contract declares in `bindings.vcs.merge.required_checks`, `[]` when it declares none. The **row check** is the store script `claude-guard-row-check`, which the wrapper passes as `--derive-bin`. No member exists in both files, so neither file is a valid instance of the other, and each member has one trust rule:

| Member | File | Rule |
|---|---|---|
| `authorized_owners` | base policy | Store value only. |
| `integration_bases` | base policy | Store value only; the compiled policy never removes or changes a literal row. |
| `git_bin`, `gh_bin`, `jq_bin` | base policy | Store value only; the only programs the guard runs besides the row check. |
| `derived_repositories` | compiled policy | A candidate row per slug, used only after the row check confirms it in this invocation. |
| `derivation` | compiled policy | Recorded for the reader; `null` or an object; the guard does not interpret it. |

The guard loads the base policy on every call, after the detaching-word check. It opens the compiled policy only when it judges a repository-bound verb (push, PR creation, merge or release creation), at the point it builds the repository context, so a command with none of those, branch deletion included, never reads it. The compiled policy supplies no value the guard executes, and the guard runs only the base policy's three tools and the row check, which it finds by the absolute path `--derive-bin` names (the wrapper is described under `## Allow surface and lifecycle guard`).

`guard-policy compile` writes the compiled policy (its contract is in [`python/README.md`](../../../python/README.md) § guard-policy): the two members and nothing else, after reading the base policy to validate it and to check each derived slug against its literal rows. The installed `claude-guard-policy` runs it with fixed arguments, the base policy and the compiled path, and takes none of its own; the home-manager activation step `claudeGuardPolicy` runs that command on every home-manager activation, after `linkGeneration` and before the settings copy, and never aborts the activation. The compiled policy is a user-writable state file, because compiling at activation cannot write the store. Since issue 377 the guard takes no trusted member from it and treats each derived row as a claim to be confirmed before it is relied on (issue 377 D1, D2).

A derived row exists for each registered project whose proof held at that compile and whose slug and two branch names `load_compiled_policy` accepts; a name it refuses, such as the branch `dev+ci`, costs that project its row (`name_unsupported`) instead of making the guard drop the whole compiled policy. A row authorizes its own repository and no other of its owner, and its `integration_branch` is the repository's integration base when it differs from the default branch.

**Row check.** `claude-guard-row-check` is a bash script under `-p`, which ignores `BASH_ENV` and exported functions; it unsets `BASH_ENV` and `ENV`, puts the store `git`, `gh` and `ssh` first on `PATH`, as `claude-guard-policy` does, and execs the `guard-policy` launcher, itself a bash script under `-p`, as `guard-policy derive` with its arguments; it is not installed on `PATH`. That launcher, and the one `claude-guard-policy` execs, come from the `agentTools` module argument, which `home/common/agent-tools/default.nix` sets as the one application of `lib/agent-tools.nix` per home configuration, so the row check, the compile wrapper and every `~/.agents/bin` launcher exec one agent_tools environment (issue 467). The guard runs it as `<derive-bin> --repository <slug>`, and it re-derives that one repository's row from the fleet registry and the contract on `origin` with the compiler's own proof (the `derive` contract is in [`python/README.md`](../../../python/README.md) § guard-policy). For a repository that has a row, the guard checks in this order, and the first failure is the verdict: (1) the slug is also a key of the base `integration_bases`, which refuses; (2) `origin/HEAD` must name the row's `default_branch` (skipped for a named repository, which has no checkout: the row check itself proves the contract's default branch against `origin`'s listed default, and the named repository's base is the confirmed row's `default_branch`); (3) the row check runs; (4) it must have exited 0 with an `outcome` of `derived` whose `row` has the compiled row's `default_branch` and `integration_branch`, and then its `required_checks`, equal as lists, order included (a report whose `row.required_checks` is not a list of strings is unreadable). `evidence` is not compared, because its commit moves with every push to the branch. A refusal at step 1, 3 or 4 names the repository, the reason (the row check's reason code, the differing branches, or `it derives required checks <derived>, the row names <compiled>` with each list as compact JSON) and `claude-guard-policy` as the repair, except that a row check that timed out at step 3 ends `timed out; transient: rerun the command` instead, because a plain rerun clears it and recompiling the policy cannot speed it up (issue 476); step 2's names the live and recorded branch. The check runs once per repository context, when that context is built (a command whose pushes name several `git -C` directories builds one context per distinct `git -C` directory and one per named repository, all under the one invocation deadline), and only for a repository that has a row: a repository with no row is judged by the base policy with no check and no network read. A repository with a row is judged by the row and never falls back to its owner literal when the check fails.

The row check runs with stdin at `/dev/null`, its output captured, its own process group and the guard's environment without `BASH_ENV`, `ENV` and every `BASH_FUNC_` variable, so no shell startup file or exported function can print a report the check never derived. It is bounded by the smaller of `--derive-timeout-seconds` (15 s) and the time left in the guard's 27-second invocation deadline, which every child it starts shares and which keeps the verdict ahead of the hook's 30-second timeout (issue 377 D6). It is not started when no time is left, and on its bound the guard kills the whole group with `SIGKILL`, so the `git`, `ssh` and `gh` grandchildren do not outlive the verdict. Once the context exists, no other child starts unless its whole `--child-timeout-seconds` bound (5 s) fits before the deadline; `main` also checks the deadline at the top of each operation. When it does not fit, the guard refuses with its fixed message, that the 27-second invocation deadline leaves too little time for the next check so it was not started, and judges no later operation of a chained command (issue 377 D12). A child that reaches its own bound refuses, so the guard answers without relying on what the harness does with a timed-out hook.

**Cost and offline behaviour.** On every repository-bound verb in a repository that has a row, nix-config included (issue 377 D3), the row check costs one remote listing, one fetch only for a branch whose listed commit the checkout lacks, a sparse export of the contract and its projection files for each branch read, the resolver and one provider read (issue 385). Measured on 2026-10-13 on host `mbp`, 10 consecutive runs of the built row check for `elevenyellow/nodocom` took a median of 3.61 s and a maximum of 4.56 s (the first run), and none of the 10 fetched. An unreachable `origin` or provider fails the check (`fetch_failed` or `provider_unproven`) and refuses the verb: there is no fallback to a ref already present or to the unchecked row, and no availability is lost, because push, PR creation, merge and release creation each need the same remote or provider to succeed. Only a fetch writes a ref, so two sessions judged at once contend for a ref lock only when both fetch a missing commit into the same registered root; a fetch that loses the lock fails `fetch_failed` and refuses, a rerun clears it, and the guard takes no lock of its own.

**A bad file.** The guard opens either policy file without blocking and reads it only when the open descriptor is a regular file of at most 1 MiB (`POLICY_MAX_BYTES`), so a FIFO, a device such as `/dev/zero` behind a symlink, a directory or a file already larger at the open is refused before a byte is read, and a file that grows past the cap while read is refused too. A compiled policy that is missing, unreadable, not a regular file, over that size, not JSON or outside its schema (a #375 seven-member file included, until the next compile replaces it) contributes no row, whole file, and blocks nothing the base policy allows (issue 377 D4). When a repository-bound verb is then refused for standing authorization, the refusal adds the reason and names `claude-guard-policy`. This grants nothing: rows only add, a derived-only repository loses authorization, and an owner-literal repository is judged as an unregistered one, with no row to check `origin/HEAD` against. A base policy that is missing, unreadable, not a regular file, over that size or outside its schema still blocks every Bash call with `invalid policy`, because it is a store file the build check loaded and a bad one is an installation defect.

**Required checks and the schema-3 transition (issue 552).** The loader demands that a row's `required_checks` be a list of distinct non-empty strings, the resolver's own rule for the contract member, so a contract that resolves always yields a row the guard loads; any other value is a malformed row, and the whole compiled policy contributes no row. The compiler writes `derivation.schema_version` 3, whose rows carry the member. A schema-2 file lacks it, so this guard reads that file as contributing no row; the activation step recompiles on every switch, so the switch that installs this guard also writes a schema-3 file. A Claude Code session started before that switch still runs the previous guard, which reads a schema-3 file as contributing no row. In both cases only a repository that relies on a derived row for its authorization is refused, until the recompile or the session restart this section asks for after an agent_tools change; a repository authorized by an owner literal keeps its authorization.

**Literal and derived rows.** `guard-policy compile` refuses a project whose slug is a key of the base `integration_bases` as `literal_conflict`: the project gets no row and the literal row stays, and each compile reports the conflict. The compiled policy cannot subtract from the base, so a repository can carry both only when the compiled policy was edited or a literal row was added after the last compile, and the guard refuses it at step 1 above (issue 377 D5). What the guard authorizes is the base `authorized_owners` and `integration_bases` plus the derived rows the row check confirms.

The activation step treats the compiler's three outcomes as follows. Status 0 leaves the complete compiled policy. Status 1 leaves a compiled policy without the refused projects' rows, and the compiler's stderr line names each refused project with its reason code. Any other status removes the compiled policy, and the step says that registered projects have lost their derived guard row and with it their derived integration branch. In both cases only a repository that relies on a derived row for its authorization is refused until `claude-guard-policy` succeeds; authorization from the base policy (an authorized owner or a literal integration row) still applies, and no call is blocked by it. If the removal fails, the step reports that the path could not be removed, and the guard reads whatever is there: a directory or an unreadable or malformed file contributes no row, and a readable earlier policy stays in force, its rows still rechecked at use. The repair is `claude-guard-policy`, run from a shell that can fetch each project's `origin` and whose `gh` keyring credential reaches the provider; a rerun repairs only the refusals a missing network or credential causes, which are `fetch_failed` and `provider_unproven`, because it can only re-derive from the registry and `origin`, and the other codes name a registry, contract or remote that has to change first.

Rows are rechecked at use, so a registry or contract change that moves a row's branches refuses until the next compile (issue 126 D6, narrowed by issue 377 D2); a project registered after the last compile has no row until the next one.

**Residual.** The guard catches the mistakes of a cooperating session and is not a sandbox. Rewriting the compiled policy alone gains nothing: it cannot add an owner, an integration base or a program, and a forged row is refused at use. What stays user-writable (issue 377 D1, D2):

- The fleet registry. A session can add an entry, but the row check still demands that the repository's own branch on `origin` publishes a resolving contract that names that project id, that repository as tracker and as release target, and that the provider confirms the name. A registry edit therefore authorizes only a repository that already declares itself adopted and that the session could register with the registration command anyway.
- Transport and tool configuration: `~/.ssh/config`, git configuration and the `gh` credential decide what `origin` and the provider answer. A session that rewrites them and the registry can forge a derivation, which takes several deliberate edits to stores unrelated to the guard.
- The checkout's object store. A session that plants an object under the id `origin` lists forges that read, as it already could before a fetch that finds the object present (issue 385).
- `~/.claude/settings.json`, a writable copy: removing the hook removes the guard.
- The window between check and use: the verb runs after the verdict, and a remote that changes between them is not seen.

A process started before a switch can keep old store paths, so start a new Claude Code session after switching an agent_tools change. `/hooks` shows that session's loaded hook command, and `just show-claude-settings` shows the generation's registered path. A host that has not switched to a generation containing an adapter still runs the previous code throughout.

## Context meter

The context meter (issue 424) is the second command hook of the same `matcher = "Bash"` `PreToolUse` entry, after the guard: the `context-meter` launcher from the agent-tools command table, timeout 10 s, no arguments and no matcher of its own, so the guard's registration is unchanged. Claude Code runs it before every Bash call; its contract is in [`python/README.md`](../../../python/README.md) § `context-meter`.

It rewrites every `workflow-state progress` invocation in a command so the gate sees the agent's measured context, never the model's own figure: each argparse spelling of `--context-tokens` is dropped and the value measured from the agent's transcript is inserted right after `progress`. A call whose context cannot be measured only loses the model's value, the ceiling and headroom flags are never touched, and a rewrite that fails its proof, or a command the lexer cannot tokenise, passes through unchanged with a `systemMessage` saying so. Each rewritten call also carries a short note saying that the value was measured.

It also tells an owner once per crossing to run its phase gate. Owners are the agents that ran `workflow-state progress`, `workflow-state mark-progress` or `sdd-gate` with an `--action-id`; the first measurement at or above `phase_budget.crossing_threshold(current(), phase)`, 200,000 for every phase unless `AGENT_PHASE_BUDGET` overrides it, adds one instruction to run the gate, unless that call is a progress call the meter rewrote to carry the measurement (it is already running the gate), and it fires again only after a measurement below the threshold. The state is one file per session and agent under `~/.agents/state/context-meter/`, never pruned (a known limitation). Parallel calls from one owner serialise on an exclusive lock on that file, held only for a read-decide-write.

The meter grants nothing. It prints no permission decision and never exits 2, so the guard judges the original command exactly as before. It fails open: on a progress call, an unmeasurable context or an unchanged call is reported in a user-visible `systemMessage` (any other call with an unmeasurable context prints nothing), and an unexpected error exits 1 with a traceback, leaving the call as the agent wrote it. A session's first tool call is always unmeasured, because Claude Code runs the hook before that turn's usage record reaches the transcript (spec D20). One limitation follows from running beside the guard: when the guard denies the call that carries the crossing instruction, the instruction is swallowed with it, and the state already records the owner as notified. A host without hooks runs no meter, so it sends no count.

## Guard/core decision

The [guard/core decision](../../../.agents/artifacts/specs/2026-09-20-issue-116-permission-guard-core-design.md) preserves the required-check floor for both merge arms and records the current protection exceptions as gaps (the permanent-head deletion check is closed by the D5 repair above). Core grants cannot override the final guard, host or provider verdict; the release core's forge `pr_merge` invoke is admitted under issue 554: the adapter refuses it unless protection holds strict required checks with admin enforcement, and `.agents/artifacts/evidence/release-554-native-certification.json` is its native certification. Any other core admission still waits for the named enforcement and conformance work. The plan-gated floor (issue 552) is a native-guard exception of the kind issue 116 D6 lists as a gap, accepted by the owner for a repository whose forge cannot protect its default branch; it is not core-admission evidence.

## Plugins

`codex-plugin-cc` is the one plugin built from a pinned input plus a repo-owned patch (`patches/agent-plugins/codex-plugin-cc.patch`, the only patch in that directory); `lib/agent-plugins.nix` patches it into a store path and names its marketplace `nix-codex`. Claude enables two plugins from marketplaces of two different source types — `skill-creator@claude-plugins-official` from a `github` marketplace and `codex@nix-codex` from a `directory` marketplace pointed at that store path. Codex has no Nix-declared marketplace: its marketplaces and plugins are runtime-managed inside `~/.codex/config.toml`, which Nix does not own.

A foreground `task --reviewer` claims the regular files behind its stdin and stdout under `<state root>/stdio-claims/<dev>-<ino>/<pid>.json`. It links its own entry first and then lists the directory, and it exits 1 before reading its packet when the list holds another live pid. An entry records its writer's process start time (`/proc/<pid>/stat`, else `ps -o lstart=`), so a pid that an unrelated process has since reused does not hold a claim; an entry without a readable start time counts as held while its pid is alive. It never deletes another pid's entry, so an entry left by a killed reviewer is ignored rather than recovered (#693). A reviewer that wrote a non-empty stdout file leaves a `finished.json` beside the entries (size and mtime of its output, pruned after an hour), and a later reviewer whose stdout file still has exactly that size and mtime exits 1: its shell opened and truncated the file before the first reviewer wrote, so running would overwrite the first object from offset 0. The output guard covers only reviewers whose lifetimes overlap, or whose redirects were opened before an earlier reviewer finished. The claim and the marker act only while a reviewer process is starting or running, so they cannot see a caller's shell opening the shared file with `>` after reviewer A has exited and before A's caller has read it: that reviewer finds an empty file, is admitted, and A's caller then reads its object as A's review. Likewise the claim guards a shared packet only against two reviewers reading it at once: it cannot see the callers' own shell writes to a fixed packet path, so an admitted reviewer can still read a packet that another caller overwrote before it started. Once a reviewer has exited, neither an output path nor a packet path is kept safe by the companion; only the per-call `mktemp -d` directory that the codex-collaboration skill asks each caller to use keeps them apart (#693).

## Accounts

`accounts/` is a Claude Code mod plus its launcher, `bin/claude-account`, for running several Claude accounts side by side. Each account is a profile directory `~/.claude-accounts/profiles/<name>` used as `CLAUDE_CONFIG_DIR`: the login is the profile's own, while settings, `CLAUDE.md`, skills, agents, plugins and transcripts are links to the `~/.claude/<entry>` paths (never to their store targets, so they follow generations). A project is bound to an account in `~/.claude-accounts/bindings.tsv`, keyed by the main checkout so every worktree shares the binding; a directory without its own binding takes its nearest bound parent's, and `default` is recorded like any account so it can override one. Rewrites of that file are serialized by a `bindings.tsv.lock` directory. `~/.claude.json` is the exception to the links: a new profile gets a one-time copy without the login, so an MCP server merged into `~/.claude.json` later (the `palmierProMcp` pattern) does not reach existing profiles until it is merged into `~/.claude-accounts/profiles/<name>/.claude.json` too. That state is runtime-owned; Nix owns only the code.

`default.nix` builds the folder into one store path (`accountsMod`), rewriting the launcher's `jq`, `git`, `curl` and real-`claude` paths and its cache-proxy URL, and installs `claudeWithAccounts` as `programs.claude-code.package`: `claude` on PATH is a script that runs `claude-account run`, which picks the bound account (or `CLAUDE_ACCOUNT=<name>` for one launch), adds the mod to `CLAUDE_CODE_PLUGIN_DIRS` and starts the pinned binary (waiting on it, so the `/account` switch below can relaunch it). A `CLAUDE_CONFIG_DIR` the caller set to something outside the profiles is kept (the mod is still added), unless `CLAUDE_ACCOUNT` asks for an account. `home/linux/claude-local` uses the pinned binary directly and is not account-aware. The mod loads from the read-only store path; the engine's only complaint is a debug-log line that it could not lay its editor types there.

In a session, `/account` lists, `/account add <name>` creates, `/account <name>` or `/account default` binds the project and switches the running session to that account: the engine reads its credential once and offers plugins no way to swap it, so `run` waits on `claude` instead of exec'ing it (exporting its pid as `CLAUDE_ACCOUNT_LAUNCHER`), and the mod calls `claude-account switch <name> <session id>`, which writes `~/.claude-accounts/switch/<launcher pid>` and sends TERM to the session's `claude` (the ancestor whose parent is that launcher, so nothing else is signalled); `run` then relaunches `claude --resume <session id>` under the new account. Transcripts are shared, so the conversation carries over; the first launch's other flags do not, and a turn still running is cut off. A session that `run` did not start (an IDE, a pre-switch launch) keeps its account, and `/account` says to exit and run `claude -c`. `claude-account status` (or `/account status`) also shows every account's 5-hour and weekly usage, fetched in parallel from the OAuth usage endpoint with each account's stored token (the macOS keychain item `Claude Code-credentials[-<sha256(config dir)[:8]>]`, or `<config dir>/.credentials.json` elsewhere). It only reads the token and never refreshes it, because a refresh would race a running `claude`; an account whose token has lapsed is shown as expired until `CLAUDE_ACCOUNT=<name> claude` is started once. The first launch under a new account asks for the sign-in; `claude-account login <name>` does it ahead of time, and `claude-account rm <name>` deletes a profile.

To change the mod, edit `accounts/` and check it with `claude plugin validate home/common/claude-code/accounts` and `claude plugin test home/common/claude-code/accounts`; `just build` runs the built launcher once as a smoke check.

## Cache proxy

`claude` reaches the Anthropic API through `cache-proxy` (`python/README.md` § `cache-proxy`) while the proxy is healthy, unless launched with `CLAUDE_CACHE_PROXY=0`. Routing is on by default since #450, which re-measured the routed time-to-first-token gap that had made it opt-in in #438: the paired median difference, routed with the probe minus direct, was 9.7 ms, with the 95% CI's upper end at 149.2 ms. That upper end is over the +100 ms bound the measurement was planned against, so the planned rule was not met; the user chose the looser rule of an estimate within +100 ms after the measurement, since 100 pairs cannot narrow the CI enough to pass the planned rule (`docs/spikes/cache-proxy-ttft-gap.md` § Issue 450). The service runs with `--keepalive` (#423), which `python/README.md` § `cache-proxy` describes: it replays an idle subagent conversation's last request with `max_tokens=1` to keep its prompt cache warm, the replay being the one fact 2 of `docs/spikes/cache-proxy-spike.md` measured. Dropping `"--keepalive"` from `cacheProxyArgs` in `default.nix` and rebuilding turns the pings off. It also runs with `--reorder` (#429), which `python/README.md` § `cache-proxy` describes: each subagent's first user message is reordered so that sibling subagents of one type share a cached start-up prefix, and every other request passes through unchanged. The proxy never changes the `x-anthropic-billing-header` line; the re-test that admitted the reorder, with its billing-suffix answer, is `docs/spikes/cache-proxy-prefix-retest.md` § Attempt 2. Dropping `"--reorder"` from `cacheProxyArgs` and rebuilding turns it off. To compare either flag's effect, run the built launcher by hand in the foreground on `--port 0`, once with and once without that flag, and point one session at each by a caller-set `ANTHROPIC_BASE_URL` (the proxy's `listening` line gives the port) with `ENABLE_TOOL_SEARCH=true` and `CLAUDE_CODE_TOTAL_TOKENS_REMINDER=padded-countdown`, which a routed launch also exports; `claude-account` leaves a caller-set endpoint other than the proxy URL alone whether `CLAUDE_CACHE_PROXY` is unset, `0` or `1`. The proxy cannot tell a subagent that has finished for good from one waiting to be woken, so the accepted cost has two parts: a subagent whose last reply ended its turn (`end_turn`) stops being pinged once it has had two pings since its last thread request, about 14 minutes of cache, so one woken later pays a cache rewrite, while any other subagent, one pending a tool among them, is pinged while its session stays active, for up to 60 minutes; the `keepalive_end` lines measure both. `default.nix` holds the port, `27183`, in one binding: it runs the `cache-proxy` launcher with `--port 27183 --keepalive --reorder` and `SSL_CERT_FILE` set to the nixpkgs CA bundle as the launchd agent `claude-cache-proxy` on darwin (`RunAtLoad`, `KeepAlive`; stdout and stderr append to `~/Library/Logs/claude-cache-proxy.log`, which nothing rotates) and as the systemd user unit `claude-cache-proxy` on anis-desktop (`Restart=always`, `WantedBy=default.target`; its log is the journal), and it writes `http://127.0.0.1:27183` into the launcher's `CACHE_PROXY_URL`. The service starts at activation (`just switch`) and stays declared; until something answers on the port, a launch goes direct.

Before every launch (the early exec for a caller-chosen `CLAUDE_CONFIG_DIR`, the first launch and each `/account` relaunch) `claude-account run` reads `CLAUDE_CACHE_PROXY`. `0` runs no probe: it unsets an `ANTHROPIC_BASE_URL` equal to the proxy URL, inherited from a routed parent, and leaves any other alone. Any value but unset, empty, `0` or `1` stops the launch before claude starts, with `claude-account: CLAUDE_CACHE_PROXY must be 1, 0 or unset`. Unset, empty or `1` leaves alone an `ANTHROPIC_BASE_URL` set to anything but the proxy URL, since that is the caller's own endpoint. Otherwise it probes `GET /_proxy/health` with bash's own `/dev/tcp`, so the probe starts no curl or jq process (#450), under one 0.5 s deadline for the connect, the request and the answer: a 2xx answer whose body names `"service":"cache-proxy"` exports the proxy URL and `ENABLE_TOOL_SEARCH=true` unless the caller set that variable (Claude Code before 2.1.304 turns tool search off behind a non-first-party base URL; the pinned 2.1.310 already keeps it on, so the export only changes a launch whose `CLAUDE_BIN` names an older binary), and anything else unsets `ANTHROPIC_BASE_URL`, so the launch goes direct and a dead proxy costs at most half a second. A routed launch also exports `CLAUDE_CODE_TOTAL_TOKENS_REMINDER=padded-countdown` unless the caller set that variable, to any value including empty: Claude Code sends its `<total_tokens>` budget line only to api.anthropic.com, and without the line a routed turn opens with a thinking block far more often (#450). The variable is undocumented (https://github.com/anthropics/claude-code/issues/98464). A launch that goes direct exports nothing; one started inside a routed session inherits the value and keeps it, which for a model with the `total_tokens_reminder` capability is the first-party default. The probe runs only at launch: a session keeps the route it started with, and if the proxy dies mid-session the service manager restarts it while Claude Code retries. A routed session has no Remote Control, which Claude Code turns off behind a non-first-party base URL. `CLAUDE_CACHE_PROXY=0 claude` opts one launch out, which also keeps that launch's Remote Control; exporting `CLAUDE_CACHE_PROXY=0` in the shell opts every launch out. `claude-local` is never routed: it execs the pinned binary itself and exports its own `ANTHROPIC_BASE_URL`. One started inside a routed session inherits `ENABLE_TOOL_SEARCH=true` and `CLAUDE_CODE_TOTAL_TOKENS_REMINDER=padded-countdown`; from 2.1.304 on, tool search is the default behind any gateway regardless.

## Editing the codex-plugin-cc patch

To edit `patches/agent-plugins/codex-plugin-cc.patch`: work in a scratch clone of the pinned upstream rev (see `flake.nix`), apply with `git apply --unidiff-zero` (the patch is zero-context; plain `git apply` rejects it), regenerate with `git diff -U0 <pin>`, and bump `patchRevision` in `lib/agent-plugins.nix`. Run the plugin's suite as `env -u CLAUDE_PLUGIN_DATA -u CODEX_COMPANION_SESSION_ID -u CODEX_COMPANION_TRANSCRIPT_PATH node --test tests/*.test.mjs` — with the live Claude-session env unscrubbed, 4 upstream tests fail spuriously. The seven test files that write under the shared state root (`runtime`, `state`, `liveness`, `reviewer-detach`, `broker-reaping`, `worker-postmortem`, `reviewer-stdio-isolation`) call `pinHermeticStateRoot` (`tests/helpers.mjs`), which pins `CLAUDE_PLUGIN_DATA` to a private temp root and group-kills every broker recorded there at file teardown; `isolation.test.mjs` pins and restores a root of its own per test and is left alone. That, plus a `teardownBrokerSession` that kills by default and a broker that exits on its own once nothing wants it, is why a run deposits no `codex-plugin-test-*` state dirs in `~/.claude/plugins/data/codex-nix-codex/state/` and leaves no surviving `app-server-broker` or `codex app-server` processes. When two branches both edit this patch, reconcile it by applying each side to a scratch clone and three-way merging the *source trees*, then regenerating — never by merging the patch text: `patch -p1` applies a textually-merged zero-context patch at lenient offsets with no error, so a wrong merge is silent, and an identical `patchRevision` bump on both sides hides the collision from git's conflict list entirely. To assert anything *about* the patched plugin source (a plan's verification gate, a spot check), read the scratch clone or the built store path — never `grep` the patch text: a zero-context patch carries no file attribution per line, so a patch-wide `grep -c` counts hunk lines from every touched file at once and cannot tell you which file a match sits in.
