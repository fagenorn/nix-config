# Claude Code module

## Settings

The `env` of the generated `~/.claude/settings.json` sets `BASH_MAX_TIMEOUT_MS` to `3600000` (60 minutes), the ceiling for an explicit Bash timeout, so an agent can run `just build` or `just agent-workflow-tests` in the foreground under a timeout above its duration (#261); `BASH_DEFAULT_TIMEOUT_MS` is left unset, so a command with no explicit timeout keeps the host's 120 s default.

`skillOverrides` hides twelve skills from the model's skill listing, each set to `user-invocable-only`, so `/<name>` still runs it (issue 425): the bundled `artifact-design`, `artifact-diagramming`, `artifact-capabilities` and `dataviz`, keyed by their bare names, and the claude.ai-synced `docx`, `pptx`, `xlsx`, `pdf`, `google-workspace`, `morning`, `import-memory` and `skill-creator`, keyed by their full `anthropic-skills:<name>` names. Claude Code matches a synced skill's full name before its bare one, so a user or project skill that shares a bare name stays listed. A plugin's skills ignore user-level overrides and leave the listing only when their plugin is disabled, so the skill-creator kept listed is the plugin's `skill-creator:skill-creator` and the hidden one is the claude.ai copy. The three Artifact skills are registered only in sessions that have the Artifact tool, so their entries take effect only there. `skillOverrides` also sets five claude.ai-synced skills to `off`, which removes them from the listing and from `/<name>` (issue 735): `docs`, `chrome-browser`, `built-in-browser`, `computer-use` and `deep-research`, keyed by their full `anthropic-skills:<name>` names. `permissions.deny` holds one rule, `mcp__claude_ai_Claude_Docs`, which removes every tool of the claude.ai Claude Docs connector on every host (issue 735). The server-wide rule keeps the other claude.ai connectors. `disableClaudeAiConnectors` or `ENABLE_CLAUDEAI_MCP_SERVERS=false` would drop them all, so neither is set. `tests/test_claude_code_installed.py`, run by `just agent-installed-skill-tests`, checks the map and `enabledPlugins` in the built settings.

The generated settings set `statusLine` to the `owner-actions statusline` store launcher (issue 624) on every host. It shows `owner N (oldest Xd)` for the cwd's repo only when that repo is in the fleet registry and has open issues or PRs labelled `owner-action` or `agent:human-required`, followed by `, answered M` for the issues whose decision prompt is fully ticked and waits for a run (`owner-answered`; `answered M` alone when nothing else needs the owner), and is blank otherwise. It never calls the network and refreshes its cache through a detached `owner-actions refresh`; the contract is the module docstring of [`python/agent_tools/claims/owner_actions.py`](../../../python/agent_tools/claims/owner_actions.py).

## Allow surface and lifecycle guard

Use `just show-claude-settings` to build and print the settings JSON (failing unless discovery finds exactly one artifact); its 22-entry allow surface allows `artifact-budget` and `forge-issue` outright, bare and as `~/.agents/bin/…`, and hands five lifecycle verbs (`git push`, `gh pr create`, `git branch -d`, `gh pr merge`, `gh release create`), and the raise-label rule, to a fail-closed `PreToolUse` hook. That hook's Python is `home/common/claude-code/lifecycle_guard.py`, a standard-library-only file that imports nothing from `agent_tools`: the registered command is a store wrapper that clears `NIX_PYTHON*` and runs it under `python3 -I` with `--base-policy` naming the store base policy, `--policy` naming the compiled policy at `~/.agents/state/guard/policy.json`, a path fixed at evaluation time from the configured home directory, and `--derive-bin` naming the store row check, so an owner change never touches the source. `just build` fails when the guard source or the base policy cannot load, because the wrapper's build check runs the guard as registered on a harmless payload that has no repository-bound verb. Bare `Agent` remains inert under `defaultMode = "auto"`. The guard's contract is the module docstring of `lifecycle_guard.py`, and its decisions are the records in `docs/areas/guard/adr/`.

## Console hooks

The generated settings post five events (`Stop`, `StopFailure`, `PermissionRequest`, `Notification`, `SessionEnd`) to the console at `http://127.0.0.1:27184/api/hooks` as HTTP hooks with a 2 s timeout, and run `SessionStart` through a command hook with a 5 s timeout, because `SessionStart` takes no HTTP hook (#829). That command is the store script built from `console-session-start.sh`: a dash shebang and a store curl, not a Python command, because a Python process alone costs more than the 10 ms budget a hook call may add. `allowedHttpHookUrls` is set at user level to `http://127.0.0.1:27184/*`, so any other HTTP hook URL is now blocked until it is added there. The console answers every hook with an empty `204`, so it never decides a permission or a stop. A stopped console refuses the connection at once and costs the session one dash and one curl start; one that accepts and never answers is abandoned by curl's 1 s `--max-time`, and the script always exits 0 with no output, since `SessionStart` stdout would enter the session's context. The template's comment and ADR-console-004 hold the reasoning.

## Plugins

`codex-plugin-cc` is the one plugin built from a pinned input plus a repo-owned patch (`patches/agent-plugins/codex-plugin-cc.patch`, the only patch in that directory); `lib/agent-plugins.nix` patches it into a store path and names its marketplace `nix-codex`. Claude enables two plugins from marketplaces of two different source types — `skill-creator@claude-plugins-official` from a `github` marketplace and `codex@nix-codex` from a `directory` marketplace pointed at that store path. Codex has no Nix-declared marketplace: its marketplaces and plugins are runtime-managed inside `~/.codex/config.toml`, which Nix does not own. The patched `task --json` payload also carries `turnStatus` (the final turn's status) and `error` (the message of the app-server `error` notification the turn received, or `null`). The reasoning for the pin and the patch is ADR-hosts-006.

A foreground `task --reviewer` claims the regular files behind its stdin and stdout under `<state root>/stdio-claims/<dev>-<ino>/<pid>.json`. It links its own entry first and then lists the directory, and it exits 1 before reading its packet when the list holds another live pid. An entry records its writer's process start time (`/proc/<pid>/stat`, else `ps -o lstart=`), so a pid that an unrelated process has since reused does not hold a claim; an entry without a readable start time counts as held while its pid is alive. It never deletes another pid's entry, so an entry left by a killed reviewer is ignored rather than recovered (#693). A reviewer that wrote a non-empty stdout file leaves a `finished.json` beside the entries (size and mtime of its output, pruned after an hour), and a later reviewer whose stdout file still has exactly that size and mtime exits 1: its shell opened and truncated the file before the first reviewer wrote, so running would overwrite the first object from offset 0. The output guard covers only reviewers whose lifetimes overlap, or whose redirects were opened before an earlier reviewer finished. The claim and the marker act only while a reviewer process is starting or running, so they cannot see a caller's shell opening the shared file with `>` after reviewer A has exited and before A's caller has read it: that reviewer finds an empty file, is admitted, and A's caller then reads its object as A's review. Likewise the claim guards a shared packet only against two reviewers reading it at once: it cannot see the callers' own shell writes to a fixed packet path, so an admitted reviewer can still read a packet that another caller overwrote before it started. Once a reviewer has exited, neither an output path nor a packet path is kept safe by the companion; only the per-call `mktemp -d` directory that the codex-collaboration skill asks each caller to use keeps them apart (#693).

## Accounts

`accounts/` is a Claude Code mod plus its launcher, `bin/claude-account`, for running several Claude accounts side by side. Each account is a profile directory `~/.claude-accounts/profiles/<name>` used as `CLAUDE_CONFIG_DIR`: the login is the profile's own, while settings, `CLAUDE.md`, skills, agents, plugins and transcripts are links to the `~/.claude/<entry>` paths (never to their store targets). A project is bound to an account in `~/.claude-accounts/bindings.tsv`, keyed by the main checkout so every worktree shares the binding; a directory without its own binding takes its nearest bound parent's, and `default` is recorded like any account so it can override one. `claude-account run` no longer reads the table (ADR-hosts-008); `list`, `status`, `use` and `/account <name>` still show and record it until a later change removes them. Rewrites of that file are serialized by a `bindings.tsv.lock` directory. `~/.claude.json` is the exception to the links: a new profile gets a one-time copy without the login, so an MCP server merged into `~/.claude.json` later (the `palmierProMcp` pattern) does not reach existing profiles until it is merged into `~/.claude-accounts/profiles/<name>/.claude.json` too. That state is runtime-owned; Nix owns only the code. Why profiles link rather than copy: ADR-hosts-005.

`default.nix` builds the folder into one store path (`accountsMod`), rewriting the launcher's `jq`, `git`, `curl` and real-`claude` paths and its cache-proxy URL, and installs `claudeWithAccounts` as `programs.claude-code.package`: `claude` on PATH is a script that runs `claude-account run`, which picks the account the console chooses (ADR-hosts-008: the console's `GET /api/profile` answer under a one-second deadline, else the first line of `~/.claude-accounts/chosen-profile`, else the most recently used signed-in named profile, else the first named profile by name, those last two skipping a profile the owner excluded in the console (`GET /api/excluded`), and the client unprofiled only when no named profile exists or every one is excluded; `CLAUDE_ACCOUNT=<name>` overrides one launch), adds the mod to `CLAUDE_CODE_PLUGIN_DIRS` and starts the pinned binary (waiting on it, so the `/account` switch below can relaunch it). A `CLAUDE_CONFIG_DIR` the caller set to something outside the profiles is kept (the mod is still added), unless `CLAUDE_ACCOUNT` asks for an account. `home/linux/claude-local` uses the pinned binary directly and is not account-aware. The mod loads from the read-only store path; the engine's only complaint is a debug-log line that it could not lay its editor types there.

In a session, `/account` lists, `/account add <name>` creates, `/account <name>` or `/account default` binds the project and switches the running session to that account: the engine reads its credential once and offers plugins no way to swap it, so `run` waits on `claude` instead of exec'ing it (exporting its pid as `CLAUDE_ACCOUNT_LAUNCHER`), and the mod calls `claude-account switch <name> <session id>`, which writes `~/.claude-accounts/switch/<launcher pid>` and sends TERM to the session's `claude` (the ancestor whose parent is that launcher, so nothing else is signalled); `run` then relaunches `claude --resume <session id>` under the new account. Transcripts are shared, so the conversation carries over; the first launch's other flags do not, and a turn still running is cut off. A session that `run` did not start (an IDE, a pre-switch launch) keeps its account, and `/account` says to exit and run `claude -c`. `claude-account status` (or `/account status`) also shows every account's 5-hour and weekly usage, fetched in parallel from the OAuth usage endpoint with each account's stored token (the macOS keychain item `Claude Code-credentials[-<sha256(config dir)[:8]>]`, or `<config dir>/.credentials.json` elsewhere). It only reads the token and never refreshes it, because a refresh would race a running `claude`; an account whose token has lapsed is shown as expired until `CLAUDE_ACCOUNT=<name> claude` is started once. The first launch under a new account asks for the sign-in; `claude-account login <name>` does it ahead of time, and `claude-account rm <name>` deletes a profile.

To change the mod, edit `accounts/` and check it with `claude plugin validate home/common/claude-code/accounts` and `claude plugin test home/common/claude-code/accounts`; `just build` runs the built launcher once as a smoke check.

## Cache proxy

`claude` reaches the Anthropic API through `cache-proxy` (`python/agent_tools/hosts/cache_proxy.py`) while the proxy is healthy, unless launched with `CLAUDE_CACHE_PROXY=0`; routing is on by default (ADR-hosts-004). The service runs with `--keepalive` (#423), which `python/agent_tools/hosts/cache_keepalive.py` describes: it replays an idle subagent conversation's last request with `max_tokens=1` to keep its prompt cache warm (ADR-hosts-002 records why, and what it costs). Dropping `"--keepalive"` from `cacheProxyArgs` in `default.nix` and rebuilding turns the pings off. It also runs with `--reorder` (#429), which `python/agent_tools/hosts/subagent_prefix.py` describes: each subagent's first user message is reordered so that sibling subagents of one type share a cached start-up prefix, and every other request passes through unchanged (ADR-hosts-003). Dropping `"--reorder"` from `cacheProxyArgs` and rebuilding turns it off. It also runs with `--sense-limits` (#860), which reads each response's unified rate-limit headers and the request's account and session and posts the reading to the console at `http://127.0.0.1:27184/api/readings` (ADR-hosts-007); dropping `"--sense-limits"` from `cacheProxyArgs` and rebuilding turns it off. To compare either flag's effect, run the built launcher by hand in the foreground on `--port 0`, once with and once without that flag, and point one session at each by a caller-set `ANTHROPIC_BASE_URL` (the proxy's `listening` line gives the port) with `ENABLE_TOOL_SEARCH=true` and `CLAUDE_CODE_TOTAL_TOKENS_REMINDER=padded-countdown`, which a routed launch also exports; `claude-account` leaves a caller-set endpoint other than the proxy URL alone whether `CLAUDE_CACHE_PROXY` is unset, `0` or `1`. `default.nix` holds the port, `27183`, in one binding: it runs the `cache-proxy` launcher with `--port 27183 --keepalive --reorder --sense-limits` and `SSL_CERT_FILE` set to the nixpkgs CA bundle as the launchd agent `claude-cache-proxy` on darwin (`RunAtLoad`, `KeepAlive`; stdout and stderr append to `~/Library/Logs/claude-cache-proxy.log`, which nothing rotates) and as the systemd user unit `claude-cache-proxy` on anis-desktop (`Restart=always`, `WantedBy=default.target`; its log is the journal), and it writes `http://127.0.0.1:27183` into the launcher's `CACHE_PROXY_URL`. The service starts at activation (`just switch`) and stays declared; until something answers on the port, a launch goes direct.

Before every launch (the early exec for a caller-chosen `CLAUDE_CONFIG_DIR`, the first launch and each `/account` relaunch) `claude-account run` reads `CLAUDE_CACHE_PROXY`. `0` runs no probe: it unsets an `ANTHROPIC_BASE_URL` equal to the proxy URL, inherited from a routed parent, and leaves any other alone. Any value but unset, empty, `0`, `1` or `required` stops the launch before claude starts, with `claude-account: CLAUDE_CACHE_PROXY must be 1, 0, required or unset`. `required` (#1009, used by the console's capacity probe) probes the same way and routes a healthy launch the same way, decides again an `ANTHROPIC_BASE_URL` the caller set to another endpoint, and otherwise stops the launch before claude starts with `claude-account: CLAUDE_CACHE_PROXY=required and the cache proxy is not answering`, so such a launch is never direct. Unset, empty or `1` leaves alone an `ANTHROPIC_BASE_URL` set to anything but the proxy URL, since that is the caller's own endpoint. Otherwise it probes `GET /_proxy/health` with bash's own `/dev/tcp`, so the probe starts no curl or jq process (#450), under one 0.5 s deadline for the connect, the request and the answer: a 2xx answer whose body names `"service":"cache-proxy"` exports the proxy URL and `ENABLE_TOOL_SEARCH=true` unless the caller set that variable (Claude Code before 2.1.304 turns tool search off behind a non-first-party base URL; the pinned 2.1.310 already keeps it on, so the export only changes a launch whose `CLAUDE_BIN` names an older binary), and anything else unsets `ANTHROPIC_BASE_URL`, so the launch goes direct and a dead proxy costs at most half a second. A routed launch also exports `CLAUDE_CODE_TOTAL_TOKENS_REMINDER=padded-countdown` unless the caller set that variable, to any value including empty: Claude Code sends its `<total_tokens>` budget line only to api.anthropic.com, and without the line a routed turn opens with a thinking block far more often (#450). The variable is undocumented (https://github.com/anthropics/claude-code/issues/98464). A launch that goes direct exports nothing; one started inside a routed session inherits the value and keeps it, which for a model with the `total_tokens_reminder` capability is the first-party default. The probe runs only at launch: a session keeps the route it started with, and if the proxy dies mid-session the service manager restarts it while Claude Code retries. A routed session has no Remote Control, which Claude Code turns off behind a non-first-party base URL. `CLAUDE_CACHE_PROXY=0 claude` opts one launch out, which also keeps that launch's Remote Control; exporting `CLAUDE_CACHE_PROXY=0` in the shell opts every launch out. `claude-local` is never routed: it execs the pinned binary itself and exports its own `ANTHROPIC_BASE_URL`. One started inside a routed session inherits `ENABLE_TOOL_SEARCH=true` and `CLAUDE_CODE_TOTAL_TOKENS_REMINDER=padded-countdown`; from 2.1.304 on, tool search is the default behind any gateway regardless.

## Editing the codex-plugin-cc patch

To edit `patches/agent-plugins/codex-plugin-cc.patch`: work in a scratch clone of the pinned upstream rev (see `flake.nix`), apply with `git apply --unidiff-zero` (the patch is zero-context; plain `git apply` rejects it), regenerate with `git diff -U0 <pin>`, and bump `patchRevision` in `lib/agent-plugins.nix`. Run the plugin's suite as `env -u CLAUDE_PLUGIN_DATA -u CODEX_COMPANION_SESSION_ID -u CODEX_COMPANION_TRANSCRIPT_PATH node --test tests/*.test.mjs` — with the live Claude-session env unscrubbed, 4 upstream tests fail spuriously. The seven test files that write under the shared state root (`runtime`, `state`, `liveness`, `reviewer-detach`, `broker-reaping`, `worker-postmortem`, `reviewer-stdio-isolation`) call `pinHermeticStateRoot` (`tests/helpers.mjs`), which pins `CLAUDE_PLUGIN_DATA` to a private temp root and group-kills every broker recorded there at file teardown; `isolation.test.mjs` pins and restores a root of its own per test and is left alone. That, plus a `teardownBrokerSession` that kills by default and a broker that exits on its own once nothing wants it, is why a run deposits no `codex-plugin-test-*` state dirs in `~/.claude/plugins/data/codex-nix-codex/state/` and leaves no surviving `app-server-broker` or `codex app-server` processes. When two branches both edit this patch, reconcile it by applying each side to a scratch clone and three-way merging the *source trees*, then regenerating — never by merging the patch text: `patch -p1` applies a textually-merged zero-context patch at lenient offsets with no error, so a wrong merge is silent, and an identical `patchRevision` bump on both sides hides the collision from git's conflict list entirely. To assert anything *about* the patched plugin source (a plan's verification gate, a spot check), read the scratch clone or the built store path — never `grep` the patch text: a zero-context patch carries no file attribution per line, so a patch-wide `grep -c` counts hunk lines from every touched file at once and cannot tell you which file a match sits in.
