# Claude Code module

## Settings

The `env` of the generated `~/.claude/settings.json` sets `BASH_MAX_TIMEOUT_MS` to `3600000` (60 minutes), the ceiling for an explicit Bash timeout, so an agent can run `just build` or `just agent-workflow-tests` in the foreground under a timeout above its duration (#261); `BASH_DEFAULT_TIMEOUT_MS` is left unset, so a command with no explicit timeout keeps the host's 120 s default.

`skillOverrides` hides twelve skills from the model's skill listing, each set to `user-invocable-only`, so `/<name>` still runs it (issue 425): the bundled `artifact-design`, `artifact-diagramming`, `artifact-capabilities` and `dataviz`, keyed by their bare names, and the claude.ai-synced `docx`, `pptx`, `xlsx`, `pdf`, `google-workspace`, `morning`, `import-memory` and `skill-creator`, keyed by their full `anthropic-skills:<name>` names. Claude Code matches a synced skill's full name before its bare one, so a user or project skill that shares a bare name stays listed. A plugin's skills ignore user-level overrides and leave the listing only when their plugin is disabled, so the skill-creator kept listed is the plugin's `skill-creator:skill-creator` and the hidden one is the claude.ai copy. The three Artifact skills are registered only in sessions that have the Artifact tool, so their entries take effect only there. `tests/test_claude_code_installed.py`, run by `just agent-installed-skill-tests`, checks the map and `enabledPlugins` in the built settings.

## Allow surface and lifecycle guard

Use `just show-claude-settings` to build and print the settings JSON (failing unless discovery finds exactly one artifact); its 26-entry allow surface allows the lifecycle helpers `workflow-state`, `artifact-budget`, `ship-delivery` and `orchestrate-control` outright, bare and as `~/.agents/bin/…`, and hands five lifecycle verbs (`git push`, `gh pr create`, `git branch -d`, `gh pr merge`, `gh release create`), and the raise-label rule below, to a fail-closed `PreToolUse` hook. That hook's Python is `home/common/claude-code/lifecycle_guard.py`, a standard-library-only file that imports nothing from `agent_tools`: the registered command is a store wrapper that clears `NIX_PYTHON*` and runs it under `python3 -I` with `--base-policy` naming the store base policy, `--policy` naming the compiled policy at `~/.agents/state/guard/policy.json`, a path fixed at evaluation time from the configured home directory, and `--derive-bin` naming the store row check (the terms and their producers are under `## Guard policy`), so an owner change never touches the source. `just build` fails when the guard source or the base policy cannot load, because the wrapper's build check runs the guard as registered on a harmless payload that has no repository-bound verb. A bad base policy blocks every Bash call, while a bad compiled policy contributes no row (`## Guard policy`). The hook splits the command into shell segments, tokenises each one, and adjudicates a verb **wherever a simple command starts** — after `(`/`{`/`` ` ``/`$(`/a `case` arm, after `!`/`time`/`then`/`do`, and behind `command`/`env`/`sudo`-style wrappers, stepping over their option arguments (`env -u NAME`, `sudo -u user`, attached and long forms included) — comparing *token values*, so `git  push`, `git<TAB>push` and `"git" push` all count. A word whose basename is `git` starts a git invocation: with no global option, or one `-C <dir>`, the word after them is its subcommand (`push`, or `branch` then `-d`), and with any other global option a `push` or `branch -d` anywhere among its words counts; a word whose basename is `gh` counts when its first two words are `pr merge`, `pr create`, `release create` or `release new`, or when a flag comes before the path's second word and both path words occur in order, so `gh --repo a/b pr merge 1` counts and `gh pr view 1 --json mergeable` does not (issue 400). Such an invocation is refused before any repository lookup, its problem ending `run git and gh by name, and carry a directory only as git -C <dir>` and followed by the accepted-forms clause (`## Adjudicated verbs`), when its program is named by a path, or it carries a git global option other than one `-C`, a repeated `-C`, or a `-C` directory holding whitespace, a quote or a shell-active character, or when its run reaches a shell substitution, expansion or grouping before its verb is certain: a git run still inside its global options or carrying a global option other than `-C`, whose value the walk cannot bound (`git -c k=$(…) push …`), or a gh run carrying a flag or ending before its third word (`gh pr --repo $(…) merge …`); then the verb's words among the rest of the command's words count, across segment boundaries, so `git -C $(pwd | cat) push …` blocks, also when a segment it crosses is judged on its whole text as evaluator source or an `env -S` payload (`git -C $(sh -c pwd | cat) push …`), and the reason names that invocation continuing past the substitution (issue 400 D15, D18, D19); a word taken as a `-C` value is an argument of git, never a program; a gh flag between the path words is left to the verb's grammar. A mention that is one quoted token (`echo "gh pr merge …"`), a heredoc body, or a comment is not a command and never triggers it. Everything the tokeniser cannot vouch for is refused rather than waved through: an unparseable command, shell source handed to an evaluator (`eval`/`sh -c`, matched by basename, so `/bin/sh -c` too), a segment in which `env` takes `-S`/`--split-string` (judged on its whole text, since env appends the remaining words to the split command), and a guarded verb sitting in a non-command position (an argument to `xargs`, `timeout`, …) all block. In such raw text a verb counts when its words occur in order, the first by basename, with the text read twice (words split at whitespace, quotes and shell-active characters; and again with quotes and backslashes deleted, since the shell glues the pieces into one word) and an attached `-S` payload read as a word, and it also counts when its words joined by one space occur as a substring of the text or of the text with quotes and backslashes deleted, so `sh -c 'git -C x push …'`, `sh -c "g''it push …"`, `env -Sgit push …`, `eval "${CMD:-git push …}"` and `sh -c "git branch -df x"` block too. Bare `Agent` remains inert under `defaultMode = "auto"`; verify the built artifact and guard with `tests/test_claude_permission_guard.py`, which takes the built settings through `CLAUDE_SETTINGS_PATH` and the built base policy through `CLAUDE_GUARD_BASE_POLICY_PATH`, runs under `python3 -m unittest` with `python/` on `PYTHONPATH`, and passes a fixture compiled policy and a stub row check on every invocation, so it never reads this host's compiled policy or fleet registry (three tests, `test_a_compiled_policy_round_trips_through_the_guard`, `test_a_compiled_policy_loads_whatever_branch_names_the_fleet_carries` and `test_an_arcwave_shaped_project_is_judged_by_its_compiled_row`, run `guard-policy derive` from source as the row check over a fixture fleet, and `test_the_row_check_never_sees_a_hostile_shell_environment` runs the built `claude-guard-row-check` with `HOME` at an empty fixture fleet). The same Bash `PreToolUse` entry also holds a second command hook, the context meter (`## Context meter`), which never grants or denies.

## Detaching words

Before any of that, and before its policy loads, the hook refuses the detaching words `nohup`, `setsid` and `disown` in every repository (#278): wherever a simple command starts (bare, by path, after a redirection or with one attached as in `nohup>log`, or behind a wrapper and its option arguments — `nohup` is no longer a wrapper), anywhere in evaluator source, `env -S` command text or an unparseable command, and inside a quoted `$(…)` or backtick substitution, naming the Bash tool's `run_in_background: true` and `launch-scope exec` as the routes; a mention, a heredoc body, a comment and a trailing `&` pass, and a word handed to an argv runner such as `xargs` or `timeout` is an accepted residual.

## Adjudicated verbs

The verbs it does adjudicate are validated against the live repository: `git push` only as `git push [-u] origin <branch>` onto a non-default branch with no force/delete/mirror flags, no refspecs and no namespaced refs (`refs/heads/main` and `heads/main` name the default branch too; the one exception is the tag-push arm below), `gh pr create` only as the exact `--repo/--base/--head/--title/--body` form whose repo is the detected slug and whose base is `origin/HEAD`'s branch, `git branch -d <branch>` (guarded globally, in every repo), and `gh pr merge <n> --repo <detected slug> --merge [--subject "<subject>"] [--match-head-commit <sha>] --delete-branch`, flags in that order, `<sha>` one separate word of exactly 40 lowercase hex characters whose spelling alone the guard checks (gh hands it to GitHub, which refuses the merge atomically if the PR head differs; issue 402), or, in a repository with a declared integration branch, the release arm: the same form without `--delete-branch`, only the integration branch merged into the default branch, gated on a fully green check rollup instead of forge protection, optionally behind a credential-scrub prefix (issue 400), spelled exactly `unset N && `, `unset N M && `, `env -u N ` or `env -u N -u M ` with single spaces and `N`, `M` distinct members of the credential-name set `GITHUB_TOKEN`, `GH_TOKEN` (`unset GITHUB_TOKEN && ` is the spelling derived from `bindings.tracker.credential_env.unset_before_invocation`'s exhaustive credential-name list), stripped from the start of the whole command so the remainder is still judged whole and nothing else can chain; `git push` and `gh pr create` take the `env -u` spellings at the start of their own segment (the `unset` spelling is an earlier segment there), `git branch -d` takes none, and any other `env` option or assignment, `--`, `--unset=` or attached `-uN` spelling, repeated name or doubled space leaves the text whole for the grammar to refuse; the four repository-bound verbs (every one but `git branch -d`) additionally require the repository to be inside standing authorization, which means its owner is in the base policy's `authorized_owners` or the repository itself has a derived row that the row check confirmed in this invocation, and merging further requires an open PR based on the default branch (or the repository's declared integration branch, which comes from a literal base-policy `integration_bases` row or from a confirmed derived row whose two branches differ); a default-branch base additionally demands live protection with at least one required status check and admin enforcement on the feature arm, while a declared integration base is deliberately exempt from the protection demand — it is the development-pace branch, and its CI gate stays in the shipping flow's wait-for-checks. `git push` and `git branch -d` also take one `git -C <dir>` directly after `git` (issue 400), `<dir>` one unquoted word without whitespace, quotes or shell-active characters, a relative one joined to the payload `cwd` without normalisation: the guard strips it to the canonical command and builds a push's repository context — origin slug, `origin/HEAD`, the derived-row lookup and row check, and the tag lookup — from that directory, one context per distinct directory in a command under the one invocation deadline, while branch deletion checks only its spelling; an unresolvable directory is an unknown repository, refused as outside standing authorization. The merge's own `gh` lookups run with `GITHUB_TOKEN`/`GH_TOKEN` scrubbed from their environment, so they authenticate via the gh keyring credential (whose reach covers every authorized owner) rather than any ambient environment token, which gh would prefer and which may be narrower; a machine with no keyring auth fails closed at the lookup. There is no defer path: once the hook adjudicates a verb it is validated-and-allowed or blocked, never handed back to the allowlist unexamined, and every uncertainty (unknown repo, unresolvable default branch, child timeout, non-zero or unparseable output) blocks. The guarantee is only as wide as that segment tokeniser — it approximates bash rather than being bash — which is why it refuses whatever it cannot parse, and why `tests/test_claude_permission_guard.py` carries an adversarial table (one case per class of "the parser and the shell might disagree") that any change to the guard must keep green. Every accepted spelling has one home, `FORM_TABLE` in `lifecycle_guard.py` (issue 402), each operation's forms in its template notation (`<slot>` one word, `"<slot>"` one free-text word that may begin with `-`, a slot closing a literal word, `[…]` an optional group led by its flag, a parenthesised note never matched) with three properties — whole-text characters (push and branch deletion), exact spelling (merge and release creation: single spaces, double-quoted free text) and scrub prefix (every operation but branch deletion) — compiled first on every invocation inside the unexpected-failure handler, so a template that does not compile refuses every Bash call with exit 2 and fails `just build`; one shared matcher judges each canonical command against its operation's forms in table order, and `canonical_text` reads the scrub-prefix property.

The forge adapter's two mutations are adjudicated too (#124, D9/D10). The **tag-push arm** sits inside the push verb and is judged before the branch arm: argv exactly `git push origin refs/tags/<tag>` with `<tag>` a SemVer `vMAJOR.MINOR.PATCH` (no leading zeros), standing authorization, and `git cat-file -t refs/tags/<tag>` (the base policy `git`, in the push's target directory: its `git -C` directory, else the payload `cwd`) printing exactly `tag`, so only an existing annotated tag is pushed; any other namespaced push keeps its refusal, and the branch arm, including the legacy `git push origin <tag>`, is unchanged. **Release creation** (`gh release create`, operation `release`, label "release creation") is judged on the whole command like the merge, behind the same optional credential-scrub prefix: exactly `gh release create <tag> --repo <detected slug> --verify-tag --title "<title>" --notes-file <path>`, flags in that order and nothing before or after, a SemVer `<tag>`, standing authorization, a title that passes the same free-text check as `--subject`, and an absolute `<path>` without whitespace or any shell-active character. `--target`, `--draft`, `--prerelease` and every other flag are refused, and so is gh's alias `gh release new` (it routes to the same arm, whose grammar spells `create`). The feature arm of `gh pr merge` also refuses `--delete-branch` when the PR's head is the default branch or the repository's declared integration branch (`unsafe merge: --delete-branch would delete the permanent branch <head>`), judged after the PR lookup and before any protection lookup, and a head that is missing, null, empty or not a string is refused as `cannot read the PR head branch` (#116 D5). The guard is on `PATH` as `claude-bash-lifecycle-guard` (`home.packages`) so the adapter and the resolver find it by name; the registered hook path is unchanged. The spelling fixture `tests/fixtures/forge-adapter-spellings.json` drives both the adapter suite and the guard's allowed-row table; the guard never reads it at run time. The shape fixture `tests/fixtures/guarded-command-shapes.json` (#351) lists the push, merge and branch-delete forms the `ship-issue` skill spells and the dressed shapes agents reach for, each with the guard's verdict bare, behind `unset GITHUB_TOKEN && ` and behind `env -u GITHUB_TOKEN `; it drives the guard suite's shape table and the `ship-issue` check in `home/common/agent-skills/tests/test_shell_example_contracts.py`, and the guard never reads it either; its `invocation_shapes` section (issue 400) holds the guard-only rows the `ship-issue` check never reads. `form_values` (issue 402) is guard-only too: one value per guard placeholder, from which the guard suite fills and runs every form a refusal prints.

A refusal that lies in the command's text (each recognition refusal, a form the matcher refuses, a slot value, a merge arm while another arm remains) reads `lifecycle guard: unsafe <operation>: <problem>; accepted: <form>[; or <form>…]; optional prefix: unset GITHUB_TOKEN && | env -u GITHUB_TOKEN`, and branch deletion, which takes no prefix, omits the last clause. The forms come from `FORM_TABLE` in table order: before any PR lookup the whole table, except that the merge's release form, noted `(only <integration> into <default>)`, is listed only where the repository declares an integration branch distinct from its resolved default branch, and after the lookup only the arm the PR admits, none when its head is a permanent branch no arm fits. With a repository context `<slug>` becomes the detected slug and, once the default branch resolved, `<base>` one alternative per authorized base, and the note names both branches (`only dev into main`); every other slot stays a placeholder, and a recognition refusal, which builds no context, fills nothing and lists the merge's feature form alone. The clause's two spellings stand for the whole accepted prefix set (`unset N && `, `unset N M && `, `env -u N `, `env -u N -u M `, `N` and `M` distinct members of `GITHUB_TOKEN`, `GH_TOKEN`). A refusal of the repository or the forge state (authorization and row problems, an unresolvable default branch, a default-branch push, head equal to base, a tag that is not an existing annotated tag, every PR, protection and rollup lookup or predicate failure, timeouts, the invocation deadline) names only its problem, since no spelling would pass there.

## The raise label

The hook also refuses an agent adding the `instruction-budget-raise` label (#294): in a command that mentions that label, case-insensitively, a `gh` invocation in any position whose `--add-label` value contains it is blocked, in every repository and before any other verb is judged, and an unparseable command, `eval`/`sh -c` source or a quoted `$(…)`/backtick substitution that mentions the label blocks too, while other labels, `--remove-label` and quoted mentions pass. This catches mistakes and is not enforcement: Codex has no hook, and `gh api`, GraphQL and `curl` are outside the guard, so the protection that holds is the required `Instruction Budget` check plus the user seeing the label on the PR (`.agents/knowledge/rejections/ungated-agent-merges.md`).

## Guard policy

The guard reads two policy files with disjoint closed schemas, and a loader refuses a file with any other key set (issue 377 D1). The **base policy** is a store file, `claude-bash-lifecycle-guard-base-policy.json`, built from `lifecycleGuardBasePolicy` in `default.nix`: an object with exactly `authorized_owners`, `integration_bases`, `git_bin`, `gh_bin` and `jq_bin`, which are the literal `authorizedOwners` and `integrationBases` rows (an `integration_bases` row exists only for a repository that is not a registered project, and the built set is currently empty) and the store paths of `git`, `gh` and `jq`. The **compiled policy** is the user state file `~/.agents/state/guard/policy.json`: an object with exactly `derived_repositories` and `derivation`. A **derived row** is an entry of the compiled policy's `derived_repositories`, keyed by the exact repository slug, `{default_branch, integration_branch, evidence}`. The **row check** is the store script `claude-guard-row-check`, which the wrapper passes as `--derive-bin`. No member exists in both files, so neither file is a valid instance of the other, and each member has one trust rule:

| Member | File | Rule |
|---|---|---|
| `authorized_owners` | base policy | Store value only. |
| `integration_bases` | base policy | Store value only; the compiled policy never removes or changes a literal row. |
| `git_bin`, `gh_bin`, `jq_bin` | base policy | Store value only; the only programs the guard runs besides the row check. |
| `derived_repositories` | compiled policy | A candidate row per slug, used only after the row check confirms it in this invocation. |
| `derivation` | compiled policy | Recorded for the reader; `null` or an object; the guard does not interpret it. |

The guard loads the base policy on every call, after the detaching-word check. It opens the compiled policy only when it judges a repository-bound verb (push, PR creation, merge or release creation), at the point it builds the repository context, so a command with none of those, branch deletion included, never reads it. The compiled policy supplies no value the guard executes, and the guard runs only the base policy's three tools and the row check, which it finds by the absolute path `--derive-bin` names (the wrapper is described under `## Allow surface and lifecycle guard`).

`guard-policy compile` writes the compiled policy (its contract is in [`python/README.md`](../../../python/README.md) § guard-policy): the two members and nothing else, after reading the base policy to validate it and to check each derived slug against its literal rows. The installed `claude-guard-policy` runs it with fixed arguments, the base policy and the compiled path, and takes none of its own; the home-manager activation step `claudeGuardPolicy` runs that command on every home-manager activation, after `linkGeneration` and before the settings copy, and never aborts the activation. The compiled policy is a user-writable state file, because compiling at activation cannot write the store. Since issue 377 the guard takes no trusted member from it and treats each derived row as a claim to be confirmed before it is relied on (issue 377 D1, D2).

A derived row exists for each registered project whose proof held at that compile and whose slug and two branch names `load_compiled_policy` accepts; a name it refuses, such as the branch `dev+ci`, costs that project its row (`name_unsupported`) instead of making the guard drop the whole compiled policy. A row authorizes its own repository and no other of its owner, and its `integration_branch` is the repository's integration base when it differs from the default branch.

**Row check.** `claude-guard-row-check` is a bash script under `-p`, which ignores `BASH_ENV` and exported functions; it unsets `BASH_ENV` and `ENV`, puts the store `git`, `gh` and `ssh` first on `PATH`, as `claude-guard-policy` does, and execs the `guard-policy` launcher, itself a bash script under `-p`, as `guard-policy derive` with its arguments; it is not installed on `PATH`. The guard runs it as `<derive-bin> --repository <slug>`, and it re-derives that one repository's row from the fleet registry and the contract on `origin` with the compiler's own proof (the `derive` contract is in [`python/README.md`](../../../python/README.md) § guard-policy). For a repository that has a row, the guard checks in this order, and the first failure is the verdict: (1) the slug is also a key of the base `integration_bases`, which refuses; (2) `origin/HEAD` must name the row's `default_branch`; (3) the row check runs; (4) it must have exited 0 with an `outcome` of `derived` whose `row` has the compiled row's `default_branch` and `integration_branch`. `evidence` is not compared, because its commit moves with every push to the branch. A refusal at step 1, 3 or 4 names the repository, the reason (the row check's reason code, or the differing branches) and `claude-guard-policy` as the repair; step 2's names the live and recorded branch. The check runs once per repository context, when that context is built (a command whose pushes name several `git -C` directories builds one context per distinct directory, all under the one invocation deadline), and only for a repository that has a row: a repository with no row is judged by the base policy with no check and no network read. A repository with a row is judged by the row and never falls back to its owner literal when the check fails.

The row check runs with stdin at `/dev/null`, its output captured, its own process group and the guard's environment without `BASH_ENV`, `ENV` and every `BASH_FUNC_` variable, so no shell startup file or exported function can print a report the check never derived. It is bounded by the smaller of `--derive-timeout-seconds` (15 s) and the time left in the guard's 27-second invocation deadline, which every child it starts shares and which keeps the verdict ahead of the hook's 30-second timeout (issue 377 D6). It is not started when no time is left, and on its bound the guard kills the whole group with `SIGKILL`, so the `git`, `ssh` and `gh` grandchildren do not outlive the verdict. Once the context exists, no other child starts unless its whole `--child-timeout-seconds` bound (5 s) fits before the deadline; `main` also checks the deadline at the top of each operation. When it does not fit, the guard refuses with its fixed message, that the 27-second invocation deadline leaves too little time for the next check so it was not started, and judges no later operation of a chained command (issue 377 D12). A child that reaches its own bound refuses, so the guard answers without relying on what the harness does with a timed-out hook.

**Cost and offline behaviour.** On every repository-bound verb in a repository that has a row, nix-config included (issue 377 D3), the row check costs one remote listing, one fetch only for a branch whose listed commit the checkout lacks, a sparse export of the contract and its projection files for each branch read, the resolver and one provider read (issue 385). Measured on 2026-10-13 on host `mbp`, 10 consecutive runs of the built row check for `elevenyellow/nodocom` took a median of 3.61 s and a maximum of 4.56 s (the first run), and none of the 10 fetched. An unreachable `origin` or provider fails the check (`fetch_failed` or `provider_unproven`) and refuses the verb: there is no fallback to a ref already present or to the unchecked row, and no availability is lost, because push, PR creation, merge and release creation each need the same remote or provider to succeed. Only a fetch writes a ref, so two sessions judged at once contend for a ref lock only when both fetch a missing commit into the same registered root; a fetch that loses the lock fails `fetch_failed` and refuses, a rerun clears it, and the guard takes no lock of its own.

**A bad file.** The guard opens either policy file without blocking and reads it only when the open descriptor is a regular file of at most 1 MiB (`POLICY_MAX_BYTES`), so a FIFO, a device such as `/dev/zero` behind a symlink, a directory or a file already larger at the open is refused before a byte is read, and a file that grows past the cap while read is refused too. A compiled policy that is missing, unreadable, not a regular file, over that size, not JSON or outside its schema (a #375 seven-member file included, until the next compile replaces it) contributes no row, whole file, and blocks nothing the base policy allows (issue 377 D4). When a repository-bound verb is then refused for standing authorization, the refusal adds the reason and names `claude-guard-policy`. This grants nothing: rows only add, a derived-only repository loses authorization, and an owner-literal repository is judged as an unregistered one, with no row to check `origin/HEAD` against. A base policy that is missing, unreadable, not a regular file, over that size or outside its schema still blocks every Bash call with `invalid policy`, because it is a store file the build check loaded and a bad one is an installation defect.

**Literal and derived rows.** `guard-policy compile` refuses a project whose slug is a key of the base `integration_bases` as `literal_conflict`: the project gets no row and the literal row stays, and each compile reports the conflict. The compiled policy cannot subtract from the base, so a repository can carry both only when the compiled policy was edited or a literal row was added after the last compile, and the guard refuses it at step 1 above (issue 377 D5). What the guard authorizes is the base `authorized_owners` and `integration_bases` plus the derived rows the row check confirms.

The activation step treats the compiler's three outcomes as follows. Status 0 leaves the complete compiled policy. Status 1 leaves a compiled policy without the refused projects' rows, and the compiler's stderr line names each refused project with its reason code. Any other status removes the compiled policy, and the step says that registered projects have lost their derived guard row and with it their derived integration branch. In both cases only a repository that relies on a derived row for its authorization is refused until `claude-guard-policy` succeeds; authorization from the base policy (an authorized owner or a literal integration row) still applies, and no call is blocked by it. If the removal fails, the step reports that the path could not be removed, and the guard reads whatever is there: a directory or an unreadable or malformed file contributes no row, and a readable earlier policy stays in force, its rows still rechecked at use. The repair is `claude-guard-policy`, run from a shell that can fetch each project's `origin` and whose `gh` keyring credential reaches the provider; a rerun repairs only the refusals a missing network or credential causes, which are `fetch_failed` and `provider_unproven`, because it can only re-derive from the registry and `origin`, and the other codes name a registry, contract or remote that has to change first.

Rows are rechecked at use, so a registry or contract change that moves a row's branches refuses until the next compile (issue 126 D6, narrowed by issue 377 D2); a project registered after the last compile has no row until the next one.

**Residual.** The guard catches the mistakes of a cooperating session and is not a sandbox. Rewriting the compiled policy alone gains nothing: it cannot add an owner, an integration base or a program, and a forged row is refused at use. What stays user-writable (issue 377 D1, D2):

- The fleet registry. A session can add an entry, but the row check still demands that the repository's own branch on `origin` publishes a resolving contract that names that project id, that repository as tracker and as release target, and that the provider confirms the name. A registry edit therefore authorizes only a repository that already declares itself adopted and that the session could register with the registration command anyway.
- Transport and tool configuration: `~/.ssh/config`, git configuration and the `gh` credential decide what `origin` and the provider answer. A session that rewrites them and the registry can forge a derivation, which takes several deliberate edits to stores unrelated to the guard.
- The checkout's object store. A session that plants an object under the id `origin` lists forges that read, as it already could before a fetch that finds the object present (issue 385).
- `~/.claude/settings.json`, a writable copy: removing the hook removes the guard.
- The window between check and use: the verb runs after the verdict, and a remote that changes between them is not seen.

## Context meter

The context meter (issue 424) is the second command hook of the same `matcher = "Bash"` `PreToolUse` entry, after the guard: the `context-meter` launcher from the agent-tools command table, timeout 10 s, no arguments and no matcher of its own, so the guard's registration is unchanged. Claude Code runs it before every Bash call; its contract is in [`python/README.md`](../../../python/README.md) § `context-meter`.

It rewrites every `workflow-state progress` invocation in a command so the gate sees the agent's measured context, never the model's own figure: each argparse spelling of `--context-tokens` is dropped and the value measured from the agent's transcript is inserted right after `progress`. A call whose context cannot be measured only loses the model's value, the ceiling and headroom flags are never touched, and a rewrite that fails its proof, or a command the lexer cannot tokenise, passes through unchanged with a `systemMessage` saying so. Each rewritten call also carries a short note saying that the value was measured.

It also tells an owner once per crossing to run its phase gate. Owners are the agents that ran `workflow-state progress`, `workflow-state mark-progress` or `sdd-gate` with an `--action-id`; the first measurement at or above `agent_tools.phase_budget`'s context ceiling less its headroom adds one instruction to run the gate, unless that call is a progress call the meter rewrote to carry the measurement (it is already running the gate), and it fires again only after a measurement below the threshold. The state is one file per session and agent under `~/.agents/state/context-meter/`, never pruned (a known limitation). Parallel calls from one owner serialise on an exclusive lock on that file, held only for a read-decide-write.

The meter grants nothing. It prints no permission decision and never exits 2, so the guard judges the original command exactly as before. It fails open: on a progress call, an unmeasurable context or an unchanged call is reported in a user-visible `systemMessage` (any other call with an unmeasurable context prints nothing), and an unexpected error exits 1 with a traceback, leaving the call as the agent wrote it. A session's first tool call is always unmeasured, because Claude Code runs the hook before that turn's usage record reaches the transcript (spec D20). One limitation follows from running beside the guard: when the guard denies the call that carries the crossing instruction, the instruction is swallowed with it, and the state already records the owner as notified. A host without hooks runs no meter, so it sends no count.

## Guard/core decision

The [guard/core decision](../../../.agents/artifacts/specs/2026-09-20-issue-116-permission-guard-core-design.md) preserves the required-check floor for both merge arms and records the current protection exceptions as gaps (the permanent-head deletion check is closed by the D5 repair above). Core grants cannot override the final guard, host or provider verdict; future core admission waits for the named enforcement and conformance work.

## Plugins

`codex-plugin-cc` is the one plugin built from a pinned input plus a repo-owned patch (`patches/agent-plugins/codex-plugin-cc.patch`, the only patch in that directory); `lib/agent-plugins.nix` patches it into a store path and names its marketplace `nix-codex`. Claude enables two plugins from marketplaces of two different source types — `skill-creator@claude-plugins-official` from a `github` marketplace and `codex@nix-codex` from a `directory` marketplace pointed at that store path. Codex has no Nix-declared marketplace: its marketplaces and plugins are runtime-managed inside `~/.codex/config.toml`, which Nix does not own.

## Accounts

`accounts/` is a Claude Code mod plus its launcher, `bin/claude-account`, for running several Claude accounts side by side. Each account is a profile directory `~/.claude-accounts/profiles/<name>` used as `CLAUDE_CONFIG_DIR`: the login is the profile's own, while settings, `CLAUDE.md`, skills, agents, plugins and transcripts are links to the `~/.claude/<entry>` paths (never to their store targets, so they follow generations). A project is bound to an account in `~/.claude-accounts/bindings.tsv`, keyed by the main checkout so every worktree shares the binding; a directory without its own binding takes its nearest bound parent's, and `default` is recorded like any account so it can override one. Rewrites of that file are serialized by a `bindings.tsv.lock` directory. `~/.claude.json` is the exception to the links: a new profile gets a one-time copy without the login, so an MCP server merged into `~/.claude.json` later (the `palmierProMcp` pattern) does not reach existing profiles until it is merged into `~/.claude-accounts/profiles/<name>/.claude.json` too. That state is runtime-owned; Nix owns only the code.

`default.nix` builds the folder into one store path (`accountsMod`), rewriting the launcher's `jq`, `git`, `curl` and real-`claude` paths and its cache-proxy URL, and installs `claudeWithAccounts` as `programs.claude-code.package`: `claude` on PATH is a script that runs `claude-account run`, which picks the bound account (or `CLAUDE_ACCOUNT=<name>` for one launch), adds the mod to `CLAUDE_CODE_PLUGIN_DIRS` and starts the pinned binary (waiting on it, so the `/account` switch below can relaunch it). A `CLAUDE_CONFIG_DIR` the caller set to something outside the profiles is kept (the mod is still added), unless `CLAUDE_ACCOUNT` asks for an account. `home/linux/claude-local` uses the pinned binary directly and is not account-aware. The mod loads from the read-only store path; the engine's only complaint is a debug-log line that it could not lay its editor types there.

`claudeWithAccounts` also puts `claude-orchestrate` on PATH, the command that starts an orchestration session (issue 425): a script that exports `ENABLE_CLAUDEAI_MCP_SERVERS=false`, replacing any inherited value, and execs `claude-account run "$@"`, so the account, the mod and the `/account` switch are `run`'s, and the setting survives a switch because `run` relaunches `claude --resume` from its own process. Claude Code then skips the claude.ai connector fetch for that session, so neither it nor any of its subagents carries claude.ai connector instructions or tools; other MCP servers (palmier-pro, a project's `.mcp.json`) still load, and the claude.ai-synced skills stay governed by `skillOverrides` (`## Settings`). Plain `claude` leaves the variable alone and keeps the connectors. Start an orchestration with `claude-orchestrate`, then run `/orchestrate-issues …` inside it. `tests/test_claude_code_installed.py` runs both built launchers against a stub `CLAUDE_BIN` and checks the arguments and environment each hands it.

In a session, `/account` lists, `/account add <name>` creates, `/account <name>` or `/account default` binds the project and switches the running session to that account: the engine reads its credential once and offers plugins no way to swap it, so `run` waits on `claude` instead of exec'ing it (exporting its pid as `CLAUDE_ACCOUNT_LAUNCHER`), and the mod calls `claude-account switch <name> <session id>`, which writes `~/.claude-accounts/switch/<launcher pid>` and sends TERM to the session's `claude` (the ancestor whose parent is that launcher, so nothing else is signalled); `run` then relaunches `claude --resume <session id>` under the new account. Transcripts are shared, so the conversation carries over; the first launch's other flags do not, and a turn still running is cut off. A session that `run` did not start (an IDE, a pre-switch launch) keeps its account, and `/account` says to exit and run `claude -c`. `claude-account status` (or `/account status`) also shows every account's 5-hour and weekly usage, fetched in parallel from the OAuth usage endpoint with each account's stored token (the macOS keychain item `Claude Code-credentials[-<sha256(config dir)[:8]>]`, or `<config dir>/.credentials.json` elsewhere). It only reads the token and never refreshes it, because a refresh would race a running `claude`; an account whose token has lapsed is shown as expired until `CLAUDE_ACCOUNT=<name> claude` is started once. The first launch under a new account asks for the sign-in; `claude-account login <name>` does it ahead of time, and `claude-account rm <name>` deletes a profile.

To change the mod, edit `accounts/` and check it with `claude plugin validate home/common/claude-code/accounts` and `claude plugin test home/common/claude-code/accounts`; `just build` runs the built launcher once as a smoke check.

## Cache proxy

`claude` reaches the Anthropic API through `cache-proxy` (`python/README.md` § `cache-proxy`) while the proxy is healthy. It forwards requests unchanged today; request reshaping is the follow-up to #422, and the spike behind it is `docs/spikes/cache-proxy-spike.md`. `default.nix` holds the port, `27183`, in one binding: it runs the `cache-proxy` launcher with `--port 27183` and `SSL_CERT_FILE` set to the nixpkgs CA bundle as the launchd agent `claude-cache-proxy` on darwin (`RunAtLoad`, `KeepAlive`; stdout and stderr append to `~/Library/Logs/claude-cache-proxy.log`, which nothing rotates) and as the systemd user unit `claude-cache-proxy` on anis-desktop (`Restart=always`, `WantedBy=default.target`; its log is the journal), and it writes `http://127.0.0.1:27183` into the launcher's `CACHE_PROXY_URL`. The service starts at activation (`just switch`); until something answers on the port, every launch goes direct.

Before every launch (the early exec for a caller-chosen `CLAUDE_CONFIG_DIR`, the first launch and each `/account` relaunch) `claude-account run` leaves alone an `ANTHROPIC_BASE_URL` set to anything but the proxy URL, since that is the caller's own endpoint. Otherwise it probes `GET /_proxy/health` with a 0.5 s limit: an answer naming `"service":"cache-proxy"` exports the proxy URL and `ENABLE_TOOL_SEARCH=true` unless the caller set that variable (before 2.1.304 Claude Code turns tool search off behind a non-first-party base URL, and the pin is older), and anything else unsets `ANTHROPIC_BASE_URL`, so the launch goes direct and a dead proxy costs at most half a second. The probe runs only at launch: a session keeps the route it started with, and if the proxy dies mid-session the service manager restarts it while Claude Code retries. A routed session has no Remote Control, which Claude Code turns off behind a non-first-party base URL. `ANTHROPIC_BASE_URL=https://api.anthropic.com claude` goes direct for one launch. `claude-local` is never routed: it execs the pinned binary itself and exports its own `ANTHROPIC_BASE_URL`. One started inside a routed session inherits `ENABLE_TOOL_SEARCH=true`; from 2.1.304 on, tool search is the default behind any gateway regardless.

## Editing the codex-plugin-cc patch

To edit `patches/agent-plugins/codex-plugin-cc.patch`: work in a scratch clone of the pinned upstream rev (see `flake.nix`), apply with `git apply --unidiff-zero` (the patch is zero-context; plain `git apply` rejects it), regenerate with `git diff -U0 <pin>`, and bump `patchRevision` in `lib/agent-plugins.nix`. Run the plugin's suite as `env -u CLAUDE_PLUGIN_DATA -u CODEX_COMPANION_SESSION_ID -u CODEX_COMPANION_TRANSCRIPT_PATH node --test tests/*.test.mjs` — with the live Claude-session env unscrubbed, 4 upstream tests fail spuriously. The six test files that write under the shared state root (`runtime`, `state`, `liveness`, `reviewer-detach`, `broker-reaping`, `worker-postmortem`) call `pinHermeticStateRoot` (`tests/helpers.mjs`), which pins `CLAUDE_PLUGIN_DATA` to a private temp root and group-kills every broker recorded there at file teardown; `isolation.test.mjs` pins and restores a root of its own per test and is left alone. That, plus a `teardownBrokerSession` that kills by default and a broker that exits on its own once nothing wants it, is why a run deposits no `codex-plugin-test-*` state dirs in `~/.claude/plugins/data/codex-nix-codex/state/` and leaves no surviving `app-server-broker` or `codex app-server` processes. When two branches both edit this patch, reconcile it by applying each side to a scratch clone and three-way merging the *source trees*, then regenerating — never by merging the patch text: `patch -p1` applies a textually-merged zero-context patch at lenient offsets with no error, so a wrong merge is silent, and an identical `patchRevision` bump on both sides hides the collision from git's conflict list entirely. To assert anything *about* the patched plugin source (a plan's verification gate, a spot check), read the scratch clone or the built store path — never `grep` the patch text: a zero-context patch carries no file attribution per line, so a patch-wide `grep -c` counts hunk lines from every touched file at once and cannot tell you which file a match sits in.
